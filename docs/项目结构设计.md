> **权威范围**：模块边界、目录组织、依赖方向，以及跨切能力的归属。业务语义与状态取值由需求拥有；技术选型与版本由技术栈设计拥有；运行机制由机制文档拥有。

## 1. 结构原则与现状

四条原则：

1. **按业务职责划分模块**，不按前端、后端、数据库等技术层切割。
2. **一个 Python 应用、两个运行入口**（HTTP 与 Worker），不恢复多包工作空间。归档的 `packages/py-*` 存在的理由是承载自研 Agent 内核、RAG 与各类适配层；新选型改用上游成熟库（技术栈设计准则 2），这些包失去归属。**在出现第二个 Python 消费者之前不建包。**
3. **每个跨模块操作只有一个状态所有者**；读者不得从另一个模块的缓存推断权限。
4. **依赖方向无环**，并用白名单显式允许，而不是靠约定。

现状证据（2026-09-29 实测，不是推断）：根 `pyproject.toml` 的 uv workspace 成员为空；`pnpm-workspace.yaml` 只列尚未创建的前端路径；`docker-compose.yml` 只有 PostgreSQL、Redis、MinIO 三个容器；根不存在 `apps/`、`packages/`、`infrastructure/`。

## 2. 仓库布局

```text
apps/api/                      # 唯一 Python 应用（uv 项目）
  src/campfire/
    main.py                    # FastAPI 入口：路由装配、中间件、健康检查
    worker.py                  # Taskiq worker 入口：注册任务并启动
    core/                      # 跨切能力与端口实现（无业务语义）
      config/  db/  cache/  logging/
      auth/                    # SuperTokens 适配：会话校验、账号同步
      authz/                   # 授权判定端口与一期的属主实现
      model/                   # 模型网关与路由配置：唯一读取模型名的位置
      retrieval/               # 向量与字面两路检索及其合并
      jobs/                    # 待处理记录的写入与 Taskiq 投递
    skills/                    # skill 定义、注册表、工具元数据
      definitions/<skill>/     # 每个 skill 一个目录：SKILL.md + 能力清单
      registry.py              # 加载并解析定义，解析当次可用工具集合
    modules/
      accounts/                # 注册（邀请码）、登录会话、人工重置、组织账号
      consult/                 # 咨询用例：两条入口、skill 激活、上下文装配、输出与引用
      library/                 # 专业资料与案例
      profile/                 # 个性化档案
      memory/                  # 通用记忆（Graphiti）
  tests/
apps/web/                      # React H5（pnpm 工作空间）
  src/{domain,application,viewModel,view,infrastructure}/<feature>/
docs/                          # 设计文档（本目录）
infrastructure/{docker,nginx}/ # 目标归属，当前不存在
scripts/                       # 目标归属，当前不存在
```

## 3. 后端模块职责

| 模块 | 拥有的用例 | 不得承担 |
|---|---|---|
| `accounts` | 邀请码校验与注册、登录会话的建立与撤销、人工重置、组织标识 | 对任何支持对象档案的访问判定 |
| `consult` | 两条入口的用例编排：装配上下文（档案、记忆、资料与案例检索结果）、激活 skill、调用模型、产出带引用的结果 | 自行实现检索、记忆或档案的存储；决定授权 |
| `library` | 专业资料与案例的录入、来源与状态标注、撤下、检索与浏览 | 把未标注来源或未经核验的内容作为真实案例返回 |
| `profile` | 档案条目的自动写入、来源与生成方式标注、纠正与删除、按对象归属读取 | 决定谁能访问（交 `core/authz` 端口）；把系统推断当既成事实返回 |
| `memory` | 通用记忆的写入与读取、时间演变与失效判定 | 承载档案内容；跨账号共享 |

`consult` 是唯一同时读取 `library`、`profile`、`memory` 的模块：需求的"两种咨询同构"（`RQ-CON-01`）落在它身上，而不是各写一套。

## 4. 依赖方向与白名单

```text
modules/* → skills（读取定义与工具元数据）→ core/*
modules/consult → modules/library、modules/profile、modules/memory
modules/accounts、library、profile、memory → core/*
core/* → 不依赖任何模块
```

| 成员 | 允许依赖 | 禁止 |
|---|---|---|
| `skills` | `core/config`、`core/logging` | import 任何 `modules/*`；持有工具实现 |
| `modules/consult` | `skills`、`modules/{library,profile,memory}`、`core/*` | 直接访问数据库表；绕过 `core/authz` 判断归属 |
| `modules/{library,profile,memory}` | `core/*` | 依赖 `consult`；互相依赖 |
| `modules/accounts` | `core/*` | 依赖其他模块 |
| `core/*` | 上游库与 `core` 内同级 | 依赖任何 `modules/*` 或 `skills` |
| `worker` 入口 | `core/*`、`modules/{profile,memory}` | import `modules/consult`、`modules/accounts` 的路由层；回查业务用例 |

**工具注册的方式**：`skills` 只持有工具的**名称与元数据**（风险等级、所需范围、可见性）；工具的处理函数由**拥有该能力的模块**在装配处注册。因此 `skills` 不 import 任何模块，模块也不 import `skills` 的实现细节。

**Worker 的边界**：它消费的是待处理记录里的显式载荷，不回查业务用例、不假定请求上下文。技术栈设计第 5 节的失败语义在此落地。

## 5. 扩展缝

- **二期机构协作**：`core/authz` 是唯一授权判定端口，一期只有"属主即允许"一个实现。二期新增 `spaces` 模块实现同一端口（支持对象 → 授权主体 → 范围 → 期限），**调用点不变**。一期不预建该模块，也不预建空表。
- **微信小程序（远期）**：`accounts` 预留"外部凭证交换"的接入位置——小程序登录是服务端用 code 换 openid，不是 OIDC，届时作为第三种登录方式接入同一账号体系。一期不实现。
- **附件（延期）**：开放时新增 `core/storage` 与 `library`、`profile` 的附件引用，不改变现有检索与授权形状。
- **数据权利请求**（延期能力）：其状态所有者将由届时的机制文档指定，本文不预分配。

## 6. 前端组织

`apps/web/src/` 沿用单向五层：`domain/`（无框架业务类型）← `application/`（用例与端口）← `viewModel/`（交互状态与 Hooks）← `view/`（页面与组件）；`infrastructure/` 实现 application 的端口，经装配注入。

按特性在层内组织：`accounts`、`consult`（含应急与日常两条入口）、`library`、`profile`、`memory`。

- `view` 不得直接调用 HTTP、读写凭据或跨层导入 `infrastructure`；`viewModel` 不得导入 `view`；`application` 不得导入任何框架或 HTTP 库。
- 状态归属分三类：跨介质 UI 状态归 `viewModel`，组件内视觉状态归 `view`，业务驱动的视觉决策由 `viewModel` 经 Props 下传。
- 凭据不得作为权限证明，前端守卫只负责体验。

**保留五层的理由与重访条件**：它解决的"状态归谁"是真实问题，且项目既有约定（`AGENTS.md` 的跨层禁令）直接引用它。代价是样板代码；若首个特性落地后样板显著超过收益，重访层的物理粒度，而不是直接取消分层。

## 7. 全局约定

- **配置唯一入口**：`core/config`；模块不得各自读取环境变量形成第二真相。密钥经环境注入，不入版本库。
- **模型名唯一出现处**：`core/model`；业务代码不得硬编码模型名（技术栈设计第 3 节）。
- **迁移**：Alembic；迁移文件必须带中文注释说明业务意图。表归属与模块同名，跨模块读取只经用例服务。
- **命名**：注释用中文，变量、函数、类、文件名用英文。
- **健康检查**：分别报告公开内容可达、数据库可用、模型可用、异步滞后；不用一个全绿接口表示所有能力安全。

## 8. 重访条件

- 出现第二个 Python 消费者（例如独立的评测服务）→ 重新评估是否抽包。
- `library` 中资料与案例的生命周期显著分化（例如案例需要独立授权流程）→ 拆为两个模块。
- 前端五层在首个特性落地后被证明样板显著超过收益 → 重访层的物理粒度。
- `core/authz` 在一期内出现第二个实现 → 提前引入模块边界，而不是让第二个实现散落在调用点。
