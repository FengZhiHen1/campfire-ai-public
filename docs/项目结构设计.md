# 项目结构设计

> **权威范围**：模块边界、目录组织、依赖方向，以及跨切能力的归属。业务语义与状态取值由需求拥有；技术选型与版本由技术栈设计拥有；运行机制由机制文档拥有；skill 的内容由各 skill 自身的 `SKILL.md` 拥有。

> **追溯**：`RQ-ACC-01`～`RQ-ACC-06`、`RQ-CON-01`～`RQ-CON-07`、`RQ-KB-01`～`RQ-KB-04`、`RQ-MEM-01`～`RQ-MEM-06`、`RQ-LIM-01`～`RQ-LIM-04`。

## 1. 结构原则与现状

四条原则：

1. **基座与业务分离**。`agent/` 是**本项目内各功能共用的通用 Agent 底座**，不含任何领域语义；目前只有咨询一个面，其他面将来同样从它出发。基座建在 OpenAI Agents SDK 之上，补的正是该 SDK 缺少的开放标准 skill 机制（已核实：它的 `skills` 只存在于 sandbox capabilities，不是通用能力按需加载）。
2. **功能由 skill 承载**。领域能力以**开放标准**的 skill 目录交付（`SKILL.md` + 可选 `references/`、`scripts/`、`assets/`），而不是写进业务代码模块。只有需要新工具时才写代码。
3. **一个 Python 应用、两个运行入口**（HTTP 与 Worker），不建多包工作空间。理由不是"基座专属"，而是**包边界对本产品没有收益**：基座只服务本产品内部各面，没有第二个消费者；出现第二个消费者时再按重访条件评估。
4. **每个跨模块操作只有一个状态所有者**；依赖方向无环，并用白名单显式允许，而不是靠约定。

现状证据（2026-09-29 实测，不是推断）：根 `pyproject.toml` 的 uv workspace 成员为空；`pnpm-workspace.yaml` 只列尚未创建的前端路径；`docker-compose.yml` 只有 PostgreSQL、Redis、MinIO 三个容器；根不存在 `apps/`、`packages/`、`infrastructure/`。

## 2. 仓库布局

```text
apps/api/
  skills/                      # 开放标准的 skill 内容产物（不是 Python 代码）
    <skill-name>/SKILL.md      # 元数据 + 指令主体
    <skill-name>/references/   # 按需读取的文档
    <skill-name>/scripts/      # 可选：可执行代码
    <skill-name>/assets/       # 可选：模板与数据
  src/campfire/
    main.py                    # FastAPI 入口：路由装配、中间件、健康检查、工具注册
    worker.py                  # Taskiq worker 入口
    agent/                     # 基座：通用 Agent 底座（产品无关）
      runtime/                 # agent loop、会话与运行状态
      skill_runtime/           # 开放标准 skill 机制：发现、元数据装载、激活、按需加载、校验
      tools/                   # 工具池与权限系统（实现由产品侧注册）
      context/                 # 上下文装配端口：会话 / 记忆 / 档案 / 检索结果的注入接口
      model/                   # 模型网关与路由配置：唯一读取模型名的位置
      observability/           # 运行追踪与评测钩子
    surfaces/                  # 面：产品入口与运行装配
      consult/                 # 目前唯一的面（应急与日常两种触发）
    tools/                     # 产品侧工具实现，注册进基座的工具池
    modules/                   # 业务数据与用例
      accounts/                # 注册（邀请码）、登录会话、人工重置、组织账号
      library/                 # 专业资料与案例
      profile/                 # 个性化档案
      memory/                  # 通用记忆（Graphiti）
    core/                      # 跨切能力：config、db、cache、auth、authz、jobs、retrieval
  tests/
apps/web/                      # React H5（pnpm 工作空间）
  src/{domain,application,viewModel,view,infrastructure}/<feature>/
docs/                          # 设计文档（本目录）
infrastructure/{docker,nginx}/ # 目标归属，当前不存在
scripts/                       # 目标归属，当前不存在
```

## 3. 基座（`agent/`）的职责与不含的东西

| 基座拥有 | 基座不含 |
|---|---|
| 模型网关与路由 | 任何领域术语（咨询、档案、案例、支持对象…） |
| agent loop、会话与运行状态 | 业务授权判定 |
| skill 机制：目录发现、`name`/`description` 元数据装载、按匹配激活、主体与资源按需加载、校验 | 具体 skill 的内容（那是 `skills/` 下的产物） |
| 工具池与权限系统 | 具体工具的实现（那是 `tools/` 与 `core/retrieval`） |
| 上下文装配端口 | 记忆、档案、检索的语义与生命周期 |
| 流式输出与可观测钩子 | 面向用户的输出结构与呈现 |

**基座不知道自己被用在哪件事上**——这是判断某个东西该不该放进 `agent/` 的唯一标准。

## 4. skill 内容与开放标准

每个 skill 是 `apps/api/skills/<name>/` 下的一个目录，至少含 `SKILL.md`。frontmatter **只使用标准的六个字段**，不得自创：

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | ≤64 字符，仅小写字母、数字与连字符；必须与父目录同名；不以连字符开头或结尾；不得连续连字符 |
| `description` | 是 | ≤1024 字符，非空；必须同时说明**做什么**与**何时用**，含便于匹配的关键词 |
| `license` | 否 | 许可证名称或随附许可证文件的引用 |
| `compatibility` | 否 | ≤500 字符；环境要求（目标产品、系统包、网络访问等） |
| `metadata` | 否 | 自由键值映射（string→string）；**本项目自有的元数据放这里**，不改格式 |
| `allowed-tools` | 否 | 空格分隔的**预授权**工具列表；标准标注为 experimental |

渐进披露三层：元数据（约 100 token）随启动载入 → 命中后载入 `SKILL.md` 主体（建议 <5000 token、主体不超过 500 行）→ `references/`、`assets/`、`scripts/` 按需读取。文件引用用相对路径且保持一层深，不做多级引用链。校验使用标准的参照实现 `skills-ref validate`。

一期**不自建 skill 的安装、市场或运行时下发**：skills 随应用发布，根目录由配置指定。

## 5. 面的职责

`surfaces/consult/` 是产品入口与运行装配：HTTP 与 SSE 契约、应急表单到一次运行的装配、日常会话的推进、把基座结果映射为面向用户的输出结构。

它**不实现方法论**（那是 skill 内容），也**不直接访问数据库表**（那经 `modules/` 的用例服务）。它对两种触发的差异负责：应急由入口直接激活指定 skill，日常交由基座按 `description` 匹配。

## 6. 业务模块与工具

| 模块 | 拥有的用例 | 不得承担 |
|---|---|---|
| `accounts` | 邀请码校验与注册、登录会话的建立与撤销、人工重置、组织标识 | 对任何支持对象档案的访问判定 |
| `library` | 专业资料与案例的录入、来源与状态标注、撤下、检索与浏览 | 把未标注来源或未经核验的内容作为真实案例返回 |
| `profile` | 档案条目的自动写入、来源与生成方式标注、纠正与删除、按对象归属读取 | 决定谁能访问（交 `core/authz`）；把系统推断当既成事实返回 |
| `memory` | 通用记忆的写入与读取、时间演变与失效判定 | 承载档案内容；跨账号共享 |

`tools/` 把上述能力包装成基座可调用的工具（检索资料、检索案例、读写档案、读写记忆…）。**工具是代码，skill 是内容**：skill 通过 `allowed-tools` 声明预授权，通过指令说明何时与如何使用工具。

## 7. 依赖方向与白名单

```text
surfaces/* → agent/*、tools/*、modules/*、core/*
tools/*    → modules/*、core/*
agent/*    → core/config、core/logging 与上游库
modules/*  → core/*
core/*     → 上游库与 core 内同级
```

| 成员 | 允许依赖 | 禁止 |
|---|---|---|
| `agent/*` | `core/config`、`core/logging`、上游库 | import `modules/*`、`surfaces/*`、`tools/*`；出现领域术语 |
| `tools/*` | `modules/*`、`core/*` | import `surfaces/*`；绕过用例服务直接写表 |
| `surfaces/*` | `agent/*`、`tools/*`、`modules/*`、`core/*` | 直接访问数据库表；实现方法论 |
| `modules/*` | `core/*` | 依赖 `surfaces/*`、`agent/*`；互相依赖 |
| `core/*` | 上游库 | 依赖 `agent/*`、`surfaces/*`、`modules/*` |
| `worker` 入口 | `core/*`、`modules/{profile,memory}` | import `surfaces/*`；回查业务用例 |

**工具注册在装配处完成**（`main.py` / `worker.py`），因此 `agent/*` 不需要 import `tools/*`。

## 8. 扩展缝

- **新增面**：新增 `surfaces/<face>/`，复用基座与工具池；**不改基座**。
- **新增领域能力**：优先新增 skill 内容（`SKILL.md` + `references/`）；只有需要新工具时才写代码。
- **二期机构协作**：`core/authz` 是唯一授权判定端口，一期只有"属主即允许"一个实现；二期新增 `spaces` 模块实现同一端口，调用点不变。一期不预建该模块与空表。
- **微信小程序（远期）**：小程序登录是服务端用 code 换 openid，不是 OIDC，届时作为第三种登录方式接入 `accounts` 的同一账号体系。
- **附件（延期）**：开放时新增 `core/storage` 与 `library`、`profile` 的附件引用，不改变现有检索与授权形状。

## 9. 前端组织

`apps/web/src/` 沿用单向五层：`domain/` ← `application/` ← `viewModel/` ← `view/`；`infrastructure/` 实现 application 的端口，经装配注入。按特性在层内组织。

- `view` 不得直接调用 HTTP、读写凭据或跨层导入 `infrastructure`；`viewModel` 不得导入 `view`；`application` 不得导入任何框架或 HTTP 库。
- 状态归属分三类：跨介质 UI 状态归 `viewModel`，组件内视觉状态归 `view`，业务驱动的视觉决策由 `viewModel` 经 Props 下传。
- 凭据不得作为权限证明；前端守卫只负责体验。

保留五层的理由与重访条件：它解决的"状态归谁"是真实问题，且项目既有约定直接引用它；若首个特性落地后样板显著超过收益，重访层的物理粒度，而不是直接取消分层。

## 10. 全局约定

- **配置唯一入口**：`core/config`；模块不得各自读取环境变量形成第二真相。密钥经环境注入，不入版本库。
- **模型名唯一出现处**：`agent/model`；业务代码不得硬编码模型名。
- **skill 根目录**由配置指定，校验纳入工程检查（`skills-ref validate`）。
- **迁移**：Alembic；迁移文件必须带中文注释说明业务意图。表归属与模块同名。
- **命名**：注释用中文，变量、函数、类、文件名用英文。
- **健康检查**：分别报告公开内容可达、数据库可用、模型可用、异步滞后；不用一个全绿接口表示所有能力安全。

## 11. 重访条件

- 基座出现**本产品之外**的消费者，或本产品内的面增长到基座与面的依赖开始互相渗透 → 评估抽包。
- skill 数量增长到元数据常驻列表超出上下文预算 → 引入按面分组或按需筛选的装载策略。
- `library` 中资料与案例的生命周期显著分化（例如案例需要独立授权流程）→ 拆为两个模块。
- `core/authz` 在一期内出现第二个实现 → 提前引入模块边界。
- 前端五层在首个特性落地后被证明样板显著超过收益 → 重访层的物理粒度。
