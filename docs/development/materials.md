## 1. 四个落点，各自能放什么

| 落点 | 位置 | 版本控制 | 能放什么 | 不能放什么 |
|---|---|---|---|---|
| `materials/2026-ai-opensource/` | 仓库内（任何泳道共享同一路径，因为它在 Git 里） | **入库** | 文本、配置、许可与归属说明、**脱敏**证据索引、报告与清单草稿 | 大文件、原始音视频、未脱敏个案、凭据 |
| `deliverables/2026-ai-opensource/<run-id>/` | **原始仓库根**（不是泳道根） | **忽略**（`.gitignore` 与 `.dockerignore` 均有 `/deliverables/`） | 正式运行的原始输出、截图、录屏、评分表、日志 | 任何需要评审者读的**可提交**材料（它们该进 `materials/`） |
| `.tmp/` | 仓库内 | 忽略 | **可丢弃**过程产物（试验、转储、一次性分析） | 任何唯一副本（判据：`git ls-files .tmp` 为空） |
| `demo/` | 仓库内 | 忽略 | **可再生预览**：对外展示用的逐屏截图 | **正式运行证据**（它每轮覆盖，见 §3） |

**为什么 `deliverables/` 必须在原始仓库根**：泳道会被 `scripts/worktree.py remove` 清理。
把它放在泳道里，等于把「唯一一份正式运行证据」放在一个按设计会被删掉的目录下。解析方式：

```bash
git rev-parse --path-format=absolute --git-common-dir   # 原始仓库的 .git（所有泳道共享）
git rev-parse --show-toplevel                           # 当前泳道根——两者不同即说明在泳道里
```

`deliverables/` 落在 `$(dirname $(git rev-parse --path-format=absolute --git-common-dir))` 下。
**先算路径再写入**，不要用相对路径 `../..` 猜层级。

## 2. 目录结构

```text
materials/2026-ai-opensource/          # 入库：可评审、脱敏、许可清楚
  claims.json                          # 正式事实索引（每行一条对外主张，见 §4）；**唯一**事实索引
  runs/<run-id>/                       # 单次运行的**摘要**与配置（原始件在 deliverables）
    manifest.json                      # 模型 ID、版本/commit、案例集 SHA256、参数、日期、评分 prompt hash
    summary.md                         # 计数、分母、失败、限制（不含原始用户文本）
  licenses/                            # 第三方资源清单、许可与归属说明
  report/                              # 技术报告与作品简介草稿（每项事实指回 claims.json 的 claim_id）

deliverables/2026-ai-opensource/<run-id>/   # 忽略：单次运行的原始件
  manifest.json  outputs.jsonl  ratings.json  adjudication.json  summary.md
  logs/  screenshots/  video/
```

- 一个 `run_id` 一个目录，`run_id` **全局唯一**（建议 `<UTC日期>-<用途>-<序号>`，如
  `20261029-formal40-01`）。**已存在的 `run_id` 不重用**。
- `materials/` 里的 `runs/<run-id>/` 是**摘要与配置**；原始输出留在 `deliverables/` 并在
  `manifest.json` 里写明绝对路径与文件 SHA256。签名式引用：`run_id + 文件路径 + sha256`。
- **事实索引只有一份**：`claims.json`。不要再建 `claims.csv` 或第二份清单——两份索引必然分叉，
  而分叉时没人知道哪份算数。

## 3. 正式证据不被覆盖

- **正式运行证据一经冻结不得覆写**。要重跑就新开 `run_id`，旧目录原样保留——「跑坏了所以覆盖掉」
  是不可接受的：失败本身是证据（拒答、超时、工具失败都必须进分母）。
- `demo/` 与 `shots/` 是**可再生预览**，每轮开新批时清空自己；因此**它们不能承担正式证据**。
  需要留存时：先把该轮产物复制进 `deliverables/<run-id>/`，再让下一轮清理。
- 写任何清理脚本前先确认目标路径落在 `demo/`、`.tmp/` 或某个**已归档**的 `run_id` 内；
  不确定时停下来问，不按通配符批量删（`git clean -xdf` 会连 `demo/` 与未入库的 `deliverables/`
  一起带走）。

## 4. 事实状态机：每条对外主张都要有一行

`claims.json` 的字段（与竞赛合同的统一证据索引一致）：

| 字段 | 含义 |
|---|---|
| `claim_id` | `CLM-01`… 稳定编号 |
| `claim_text` | 可以对外讲的**原话** |
| `status` | `verified` / `partial` / `unverified` / `contradicted` |
| `source` | `repo@commit` 或 `run_id` + 文件 + sha256；许可/原件版本与取得日期 |
| `limitations` | 样本量、审查人层级、未覆盖功能、适用边界 |
| `report_section` / `video_scene` | 实际引用位置（没引用就留空，不编） |
| `public_safe` | 能否公开、脱敏到什么程度 |
| `owner` / `next_action` | 未解决的事实与承担人 |

**状态的定义与允许的表述**：

| 状态 | 含义 | 允许的写法 |
|---|---|---|
| `verified` | 有可复核原件（`run_id` + 原始输出 + 评分记录），且主张范围**没有超出证据**：只讲「在这批冻结案例上的可观察表现」 | 可以用完成式，但必须同时写出评分者类型、样本量与适用边界 |
| `partial` | 部分成立：样本小、只跑了一部分、审核层级不足、条件受限 | 必须写明局限，不得省略分母与条件 |
| `unverified` | 没跑过、没审过、只有设计稿或计划 | **不得**写成成果；只能写成「设计/计划/待验证」 |
| `contradicted` | 已有证据与主张相反 | **不得**出现在视频或报告结论里，必须先修正主张 |

**安全与专业有效性单独设线**：即使 AI 双盲评分全部完成，凡主张「临床安全」「专业上正确」
「对真实家庭有效」的，最多 `partial`，且必须写明「未经专业审核」。**AI 评分不是专业审核**，
它只能证明「在这批合成案例上、按这套量表和这两套评分提示词，得分与硬失败数是这些」。
未跑完评分的那一项写 `pending`——不写 0 分、不写通过。

## 5. 不能当证据的东西

| ❌ 不能替代 | 为什么 |
|---|---|
| 工程单测/门禁全绿 | 它证明「按设定运行」，不证明咨询建议专业正确，也不证明安全（inbox 01 的 L0 层） |
| 候选案例集、校验脚本通过 | 结构校验只证明字段与编号自洽，不证明医疗内容正确 |
| 一次外部抖动后的重试成功 | **重试成功不等于模型可靠**：端点抖动、超时、限流后的第二次成功是环境恢复，不是稳定性证据。要报告的是「首轮失败率与失败类型」，重试策略与次数写在 manifest 里，原始失败日志照样保存 |
| AI 评分（含两套独立 agent 双盲） | **不是人工评审，也不是专家背书**。可写「两套独立 AI 双盲评分（模型 ID + prompt hash）」，不得写「专家评估」「人工盲评」「临床验证」「临床级安全率」 |
| 单轮「看起来很好」的个案 | 个案可作示例，不能支撑比例、通过率或「普遍适用」；分母与样本必须写明 |
| 理想化截图、单页动画 | 不能替代固定版本上的连续录屏与实际工具轨迹 |

## 6. 评测执行协议：唯一入口，不在本仓复写

**唯一执行协议**：`inbox/chatgpt/Campfire-AI/evaluation/scenario-benchmark/01–04`
（目标与实验协议、场景与标注、评分与安全门、执行与报告）＋ `05-快速先导评测执行合同.md`
＋ `competitions/2026-AI-OpenSource/参赛材料制作与证据交接合同.md`。**inbox 只读**：
不修改、不把其正文抄成第二份协议；本仓只记录执行产物与事实。

必须遵守的少数硬约束（细节以 inbox 为准）：

- **对照组 A/B/C 同底座模型、同样背景信息**；C 组多看到的信息要另标为「完整产品体验」副实验。
- **正式集冻结后不得用测试集调提示词**；某个 case 因失败而改系统（无论改的是产品缺陷、
  skill/工具还是规范），该 case 转入**回归集**，下一轮用**未见案例**评估，报告必须区分
  「改进前 / 改进后」两批结果。**修复本身是好事，但它不修复已经测出来的分数**——不能用改完
  之后在同一批冻结案例上的重跑结果替换冻结前那一批。
- **分母完整**：错误、拒答、超时、无输出都进分母；只报成功请求等于伪造分数。
- **先判硬失败，再算质量分**；硬失败数目单独报告，不得被平均分抵消。
- 多轮场景的第二轮输入**预先写好**，不允许看结果后即兴追问。
- **评分者类型要如实标注**：inbox 协议里「至少两名独立评审、高风险由合适资质人员审核」的条目，
  用 AI 双盲评分顶替时**不算满足**——本仓把这类运行标为「AI 双盲评分运行」，并写明哪些协议
  条目因此仍未满足。这不阻止运行，只约束表述（§4、§7）。

## 7. 正式评分怎么做：两套独立 agent 盲评

**2026-10-29 用户裁决：正式评测采用 agent 独立评分，不依赖人工。** 人工缺失**不阻断**运行——
该跑就跑、该出数就出数，只是表述层级随评分者类型降级（§4）。

| 条件 | 判据 | 未满足时 |
|---|---|---|
| **两套独立评分 agent** | ≥2 个独立评分器：各自独立的评分提示词（**记 prompt hash**）与评分模型（记精确模型 ID），**互不可见**彼此结论；隐去 A/B/C 身份 | 该轮不得称「正式评分」，只能称单评者探索结果 |
| **保留分歧** | 各评分器的**原始分逐条存盘**（`ratings.json`），分歧逐条记录（`adjudication.json`：分歧点 + 裁定 + 理由），**不得只报均值、不得只报一致项**；一致率与不一致清单同时给 | 该轮不得引用分数 |
| **评分可复现** | `manifest.json` 记评分模型 ID、prompt hash、温度与参数、评分者脚本/版本 commit；评分输入与原始输出同存 | 该轮结果不得引用 |
| **案例集冻结与哈希** | `manifest.json` 记案例集 SHA256 与版本号 | 该轮不得称「正式」 |
| 版本可追溯 | 被评系统的模型 ID、repo commit、参数、知识快照摘要齐备 | 只能称「探索运行」 |
| 风险专业审核（**增强项，非运行前提**） | 高风险用例由具备相关资质者复核 `must_check/must_not` 与升级判据 | **不阻断运行**；但安全/有效性类表述一律 `partial` 或 `pending`，并写明「未经专业审核」 |

- **AI 评分可以主张**：「在冻结的 N 个合成案例上，两套独立 agent 盲评的硬失败数为 X、约束覆盖
  为 Y/Z，分歧 M 条（裁定记录见 `adjudication.json`）」——这类表述可核验、可复现。
- **AI 评分不能主张**：临床安全、专业正确性、真实家庭疗效，以及任何「已获人工/专家评审」的说法。
- 若某轮里既有 AI 双盲评分又有专业人员复核，**分开标注**（哪几条是专业审过、哪几条只有 AI 评分），
  不得合并成一个「已审核」的笼统标签。

## 8. 可入库内容的边界（脱敏与许可）

- **可以入库**：文本、配置、许可与归属说明、脱敏后的证据索引、报告与清单。判据是
  「换一个人从 Git 里能读懂并复核」，而不是「文件在我机器上」。
- **不得入库**：真实家庭/儿童资料与可识别信息、任何访问凭据与 token、私有仓库地址、
  未授权第三方素材、原始音视频大文件。
- **截图与录屏**：不出现学校名称、学校 LOGO、指导教师信息（赛事匿名要求），不出现他人账号
  与真实家庭内容；文件元信息同样要清。
- 只有 `.gitignore` 不能清除**已经提交过**的敏感历史：发现已入库的敏感内容，报告并停下来等
  授权处理，不擅自改写历史。

## 9. 交接给主 agent 的最小内容

```text
- 产物：materials/… 与 deliverables/<run-id>/… 的路径、大小、sha256
- 事实：每条主张的 status 与 source（repo@commit 或 run_id）
- 验证：实际跑过的命令与结果（跑过/没跑过分开写）
- 待决：仍为 `pending` 的评分项（未跑完的两套独立评分）与可选的专业审核
```

**完成定义不是「Agent 说完成」**：每份材料要能指回一条 `verified` 的原始证据；未过闸的项
写明准确的阻断原因与回退方案。

## 10. 本文件何时失效

- 赛事规则、材料规格或评分表变更（inbox 的赛事文件更新）。
- 评测协议版本变更（inbox 01–05 升版）。
- `materials/` 或 `deliverables/` 的落点/忽略规则变更（`.gitignore`、`.dockerignore`）。
- 评测执行方式变更（例如换用独立实例或真命名空间隔离后，「串行运行」的假设不再必要）。
