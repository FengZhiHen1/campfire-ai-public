## 1. 静态与基础设施（不需要登录）

### 1.1 就绪探针

```bash
curl -fsS https://campfire.wenran.me/readyz | jq
```

**通过判据**：HTTP 200，且 `ready` 为 `true`，七项全为 `ok`：

    auth  database  queue  model  falkordb  agent_assembly  skills

**为什么这条排在最前**：`/readyz` 覆盖核心业务链（含 Agent 装配）。它过不了，
后面所有页面测试都会在「发消息 503」上失败，先看它能把排查时间从「到处看」压到一处。
另外**刻意不用 `/livez`**——那只看进程活着，一个装配失败、核心端点必回 503 的版本
在它眼里是健康的。

### 1.2 页面路由（SPA）

逐条访问，判据是 **200 且响应体含 `<div id="root">`**（而不是 API 的 JSON）：

    /                      首页
    /login                 登录页（唯一免登录页面）
    /consult               咨询记录列表
    /consult/emergency     应急现场采集
    /profile               档案
    /cases                 案例库
    /settings              我的
    /settings/memory       记忆
    /guide                 使用说明

**为什么每条都要单独访问而不是只点首页**：这些是**深链/刷新**路径。此前有过一个
真实缺陷——`/consult`、`/profile` 被 nginx 的 API 前缀正则截走，返回 JSON 404/405。
从首页点进去不会触发（客户端路由），只有直接访问或刷新才暴露。

### 1.3 静态资源

从首页 HTML 里取 `<script src>` 与 `<link href>` 的真实路径，逐个请求：

**通过判据**：都 200，且 `Content-Type` 分别是 `application/javascript` / `text/css`
（MIME 错了会白屏，而状态码仍是 200）。

### 1.4 未登录的访问边界

    GET /api/consult/sessions      -> 401
    GET /api/profile/objects       -> 401
    GET /api/memory/episodes       -> 401
    GET /api/library/items         -> 401

**通过判据**：全部 401（不是 404，也不是 200）。404 说明路由没挂上；
200 说明鉴权漏了。

## 2. 注册与登录

### 2.1 注册（邀请码）

1. 打开 `/login`，切到「注册」模式；
2. 填账号名、密码、**邀请码**；
3. 提交。

**通过判据**：注册成功后进入需登录页面（不弹错误）。
**关键负例**（必测）：用一个**假邀请码**再注册一次 →
应返回**我方文案**「邀请码无效或已不可用」，而不是 500 或空白。

> 这条负例同时证明「复写注入的邀请码校验真的在执行」。
> 判据来自实测：`POST /api/auth/signup` 在正确前缀下返回的正是这句业务文案。

### 2.2 再次使用同一邀请码

用**同一个已用过的码**注册第二个账号。

**通过判据**：失败，提示邀请码不可用。这是「一码只用一次」的核心约束
（对应验收 `AC-15`），实现里有一处专门的补偿逻辑守着它。

### 2.3 登录

用 2.1 建好的账号在 `/login` 登录。

**通过判据**：进入首页，且刷新后**仍保持登录**（凭据是 httpOnly cookie，
刷新不该掉线；掉线说明 cookie 域或 `X-Forwarded-Proto` 配错）。

## 3. 咨询面（核心链路）

### 3.1 建会话并发一条消息

1. `/consult` → 新建会话；
2. 输入一句话，发送。

**通过判据**：

- 消息发出后**逐字出现**（流式），而不是整段一次性蹦出来；
- 结束后出现依据区（引用卡片）。

> 「逐字出现」是 SSE 是否真的没被缓冲的唯一可靠判据。状态码在这里帮不上忙——
> 缓冲与不缓冲都是 200。已用假上游做过对照实验：删掉 `proxy_buffering off`
> 一次，5 条事件从「间隔 0.4 秒逐条到达」变成「全部挤在 2.02 秒一次性到达」。

### 3.2 刷新续传

在**回答进行中**刷新页面。

**通过判据**：回到该会话并能看到完整回答（经历史水合），不丢消息、不重复发送。
这是两段式设计（先 POST 拿 `run_id`、再订阅流）要保证的性质。

### 3.3 取消

回答进行中点「停止」（若有该入口）。

**通过判据**：流停止，界面进入可控状态，不报错。

### 3.4 应急入口

`/consult/emergency` → 填八项现场情况 → 提交。

**通过判据**：提交后直接进入对话页并开始回答（不必再手工发一条消息）。

### 3.5 历史会话

`/consult` 列表里能看到 3.1 建的会话，点进去能看到历史消息。

## 4. 档案面

### 4.1 建支持对象

`/profile` → 新建（填名称）。

**通过判据**：列表出现该对象；刷新后仍在（真的落库了）。

**关键负例**：名称留空提交 → 应被拒（422/内联错误），不是 500。
这条对应数据库的 `ck_..._display_name_not_blank` 约束——CI 日志里就能看到
它被触发过，说明有负例在守着它。

### 4.2 改名 / 归档 / 恢复

对同一对象依次做改名、归档、恢复。

**通过判据**：每步都生效且是**幂等**的（重复归档不报错）；
归档后新条目被拒（409），但仍可读。

### 4.3 条目与候选层

在对象下新增一条档案条目。

**通过判据**：新条目进入**候选层**（待确认），需确认后才进稳定层。
这是「系统推断不当既成事实」的产品约束。

### 曾踩到的坑（留档，因为同类问题还会再出现）

**443 为什么当时不通**：`https://43.161.195.236` 从**服务器自身**访问也超时，而 Docker 对
80/443 的 DNAT 规则完全对称、本机 iptables 无 443 的 DROP 规则——因此判定为云侧安全组，
而不是配置问题。这个判定后来被证实（放行即通）。

**启用跳转时暴露的两个缺陷**（都只在「真的去启用」时才现形，详见提交
`fix(nginx): 80→443 跳转改用独立 server 块`）：

1. 跳转写进 80 的 server 块 → 与 SPA 的 `location /` 重复，nginx **拒绝启动**
   （`[emerg] duplicate location "/"`）。所幸脚本「校验失败即回滚」救了下来。
2. 改完第 1 条后 `nginx -t` 通过了，但跳转**被静默忽略**——两个 server 块争同一个
   `server_name`，nginx 只保留先出现的那个，且**只打 warn 不打 error**。
   除了实际发请求看状态码，没有别的办法发现。

**一个必须记住的连锁故障点**：80 跳转启用后，ACME 挑战路径**必须豁免**，否则证书续期
会失败——而且要等到证书快过期才发现。已回归验证：跳转启用后
`tls-renew.sh --dry-run` 仍报「all simulated renewals succeeded」。

### SSE 逐条到达怎么测的

这一条**不能**用状态码判定：缓冲与不缓冲都是 HTTP 200，最终内容也完全一样。因此测量的是
**事件到达时刻**——用底层的 `http.client.read1()` 增量读取（`urllib` 的 `read()` 会等到流
结束，那样测不出任何东西），记录每个 SSE 事件相对开始的时刻：

    564 个事件，首末跨度 13.84 秒，53 个不同到达时刻
    ⇒ 事件分布在多个时刻，未被缓冲

对照数据：此前用假上游做过消融——删掉 `proxy_buffering off` 一次，5 条事件从
「间隔 0.4 秒逐条到达」变成「全部挤在 2.02 秒一次性到达」。

### 本轮由验收抓出并修复的两个 P0

两条都只在**真实浏览器 + 真实部署**下暴露，单测与本地开发都看不见：

1. **登录/注册完全不可用**——`session.ts` 的 `recipeList` 漏了 `EmailPassword.init()`，
   SDK 在发请求前就抛异常。单测没抓到是因为它把这个模块整个 `vi.mock` 掉了。
2. **发消息必失败**——明文 HTTP 下 `crypto.randomUUID` 不存在（secure context 专有），
   幂等键生成抛 `TypeError`。本地 `localhost` 属 secure context，因此开发时正常。

详见提交 `fix(web): 修复登录与发消息两处「上线才暴露」的缺陷`。
