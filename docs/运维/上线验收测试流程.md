## 1. 静态与基础设施（不需要登录）

### 1.1 就绪探针

```bash
curl -fsS https://campfire.wenran.me/readyz | jq
```

> ⚠️ **不要在浏览器里打开 `/readyz` 当作判据**。它的响应体是 JSON，浏览器
> 不渲染也读不出结构；更常见的是**被浏览器扩展/广告拦截器直接拦掉**，
> 报 `net::ERR_BLOCKED_BY_CLIENT`。**那说明不了服务好坏**——
> 它只说明这次请求没发出去（或被本地拦截了）。
>
> ⇒ **「打不开」≠「服务坏了」**。判据取命令行（上面那条）。
> ⇒ **若命令行也不可达**（连接被拒 / 超时 / DNS 失败）：那**是**一回事，
> **如实记为「受阻」并附上原始报错**，不要猜「站点坏了」，也不要记「通过」。
> **本机代理环境变量是已知陷阱**（`HTTP_PROXY` 可能指向不存在的本地端口）：
> 若报 `Failed to connect ... over proxy`，用 `curl --noproxy '*' -fsS <URL>` 重试一次，
> 并**把两次结果都记下来**。

**通过判据**：HTTP 200，且 `ready` 为 `true`，七项全为 `ok`：

    auth  database  queue  model  falkordb  agent_assembly  skills

**为什么这条排在最前**：`/readyz` 覆盖核心业务链（含 Agent 装配）。它过不了，
后面所有页面测试都会在「发消息 503」上失败，先看它能把排查时间从「到处看」压到一处。
另外**刻意不用 `/livez`**——那只看进程活着，一个装配失败、核心端点必回 503 的版本
在它眼里是健康的。

### 1.2 页面路由（SPA）

逐条访问，判据是 **200 且响应体含 `<div id="root">`**（而不是 API 的 JSON）：

    /                      首页
    /login                 登录页（唯一免登录页面）
    /consult               咨询记录列表
    /consult/emergency     应急现场采集
    /profile               档案
    /cases                 案例库
    /settings              我的
    /settings/memory       记忆
    /guide                 使用说明

**为什么每条都要单独访问而不是只点首页**：这些是**深链/刷新**路径。此前有过一个
真实缺陷——`/consult`、`/profile` 被 nginx 的 API 前缀正则截走，返回 JSON 404/405。
从首页点进去不会触发（客户端路由），只有直接访问或刷新才暴露。

### 1.3 静态资源

从首页 HTML 里取 `<script src>` 与 `<link href>` 的真实路径，逐个请求：

**通过判据**：都 200，且 `Content-Type` 分别是 `application/javascript` / `text/css`
（MIME 错了会白屏，而状态码仍是 200）。

### 1.4 未登录的访问边界

    GET /api/consult/sessions      -> 401
    GET /api/profile/objects       -> 401
    GET /api/memory/episodes       -> 401
    GET /api/library/items         -> 401

**通过判据**：全部 401（不是 404，也不是 200）。404 说明路由没挂上；
200 说明鉴权漏了。

## 2. 注册与登录

### 2.1 注册（邀请码）

1. 打开 `/login`，切到「注册」模式；
2. 填账号名、密码、**邀请码**；
3. 提交。

**通过判据**：注册成功后进入需登录页面（不弹错误）。
**关键负例**（必测）：用一个**假邀请码**再注册一次 →
应返回**我方文案**「**邀请码无效或已被使用**」，而不是 500 或空白。

> **⚠️ 文案有【两层】，判据取界面那一层**（2026-10-06 按代码核实）：
> **界面**显示的是前端文案「**邀请码无效或已被使用**」
> （`apps/web/src/features/accounts/domain/authFailure.ts:37`）；
> **后端**返回的原文是「**邀请码无效或已不可用**」
> （`apps/api/src/campfire/modules/accounts/registration.py:95`）。
> 前端**刻意不复述** —— 注意**不复述的是 SDK 层的原始错误**（那里含字段名与英文句子，如
> `Field is not optional`），**不是**上面那句后端中文复写文案；透出 SDK 原文既不符合本产品语言，
> 也把「服务端如何描述这次拒绝」变成可外部观察的枚举渠道（同文件 `:28-30`）。
> ⇒ 判据写界面那句；**若在 F12 → Network 里看到后端那句，也算正常**。

> 这条负例同时证明「复写注入的邀请码校验真的在执行」。
> 判据来自实测：`POST /api/auth/signup` 在正确前缀下返回的是**后端那条**业务文案
> （「邀请码无效或已不可用」，见上方两层说明）——**界面把它换成了前端那句**，
> 两者是同一件事的两个呈现层。

### 2.2 再次使用同一邀请码

用**同一个已用过的码**注册第二个账号。

**通过判据**：失败，提示邀请码不可用。这是「一码只用一次」的核心约束
（对应验收 `AC-15`），实现里有一处专门的补偿逻辑守着它。

### 2.3 登录

用 2.1 建好的账号在 `/login` 登录。

**通过判据**：进入首页，且刷新后**仍保持登录**（凭据是 httpOnly cookie，
刷新不该掉线；掉线说明 cookie 域或 `X-Forwarded-Proto` 配错）。

## 3. 咨询面（核心链路）

### 3.1 建会话并发一条消息

1. `/consult` → 新建会话；
2. 输入一句话，发送。

**通过判据**：

**【形态判据】**（回答「传输与渲染对不对」）

- 消息发出后**逐字出现**（流式），而不是整段一次性蹦出来；
- 结束后出现依据区（引用卡片）。

**【成效判据】**（回答「这一步本来要达成什么」）——**本轮新增，缺了它就会漏检**

- **工具调用行没有落在未完成态**：答复里出现的每一条工具调用行，都应以
  「**已结束**」收尾，而**不是**「`未完成`」。
  ⇒ **描述判据**：**工具行显示为已完成 / 成功收尾**；
  ⚠️ **不要把某个字面量写进结论**（例：不要写「必须显示『已完成』」）——
  工具名的**友好化文案**与**状态词**会随前端文案迭代变动
  （`ToolIndicator` 的当前实现是 `工具名 · 进行中 / · 未完成 / · 已结束`）。
  **判据要落在「这一行是成功收尾还是失败收尾」这个语义上**，
  至于那一行显示中文友好名还是标识符，是另一件事（见 §8 与 [测试人员指南](测试人员指南.md) §9）。
  **⚠️ 兜底（不论工具行怎么改版都成立）**：名称与状态词**正在改版**（改为中文友好名，
  并新增查不到映射时的中性名「其他操作」，见
  `apps/web/src/features/consult/view/MessageParts/toolLabels.ts:64`）⇒
  **本判据只依赖两件事**：① 这一行是成功还是失败收尾（语义）；
  ② **若界面上一条工具行都找不到**、而回复又声称做了某事（建档/记录/检索），
  **请把这件现象本身记下来**（可能是缺陷，也可能是改版换了入口形态），
  **不要用「没看到未完成」反推成成功**——找不到可判的行时按 §8.3 记「受阻」或「观察」。
- **若回复声称「已记录 / 已建档 / 已记住」⇒ 必须去另一个页面确认它真的存在**：
  去 `/profile`（档案）或 `/settings/memory`（记忆）看有没有**本次新建的那一条**。
  ⇒ **在咨询页里看到"成功的样子"不构成证据**（见 §8 通则）。
- **回复本身要给出你问的那件事**：请求了三条建议，就应能在正文里数出三条。
  **模型回答与工具失败是两回事**：工具全失败时回复仍可能流式正常、界面不报错——
  **那正是本条要挡住的形态**（见下方本轮实例）。

> ⚠️ **为什么必须补这一组（本轮真实漏检，不是假想）**：2026-10-05 的真实测试人员报告
> （`.tmp/测试反馈/篝火智答测试反馈报告.md`）发现**新账号首次咨询建档失败**
> （`QA-01`）：界面表现为 **`create_support_object · 未完成` 卡片 + 回复正常流式 +
> 界面不报错**。而当时的判据只有上面那两条**形态判据** ⇒ **它完美通过了**，
> 工具却**全部失败**（档案页与记忆页随后都是空的）。
> ⇒ **「传输没被缓冲」「部件在」「没报错」都只是必要条件，不是成效。**

> 「逐字出现」是 SSE 是否真的没被缓冲的唯一可靠判据。状态码在这里帮不上忙——
> 缓冲与不缓冲都是 200。已用假上游做过对照实验：删掉 `proxy_buffering off`
> 一次，5 条事件从「间隔 0.4 秒逐条到达」变成「全部挤在 2.02 秒一次性到达」。

### 曾踩到的坑（留档，因为同类问题还会再出现）

**443 为什么当时不通**：`https://43.161.195.236` 从**服务器自身**访问也超时，而 Docker 对
80/443 的 DNAT 规则完全对称、本机 iptables 无 443 的 DROP 规则——因此判定为云侧安全组，
而不是配置问题。这个判定后来被证实（放行即通）。

**启用跳转时暴露的两个缺陷**（都只在「真的去启用」时才现形，详见提交
`fix(nginx): 80→443 跳转改用独立 server 块`）：

1. 跳转写进 80 的 server 块 → 与 SPA 的 `location /` 重复，nginx **拒绝启动**
   （`[emerg] duplicate location "/"`）。所幸脚本「校验失败即回滚」救了下来。
2. 改完第 1 条后 `nginx -t` 通过了，但跳转**被静默忽略**——两个 server 块争同一个
   `server_name`，nginx 只保留先出现的那个，且**只打 warn 不打 error**。
   除了实际发请求看状态码，没有别的办法发现。

**一个必须记住的连锁故障点**：80 跳转启用后，ACME 挑战路径**必须豁免**，否则证书续期
会失败——而且要等到证书快过期才发现。已回归验证：跳转启用后
`tls-renew.sh --dry-run` 仍报「all simulated renewals succeeded」。

## 8. 判据的两种形态与跨页核对（★ 通则，适用于本文每一条）

> 本节是**一条通则**，不是某一节的补充。写它的原因是本轮真实漏检了一次
> （`QA-01`：形态判据全过、核心功能实际失败），而**同类缺陷还会再出现**。

### 8.1 每条判据都要问两遍

**每写一条判据，都要问这两个问题**（**建议把这一行直接抄进你的判据区**）：

> **「这一步本来要达成什么成效？我在哪里能看到它？」**

| 形态判据（回答「传输与渲染对不对」） | 成效判据（回答「这一步本来要达成什么」） |
| --- | --- |
| 流式逐字出现（没被缓冲） | 工具行**成功收尾**，不是 `未完成` |
| 依据区出现（渲染部件在） | 回复里**确实有你问的那几条**内容 |
| 不报错、HTTP 没炸 | 声称「已记录/已建档」的事，**在另一个页面里真的存在** |
| 状态码 200 / 401 / 422 正确 | 数据真的落库（刷新后仍在） |
| 页面能打开 | 打开后**有正确的数据**，不是空态冒充成功 |

**只有形态判据的后果（本轮实例）**：`QA-01` 的界面表现是
**「回复正常流式 + 依据区在 + 界面不报错」** ⇒ 当时的形态判据**全部通过**，
而两个建档工具**都失败了**（`create_support_object · 未完成`），
档案页与记忆页随后都是空的。
⇒ **形态判据是必要条件，不是成效。** 只写形态判据的验收单，
**对一个「什么都没做成功、但界面很平静」的版本是绿的**。

### 8.2 跨页核对（怎么落实 8.1 的第二问）

**通则：凡「回复声称做了某事」的功能，判据必须包含「去另一个页面核对」。**

理由：**缺陷在「当前页」看不见**。`QA-01` 在咨询页里显示得像成功了——
工具卡片只是安静地留着，回复也正常流式。**只有切到档案页/记忆页才看得见它没做成。**

| 回复声称 | 去哪里核对 | 核对什么 |
| --- | --- | --- |
| 已建档 / 已创建支持对象 | `/profile` | 列表里出现**本次新建的那一个**（刷新后仍在） |
| 已记住 / 已记录偏好 | `/settings/memory` | 时间线里出现**本次那一条** |
| 已查阅资料 / 已检索案例 | 依据区是否给出**引用卡片** | 引用卡片有内容，不是空块 |
| 已发出行动卡（应急） | 对话页的行动卡 | 卡片**有内容**，不是空壳或没有 |

**核对方式**：切到目标页面 → **刷新一次** → 确认那一条在。
**空态页面不是失败**（§5.1、档案页空态都是合法的），
**但「本轮刚声称创建过、这边却是空」是失败**——两者的区别就是**本次操作**。

### 8.3 结果分类（五档，别只写「通过/失败」）

一条用例的结论**只能**落在这五档里。**「受阻」是本轮补上的一档**——
它专门处理「验证条件没满足，既不能判通过、也不能判失败」的情形：

| 档 | 判据（什么情况下用它） |
| --- | --- |
| **通过** | 观察与预期相符，**仅限所述范围**（写清范围） |
| **失败** | 观察到**明确异常** |
| **观察** | 现象已记录，但**产品判据或已知问题状态尚待核对** |
| **受阻** | **验证条件未满足，不能判通过或失败**（例：探针被本地扩展拦掉、工具不可用、环境缺失） |
| **未测试** | **本次没有执行**（不是「执行了没结论」） |

**⚠️ 最容易误用的两档**：

- **「受阻」不是「失败」**：拿不到 HTTP 状态码时，**不能推断站点坏了**
  （本轮 `/readyz` 被浏览器扩展拦掉，报 `net::ERR_BLOCKED_BY_CLIENT`——
  正确结论是**受阻**，不是「健康检查失败」）；
- **「受阻」也不是「通过」**：拿不到证据时**不能默认它没事**。
  **判据没取到时，默认动作是补测或如实记「受阻」，不是猜。**

**报告请写明分母**：若完整清单未知（例：只拿到部分测试材料），
**不计算通过率**，直接说明「用例总分母未知」。**这比给一个虚高的通过率诚实，
也比让人误以为已覆盖全部。**

### 8.4 版本核实（⚠️ **测试人员侧做不到，只能由运维侧核实**）

**本轮真实报告的原文**：「**生产版本号未在本次核实**」、
「**附件提供的版本与提交信息未在本次确认**」。

**⇒ 核实结论（本包实测 4 条排除证据，见下）：从公开侧拿不到生产在跑哪个提交。**
**因此不要把这条写成测试人员的必做步骤**——那会得到一份永远「未核实」的报告。
**正确的做法是把它标成【运维侧核实项】，并在报告里明确「无法由本次测试核实」。**

**运维侧核实命令**（在服务器 `/opt/campfire` 下执行）：

```bash
grep '^IMAGE_TAG=' .env.prod && \
  docker compose -f docker-compose.prod.yml --env-file .env.prod ps
```

**判据**：`IMAGE_TAG` 的值应等于**本次发布用的提交 SHA 前 12 位**，
且 `api` / `web` / `worker` 容器的 `IMAGE` 列**都指向同一个 tag**
（三者指向不同 tag = 只换了一半，是缺陷）。

**⚠️ 为什么测试人员做不到（4 条实测排除，不是推测）**：

1. **没有版本端点**：`grep -r '/version\|__version__\|BUILD_SHA\|GIT_COMMIT'` 在
   `apps/api/src/campfire` 下**零命中**；
2. **OpenAPI 文档未对外暴露**：`https://campfire.wenran.me/openapi.json` 返回的是
   **SPA 的 HTML**（nginx 把它交给前端 `location /`），`/api/openapi.json` 返回 **404**；
   `/docs` 同样返回 SPA HTML ⇒ **拿不到 `FastAPI(version=...)`**，
   且该值本就是硬编码的 `"0.1.0"`（**不代表提交**）；
3. **`/readyz` 不含版本**：它的 7 个组件只回报组件状态（`model` 项回报的是
   **模型名** `deepseek-v4.1-flash`，不是构建版本）；
4. **镜像仓库是私有的**：向 GHCR 匿名申请
   `ghcr.io/.../campfire-api` 的 pull token 返回
   `{"errors":[{"code":"DENIED"}]}` ⇒ **无法从镜像 tag 反查**。

**唯一从公开侧可见的指纹**是首页 HTML 里的产物文件名
（形如 `/assets/index-<hash>.js`）——**但它不能当作版本核实手段**，
两个理由：① 它**不映射到提交 SHA**，没有对照表就读不出结论；
② 前端产物哈希**只随前端源码变化**，而发布里常混着**纯后端或纯文档提交**
（本轮最后一次发布就是「前端源码 0 文件改动」）⇒ **产物哈希根本不会变**，
用它「核实版本」会得到**假绿灯**。

> ⇒ **测试人员在报告里请直接写**：「生产版本号**本次无法从公开侧核实**，
> 须由运维侧按 §8.4 的命令确认」。**这是如实结论，不是测试没做。**

结束，那样测不出任何东西），记录每个 SSE 事件相对开始的时刻：

    564 个事件，首末跨度 13.84 秒，53 个不同到达时刻
