# 发布、回滚与备份

> **本文是运维动作的唯一操作说明。** 它约束三件事：怎么发一版、出问题时怎么退回去、
> 数据怎么备份与恢复。可执行部分都在 `scripts/`（`backup.sh` / `restore.sh` /
> `rollback.sh` / `tls-issue-cert.sh` / `tls-enable-redirect.sh`）与
> `.github/workflows/deploy.yml`，本文只讲**为什么这样做**与**每一步的判据**。
>
> 状态：2026-10-01 编写，同日生产落地并订正。**此前本条写「目标服务器、域名与 TLS 证书
> 在仓库中不存在任何事实」——已不成立**：现为 `campfire.wenran.me` → `43.161.195.236`
> （腾讯云 HK），部署目录 `/opt/campfire`，证书由 Let's Encrypt 签发（见第 6 节）。
> 因此下文出现的 `$DEPLOY_HOST` 等已换成实际值，而**凭据仍在服务器 `.env.prod` 里**
> （不入库）。

## 0. 先读这一页：三条不可违背的纪律

1. **发布验证用 `/readyz`，不用 `/livez`。** `/livez` 只看进程活着——一个「Agent 装配
   失败、核心端点必回 503」的版本在它眼里完全健康。这个假健康在本项目真实发生过
   （模型网关因 `no_proxy` 配置无法构造），因此两个端点被刻意拆开。
2. **迁移必须向后兼容一版。** 回滚只换镜像、**不做数据库 downgrade**（理由见第 4 节）。
   这条纪律是「回滚能成立」的前提，不是可选项。
3. **破坏性动作必须显式确认。** `restore.sh` 与 `rollback.sh` 不加 `--yes` 只做演练，
   不改任何东西。这不是麻烦，是防「手滑覆盖生产数据」的唯一屏障。

## 1. 发布

### 1.1 触发

发布是**手动**的（`workflow_dispatch`），不是 push `master` 自动上线：

```text
GitHub → Actions → Deploy → Run workflow
  image_tag: 留空（默认取当前提交 SHA 前 12 位）
  deploy:    先不勾（只构建推送镜像），验证镜像构建成功后再勾选发布
```

**为什么不用「push master 即发布」**：旧链路就是这么做的，且它对生产目录执行
`git reset --hard origin/master`——未提交的运维改动会被无声抹掉，失败时目录停在
「文件已换、服务未重启」的半更新状态。镜像发布没有这个问题：镜像要么完整推送成功，
要么没有；生产目录始终由 compose 指向某个确定的 tag。人工闸门是刻意保留的。

### 1.1b 「改一个 bug 并上线」的完整路径（2026-10-01 实测跑通）

CD 链路跑通后，这是标准路径，**全程不需要手工 ssh 到服务器**：

```bash
# 1. 本地修复 + 跑门禁
uv run ruff check . && uv run ruff format --check . && uv run pytest
cd apps/web && pnpm exec vitest run && pnpm exec oxlint src && pnpm exec tsc --noEmit && cd ../..

# 2. 提交并推送（英文 type 前缀 + 中文标题正文）
git add <本次涉及的文件> && git commit && git push origin HEAD:master

# 3. 等 CI 绿（三个 job：设计文档一致性、后端、前端）
gh run list --limit 3

# 4. 触发发布（deploy=true 才会真的上线）
gh workflow run deploy.yml --ref master -f deploy=true
gh run watch <run-id>          # 或 gh run list --workflow=deploy.yml --limit 1

# 5. 验收（发布流程自身已轮询 /readyz，这里补业务面）
uv run --no-project python .tmp/acceptance_section1.py --base https://campfire.wenran.me
```

实测耗时：build-and-push 约 3.5 分钟，release 约 1.5 分钟，**合计约 5 分钟**。

**发布失败时**：`deploy.yml` 会在第 6 步（启动新版本）之后轮询 `/readyz`；失败会打印
api 容器最近 60 行日志并提示回滚。注意**先判断是不是误报**——上面第 3 号缺陷就是把
成功报成了失败，而回滚一个正常版本会把小事变成事故。

### 1.2 发布链路做了什么

```text
build-and-push                           release（需勾选 deploy）
  1. 计算 tag（提交 SHA 前 12 位）         1. 校验 DEPLOY_* Secrets 齐备（缺则硬失败）
  2. 构建并推送 api 镜像 → GHCR            2. 上传编排、infrastructure/ 与 scripts/
  3. 构建并推送 web 镜像 → GHCR            3. 目标机登录 GHCR 并 pull
     （VITE_API_DOMAIN 构建期内联）        4. **发布前快照**：backup.sh 写 ./backups/
  4. 写发布摘要（含回滚命令）               5. **再迁移**：alembic upgrade head
                                          6. 启动：compose up -d --no-build
                                          7. **验证**：轮询 /readyz 直到 200
```

**第 4 步（快照）为什么不能省**：迁移是本次发布中唯一**不可逆**的动作——镜像可以换回去、
代码可以回滚，但 `alembic upgrade head` 删掉的一列、改掉的一个类型，退不回来。快照失败即
中止发布：一个「没有回滚点的迁移」比不发布更危险。快照用仓库里的 `backup.sh`（不另写一份），
产物落在目标机的 `$DEPLOY_PATH/backups/`。

**第 5 步为什么在切换之前**：反过来的话，新代码会先面对旧 schema 一段时间——那些请求
要么 500、要么静默写错。而迁移在前时，「迁移完成、切换失败」这一中间态是安全的：
旧容器仍能正常工作（因为迁移向后兼容）。

**第 7 步的上界是 120 秒**（40 次 × 3 秒）。超时即失败，并打印 api 容器最近 60 行日志。

### 1.3 首次发布前必须准备好的东西

由运维提供，**不在仓库里**（仓库不含任何真实凭据，这是刻意的）：

| 名称 | 用途 | 备注 |
| --- | --- | --- |
| 目标服务器 | 单机 Docker Compose v2 | |
| 域名与 TLS 证书 | Nginx 443 | 仓库中的 `nginx.conf` 有 TLS server 块，但**默认注释掉**——证书路径由运维填 |
| `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_SSH_KEY` / `DEPLOY_PATH` / `DEPLOY_KNOWN_HOSTS` | GitHub Secrets，供 `release` job 使用 | 缺任一项，勾选发布时会**硬失败并点名** |
| `PUBLIC_BASE_URL` | 前端构建期 `VITE_API_DOMAIN` | 不配则回落到 `https://localhost`（业务请求走同源，该值只用于 supertokens-web-js 的 init） |

> **CD 链路已于 2026-10-01 首次真实跑通。** 那一次连撞三个缺陷，都只在「真的执行
> release」时才现形（此前只跑过 `deploy=false` 的构建推送，release 一直显示 `skipped`）：
>
> 1. `release` 任务缺 `packages: read` → 拉私有 GHCR 镜像 **403**，而报错长得像
>    「仓库路径写错了」；
> 2. `backup.sh` 读不到 env 文件里的密码 → 发布前快照**必然失败**（报「BGSAVE 超时」，
>    实际是 `NOAUTH`；且 `redis-cli` 未认证时退出码为 0，使守卫形同虚设）；
> 3. 发布验证的 `docker compose exec` 漏了 `--env-file` → 解析强制变量失败，
>    **把「部署成功」误报成失败**（这是最坏的一类：会诱使人回滚一个正常的版本）。
>
> 三个都已修复并提交。第 3 条修好后重跑，验证步骤**第 1 次探测**即返回 200。
>
> **教训（值得记住）**：一条从未被真实执行的链路，其正确性是未知的。它看起来完整
> （有权限声明、有快照步骤、有验证步骤、有回滚提示），但每个环节都可能因为一个
> 缺失的参数而失败——而这些失败只会在第一次真跑时一起出现。

目标机上的 `.env.prod` **由运维手动维护**（`release` 不上传它，避免发布覆盖生产凭据）。
模板见仓库根的 `.env.example.prod`，所有值都是 `CHANGE_ME_*` 占位符。

`.env.prod` 里必须有这三行——它们共同决定 compose 用哪个镜像：

```text
IMAGE_API=ghcr.io/<owner>/<repo>/api    # 仓库地址，不含 tag
IMAGE_WEB=ghcr.io/<owner>/<repo>/web
IMAGE_TAG=<提交 SHA 前 12 位>
```

`release` job 会用 `sed` 推进这三行（首次部署时自动追加）。**三者缺一不可**：
compose 的 `image:` 是 `${IMAGE_API:-campfire-api}:${IMAGE_TAG:-local}`——
只给 `IMAGE_TAG` 而不给 `IMAGE_API`，compose 会去找 `docker.io/library/campfire-api`，
与 GHCR 上推的引用不同名，`pull` 永远拉不到（这是 2026-10-01 修掉的真实缺陷）。

### 1.4 发布后的人工复核

`/readyz` 返回 200 只证明「七项探针都就绪」。仍建议做一次：

```bash
curl -fsS https://<域名>/readyz | jq       # 七项组件应全为 ok
```

然后走一遍真实用户路径（登录 → 建会话 → 发一条消息 → 看到流式回复）。理由：探针覆盖的是
依赖可达性，不是「业务链路真的通」——两者会在装配缝上分叉。

## 2. 备份

### 2.1 备份什么、为什么

| 数据 | 内容 | 丢失后果 |
| --- | --- | --- |
| PostgreSQL | 账号、会话归属、档案、资料与案例、RAG 节点、删除墓碑、待处理记录，**以及 SuperTokens core 自己的表** | 不可恢复的业务数据丢失；用户与内容一起没了 |
| FalkorDB | Graphiti 长期记忆（按账号分图） | 记忆图丢失——已积累的长期记忆无法重建（它由模型抽取生成，不是可重放的输入） |
| Redis | 队列、在途运行缓冲（runbus） | 待处理记录靠兜底扫描重投（设计如此），但**在途运行会丢**，且要等最多一个扫描周期 |

因此三样都备份，Redis 可以用 `--skip-redis` 关掉（代价如上）。

### 2.2 用法

```bash
# 生产
scripts/backup.sh \
  --out-dir /var/backups/campfire \
  --compose-file docker-compose.prod.yml \
  --env-file .env.prod
```

产物在 `<out-dir>/<UTC 时间戳>/`：

```text
postgres.dump         pg_dump 自定义格式（-Fc），可被 pg_restore 选择性恢复
falkordb-dump.rdb     FalkorDB 快照
redis-dump.rdb        Redis 快照（除非 --skip-redis）
SHA256SUMS            校验和清单（restore.sh 恢复前必校验）
manifest.txt          大小、来源与恢复命令
```

### 2.3 几个实测踩到的点（脚本已内建处理）

- **FalkorDB 的持久化目录不是 `/data`**，而是 `/var/lib/falkordb/data`。按 Redis 惯例写
  `/data` 会得到 `cat: can't open '/data/dump.rdb': No such file or directory`——而
  `BGSAVE` 明明成功了，看起来像权限问题。脚本改为用 `CONFIG GET dir` / `dbfilename`
  **问服务自己**，对 dev 与 prod 两种镜像都成立。
- **必须等 `LASTSAVE` 变化再拷**。`BGSAVE` 是异步的，发完就拷会拿到正在写的文件
  （一个损坏的 RDB）。脚本最多等 30 秒。
- **备份后立刻用 `pg_restore --list` 校验**转储可解析。没有这一步，损坏要到恢复时才发现
  ——那时旧的可用数据已经被覆盖了。
- **保留周期由运维决定，脚本不删任何东西**。自动删除是不可逆操作，删错保留期的代价
  高于多存几份。

### 2.4 建议的保留策略与异地副本

本文只给建议，不写进脚本（这是运维决策）：

- 每日一份，异地保留 30 天；每周一份，保留 3 个月。
- **必须复制到另一台机器**。同一块盘上的备份在磁盘故障时与源数据一起丢——那不是备份。
  推荐：`rclone`/`rsync` 推到对象存储，或另一台机器的独立磁盘。

## 3. 恢复

### 3.1 这是破坏性操作

```bash
# 第一步永远是演练：不加 --yes，脚本只打印将做什么
scripts/restore.sh --from /var/backups/campfire/20261001T085613Z

# 确认后再执行
scripts/restore.sh --from <目录> --yes
```

脚本在动任何数据之前会：

1. 校验 `SHA256SUMS`（不通过即中止——拿损坏的备份覆盖仅存的可用数据是最坏结果）；
2. 打印将要做什么并退出（未加 `--yes` 时）。

### 3.2 恢复顺序与理由

**PostgreSQL → FalkorDB → Redis**。数据库在前，因为图库与队列的数据都引用它
（例如 `pending_write.id` 派生出图库侧的 episode 标识）——先恢复引用方会让一致性判断
失去依据。

### 3.3 恢复之后必须做的四件事

```bash
# 1) 迁移到最新（备份来自旧 schema，代码是新版本的）
docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm api alembic upgrade head

# 2) 启动并验证就绪（--no-build：发布目录没有源码，镜像缺失时必须响亮失败而不是本地兜底构建）
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --no-build
curl -fsS http://<目标>/readyz

# 3) 抽查业务数据——「命令没报错」不等于「数据回来了」
#    至少核对：账号数、支持对象数、资料条目数、以及一条会话能否打开

# 4) 记录：时间、来源备份目录、执行人
```

**第 3 步不是形式**。本项目在验证 `backup.sh` 时做过一次真实恢复演练：把转储恢复到
一个临时库后，逐表比对行数——`activity_log_p202609` 11786、`emailpassword_users` 4914、
`session_info` 2711、`agent_messages` 196、`data_campfire_node` 92、`agent_sessions` 65
全部一致。**没有这条比对，就无法排除「恢复出了一个空库」。**

## 4. 回滚

### 4.1 为什么回滚不 downgrade 数据库

**回滚只换镜像。** 这是刻意的：

- 迁移里可能有删列、改类型、合并表等**不可逆**操作，`alembic downgrade` 会丢数据；
- 更难办的是「新版本已写入的数据」：旧代码读不懂新列，downgrade 也补不回来。

正确的形态是**迁移向后兼容一版**：新 schema 能被旧代码正常使用（只加列不改语义、
不删列、不重命名）。这样回滚只是「换回旧镜像」，数据完整。

若某次迁移**无法**向后兼容（例如必须删列），那它就不是「可回滚的发布」，需要
变更窗口 + 停机 + 数据导出，属于另一次流程，不在本文覆盖。

### 4.2 用法

```bash
# 演练（不加 --yes，只打印将做什么）
scripts/rollback.sh --target-sha <上一个 SHA> --host deploy@<主机> --path /opt/campfire

# 执行
scripts/rollback.sh --target-sha <上一个 SHA> --host deploy@<主机> --path /opt/campfire --yes
```

脚本做四件事：改 `.env.prod` 的 `IMAGE_TAG` → `compose pull` → `compose up -d` →
轮询 `/readyz`。执行前会先打印当前版本与目标版本；两者相同时直接退出（不折腾生产）。

回滚**只改 `IMAGE_TAG`**（`IMAGE_API`/`IMAGE_WEB` 不变——它们指向同一个仓库，
版本由 tag 决定）。因此只需该版本仍在 GHCR 上。

**拉镜像失败时是安全的**：此刻还没重启，生产仍在旧版本上跑。脚本会提示
`.env.prod.before-rollback`（它每次回滚前留的副本）。

### 4.3 怎么知道有哪些版本可退

- 当前版本：目标机上 `grep IMAGE_TAG .env.prod`
- 历史版本：GHCR 的镜像列表（`ghcr.io/<owner>/<repo>/api` 的 tags 就是历次发布提交的
  SHA 前 12 位）

因为 tag 用提交 SHA，**每个 tag 都能反查出是哪个提交**——这是不用 `latest` 或时间戳的原因。

### 4.4 回滚也失败怎么办

1. 先让服务可用：`rollback.sh` 回到**更早**的 tag（GHCR 里往前找）。
2. 若是数据问题（例如迁移已破坏旧代码的假设），不要再反复换镜像——那会在不一致的
   数据上反复启动。此时应：
   - 停 api 与 worker（避免继续写入不一致状态）；
   - 用 `restore.sh` 恢复到发布前的备份；
   - 记录并复盘。
3. 全程保留证据：`docker compose logs`、目标机 `.env.prod` 的历史副本、
   `/readyz` 的输出。

## 5. 演练建议

**未演练过的备份不算备份，未演练过的回滚不算回滚。** 建议：

- **每季度**做一次恢复演练：拿最新的备份恢复到一台临时机器，走完第 3.3 节的四步。
- **每次发布**记录 tag 与时间，保留最近 3 个可用版本在 GHCR。
- 演练本身要记录：日期、来源备份、耗时、发现的问题。演练的目的是**发现恢复流程里的
  洞**，所以「很顺利，没问题」也是一种可疑的结论，值得看一眼是不是漏了校验步骤。

## 6. TLS 证书（签发与启用跳转）

证书是**运维产物**，不在仓库里（`.gitignore` 已忽略 `**/nginx/ssl/`、`*.pem`、`*.key`）。
两个脚本分别负责签发与开启跳转，**都不在发布流程里自动执行**。

### 6.1 签发/续期：`scripts/tls-issue-cert.sh`

用 Let's Encrypt 的 **HTTP-01 / webroot** 方式。为什么不用 DNS-01：那需要把 Cloudflare
Token 放到服务器上，而该 Token 对**整个 zone** 有写权限（同 zone 下还有其它项目的记录）
——为一张证书把全 zone 写权限放到公网机器上，代价远大于收益。

判据：脚本会先检查域名解析是否指向本机、webroot 是否真的经 nginx 可读（自测一次），
再调用 certbot 容器签发，最后生成 `ssl.d/campfire.conf`（443 的 server 块）并
`nginx -t` + reload。**签发成功不等于启用成功**，因此它把两步分开报告。

续期由 **systemd timer 自动执行**（`campfire-tls-renew.timer`，每日跑；安装用
`scripts/tls-install-renew-timer.sh`）。也可手动跑 `scripts/tls-renew.sh`；
加 `--dry-run` 则只向 ACME 真实校验、不落盘证书。证书 90 天有效。

**为什么用 timer 而不是 cron**：`Persistent=true` 能在机器关机错过后补跑（小机器重启
是常态），且日志进 journald 可查。

### 6.2 开启 80→443 跳转：`scripts/tls-enable-redirect.sh`

**这个脚本刻意不随签自动执行**，因为它依赖一个部署期事实：443 从公网是否真的可达。

首次部署就撞上了这件事：443 被**云安全组**拦着（80 通、443 超时；服务器访问自己的
公网 IP 也是同样结果，而 Docker 对两者的 DNAT 规则完全对称、本机 iptables 无 443 的
DROP 规则）。若证书一签好就加跳转，站点会从「能用」变成「完全打不开」，而证书本身正常，
排查会先怀疑证书。**该判定后来被证实**：控制台放行 443/tcp 后立即连通。

因此它的判据是**三项前置**全过才动配置，任一不过就保持不跳转并说明原因：

1. TCP 443 可连；
2. TLS 握手且证书链校验通过（`Verify return code: 0`）；
3. HTTPS 上的 `/readyz` 返回 200。

只验第一条是不够的：端口通但证书链不对时，跳转会把用户送进浏览器警告页——比留在 HTTP 更糟。

动作完成后它还会验**两项结果**（共五项），因为「没报错」不等于「切过去了」：

4. `http://` 首跳返回 301，且 `-L` 跟随后的最终页是 `https://` 上的 200；
5. `.env.prod` 的三项域名配置都已是 `https://`（`Secure` 属性正由它们推导）。

### 6.3 启用 HTTPS 要改**三处**，不是一处

这是自查发现的一个容易漏的地方（2026-10-01）：脚本原先只写 `redirect.conf`，但把站点真的
切到 HTTPS 还需要把**后端的域名配置**一起改：

    infrastructure/nginx/redirect.d/redirect.conf   80 -> 443 跳转
    .env.prod: SUPERTOKENS_API_DOMAIN               http:// -> https://
    .env.prod: SUPERTOKENS_WEBSITE_DOMAIN           http:// -> https://
    .env.prod: PUBLIC_BASE_URL                      http:// -> https://（前端下次构建用）

漏掉后两项的症状是**静默不安全**：SuperTokens 按这两个值推导 cookie 域与 `Secure` 属性、
以及重定向地址白名单。页面已是 https 而它们仍是 http 时，会话 cookie 不会带 `Secure`
（凭据可能在明文回传路径上被网络攻击者取走），而**登录照样能用**——因此不会有人发现。

顺序也有讲究：**先切配置、再切跳转**。反过来的话，跳转先生效而配置仍是 http，
中间会有一小段「HTTPS 页面 + http 配置」的组合。

#### 跳转必须是独立 server 块（两个只在真机暴露的 nginx 陷阱）

2026-10-01 实际启用跳转时连撞两个，都**不是笔误而是设计错误**，且**都只在「真的去启用」
时才现形**——平时不写 `redirect.conf` 就永远碰不到：

1. **跳转写进 80 的 server 块 → nginx 拒绝启动。** 那个块已经
   `include app-locations.conf`，而那里有 SPA 的 `location /`；同一 server 内重复 location
   让 nginx 直接报 `[emerg] duplicate location "/"`。所幸脚本「`nginx -t` 失败即删除跳转
   文件」，线上未受影响。
2. **两个 server 块争同一个 `server_name` → 跳转被静默忽略。** 修完第 1 条后
   `nginx -t` 通过了，但 `http://…/` 仍返回 200。因为 80 的块写着
   `server_name campfire.wenran.me _;`，跳转块也写 `campfire.wenran.me`，nginx 只保留
   **先出现**的那个：

       [warn] conflicting server name "campfire.wenran.me" on 0.0.0.0:80, ignored

   **它只是 warn 不是 error，`nginx -t` 照样通过**——除了实际发请求看状态码，没有别的
   办法发现。修法：主块只声明 `_`（它本来就是 80 的默认块），真实域名交给跳转块精确匹配；
   这样用 IP 直连排障仍走主块。

两条都用本地 nginx 做过最小复现，确认是 nginx 的实际行为而非推测。

#### cookie 的 `Secure` 属性：切换前 False、切换后 True

这是「三处配置」那个修复的直接证据（实测，非推断）：

    切换前（HTTP 配置 -> HTTP 访问）  sAccessToken  HttpOnly=True  Secure=False
    切换后（HTTPS 配置 -> HTTPS 访问） sAccessToken  HttpOnly=True  Secure=True

`Secure=False` 在纯 HTTP 下是**正确的**（HTTP 下带 `Secure` 的 cookie 浏览器不回传，
反而登不上）；要防的是「页面已 HTTPS、配置仍旧 http」那种错配。

#### 实测的 cookie 属性（2026-10-01，HTTP 访问）

用裸 socket 读 `Set-Cookie` 原文（**不能用 `urllib`**——它把多个 `Set-Cookie` 合并成
一行，会误报成 `HttpOnly=False`；我第一次就是这么测错的）：

    sAccessToken    HttpOnly=True   Secure=False  SameSite=lax  Path=/
    sRefreshToken   HttpOnly=True   Secure=False  SameSite=lax  Path=/api/auth/session/refresh

`HttpOnly=True` 符合项目结构设计第 9 节「凭据不可被前端 JavaScript 读取」。
`Secure=False` 在纯 HTTP 下是**正确的**（HTTP 下带 `Secure` 的 cookie 浏览器不会回传，
那样反而登不上）；要防的正是上面那种「页面已 HTTPS、配置仍旧 http」的错配。

脚本因此在最后加了第四项验证：登录响应里的会话 cookie 是否带 `Secure`。
不带就提示人工确认（探针用的账号不存在，只回报告有/无，不复述 cookie 值）。

`restore.sh` 之外的这些脚本都**不在发布流程里自动执行**，需要人工触发。
