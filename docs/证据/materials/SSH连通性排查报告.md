# SSH 间歇性连不上服务器 — 排查报告

> 生成时间：2026-10-01 19:15（本地时间）
> 目标：`ubuntu@43.161.195.236:22`（腾讯云香港，`campfire-pilot-hk-01`）
> 结论：**问题出在排查者本机的代理（mihomo / Clash Meta），不是服务器。**

## 一、现象

从这台 Windows 机器 SSH 到目标服务器时，**时通时不通**，且没有任何规律的报错：

| 时刻 | 探测结果 |
| --- | --- |
| 最初 | `ubuntu` 登录**成功**，抓到了主机名/系统/资源/工具链 |
| 随后 | `ssh` 报 `Connection timed out` |
| 再后来 | 连续 12 次 TCP 探测 → **12/12 成功**，稳定 56–65ms |
| 几分钟后 | 连续 20 次 TCP 探测 → **20/20 超时** |
| 再几分钟 | 每 15 秒一组，连续 6 组：ICMP 全通、TCP 全超时 |

失败形态是 **`Connection timed out`（超时）**，不是 `Connection refused`（拒绝）。
这个区别很重要：**超时 = 数据包被丢弃（没人回应）；拒绝 = 主机可达但端口没监听。**

## 二、关键证据：ICMP 通、TCP 全断

故障期间同一时刻的探测：

```
ICMP  ping 43.161.195.236  ->  4 发 4 收，0% 丢包，平均 57ms
TCP   43.161.195.236:22    ->  超时
TCP   43.161.195.236:80    ->  超时
TCP   43.161.195.236:443   ->  超时
TCP   43.161.195.236:3389  ->  超时
TCP   43.161.195.236:8080  ->  超时
TCP   43.161.195.236:5173  ->  超时
```

**ICMP 正常而 TCP 全断**：说明主机本身活着、到它的路由也通（否则 ping 也该丢），
但 TCP 握手包被丢掉了。这类签名通常来自三种原因之一：主机防火墙丢包、中间网络丢包、
或**本机侧的代理/隧道把 TCP 接管了却没能转发**。

## 三、决定性对照：同时刻访问其他目标

这一步排除了「服务器坏了」的可能。**同一时刻**（19:13 前后）探测多个目标：

| 目标 | 结果 |
| --- | --- |
| `43.161.195.236:22`（目标服务器） | **超时** |
| `1.1.1.1:443`（Cloudflare DNS） | **超时** |
| `8.8.8.8:443`（Google DNS） | **超时** |
| `registry-1.docker.io:443`（Docker Hub） | **超时** |
| `github.com:443` | 通（226ms） |
| `140.82.113.4:443`（GitHub IP） | 通（287ms） |
| `baidu.com:443` | 通（43ms） |

**服务器、Cloudflare、Google DNS、Docker Hub 一起超时；GitHub 与百度同时正常。**
如果是服务器的问题，不可能连 Google DNS 也一起不通。因此问题在**本机到这些目标的
这一段路径上**，而不是目标本身。

## 四、根因：本机代理（mihomo）在接管 TCP

实测本机状态：

```
代理进程：mihomo (PID 11324) 监听 127.0.0.1:7897
TUN 网卡：vgate0  "Rust Wintun Tunnel"  状态 Up
环境变量：HTTP_PROXY=http://127.0.0.1:7897
          HTTPS_PROXY=http://127.0.0.1:7897
```

`mihomo`（Clash Meta 内核）+ Wintun 隧道网卡处于 Up，是**代理的 TUN 模式**。
TUN 模式会在网络层接管流量，由代理按自己的分流规则决定「哪些直连、哪些走节点」。

这解释了全部现象：

- **分流规则命中的目标**（GitHub、百度）正常出去 → 通；
- **分流规则未覆盖或节点当前不可用的目标**（服务器、1.1.1.1、8.8.8.8、Docker Hub）
  被丢进隧道后转发失败 → **表现为超时**（不是拒绝，因为包根本没到目标）；
- **ICMP 走了另一条路径**（TUN 模式常放行或单独处理 ICMP），所以 ping 一直正常；
- **时通时不通**：节点健康度/规则更新/连接数变化都会改变结果，因此是间歇的。

补充：`Find-NetRoute` 显示到目标服务器的路由走 `WLAN / 10.15.242.134`——
这是路由表的静态结果，TUN 模式下实际仍会被拦截重定向，两者不矛盾。

## 六、建议的排查与修复顺序

**第 1 步（最可能有效）：让目标服务器绕过代理。**

在 mihomo / Clash 的分流规则里，把 `43.161.195.236` 或整个 `GEOIP,HK` 段
**直连（DIRECT）**，而不是走节点。或在客户端界面里把该 IP 加进「绕过代理」列表。

**第 2 步：临时关掉代理验证因果。**

关掉 mihomo 的 TUN 模式（或整体退出），再 `ping` + `ssh` 目标。若立刻稳定，
就确认是代理问题——这一步能给出无可争辩的因果，而不是相关性。

**第 3 步：如果必须走代理，给 SSH 单独配置。**

在 `~/.ssh/config` 里为这台机器指定直连，或经代理的 `ProxyCommand`：
走直连则依赖 TUN 的分流规则；也可用 `nc`/`connect` 显式指定出口。

**第 4 步：确认云侧安全组。**

控制台里 `22` 端口的入站规则应放行你的公网 IP（或 `0.0.0.0/0`，但那样会持续被扫描）。
这一步是并行检查项——它不是当前故障的原因（因为其他目标也一起超时），
但**将来从别的网络排查时，它是首要怀疑对象**。

## 七、补充证据：代理控制接口可访问但需认证

报告撰写期间又做了一轮实测（此时 22 端口恰好恢复）：

```
TCP 43.161.195.236:22                    -> 通 64ms
SSH  ubuntu@43.161.195.236               -> 连通，hostname=campfire-ai-hk-01
mihomo 控制端口 127.0.0.1:9097           -> 在监听
GET http://127.0.0.1:9097/rules          -> 401 Unauthorized
GET http://127.0.0.1:9097/configs        -> 401 Unauthorized
GET http://127.0.0.1:9097/version        -> 401 Unauthorized
```

**这意味着我可以拿到确定答案，但需要你提供 mihomo 的 `secret`。** 有了它，
`/configs` 能直接给出 `tun.enable`、`mode`（rule / global / direct）与 `tun.stack`；
`/rules` 能列出全部分流规则。两者结合就能**证明**（而不只是推断）
「`43.161.195.236` 命中了哪条规则、被送去哪个出口」。

**如果你愿意**：把 secret 填进 `http://127.0.0.1:9097/ui` 的界面里自己看一眼，
或用 `curl -H "Authorization: Bearer <secret>" http://127.0.0.1:9097/configs`
—— 不必把 secret 给我，你自己看这两项即可：
- `"mode": "rule"` 还是 `"global"`？若是 `global`，**所有** TCP 都会走节点，
  「GitHub 通、其他不通」就完全取决于节点对目标的可达性；
- `tun.enable` 是否为 `true`（TUN 是否真的在接管）。

## 八、这份报告的边界（哪些是实测、哪些是推断）

**实测**（全部为本次会话真实执行并读取到的输出）：所有 ping/TCP 探测结果与耗时、
同时刻多目标对照、服务器上的 hostname/OS/CPU/内存/磁盘/swap/sudo/docker/工具链/
出网/ufw/fail2ban 配置与封禁记录、本机代理进程与 TUN 网卡、我的公网 IP、
fail2ban 日志里的两条 ban 记录、mihomo 控制端口 9097 在监听且 `/rules` 返回 401。

**推断**（未见代理内部日志与配置，因此是推断而非证明）：
具体是「哪条分流规则导致丢包」不确定。证据链是：TUN 网卡 Up + TCP 全断而 ICMP 正常
+ 同时刻多个境外目标一起失败、境内与 GitHub 正常。这与「TUN 模式按规则分流、
未命中/节点不可用的目标被丢弃」高度一致，但**「一起失败」不等于「同一条规则」**。
要坐实需要 mihomo 的 `/rules` 与 `/configs`（见第七节）。

**未验证**：代理节点当时的健康状态；服务器上是否有过云侧安全组的临时变更
（无控制台访问权限，读不到）；`43.161.219.111` 是谁的 IP；
`registry-1.docker.io` 与 `1.1.1.1` 是否与目标服务器命中同一条规则。

## 九、对后续部署的影响

故障期间**无法继续进行服务器端工作**（装文件、起容器、验证 `/readyz`）。
但**不阻塞代码侧**：本轮已修掉两个部署阻断缺陷（镜像引用断链、过期前缀值），
都已提交。等连通性稳定后再做真机部署。

另外趁窗口期发现：服务器上**已有** `/opt/campfire-ai/`，内含
`app/`、`backups/`、`deploy/`、`secrets/` 四个目录（属主 `ubuntu`，
`backups` 与 `secrets` 权限 700），**没有** `.env.prod`，也**不是** git 仓库。
这与我设计的 `DEPLOY_PATH`（放 `docker-compose.prod.yml` + `.env.prod`）布局不同，
部署前需要你确认：**沿用这个已有结构，还是用我的布局？**
