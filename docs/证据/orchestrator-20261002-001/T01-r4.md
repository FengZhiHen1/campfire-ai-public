## 1. P1-1'（核心）：主判据改为结构化表征

### 1.1 缺陷（裁决与复验我均采信）

判据形态「整页图高 ≥ `requiredContentHeightPx × 倍率`」**无法区分它想区分的两个状态**：
短内容下 `required` 塌成文档自身高（`.phone-shell{min-height:100svh}` 把页面撑到视口高，
这在 desktop 外壳下是常态），未展开的陷阱图高**恰好等于**需要值 ⇒ 守卫绿，而内容仍被滚出容器。
这是同一判据上的**第三种错法**：不是量选错、不是算式错，而是**比较式本身不成立**。

### 1.2 修法：主判据改为「页面上还有没有元素在裁内容」

按裁决主判据 ① 实现：

```ts
// 主判据（结构化表征，不依赖任何跨来源数值比较）
export function findClippedElements(page: Page): Promise<ClippedElement[]>
export function assertNoClippedContent(clipped: readonly ClippedElement[], context: string): void
```

扫描集合与排除规则**完全按裁决**：
1. `overflow-y ∈ {auto, scroll, hidden, clip}`（含 `hidden`/`clip` —— 只扫 `auto|scroll`
   会完全看不见「内容被裁且不可滚动」的外壳形态）；
2. **排除刻意截断**：`text-overflow: ellipsis`、`-webkit-line-clamp != none`；
3. **我另加第三条排除**：`clip-path != none`。

关于第 3 条（我加的，附实测依据）：我用真实页面探针扫了 10 页，发现除裁决指出的
`span.sp-title`（ellipsis，差 2px）之外，还有 `.sr-only`（`components.css:75`：
1×1px + `clip-path: inset(50%)`）差 **27px**。它是**无障碍用途的视觉隐藏**
（内容对屏幕阅读器仍可见），更不是「被裁的内容」。若不排除，`chat` 与 `cases` 各有一个假红源。
三者的共同点是**该 CSS 属性的用途就是截断**，所以按属性判定比按像素差判定更本质
——这也解释了为什么不能靠调大容差解决：27px 的刻意隐藏比 2px 的省略还大。

### 1.4 永久用例覆盖短页（裁决「这条必须做」）

`guard-nonvacuity.spec.ts` 从只测 profile（长页）扩到 **profile + memory（短页）**，
两页 × 两种 padding × 两个视口 = **8 份证据**（落盘 `tmp/screenshots/.run/guard-nonvacuity/`）。
短页选定依据：`memory` 在外壳下内层溢出 156px 而**文档高等于视口高**，正是「required 塌成文档高」的形态。

8 份证据里，**两页两视口的陷阱态都由新主判据判红**，而辅助高度判据在短页 desktop 下仍是绿的

### 1.5 「以视口为基准」的开闸条件已移除（裁决 ③）

旧 `assertExpanded` 开头是 `if (measurement.hiddenOverflowPx <= 0) return;`——
这正是本轮盲区的放行者。现在无论溢出量多少都扫一遍；高度比较也不再有「先看溢出量再决定要不要判」
的短路（`assertFullPageExpanded` 里的短路也一并去掉）。

### 1.6 容差依据（裁决要求「不许凭感觉取」）

见报告 §3 的 P2-E 与 `paths.ts` 里两个常量的注释。要点：按 CSS 属性排除刻意截断后，
真实页面在 1px 阈值下的**非刻意裁切条目数为 0**（探针实测，10 页）；容差只承担
`clientHeight`/`scrollHeight` 的整数取整（实测同类差异 2px）。目标场景里真被裁量级是
**156px 起**，故 2px 不会掩盖任何真裁切。

### 1.7 诚实登记的边界

1. `findClippedElements` 是**逐元素**判据，因此它抓的是「有元素在裁内容」。
   若某种失效形态**不表现为任何元素裁切**（例如内容被 `transform` 移出可视区而不触发布局溢出），
   本判据看不见。我未构造出这种形态，也未验证。
2. 排除规则按 CSS 属性判定，因此一个「既带 ellipsis 又真的裁掉了应该有内容」的元素会被排除。
   我把这类元素**仍然返回**（带 `deliberateReason`），审查者可在证据里看到它们，
   但判据不会因它们失败——这是按裁决要求的取舍。
3. 辅助判据在「文档高」这条来源上仍可能被 `.phone-shell{min-height:100svh}` 抬高，
   故它**只能当辅助**；我已把这一点写进它的 TSDoc，避免将来被提回主判据。

### P2-B `neutralise.ts` 的 TSDoc 仍描述被否决的相加算式 —— 已改为实际算式

`assertFullPageExpanded` 的 TSDoc 原文写「为什么判据是 `(viewportHeight + hiddenOverflow) × dsf`」，
那是**已被裁决 4 否决**的算式（且我在 r3 就已改为「逐滚动来源取最大」）。
现在该 TSDoc 描述的是**实际实现**：判据是
`图高 ≥ requiredContentHeightPx × 倍率 − 容差`，并显式写清「这是辅助判据、为什么不能单独用」。

### P2-C 消融态整段跳过 `expandForFullPage`（注释与代码不符）—— 改为只跳过展开

fixed 中和与 `assertNoFixedAtCaptureTime` 始终执行。（`shots.spec.ts` 里那个重复的开关常量也删了，
现在只有一个开关、一个位置。）

### P2-E 同一量两条判据容差口径不一致 —— 已消除

先说清「是不是同一个量」（这决定了该怎么修）：
- `capture()` 与 `buildManifest()` 比的是「**PNG 像素高** vs CSS 内容高 × 倍率」；
- `assertFullPageExpanded()` 比的是同一个东西 → **同一个量**，必须共用一个常量；
- (旧)`CLIP_TOLERANCE_PX` 作用在「元素自身 `scrollHeight − clientHeight`」上，
  **不涉及 PNG 像素、不乘倍率** → **另一个量**。

因此不能简单「统一成一个 2」，而应把两个量各自命名、各自说明依据：

| 常量 | 作用量 | 系数 | 依据 |
| --- | --- | --- | --- |
| `PNG_HEIGHT_TOLERANCE_PX` | PNG 像素高 vs CSS 内容高 × 倍率 | 乘 `DEVICE_SCALE_FACTOR` | 沿用 `tmp/design-render/README.md:19,40-44`（高度 1–2px 偏差，2px 吸收） |
| `CSS_LAYOUT_TOLERANCE_PX` | 纯 CSS 空间（裁切差、内容高比较） | 不乘 | 真实页面探针实测（§1.6） |

`capture()`、`buildManifest()`、`assertFullPageExpanded()` 三处**共用 `PNG_HEIGHT_TOLERANCE_PX`**
（P2-E 的实质要求）；旧名 `FULL_PAGE_HEIGHT_TOLERANCE_PX` 与 `CLIP_TOLERANCE_PX` 均已重命名，
以免名字暗示它们可以互换。

关于「12/20 张余量恰好为 0」：修完后 `capture()` 的判据是 `|图高 − 内容高×2| ≤ 4 设备像素`、
守卫是 `图高 ≥ 内容高×2 − 4`，两者现在**同容差**，因此不会再出现「一条过一条不过」的口径错位。
余量为 0 本身不是缺陷（它意味着 PNG 高精确等于内容高×2），而是**口径必须一致**的理由。

逐元素判据抓的是「有元素在裁内容」。若存在**不表现为布局溢出**的失效形态
（如 `transform` 把内容移出可视区），主判据看不见。我未构造出这种形态，也未验证——
**这是本轮修法的已知盲区，不是已解决问题**。

### 4.3 辅助判据仍受 `min-height:100svh` 影响

辅助高度判据在「文档高」这条来源上仍会被 `.phone-shell{min-height:100svh}` 抬高，
因此它在短页 desktop 下仍是绿的（§1.4 表中 `heightCriterionRed=false`）。
它现在只作辅助，不会导致漏报；但如果将来有人把它提回主判据，盲区会**原样复现**。
我把这条写进了它的 TSDoc。
