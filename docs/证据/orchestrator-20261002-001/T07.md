**文档已把它登记为「未实现项」**（`docs/design/pages/对话页.md:25`，T06 写的）：
> 授权语义写的是「宽度不足时整体截断为『技能 N 个』——不折叠为 +N 徽标」，
> 但当前实现里**没有这条折叠逻辑**，全仓无「技能 N 个」文案与计数折叠。

### 实测阈值（T06 在 390 宽页头上实测 0–7 个标签，已写进 `对话页.md:17-21`）

| 标签数 | 表现 |
|---|---|
| ≤ **3** | **标题不截断**（3 个中文标签合计 199.45px，标题仍余 64.39px） |
| ≥ **4** | **标题被截断**（`scrollWidth 56 > clientWidth 0`，标题整段不可见） |
| ≥ **5** | **页头横向溢出**（合计 332.42px，`documentElement.scrollWidth` **390 → 464**）——**这一态是可访问性缺陷**（内容不可达），不是设计意图 |

### 修法（**按文档语义，不是自创**）

按 `对话页.md` 的授权语义：**「宽度不足时整体截断为『技能 N 个』」**——
即**不是**「显示前 N 个 + `+N` 徽标」，而是**整体改成一个汇总标签**。

**要求**：
1. **实现必须与文档语义一致**（汇总为一个「技能 N 个」标签），
   **不要**自行改成「+N 徽标」（那是文档明确否定的形态）；
2. **触发条件要可复现、可测**：文档说的是「**宽度不足时**」，而实测阈值是按**标签数**定的。
   ⇒ **你必须给出一个判据并说明理由**：
   - 若按**宽度**判（用 `ResizeObserver`/`scrollWidth` 实测溢出）⇒ 更贴合文档措辞，但要处理首帧；
   - 若按**数量**判（如 ≥4 折叠）⇒ 更简单，但**是把「宽度」近似为「数量」**，须在代码注释里写明这个近似及其依据（实测：3 个不溢出、5 个溢出、4 个是标题被截断的起点）。
   **两者都可接受，但必须写明理由**，并在报告里给出你实测的触发点。
3. **`.sp-tag` 的 CSS 已在 T05 补齐**（`flex: none`）——**不要**再改它的样式；
4. **必须留测试**：折叠态与非折叠态各一条（≥4 个标签 ⇒ 出现「技能 N 个」且不出现单个技能名）。

## ② 确认单的可达性（**P1**）—— **但先读这一段，它有一个既有的、经过论证的取舍**

### 编排器实测的当前状态

**5 处**都是 `<div className="confirm-sheet" role="dialog" aria-modal="false" …>`：
`SettingsPage.tsx:165`、`MemoryPage.tsx:277`、`ProfilePage.tsx:363` / `:646` / `:689`
（**不是 6 处**——`:636` 与 `:633` 是注释行，不是元素）。

**T03b 的实测缺陷**：焦点**不进入**单内（`activeInsideSheet=false`）、
**Tab 会跑出到背景**（设置页 2 步即逃出）、**Esc 不关闭**、**无 `::backdrop`**。

### ⚠ **源码里已有一处经过论证的取舍——你必须先读它**

`apps/web/src/features/profile/view/ProfilePage.tsx:632-641`（**原文**）：
> 为什么不用原生 `<dialog>.showModal()`：**jsdom 未实现 showModal（T10 实测）**，
> 而前端测试环境是 jsdom；`role="dialog"` + `aria-modal="false"` 与设置页的登出确认
> 同一做法，**不声称模态语义（焦点陷阱、Esc 关闭未实现也未验证）**。

**编排器独立实测确认这个前提成立**（`jsdom@30.1.1`）：
```
hasShowModal: "undefined"      ← showModal 不存在
hasClose:     "undefined"
hasDialogElement: "function"   ← 元素类存在，但方法没有
openIsOwnProp: true
```
⇒ **「改用原生 `<dialog>.showModal()`」这条路在 jsdom 下会挂**（T03b 的建议被此约束挡住）。
**但注意**：源码注释说的是「**未实现也未验证**」，即**这是一个已知的、被记录下来的未完成项**，
不是「已论证为不该做」。

### 修法（**二选一，选哪个都要给出理由**）

**路线 A：改成原生 `<dialog>` + `showModal()`**
- 契约 `docs/design/components.html` 里**用的就是** `<dialog class="confirm-sheet">`
  （编排器实测：契约页有 **2 处 `<dialog>`**，其一带 `class="confirm-sheet"`，
  且契约定义了 `.confirm-sheet::backdrop`）⇒ **这条路与契约一致**；
- **代价**：jsdom 无 `showModal` ⇒ 你必须**同时**解决测试策略（例如在测试 setup 里 polyfill
  `showModal`/`close`，或在测试中走 `open` 属性路径）。**polyfill 要写清为什么不会掩盖真实缺陷。**
- 收益：`showModal()` 自带**焦点进入 + 焦点陷阱 + Esc 关闭 + `::backdrop`**，四项一次解决。

**路线 B：保留 `<div>`，手工补四项**
- 补**初始焦点**（进入单内首个可聚焦元素）、**焦点陷阱**（Tab 循环）、**Esc 关闭**、
  并把 `aria-modal` 改为 **`"true"`**（**`"false"` 是在声称非模态，与焦点陷阱自相矛盾**）。

**编排器倾向 A**（与契约一致、四项一次解决），**但批准 B**——
**理由必须写进报告**（例如「测试环境改动面太大」是正当理由；
「A 太麻烦」不是）。**不要两条混做一半。**

### 现有测试约束（**不要破坏，必要时同步更新**）

`apps/web/src/features/accounts/view/SettingsPage.test.tsx:169` 与 `:220` 有
`expect(screen.getByRole('dialog')).toBeDefined();`
⇒ **`role="dialog"` 这一可查询性必须保留**（原生 `<dialog>` 也满足 `getByRole('dialog')`，
但**仅当它 open 时**——请自己确认，必要时调整测试并说明）。

### 验收判据

- [ ] **焦点进入**：打开后 `document.activeElement` 在单内（给出实测）。
- [ ] **焦点陷阱**：连续 Tab **不逃出**单内（给出 Tab 序列，至少 6 步）。
- [ ] **Esc 关闭**：给出实测。
- [ ] **遮挡**：`::backdrop` 生效（若走 A）或遮罩层存在（若走 B）。
- [ ] **`aria-modal` 与焦点陷阱不矛盾**（走 B 时必须是 `"true"`）。
