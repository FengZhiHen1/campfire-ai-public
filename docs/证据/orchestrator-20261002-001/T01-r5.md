## 1. P1-A：`expandForFullPage` 改为放开**所有**溢出容器（不只是面积最大者）

### 1.1 缺陷与机制（与裁决一致，我复现过）

旧实现：

```ts
const container = scrollables.reduce<Element | null>((best, element) => {
  if (best === null) return element;
  return element.clientWidth * element.clientHeight > best.clientWidth * best.clientHeight ? element : best;
}, null);
```

T02 落地后真实外壳与用例的模拟外壳**同时存在**，两者面积**完全相同**（390×844 = 329160），
`>` 比较在平局时保留文档序在前者（外层模拟容器）；真实 `.device-screen` 是它的**后代**、
不在被展开的祖先链上 ⇒ 仍裁 1241px ⇒ 主判据红。

### 1.2 修法

按裁决第 1 条：**所有** `scrollHeight > clientHeight + 容差` 的容器**及其整条祖先链**都放开。
不再有「面积最大」这个概念，因此也不再有靠文档序决胜的选择。

```ts
// 待放开集合 = 每个滚动容器自身 ∪ 它的整条祖先链（一路到 documentElement）。
// 用 Set 去重：多个容器的祖先链会大量重叠（真实外壳与模拟外壳共享 #root 以上）。
const toLoosen = new Set<Element>();
for (const container of scrollables) {
  let cursor: Element | null = container;
  while (cursor !== null) { toLoosen.add(cursor); cursor = cursor.parentElement; }
}
if (document.body !== null) toLoosen.add(document.body);
```

配套：`expandedScrollContainer` 由「单个描述」改为**多个用顿号连接**（字段仍是字符串，
sidecar 可读性不变）；`expandedAncestors` 现在是各容器祖先链的并集（去重）。
字段 TSDoc 已同步（避免注释与实现不符）。

### 1.3 实测（canary 证明这条修法是承重的）

我写了一个**临时** canary（`canary-opens-all.spec.ts`，验证完已删，输出留档
`T01-assets/canary-opens-all.txt` 与 `canary-opens-all-desktop.json`），复现 T02 报告 §3.8(c)
的 doubleShell 形态（**刻意不中和真实外壳**）：

```
--- desktop ---
containersBefore: div#__sim_screen__(156px) | div.device-screen(1184px)
expandedScrollContainer: 'div#__sim_screen__、div.device-screen'   ← 两个都放开了
expansionMessage: ''                                              ← 主判据通过
captureRed=False  realClipsAfter=[]                               ← 展开后无裁切
```

**非空洞性对照**：我把 `scrollables` 临时缩成「只取第一个」（即旧的单容器行为）重跑同一 canary：

```

```

即**该 canary 在旧行为下确实会红**（复现 T02 的报错形态），恢复修法后转绿。
随后已把文件从备份还原，并用 `Select-String` 确认临时改动（`ABLATION-CHECK`）无残留。

**mobile 侧的实测事实**（解释「为何只有 desktop 变红」）：mobile 视口下真实外壳三层是
`display: contents`（`global.css` 的窄视口退化），`.device-screen` 的 `clientHeight/scrollHeight`
均为 0、不裁任何内容 ⇒ **叠加形态只在 desktop 成立**。这与 T02 报告「mobile project 通过、
desktop 变红」自洽。canary 里我按视口分别断言了这个前提（desktop 要求 ≥2 个容器，
mobile 要求真实外壳**不是**滚动容器）。

## 2. P1-B：`guard-nonvacuity` 的构造前提更新

### 2.1 选法（裁决给了 (a)/(b) 二选一，我选 (a)，理由为实测）

我先在两视口实测了真实外壳（探针 `probe-shell.spec.ts`，验证完已删，输出留档
`T01-assets/probe-shell-{desktop,mobile}.json`）：

| 视口 | 真实外壳三层 | `.device-screen` | 陷阱是否存在 |
| --- | --- | --- | --- |
| desktop | `display: block/grid` | `overflow-y:auto`，clientH=844 / scrollH=2028（profile） | **存在**（裁 1184px，陷阱图 2000px） |
| mobile | 三层均 `display: contents` | clientH=0 / scrollH=0 | **不存在**（文档滚动，陷阱图 4056px = 内容全高、`clipped=[]`） |

⇒ 选 (b)「直接针对真实 `.device-screen`」只在 desktop 可行，**mobile 上无东西可证**；
而放行判据要求两个 project 都产出完整证据。故选 **(a)：注入模拟外壳前先中和真实外壳**，
用产品自己在窄视口用的同一种手段（`display: contents`）——不引入新语义，且**与视口无关**。

用「删除真实外壳 DOM 节点」而不是本方案的替代被我否决：那会改变 `#root` 的子树结构，
使被测形态与产品实际渲染的形态脱钩。

### 2.2 文件头声明（裁决要求「必须加一段」，非可选）

已在 `guard-nonvacuity.spec.ts` 文件头写入：

> **T02 落地后前提已变（2026-10-02）**
> T02（设备外壳）已于 2026-10-02 落地，本用例原来的「应用无外壳」前提已不成立，
> 故改为：**注入模拟外壳之前，先用产品自己在窄视口使用的退化方式（`display: contents`）
> 中和真实外壳的三层**，把 `#root` 恢复成「无外壳」形态，再跑原来的两种 padding 形态。
> …（后接「为什么选这个做法」的两视口实测依据、以及「为什么不是删 DOM 节点」）

## 4. 两条顺带 P2

### P2-B' `neutralise.ts` 成员 TSDoc 仍写相加式 —— 已改为实际口径

`assertExpanded` 的成员注释原文写「判据：展开后的内容高 ≥ 视口高 + 展开前测得的隐藏溢出」，
那是**已被否决的相加式**（且早不再是主判据）。现改为写明两条实际判据：

```
判据分主辅两条（口径与实现一致，不复制旧式）：
  1. 主判据：`assertNoClippedContent` —— 页面上不再有元素在裁切内容
     （结构化表征，不依赖任何数值比较）；
  2. 辅助判据：展开后内容高 ≥ 展开前测得的 `requiredContentHeightPx`（含容差）。

这里**不是**「内容高 ≥ 视口高 + 展开前隐藏溢出」——那个相加式已被否决
（跨来源相加会在 desktop 外壳下误报：1000 + 1184 = 2184 > 真实内容高 2133）。
```

### P2-E' 裸 `+1` 与 `CSS_LAYOUT_TOLERANCE_PX`(=2) 口径不一致 —— 已统一取具名常量

裁决指出的现象：实测「恰好 2px 溢出」的元素**不算被裁却算可滚动容器**（两处判据互相矛盾）。
处置：`expandForFullPage` 的容器扫描改用**同一个** `CSS_LAYOUT_TOLERANCE_PX`（由参数传入）：

```ts
return scrollable && element.scrollHeight > element.clientHeight + tolerancePx;
```

**两处意图差异的说明**（裁决要求「统一口径或另起具名常量并说明两处意图差异」）：
我选择**统一**而不是另起常量，因为两处问的是同一个问题——「这个元素的 `scrollHeight` 是否
真的大于 `clientHeight`（而非整数取整噪声）」。既然同问，就该同答；
若用两个值，会出现「2px 时：`findClippedElements` 说没被裁、而展开逻辑说它是溢出容器」
这种自相矛盾的状态，正是本条 P2 要消除的。已在 `expandForFullPage` 的注释里写明这一理由。
