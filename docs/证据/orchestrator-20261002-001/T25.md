## 1. 结论

**缺陷成立，且我已用真实 nginx 复现它，并用同一套装置证明修复有效。**

三句话的结论（每句都有 §3/§4/§6 的机械读数支撑）：

1. **修前**：`/readyz/deep` 经真实 nginx（`nginx:1.27-alpine` + 真实仓库 `nginx.conf`）
   落到 SPA 的 `location /`，被 `try_files` 回成 `index.html`
   ⇒ **HTTP 200 + `Content-Type: text/html` + SPA 正文**
   （`Content-Length: 65`、带 `ETag`/`Last-Modified`/`Accept-Ranges`，是静态文件无疑）。
2. **修后**：加了 `location = /readyz/deep` 之后，同一路径变成
   **HTTP 200 + `Content-Type: application/json` + 上游正文**
   （`Content-Length: 68`、带 `Cache-Control: no-store`）。
   **两组的唯一输入差异就是那一条 location**（§2/§3 的 SHA256 与逐字节派生自证）。
3. **回归守卫已落地且实测能红**：新增 `apps/api/tests/test_nginx_probe_routes.py`，
   数据源是**应用真实注册的路由表**（`campfire.main.app.routes`），
   **不硬编码 `/readyz/deep`**。消融（撤掉那条 location）⇒ **守卫红**（§6）。

**残余与未闭合项（我不同意把它算作"已完成"的部分）见 §8**，其中最重要的一条：

> **守卫是单向的**：它能抓「应用新增端点但 nginx 忘了加 location」（这正是本缺陷的形态），
> **但不能抓**「nginx 有 location 而应用删了端点」。我实测了这一方向（§6.3），
> **结果是绿**，我没有为此发明第二条判据——如实报出，而不是把它藏起来。

### 2.2 位置选择的理由（不只是"照着抄"）

- **放在 `/readyz` 紧跟之后**：该组四条（`/livez`、`/readyz`、`/readyz/deep`、`/health`）
  是同一类东西（反代到后端的运维探针），差异只在「谁周期性调用」。放一起，
  下次有人加第五条时眼睛扫得到。
- **用 `location =`（精确匹配）而不是 `location /readyz/deep`（前缀匹配）**：
  与同组三条一致。前缀匹配会顺带吃掉 `/readyz/deepXYZ` 这类并不存在的路径——
  探针上没有任何收益，却让一次笔误静默通过。**守卫也按 `=` 判**（见 §5）。
- **`proxy_pass` / `Host` / `no-store` 三行与 `/readyz` 逐字相同**：`no-store` 是必需的，
  理由与文件头第 2 条一致（缓存会让「已恢复」与「已故障」互相污染）；对深探针尤其重要，
  因为它的结论带配额成本，被缓存会把一次真实探测的结论复用成很多次假结论。
- **注释里写明「不进周期健康检查」**：这是用户裁决的成本纪律，写在配置里（而不是只写在
  任务包或报告里）才能让改配置的人看见。§4 给了三处引用的机械读数。

### 2.3 为什么没有动 `docker-compose.prod.yml` / `deploy.yml` / `acceptance_probe.py`

**本包不需要改它们**，而且 §4 实测证明它们本来就**没有**引用 `/readyz/deep`——
正是这个「没有」让成本纪律成立。若为了"让它更明确"而往 healthcheck 里加注释，
反而会让「这三个文件是否引用深探针」的机械检查出现噪音。故一律只读核实。

- **真实 nginx**：`nginx:1.27-alpine`（仓库 `Dockerfile.web` 用的就是 1.27 线，

## 5. 回归守卫：选了 **(a) pytest**、为什么、数据源为什么不是"永不失败的检查"

**交付物**：`apps/api/tests/test_nginx_probe_routes.py`（新增，5 个用例，实测 5 passed）。

### 5.1 为什么选 (a) pytest 而不是 (b) 独立脚本 + CI 步骤

任务包说两者只是"用例 vs 脚本"的载体差异、都可行、由我判断。我选 **(a)**，三条理由：

1. **判据的数据源就是 Python 应用对象**（`campfire.main.app.routes`）。
   pytest 同进程直接 `import campfire.main`；独立脚本要另起子进程并自行处理
   `sys.path`、`.env`、依赖装配——**多出来的那一层失败面与判据无关，却会让守卫红**。
   一个会因为环境问题而不是因为配置问题变红的守卫，会先被当成噪音关掉。
   （本仓已有正例：`test_check_task_pack.py` 用 `importlib` 按路径加载
   `scripts/check_task_pack.py`，那是"脚本本身要被测"；而**本判据的输入在应用对象上**，
   所以 pytest 是更顺的那一侧。）
2. **判据的既有承载处就是 `apps/api/tests/`**：探针自身的形状由 `test_health.py` 钉住
   （`/readyz/deep` 的组件集合、503 语义、未登录可达），探针的**路由可达性**与它同源。
   分成两处必然漂移——这正是 `app-locations.conf` 文件头第 4 条论证的同一件事。
3. **不需要动 CI 配置**：`ci.yml` 的 backend job 已经跑 `uv run pytest`，本用例自动进 CI。
   走 (b) 要给 `ci.yml` 加步骤，而 `deploy.yml` 的每一步都要 SSH 到生产——
   不该把一个纯静态检查塞进发布流程。（任务包允许改 `deploy.yml`，但**没有理由要改**。）

### 5.2 ★ 数据源：为什么它不是"永远不会失败的检查"

**硬编码写法的失效形态**（`assert "location = /readyz/deep" in conf`）：
**新加端点时它不会红**——而**这正是本缺陷的形态**：T19 在 `main.py` 加了
`@app.get("/readyz/deep")`，**没有任何东西因此变红**，直到人工比对才发现。

**本守卫的做法**：参考集合来自**应用真实注册的路由表**：

```python
routes = main_module.app.routes
return frozenset(
    route.path for route in routes
    if isinstance(route, APIRoute) and not route.path.startswith("/api")
)
```

实测读数（`_t25_reverse_ablation.py`）：

```
真实参考集合（来自 campfire.main.app.routes）：['/health', '/livez', '/readyz', '/readyz/deep']
配置里已声明的路径：['/', '/api', '/api/', '/assets/', '/health', '/index.html',
                     '/livez', '/nginx-health', '/readyz', '/readyz/deep',
                     '^/api/consult/runs/[^/]+/stream$']
```

⇒ 参考集合是**自动**得到的：`/readyz/deep` 出现在里面，是因为 `main.py` 真的注册了它。
**下一个端点被注册时会自动进入参考集合**；若那时配置文件没跟上，守卫就红。

**「不读 `/api` 下的路径」这条规则的来源**：`main.py` 的 `_API_PREFIX` 注释明写
「存活/就绪/诊断三个探针**不**加这个前缀：它们是基础设施判据」。
⇒ 我是**引用应用自己的声明**，不是自己发明一条分类。

**三条防护，防止守卫退化成恒真**（这一点被单独做成用例，不是靠一句声明）：

- `test_discovery_source_is_not_empty`：参考集合必须 ≥ 2 条，且都不在 `/api` 下。
  （空集合会让主判据的 `for` 不执行 ⇒ 恒真 ⇒ 又一个永不失败的检查。）
- 主判据内部**再断言一次** `assert probes`，让"数据源坏了"与"配置缺 location"在
  失败信息上分得开（前者指向守卫，后者指向配置）。
- `TestGuardGoesRed` 两个用例给判据**必然红**的输入（见 §5.3）。

### 5.3 判据契约（`=` 精确匹配，`test_parser_is_discriminating` 钉住解析器）

- 路径必须在，**且修饰符必须是 `=`**。前缀匹配（`location /readyz/deep`）也算不合规：
  它会顺带吃掉 `/readyz/deepXYZ` 这类不存在的路径，而探针上没有任何收益。
- 解析器只认行首的 `location` 指令，**不认注释里的**：

```python
assert _nginx_locations(text) == {
    "/livez": "=",
    "/assets/": "",
    "^/api/consult/runs/[^/]+/stream$": "~",
}   # 输入里第一行是 "# location = /commented-out {  ← 注释里的不算"
```

## 6. 消融实测：撤掉 location ⇒ 红

### 6.1 装置（保证"两次运行之间只有被测变量不同"）

### 6.3 反向方向（从应用侧删端点）—— **实测是绿，如实报出**

任务包要求「（若可行）从应用侧删掉端点 ⇒ 也应红/或说明为何不」。
**它不会红**，我实测了（`_t25_reverse_ablation.py`）：

```

  参考集合 去掉 /readyz/deep（模拟应用侧删端点） -> 绿（无缺失）；missing=[]
```

**原因**：判据是「**每一个**参考路径都有 location」，是**单向蕴含**。
参考集合少一条 ⇒ 约束变弱 ⇒ 仍然满足。

**我为什么没有为此再加一条判据**：
- 方向不同。本缺陷（T19 的缺口）是"应用有、nginx 没有"。反向的
  "nginx 有、应用没有"是**多出一条无效 location**，后果是那个路径被反代到 api 后拿 404
  ——**是 404，不是 200+HTML，可辨认，危害等级不同**。
- 写 `assert declared["/readyz/deep"]` 就要**硬编码**那个名字，等于把守卫最宝贵的那条性质
  （数据源自动跟随应用）换成一份手工清单——正是 §5.2 论证要避免的形态。
- 一条**更值钱的**替代做法（若复查者认为需要）：断言配置里「反代到 `$campfire_api` 的根级
  精确 location 路径 ⊆ 应用注册的根级路径」——那是同一套数据源的对称用法。
  **我没有实现它**，因为任务包只要求单向（新增端点时守卫要红），而我不在那个方向上
  发明未被要求的判据。**这里如实标注为未闭合项（§8）。**

**证据强度标注**：§6.3 是**直接调用判据函数**并喂入修改过的参考集合，
**不是**端到端消融——它**不经过** `campfire.main.app.routes`，所以它证明的是
"参考集合少一条时判据怎么走"，**不是**"改掉 `main.py` 之后 pytest 会怎样"。
之所以不改 `main.py`：`apps/api/src/campfire/**` 是本包明令不许改的文件
（T19/T20/T21/T22 正在改；本机 `main.py` 已有 20 处未提交改动）。**这是刻意的边界，
不是遗漏**，而且它对本节结论无影响：结论恰好是「**不会**红」，因而"真去改 `main.py`"
只会得到同一个绿。
