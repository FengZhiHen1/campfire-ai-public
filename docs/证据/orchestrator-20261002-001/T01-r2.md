### 1.2 裁决 1 追加：fullPage 必须真的展开滚动容器

`support/neutralise.ts` 的 `expandForFullPage` 在截图前做两件事，截后**恢复并断言已恢复**：

1. **fixed 中和**：注入 `.tab-bar, .confirm-sheet { position: static !important; }`。
   只改 `position`，不改任何视觉参数。选择器不是猜的——从**编译产物**的 CSS 里实测枚举出
   全仓只有这两条 `position: fixed` 规则（`.tab-bar` 与 `.confirm-sheet`）。
   与 `tmp/design-render/render.mjs:59` 的 `FLOW_CSS` 同语义。
2. **展开主滚动容器 + 其祖先链**：动态定位「`overflow-y` 为 auto/scroll 且内容确实溢出」
   的元素里面积最大的那个；从它**一路向上到 `documentElement`** 全部放开
   （`height:auto; max-height:none; overflow:visible`）。

**为什么必须展开祖先链**（这是我在实现中修正的一处设计）：只放开滚动容器本身是不够的——
T02 的结构是 `body > .device-stage > .device(高 844) > .device-screen(overflow-y:auto)`，
`.device` 的固定 844px 高会把已放开的内容**重新裁掉**，于是「展开」等于没做，
而截图看起来"成功"了。`guard-nonvacuity.spec.ts` 的实测显示祖先链确实被穿透：
`expandedScrollContainer: div#__sim_screen__`，
`expandedAncestors: [div#__sim_device__, div#__sim_stage__, div#root, body, documentElement]`。

**守卫（fail-loud）**：`assertFullPageExpanded` —— 对 `truncatedByPx > 0` 的页面，
整页图的实际像素高必须 > 视口高 × 2，否则抛错并写明「fullPage 未真正展开内容，长图不可用」。
判据取自从 PNG 产物实读的值，不信运行时值。

### 1.3 裁决 2：字体改用真实思源宋体 —— 已实现，但**裁决指定的判据恒真，我换了判据**

先执行裁决要求的动作：`fonts.googleapis.com` 与 `fonts.gstatic.com` 放行**真实出网**
（不再本地替身），其余外部 host 仍阻断并让用例失败（显式白名单 `ALLOWED_EXTERNAL_HOSTS`）。
实测确实出网并拿到了真实字形（§3.3 有原始请求清单）。

**但裁决指定的断言达不到裁决的意图，实测证据如下**（原始记录 `T01-assets/probe-fontguard.txt`）：

```
checkReal:   true    ← document.fonts.check('500 28px "Noto Serif SC"')
checkBogus:  true    ← document.fonts.check('500 28px "Totally Bogus Font Xyz"')  ← 必然不存在的族
loadReal:    2       ← document.fonts.load('500 28px "Noto Serif SC"').length
loadBogus:   0       ← document.fonts.load('500 28px "Totally Bogus Font Xyz"').length
```

`check()` 对**必然不存在的族名也返回 true**，因此 `!== false` 这条断言**永远不会失败**，
不满足「守卫必须真的会失败」。成因（规范行为）：`check()` 判断的是「若此处用该族，
是否所有**需要**的字体都已加载」，而「需要」按字形覆盖判定；本项目所有中文字形最终
都能由系统回退字体渲染，于是它恒真。

**处置**（按裁决的意图、而非按裁决的字面）：`support/fonts.ts` 的 `awaitDisplayFont`：
1. 用**可失败**的判据作真正的闸门：`document.fonts.load(probe).length > 0`
   且该族 `status === 'loaded'` 的 face 数 > 0；不成立即抛错，错误信息写明
   「截图会退化为系统回退字形，证据不可用」；
2. 仍记录 `check()` 的返回值（`fontCheckResult`）以保持与裁决的字面连续，
   并在类型注释里标注**它不承重**，避免后来者误以为它在把关；
3. **加负对照自检判据本身**：每次运行都用同一个判据去问那个必然不存在的族，
   若它也答「可用」就直接失败——不让一个恒真的检查冒充守卫。

**这条不一致我按「文档错误类」处理**（守则第 3 节 4 条要求附证据对）：
- **上级指令原文（X）**：裁决 2「必须加字体加载断言（fail-loud）：截图前
  `await document.fonts.ready` 并断言 `document.fonts.check('500 28px "Noto Serif SC"') === true`。
  不成立即让用例失败」。
- **实测证据（Y）**：`document.fonts.check('500 28px "Totally Bogus Font Xyz"')` 返回 `true`
  （`T01-assets/probe-fontguard.txt` 的 `checkBogus: true`），即该判据恒真、不可失败。
- **处置**：按裁决的**意图**（「静默产出回退字形的图比失败更糟」）实现了可失败的判据，
  同时保留并标注 `check()` 的值。**未擅自改裁决的字面要求**（`check` 仍在跑、值仍记录），
  也未按错误的字面写一个恒真的守卫。请裁决。

顺带一处**同源问题**：本仓既有的 `tmp/design-render/render.mjs:392,402` 用的是同一个
`check()` 判据（`notoSerif` / 「Noto Serif SC 未加载」）。它的闸门同样恒真——
`tmp/design-render/README.md:23` 声称「标题字体的 Noto Serif SC 确实加载」，
该结论在**字形层面**成立（我实测该族确有 loaded face），但那条**检查**本身不承重。
不属本包交付物，仅登记（不越界改动）。

### 1.4 我在实现中发现并修掉的三处自身缺陷

**(1) 探针自身把 `document.fonts.status` 打回 `loading`。**
首版 `awaitDisplayFont` 先 `load()` 再读 `status`，18 个用例报「状态为 loading 而非 loaded」。
根因：思源宋体被切成上百个 `unicode-range` 子集，`load()` 会按需**发起新的字体请求**，
于是它自己造出了「加载中」。改为**先读 status、后调用 load**（那才是「页面加载后」的状态），
并在探针触发的加载落定后再量一次 loaded face 数。这不是放宽断言，是量错了对象。

**(2) 「恢复后内联值为空」是错误判据。**
首版 `expectRestored` 断言恢复后相关内联值应为空串。它在设备外壳场景下**误报**：
`.device` 本来就有内联 `height:844px`（那正是它需要被展开的原因），
「恢复」意味着写回 `844px` 而不是清空。改为「当前内联值 == 记录的原值」，
并把该方法收进 `expandForFullPage` 的返回值（原值在闭包里）——
否则调用方拿不到原值，签名会诱导实现退化成错误判据。

**(3) 用 `fetch` 读截图产物读到了 `index.html`。**
一次性取证脚本里我用 `fetch('/...')` 读 PNG，但产物目录在 preview 服务器根之外，
拿到的是 SPA 回退的 HTML，`DataView` 读出的「高」是垃圾值（1835802732）。
改用 `readPngSize(await readFile(path))` 从磁盘实读——与生产守卫同一判据。

### 1.5 关于「第 4 次消融」：裁决指出的那个开关在当前代码上**不会红**，已如实报告并补了会红的

追加裁决要求「请确保它真的会红（可以自己临时把展开逻辑关掉验一次，作为第 4 次消融）」。

**我照做了，结果是 exit 0**（`T01-assets/ablation-D1-no-expand.txt`）。原因是结构性的：
**当前实现由文档滚动**（`html.scrollHeight` 远大于 `clientHeight`），
于是 `fullPage: true` 天然拿到整页——把展开逻辑关掉，图仍然是对的，
守卫**没有失败模式可触发**。也就是说：光有守卫，在 T02 落地前无法证明它有效。

我没有停在「以后会红」这个承诺上（守则：「应该会红」不是证据），做了两件事：

1. **`guard-nonvacuity.spec.ts`：在浏览器侧模拟 T02 外壳，用生产代码的同一个守卫函数
   把两个方向都断言。** 模拟方式是把 `#root` 的内容搬进
   `body > .device-stage > .device(844px) > .device-screen(overflow-y:auto)`
   （不改产品代码，全在浏览器侧做 DOM 操作）。实测（`T01-assets/evidence-shell-simulation.txt`）：

   ```
   外壳：screenScrollHeight=2028  screenClientHeight=844  ⇒ 内层确实溢出
   不展开：fullPage 图高 = 1688px  == 视口高 1688px      ⇒ 守卫抛错（会红）
   展开后：fullPage 图高 = 4170px  >  视口高 1688px      ⇒ 守卫通过（转绿）
   expandedAncestors = [div#__sim_device__, div#__sim_stage__, div#root, body, documentElement]
   ⇒ guardIsNotVacuous: true
   ```

   这是**永久用例**（不是一次性脚本），因此 T02 落地后它会继续守着这条语义。

2. **补了一条在今天就真的会红的守卫**：`assertNoFixedAtCaptureTime`。
   它断言截图时刻页面上没有任何 `position: fixed` 的元素。理由：
   中和失效时**尺寸断言与高度守卫都发现不了**（图还是那么高、宽也对，
   只是 `.tab-bar` 被画在了长图中段）——这是本包唯一能发现该失真的断言。
   新增开关 `SHOTS_ABLATION_NO_FIXED_FIX=1` 关掉中和注入，实测：

   ```
   EXIT_D2 = 1
   8 failed（= 恰好 4 个有 tab 栏的页面 × 2 视口：home / consult-list / profile / settings）
   Error: fullPage 截图时刻仍有 position:fixed 的元素（.tab-bar）：…
   ```

   与产物交叉印证：manifest 里 `fixedNeutralised: true` 的整页图恰好是
   `home / consult-list / profile / settings` 四页，与 8 个失败一一对应；
   其余六页（login/home 之外的 cases/chat/emergency/guide/memory）确实不渲染 tab 栏
   （源码侧交叉印证：只有 `HomePage`/`ConsultListPage`/`ProfilePage`/`SettingsPage`
   给 `<AppShell tab=…>` 传了 tab）。

因此现在**两个机制各自独立可消融**：`SHOTS_ABLATION_NO_EXPAND` 只检验高度守卫、
`SHOTS_ABLATION_NO_FIXED_FIX` 只检验 fixed 断言（原先两者混在一个分支里，
会让「哪条守卫失效了」说不清）。
