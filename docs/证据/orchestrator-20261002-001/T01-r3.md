## 1. P1-1（核心）：生产守卫曾被喂错量 —— 已按裁决修法 1 修

### 1.1 根因（裁决与审查者的复现我均采信，不重复辩解）

生产调用点用**文档级**溢出作判据；设备外壳结构下滚动发生在**内层 `.device-screen`**，
于是文档级值要么 0（守卫整段跳过）要么 48（守卫通过）——**1184px 被藏住而守卫毫无反应**。
我的 `guard-nonvacuity` 当时喂的是内层溢出，**与生产不是同一个量**，所以只证明了
「函数被喂好输入时会抛错」。r2 §1.5 那句「T02 落地后它会继续守着这条语义」**不成立**，
本轮更正（见 §1.4）。

### 1.2 修法（按裁决第 1 条，并说明我为何在实现中修正了它一处）

**判据改用「隐藏溢出」**，且把「该量什么」收进一个函数、让守卫只接受它的返回值——
从签名上排除「调用方自己挑一个量」：

```ts
// neutralise.ts
export function measureOverflow(page: Page): Promise<OverflowMeasurement>
// 同时给出：documentOverflowPx（文档级）、scrollContainers（每个内层滚动容器）、
// innerOverflowPx、hiddenOverflowPx = max(两者)、requiredContentHeightPx

export function assertFullPageExpanded(params: {
  fullPngHeightPx: number;
  measurement: OverflowMeasurement;   // ← 不是裸数字
  deviceScaleFactor: number;
  context: string;
}): void
```

**实现中我发现裁决给的算式（`clientHeight + hiddenOverflow`）在溢出来自内层容器时会把
两个不同来源的量相加**：外壳场景下 `.device-screen` 的视口高是 844，而**文档**视口高在
desktop 下是 1000。我一度照字面写成 `documentElement.clientHeight + innerOverflowPx`，
desktop 下得到 `1000 + 1184 = 2184`，而真实展开后的内容高只有 `4266 / 2 = 2133`
⇒ **误报展开失败**（2184 > 2133）。这个错误被我自己新加的 DOM 层断言 `assertExpanded`
当场抓到——它使该轮在该页以 `ENOENT ... shell-pad24-EXPANDED-desktop.png` 收场
（因为断言抛在截图之前，我当时把截图也放在同一个 try 里）；
失败现场留档 `T01-assets/r3-run2.txt`（其中可见 ENOENT），
上述 2184 / 2133 两个数字可由落盘的
`tmp/screenshots/.run/guard-nonvacuity/guard-nonvacuity-pad24-desktop.json` 复算。

**处置**：改为**逐滚动来源各取所需高度、再取最大**，不跨来源相加：

```
requiredContentHeightPx = max(
  documentElement.scrollHeight,                    // 文档这条来源需要多高
  ...每个内层滚动容器的 scrollHeight               // 每条内层来源各自需要多高
)
```

语义是「页面上最高的那段内容有多高」，与滚动发生在哪一层无关——这正是裁决
「判据结构无关」的意图，只是把「相加」换成了「逐来源取最大」。
**这条修正属我对裁决算式的一处偏离，特此标注请裁决**（改动前后都满足「结构无关」这一意图，
但字面算式不同）。

### 1.3 判据是承重的：四种组合全部会红（含 padding 0/24）

`guard-nonvacuity.spec.ts` 改为：**两种 padding 形态 × 用生产同一个 `measureOverflow` 取量 ×
用生产同一个 `assertFullPageExpanded` 判定**。实测记录（`tmp/screenshots/.run/guard-nonvacuity/`
下四份 JSON，每轮运行重生成）：

| 视口 | padding | 文档级溢出（旧判据会用的量） | 隐藏溢出（新判据） | 不展开 ⇒ 守卫 | 展开后图高 | 展开 ⇒ 守卫 |
| --- | --- | --- | --- | --- | --- | --- |
| mobile | 24 | 48 | **1184** | **抛错** | 4266px | 通过 |
| mobile | 0 | **0**（旧判据整段跳过） | **1184** | **抛错** | 4170px | 通过 |
| desktop | 24 | 0 | **1184** | **抛错** | 4266px | 通过 |
| desktop | 0 | 0 | **1184** | **抛错** | 4170px | 通过 |

不展开时的抛错原文（mobile/pad=0，取自落盘的 JSON）：

```
模拟外壳(pad=0)-mobile 有 1184px 纵向内容被藏住（内部滚动容器：div#__sim_screen__(1184px)），
整页图应至少 4056px 高（= 最高滚动来源的内容高 2028px × 2），实际只有 1688px：
fullPage 未真正展开内容，长图不可用（它只截到了滚动容器的首屏）。检查 expandForFullPage 的滚动容器定位与其祖先链展开。
```

对比审查者复现的旧行为：同样是 pad=0，旧判据下 `guardWouldRun=false`（整段跳过）、
pad=24 下 `documentTruncatedByPx=48` 而 `guardWouldThrow=false`。**现在四种全部会红。**

同时新增**第二条独立通道** `assertExpanded()`：在 DOM 层断言「展开后内容高 ≥
`requiredContentHeightPx`」。它比「读 PNG 像素高」更靠近病因，且与 PNG 那条**共用同一个
`measurement` 对象**——两条通道不可能各算一个量（这正是 P1-1 的教训制度化）。

### 1.4 报告更正：r2 §1.5 的过头断言

r2 §1.5 写「T02 落地后它会继续守着这条语义」。**该断言不成立**（当时生产喂文档级、
证明喂内层级，`guard-nonvacuity:126` 与 `shots.spec.ts:147-153` 不是同一个量）。
现在该句的**正确版本**是：

> 生产守卫与 `guard-nonvacuity` 现在共用同一个取量函数 `measureOverflow` 与同一个判据函数
> `assertFullPageExpanded`，因此本用例证明「四种外壳形态下它会抛错」**等价于**证明生产路径
> 在那些形态下会抛错。**仍未证**的是「T02 真实 DOM 的任何形态下都会红」——
> 我的外壳是按 `facts.md` §3 在浏览器侧构造的**模拟**，不是 T02 的真实结构。

### 1.5 新判据的已知边界（不掩饰）

`requiredContentHeightPx` 取**最大**而非求和：对「外层容器自己藏一部分、其可见区内又嵌
一个独立滚动容器再藏一部分」这种**嵌套独立滚动**形态会**低估**（方向是让守卫更容易漏，
不构成假绿的安全风险，但削弱守卫强度）。本轮目标结构（单层 `.device-screen`）不受影响。
该边界写在 `OverflowMeasurement.requiredContentHeightPx` 的注释里。

## 2. P1-2：消融 C 对 chat 静默空转 —— 已修，且现在实测会红

**根因**（裁决与审查者一致）：`emptyListBody` 只清 `items`/`candidates`，而 chat 的承载字段是
`messages` ⇒ 开关什么都没做，却报 23 passed / exit 0。

**修法**（按裁决：清空后断言「至少有一个数组真的被清空」）：

```ts
function emptyTopLevelArrays(body): { body: unknown; clearedKeys: string[]; topLevelKeys: string[] }
// 清**所有**顶层数组（不再写死字段名单）——写死名单正是静默空转的来源

// effectiveFixtures 里先试清一次，一个都没清到就抛错点名：
throw new Error(
  `内容断言消融对页面「${shot.name}」无效：其夹具载荷里没有任何顶层数组被清空，`
  + `因此这个消融开关什么都不做，「用例仍然通过」不能证明断言有效。`
  + `载荷的顶层键：${observedKeys.join('、')}。`
  + '请把该页的承载字段纳入 emptyTopLevelArrays，或把该页从消融目标里去掉。'
);
```

**实测**（`T01-assets/ablation-C2-chat-empty-list.txt`）：

```

修订前是 `23 passed / EXIT=0`（审查者复现）；**现在是 exit 1 且报出具体断言**。

## 3. 六条 P2 的逐条处置

### P2-1 死字段 + 失实注释 —— 已删（选最小改动）

删掉 `RequestLedger.failClosedViolations` 与 `aborted`（两者从无写入点），并删掉
「兜底 handler 里 `expect.soft(...)` 的失败会走这条路」这句**承诺了不存在机制**的注释、
以及「所有失败都经账本与 `failClosedViolations` 显式表达」这句失实描述。
`expectNoUnmatchedApi` 不再拼接那个空数组，直接断言 `ledger.unmatched`。
接口注释改为显式说明**每个字段都必须有真实的写入点与读取者**，并记下这条教训的理由：
「注释承诺一个不存在的机制比字段多余更糟——后来者会据此以为未命中已被收集并断言」。

### P2-2 字体闸门偶发假红（~1/9）—— 修竞态本身，而非加重试

审查者/编排器观测到的失败信息是**「已声明的族：（无）」**，说明那一刻 `document.fonts` 里
根本没有该族的 `@font-face`，即**样式表还没被解析进 CSSOM**，而不是字体请求失败
（`document.fonts.ready` 只保证「当前已知的加载结束」，评估早于样式表落定时集合就是空的）。

处置：`awaitDisplayFont` 先**有界轮询**直到该族出现在 `document.fonts`
（上界 5s、间隔 100ms），再做承重断言。**`retries` 仍保持 0**——重试会让「真的没加载」
也侥幸通过，是把红抹掉而不是修因。失败信息也拆成两种诊断（「等到了但没加载」指向 CDN，
「根本没等到声明」指向样式表未落定），避免排障从错误方向开始。

### P2-3 部分成功会留下「旧 manifest + 混合新旧 PNG」—— 加批号 + 清残留

- 新增 `e2e/global.setup.ts`：在**所有** project 之前恰好跑一次，
  删旧 `manifest.json` 与整个 `.run/`、写本轮批号。用 globalSetup 而不是某 spec 的
  `beforeAll`：后者在两个视口 project 下会并发各清一次，先跑的会把另一个已写的 sidecar 删掉。
- 每条 sidecar 记 `runId`；`manifest.spec.ts` 汇总时校验 40 条批号一致，不一致即点名
  「落点里混了其它运行的产物」。
- `manifest.json` 顶层也记 `runId`。

**canary（证明这条检查真的会失败）**：我另起一个**不带 globalSetup** 的临时配置
（否则 globalSetup 会把伪造品抹掉，测不到那条断言），伪造一条异批 sidecar 后跑汇总：

```
Error: 有 sidecar 不属于本轮（本轮批号 2026-10-02T06:31:28.488Z-c338587a）：
       落点里混了其它运行的产物，清单会与实际 PNG 不对应
Received array:  ["tmp/screenshots/home-mobile.png(批号 FORGED-foreign-run-id)"]
1 failed
```

原始记录 `T01-assets/canary-mixed-batch.txt`；临时配置跑完已删。

### P2-4 未接线导出 —— 一条接线、一条删除

- `session.ts` 的 `FRONT_TOKEN_COOKIE`/`LAST_ACCESS_COOKIE`：**接线**（改为非导出常量，
  经 `addInitScript` 参数传入页面侧拼 cookie 名），消除 `session.ts:97-98` 那份同值字面量
  ——原来改常量不会生效也不会有人发现。
- `paths.ts` 的 `isShotKind`：**接线**而非删除。它本来就有正当用途——`manifest.json` 是
  **磁盘上的 JSON**（可能被手改、半截写入、或来自旧版本），在 `manifest.spec.ts` 里
  据 `kind` 分支前先收窄类型，未知值会立刻暴露而不是悄悄走进 `else`。

选择理由（裁决允许二选一）：两处都有真实用途，接线比删除更能消除「将来会被误用」的空间；
且都不新增依赖或重构无关部分。

### P2-6 `waitForLedgerQuiet` 的 `settled` 被丢弃 —— 改为可诊断信号

`shots.spec.ts` 现在读取返回值：`settled === false` 时 `testInfo.attach` 一份 JSON
（含 `settled`/`elapsedMs`/`recordCount` 与一句说明），fail-closed 判定仍照常执行。
选「attach 警告」而不是「直接失败」的理由：账本未静默**不等于**判定错误，
它只是降低了该次判定的强度；把一个诊断信号直接升级为失败会在慢机器上产生假红，
而这条 P2 的要求是「至少让它可诊断，不得静默丢弃」（裁决原文）。

## 5. 文档错误类：两处归因更正（P2-5）

### 5.1 `docstring-promise | assertions.ts:145` 的命因

- **我 r2 §3.7 的错误说法**：「脚本自述的误报形状：返回类型为对象字面量时可能误定位」。
- **实测命因**（审查者用 `quality_floor.py:890-894` 复核，我复核一致）：走的是
  **`declared && !thrown`** 分支——**声明了 `@throws` 但函数体内没有 `throw` 关键字**。
  `evaluateAssertion` 的异常经 `pollUntilSatisfied` / `assertNever` 传递抛出，
  函数体内确实没有字面 `throw`。
- **结论**：注释是**真实且正确**的（该函数确实会抛），这是**语法级检查的传递性盲区**，
  **不是误定位**。我 r2 那条归因与实测不符，此处更正；裁决记录里编排器也一并更正了
  其此前对我的采信。
- 状态：不改注释与代码（`@throws` 应当声明）。已接受为检查器已知盲区。

### 5.2 `expectNeverRequested` 的 canary

- **我 r2 §5 的错误说法**：该断言的非空洞性由「消融 A 反向走通过」证明。
- **实测**：消融 A 走的是 **`expectNoUnmatchedApi`**（`network.ts:251`），
  与 **`expectNeverRequested`**（`network.ts:274`）**不是同一个函数**——
  两条断言碰巧都读 `records`/`unmatched`，但触发路径不同，因此那个 canary 不成立。
- **处置**：结论本身成立（0 命中），但**我的 canary 是错的**。审查者已另补真 canary
  （`PROBE_NEVER_REQUESTED_MSG`：喂一个确实被请求过的前缀，断言抛错点名）。
  我本轮**不再援引消融 A**，接受审查者那份独立 canary 作为该断言的证据。

### 6.1 需要裁决：我对裁决算式做了一处等价意图的偏离

裁决第 1 条给的判据是「fullPage 图高 ≥ `(clientHeight + hiddenOverflow) × 倍率`」。
我实现为「≥ `requiredContentHeightPx × 倍率`」，其中 `requiredContentHeightPx` 是
**逐滚动来源取最大**（文档的 `scrollHeight` 与每个内层容器的 `scrollHeight`），
**不跨来源相加**。理由见 §1.2：字面相加在 desktop 下会得到 2241 而真实内容高只有 2133，
产生**误报**（已被我自己的 DOM 层断言抓到，失败现场 `r3-run2.txt`）。
