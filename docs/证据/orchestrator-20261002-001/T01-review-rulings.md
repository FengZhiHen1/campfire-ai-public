### P1-1（核心）：生产守卫被喂了**错误的量** —— 编排器独立复现，成立

**审查者的论证**：`shots.spec.ts:147-153` 用**文档级**溢出（`documentElement.scrollHeight - clientHeight`）
作 `truncatedByPx`；在 T02 外壳结构下内层 `.device-screen` 承担滚动，文档级溢出要么 0（守卫整段跳过）
要么是个小值（守卫通过），于是 **1184px 被藏住而守卫毫无反应**。

**编排器独立复现**（探针 `facts-probe/verify-guard-input.html`，按 facts.md §3 的目标外壳结构 + 长内容）：

| 视口 | stage padding | 文档级溢出（守卫的输入） | 守卫会运行? | 内层真实藏住 | 守卫会抛错? |
|---|---|---|---|---|---|
| 390×844 | 24 | **310** | yes | **1404** | **no** |
| 390×844 | 0 | 0 | **no** | 1404 | **no** |
| 1280×1000 | 24 | **154** | yes | **1404** | **no** |
| 1280×1000 | 0 | **140** | yes | 1404 | **no** |

**四种组合全部漏过**：文档级溢出（0~310）与真实藏住量（1404）差一个数量级，
判据用前者，守卫在此结构下**不可能红**。

**归属要分清**（审查者也分清了，我确认这个分法正确）：
- **裁决给的字面判据本身有错** —— 我在裁决 A 里写「对 `truncatedByPx > 0` 的页面，
  整页图必须显著高于视口高」，并把它当 fail-loud 守卫。我**选错了量**：`truncatedByPx` 是**文档级**溢出，
  而外壳结构下溢出发生在**内层容器**。这是我的设计错误。
- **执行者实现无误**：它照裁决实现，且自己发现的「必须展开祖先链」是对的、
  `expandForFullPage` **实测有效**（审查者验证：穿透 5 层祖先链、展开后内容高 2085 → 长图 4170，
  与随包 `profile-mobile-full.png` 同高）。
- **执行者报告有一处过头**：r2 §1.5 称「T02 落地后它会继续守着这条语义」——该断言**不成立**，
  因为 `guard-nonvacuity.spec.ts:126` 喂的是**内层容器**溢出（1184），而生产调用点喂的是**文档级**溢出，
  **不是同一个量**。它只证明「函数被喂内层溢出时会抛错」，不证明生产路径会红。记 P1（报告有效性断言过头）。

**裁决：P1-1 必须修**。修法（**我选审查者建议的第一条**，因为它把判据改成结构无关的）：
1. 判据改用「隐藏溢出」= `max(文档级溢出, 所有 overflow:auto/scroll 后代的 scrollHeight − clientHeight)`；
   要求 fullPage 图高 ≥ `(clientHeight + hiddenOverflow) × 倍率`。
2. **`guard-nonvacuity.spec.ts` 必须喂与生产调用点相同的量**（即上面那个 max），
   且必须包含 **stage padding = 24 与 0 两种形态**（审查者实测这两种在 pad=0 时会整段跳过守卫）。
   否则它仍在验一个与生产不同的东西。
3. 修完后**必须给出「在 T02 目标结构下守卫会红」的直接证据**：即「不展开时守卫抛错」那条路径，
   要用**生产同一个输入函数**、在**含 padding 的外壳结构**上跑出来。

**为什么这条重要**：它正是追加裁决想防的静默陷阱——「20 张外壳首屏冒充整页长图」。
守卫失效意味着 **T03 会拿被裁掉 1184px 的图去审版式**，结论全废。
我此前采信裁决 B 时只核了「D2 消融会红」，没有独立构造外壳验 P1-1 的那个量——**这是我的复核盲区**。

### P1-2：消融 C 对 `chat` **静默空转** —— 编排器独立复现，成立

**编排器独立复现**：
```
$env:SHOTS_ABLATION_EMPTY_LIST='chat'; pnpm --filter @campfire/web shots
→ 23 passed, EXIT=0     ← 消融"通过"了，但它什么也没做
```
根因（我读码确认）：`fixtures.ts:677` 的 `emptyListBody` 只清顶层 `items` / `candidates`，
而 chat 的载荷承载字段是 **`messages`**（`fixtures.ts:193`）——于是清空逻辑没碰到任何数组，
断言当然不会红。

**裁决：必须修（P1）。** 审查者的处置正确：**清空后断言「至少有一个数组真的被清空」**，
否则抛错点名。理由：这是「**会把「没做消融」报成「消融通过」的通道**」——
比断言本身有缺陷更危险，因为它污染的是**验证手段的可信度**。
执行者的 `fixtures.ts:669-671` 注释确实披露了「只动 items/candidates」，但**披露不等于会失败**：
一个静默空转的消融开关仍会被当成有效消融。故按 P1，不降级。
