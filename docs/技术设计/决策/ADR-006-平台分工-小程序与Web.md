# ADR-006：平台分工——小程序服务需求侧，Web 服务供给侧

> **状态**：2026-06-30 时点的平台分工假设；当前仅 Web 活跃，小程序终态是否按需求/供给分端须重访，见[需求发布范围](../../需求/功能需求与验收.md)及[技术栈设计](../技术栈设计.md)。下文“终态不变”为历史文本，不是新目标确认。
>
> **修订注意**：小程序资质审核通过前的内测期，「Web 不承载需求侧能力」的边界由 [ADR-012](./ADR-012-内测期Web承载需求侧服务.md) 作时限性修订；ADR-012 退役后本文恢复完整效力。MVP 期执行节奏由 [ADR-014](./ADR-014-MVP平台收束-暂缓小程序.md) 调整（小程序暂缓、Web 全量承载），终态分工不变。

## 上下文

ADR-002 曾决策「Taro 微信小程序优先、H5 管理后台远期预留」，但实施中 `apps/react-web`（React 19 + Vite）已成为主 Web 应用并通过 H5 部署，`apps/mini-program`（Taro）并存，前端形态长期缺乏正式决策。2026-06-30 需求基线 v2.0 确立了四方画像（监护人/志愿者为需求侧，老师/专家为供给侧），平台分工需按画像使用场景正式收束。

## 备选与评价

- **小程序=需求侧，Web=供给侧**：监护人/志愿者的核心场景是危机时刻——必定在手机端、微信内零门槛；老师/专家的案例录入审核、工单处理、档案共建重表单、重审核，桌面端效率远高于移动端。平台形态与画像场景一一对应。
- **小程序全员，Web 仅管理后台**：供给侧在小程序上操作案例审核/工单，移动端表单效率受限，专家时间稀缺（P4 画像约束）会被进一步消耗。
- **Web 为主，小程序后补**：危机场景要求零安装、微信直达，Web 无法满足应急可达性。

## 决定

- **微信小程序**（Taro）= 需求侧入口：监护人 + 志愿者的应急咨询、档案记录与查看、趋势复盘、科普、工单家属侧；
- **Web 端**（react-web，React + Vite）= 供给侧工作台：老师/专家的案例录入与审核、工单处理、档案共建 + 管理员平台管理。

## 后果

- 正面：两个前端各自服务匹配的画像，技术选型（Taro / React+Vite）与已投入的代码资产一致，无需返工；
- 负面：需长期维护两个前端应用与 `ts-shared` 契约同步；小程序端不承载供给侧能力，老师/专家的移动办公场景（如临时接特急工单）需要小程序内轻量通知通道补充（具体形态延后设计）。

## 重访条件

供给侧出现明确的移动办公诉求（如特急工单手机接单成为高频路径），或 Taro 跨端路线与微信生态政策发生重大变化时。
