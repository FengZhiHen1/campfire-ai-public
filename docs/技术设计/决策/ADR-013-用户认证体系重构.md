# ADR-013：用户认证体系重构——身份-凭证分离与角色准入生命周期

> **状态**：有效（2026-08-04 决策）
> **机制细节**：由 [认证与访问](../机制/认证与访问.md) 唯一拥有，本文不复制其状态机、矩阵与流程定义。

## 上下文

认证现状为双轨制：后端正式 JWT 账密轨完整但**未被前端使用**；两个前端均无登录/注册界面，全部业务路由挂在 `get_anonymous_user` 评委演示轨（所有请求映射到预置 expert 账号）。角色枚举缺 `volunteer`（M6 需求已存在）；「老师/专家实名认证」（需求风险约束的双保险之一）无准入流程，仅一个 real_name 字段；ADR-012 新增邀请码制、手机号合并锚点与过审后微信登录的约束。产品处于预发布窗口期，无真实用户数据，是破坏性重构成本最低的时机。

## 备选与评价

**身份模型**：

- 单用户表（现状）：所有认证字段挤在 users 表，微信登录落地时需要二次重构；
- **身份-凭证分离（选定）**：User 主体 + Credential 渠道凭证（密码/微信/可扩展），ADR-012 的手机号锚点合并与多渠道演进天然契合，代价是一次破坏性表结构迁移（预发布可承受）。

**匿名演示轨**：

- 保留匿名访问（如未登录可看通用安全卡）：邀请码制下内测用户全是定向注册者，匿名无真实服务对象，且引入「部分内容公开」的边界复杂度；
- **废除（选定）**：全量正式认证；终态危机零门槛由微信静默登录解决，演示需求改用正式演示账号。

**角色模型**：

- **单角色互斥（选定）**：需求 M6 与产品定位已定「注册时选角色，区别于家属」；一人多职业身份记 `missing evidence`，不为此建多角色结构。

**角色准入**：

- 全角色自助注册即激活（现状）：teacher/expert 无实名审核，不满足「实名认证 + 案例审核」双保险约束；
- **准入状态机（选定）**：family/volunteer 自助激活；teacher/expert 注册提交实名+资质 → `pending_review` → 管理员审核；admin/maintainer 维持管理员分配。

**Token 模型**：

- opaque session / PASETO：需替换现有 Redis 黑名单与验签链路，无明确收益；
- **维持 JWT 双 token + 轮换（选定）**，增强 refresh 家族盗窃检测（旧 token 复用 → 全家族吊销）。

**登录标识**：

- 用户名（现状）：微信原生用户记忆成本高，且引入「用户名唯一性」额外概念；
- **手机号（选定）**：手机号已必填且唯一，C 端惯例，username 字段废除。

**手机号短信验证时机**（锚点可信度 vs 外部依赖成本）：

- 注册即验证：锚点全程可信，但内测期即引入短信服务商依赖与按条成本；
- **绑定时补验（选定）**：注册仅格式校验；微信绑定合并流程强制短信验证。内测期零外部依赖，邀请码制下用户定向、风险窗口可控；
- 不验证、合并走人工：运营负担不可扩展，排除。

**RBAC 语义**：

- 数值层级继承（现状 FAMILY=1…MAINTAINER=5）：专家自动继承家属能力等语义粗糙问题，权限边界不可审；
- **显式角色→能力映射（选定）**：矩阵即文档，越权用例可直接对照验收。

## 决定

按上述选定方向重构认证体系：身份-凭证分离模型；废除匿名演示轨、全量正式认证；六角色单角色互斥 + teacher/expert 准入审核状态机；JWT 双 token + 轮换 + 家族盗窃检测；手机号登录标识；手机号短信验证延至微信绑定合并时；显式角色→能力映射。机制细节与迁移设计见[认证与访问](../机制/认证与访问.md)。

## 后果

- 正面：认证体系从「演示可用」变为「生产可用」；微信登录与账号合并的机制缝已预留，落地时不需再重构；邀请码与准入审核使内测与供给侧准入可控；显式 RBAC 矩阵可直接支撑隐私验收用例；
- 负面：破坏性迁移（users 表结构变更、业务路由依赖全量切换、前端需新增登录/注册界面）；管理员承担准入审核与内测期密码重置的运营负担；短信服务商为确定的近期外部依赖。

## 重访条件

- 微信开放平台认证完成 → 激活微信渠道与绑定合并（含短信验证依赖引入）；
- 一人多职业身份成为高频诉求 → 重访多角色结构；
- 内测期出现手机号抢注实际事件 → 短信验证时点提前至注册。
