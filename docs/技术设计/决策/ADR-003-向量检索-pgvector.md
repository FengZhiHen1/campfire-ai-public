# ADR-003：向量检索选择 pgvector 而非独立向量库

> **状态**：有效（2026-05-23 决策）

## 上下文

案例切片需要向量语义检索，需选择向量存储方案。早期需求材料（转型后需求分析、细节设计原稿）曾按 MySQL + ChromaDB 表述，本决策作出后统一为 PostgreSQL + pgvector。

## 备选与评价

- **pgvector（PostgreSQL 插件）**：与 PostgreSQL 统一数据层，减少一个独立运维组件；SQL + 向量混合查询天然满足标签过滤式检索需求；初期 < 10 万切片规模下 HNSW 索引性能完全满足 TTFT 约束。
- **ChromaDB（独立部署）**：轻量，但引入第二个数据存储与运维面。
- **Milvus（专业向量库）**：大规模性能强，但对 < 10 万切片与 1-3 人团队过重。

## 决定

pgvector 作为主方案。

## 后果

- 正面：运维组件精简；
- 负面：百万级向量后需迁移至专业向量库。

## 重访条件

向量规模接近或超过 100 万、检索延迟威胁 TTFT ≤ 3s 约束时，按[总体架构](../总体架构.md) §6 的后备方案评估 pgvectorscale / Milvus / Qdrant。
