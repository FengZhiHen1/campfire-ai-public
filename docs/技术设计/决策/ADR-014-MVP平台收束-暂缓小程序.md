# ADR-014：MVP 平台收束——暂缓 mini-program，Web 全量承载

> **状态**：Web 活跃、小程序冻结的执行安排沿用；“终态分工不变”为旧时点假设，需重新验证，见[技术栈设计](../技术栈设计.md)。

## 上下文

小程序资质审核未通过（ADR-012 的前提）且过审时间不可控，需求侧无法经小程序触达；ADR-012 已使 MVP 事实上 Web-only（需求侧内测全在 Web）。双前端维护成本是 ADR-006 自认的负面后果：1-3 人团队同时背负机制设计欠账、Agent 化落地与前端五层重组（DSR-006），每个需求侧功能做两遍是当前最大的速度损耗。mini-program 现状为演示轨半成品（无登录界面、业务路由挂评委轨），按 ADR-013 本就需返工，冻结几乎无沉没成本损失。

## 备选与评价

- 双端并行（现状延续）：投入产出为零——小程序无法上架，做的功能没有用户；
- **MVP 期暂缓（选定）**：MVP 只做 Web；ADR-006 终态分工保留，资质路径明朗后重启，决策完全可逆；
- 终态放弃：修订 ADR-006、改走公众号 H5 补位——但公众号路径未验证（`missing evidence`），推翻「危机场景微信零门槛」的终态判断为时过早。

## 决定

1. **MVP 期冻结 mini-program 开发**：代码保留于仓库，移出 active 构建与 CI；不做五层重组与新特性开发；
2. **Web 为 MVP 期唯一活跃前端**：供给侧工作台 + 需求侧服务；需求侧范围维持 [ADR-012](./ADR-012-内测期Web承载需求侧服务.md)（应急咨询 + 档案，邀请码制，手机号账号锚点）；
3. **ADR-006 终态分工（小程序 = 需求侧）不变**；小程序重启并稳定后，ADR-012 的退役安排照常生效；
4. 后续需求侧模块（M5 趋势复盘、M6 协作照护、M7 科普、M4 家属侧）进入实现时**默认 Web 先行**，小程序重启后按 ADR-006 归位；
5. 微信生态可达性补位（公众号菜单 + H5、网页授权登录）登记为 `missing evidence`，验证后择机实施。

## 后果

- 正面：前端维护面减半，五层重组只做单端；需求侧迭代速度提升；ADR-012 的过渡叙事简化为「内测即 MVP 平台形态」；决策可逆，Taro 资产与 ADR-013 的 wechat 渠道预留全部保值；
- 负面：微信内零门槛的终态体验推迟；公众号 H5 补位未验证期间，微信生态触达依赖私域分发链接；冻结的 Taro 代码随时间贬值（五层重组与契约演进使其重启成本递增）。

## 重访条件

- 小程序资质路径明朗（过审，或明确可行的类目方案）→ 重启开发，回归 ADR-006 终态；
- 公众号 H5 路径验证完成 → 重估微信生态补位的正式形态（可能影响 ADR-006 重访）；
- MVP 验证显示家属触达/转化因渠道受限显著不达标 → 提前重访。
