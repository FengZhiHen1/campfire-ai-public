# ADR-012：内测期平台分工——Web 承载需求侧内测服务

> **状态**：有效（2026-08-04 决策，对 [ADR-006](./ADR-006-平台分工-小程序与Web.md) 的需求侧边界作时限性修订）
>
> **修订注意**：mini-program 开发已由 [ADR-014](./ADR-014-MVP平台收束-暂缓小程序.md) 于 MVP 期暂缓——本文的「内测期」安排即 MVP 平台形态；退役条件改由 ADR-014 的重启条件驱动（小程序重启并稳定后照常生效）。

## 上下文

ADR-006 确立「小程序 = 需求侧、Web = 供给侧」的终态分工，但其前提——小程序可通过微信资质审核上架——当前不成立：小程序尚未通过资质审核，需求侧用户（监护人/志愿者）无法经微信触达，内测无从开展。《总体架构》风险表原将「H5 网页版兜底」列为审核不通过时的后备预案，现需将其升级为正式维护的过渡渠道。

实施现状对本决策有利：`apps/react-web` 已具备应急咨询（consult）与档案（profiles）页面并经 H5 公网部署；账号体系为用户名 + 密码 + 手机号（唯一约束）+ JWT/RBAC；尚无邀请码与微信登录（code2session）能力。

## 备选与评价

**内测功能范围**：

- 完整需求侧镜像：内测体验与小程序目标形态对齐，但趋势复盘/科普/工单家属侧均需双端并行开发，过渡期投入翻倍；
- **应急咨询 + 档案（选定）**：核心应急链路与档案这一数据资产沉淀点均可跑通，且与 react-web 现有页面基本对应；其余需求侧功能待小程序过审后提供；
- 仅应急咨询：档案缺失导致内测数据资产无法沉淀，过审后冷启动问题依旧。

**访问控制**：

- 开放注册（现状）：零改动，但医疗敏感场景下公网开放服务的合规暴露面大，「内测」名不副实；
- **邀请码制（选定）**：注册需有效邀请码，运营生成、定向分发、可停用；规模可控可追踪，开发量小；入口（URL/公众号菜单/私域转发）本身不设限，由邀请码把关；
- 申请 + 人工审核：控制最强，但运营负担重，家属危机场景下等待成本高。

**过审后去向**：

- **逐步下线（选定）**：Web 需求侧仅作过渡，小程序过审并稳定后回归 ADR-006 终态分工，避免双端长期并行维护；
- 长期保留为补充入口：可覆盖桌面场景，但违背 ADR-006 的画像-平台对应逻辑，维护成本长期化。

## 决定

1. **内测期 Web 端在供给侧工作台之外，同步承载需求侧内测服务**，范围限定「应急咨询 + 档案记录与查看」（监护人与志愿者通用）；趋势复盘、科普、工单家属侧待小程序过审后提供。Web 端按角色收敛导航，需求侧内测用户不可见供给侧功能。
2. **访问控制采用邀请码制**：注册需有效邀请码；邀请码由运营侧生成、定向分发、可停用。注册其余字段维持现状（用户名 + 密码 + 手机号 + 角色）。
3. **账号以手机号为统一锚点**：内测沿用现有账号体系；小程序过审后新增微信登录，首次登录以手机号绑定合并至既有账号，内测期档案与咨询记录无缝保留。
4. **退役安排**：小程序过审并稳定运行后，停止发放邀请码、逐步下线 Web 需求侧入口，平台分工回归 ADR-006 终态。

## 后果

- 正面：需求侧触达不被审核阻塞，内测可即时开展；档案与咨询数据提前沉淀，缓解过审后的冷启动；手机号锚点保证账号与数据无缝迁移；邀请码机制改动小、可控；
- 负面：需新增邀请码生成/校验/停用能力；过渡期内 Web 端需求侧功能与小程序并行维护，`ts-shared` 契约同步范围扩大；按角色收敛导航带来一次性的 UI 调整。

## 与 ADR-006 的关系

本决策触发 ADR-006 重访条件中的「微信生态政策发生重大变化」（资质审核未通过）。本 ADR 仅对「Web 不承载需求侧能力」作**时限性修订**，不改变 ADR-006 的画像-平台终态分工；退役条件满足后，ADR-006 恢复完整效力。

## 退役与重访条件

- **退役条件**：小程序通过资质审核并稳定运行 → 停止发放邀请码、下线 Web 需求侧入口，本 ADR 标记为「已退役」；
- **重访条件**：小程序长期无法过审 → 重访是否将 Web 需求侧入口常态化运营；或微信生态政策再次发生重大变化。
