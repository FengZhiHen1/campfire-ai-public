# ADR-016：授权与发布由业务代码强制执行

> **决定**：空间授权、建议发布、计划停用及来源有效性由服务端业务用例和主库状态强制判定；AI 内核与安全扩展仅是受限执行手段，新接口先验证完整可行动输出再发布。**理由**：授权撤销与安全异议必须在并发和缓存滞后时仍生效，提示词、扩展加载顺序与流式格式校验均无法独立保证。**被否决项**：保持 Agent 自治流式输出与“安全扩展首位注册”作为主要强制门。
> **状态**：2026-09-26 用户授权自主收敛；`/api/v2` 未实现。旧 `/api/v1` 实现已随其余旧代码归档，仅作参考。

## 上下文与挑战旧决定的证据

`ADR-009` 为危机中先读内容而设计确定性安全层，其不等待模型的理由继续成立；但行为桶、危机阶段和自动四段式不是新产品确认的必要入口。`ADR-011` 将安全代码作为第一方扩展，靠首位加载与启动断言保证挂载；`ADR-015` 假设生成型 SSE 可以先逐 token 输出、事后验证结构化结果。新需求明确同一用户跨多人空间、授权可即时撤销、安全异议条目级即时停用、旧摘要不得越权再读。仅在生成前挂载扩展、生成后校验结构，不能收回已经输出到客户端的受限或危险片段；这是对原“加载即可保证全链路安全”理由的新反例，而非反对复用 Agent 内核。

## 真实方向与取舍

| 方向 | 优势 | 不可接受或新增的成本 |
|---|---|---|
| 延续旧 Agent 面 + 统一 token SSE | 可复用已有客户端，首 token 很快 | 生成中撤销/停用后的迟到 chunk 已分发，历史重连可绕过当前授权，输出后校验太晚 |
| 业务代码强制当前授权 + 完整结果校验后发布（选定） | 授权和停用有事务线性化点，模型与缓存故障能 fail-closed | 用户等待完整答案时间增加，需显示已审阅基础内容与非行动性进度，须单独验证可用性 |
| 所有内容人工逐条审批 | 发布安全边界单纯 | 首次通用帮助及高频日常记录无法及时使用，超出现有专业资源证据 |

## 决定与后果

- 公开基础内容通过独立审阅版本可不登录获取；登录后的情境 AI 可读取当前合法范围，危险内容、高影响操作和权限更改由代码控制。
- 主库中授权版本、条目状态和来源发布状态是读取与发布的最终真相；Token、Redis 或 Agent 工具白名单只可缩小权限，不能扩权。授权库不可达时拒绝受限访问，公共基础内容仍能使用。
- 候选 AI 产出先完成结构、来源主张、当前授权/停用状态和禁止内容检查；未完成的可执行文本不通过新 `/api/v2` 逐 token 暴露。后续若证实可靠的增量安全验证可在不泄漏的前提下重访流式体验。
- 保留 `py-agent-kernel` 及可用扩展作为受控执行基础，但不靠 security 扩展加载顺序保障业务不变量。旧 `/api/v1` 实现不被默认为安全上线的新接口，迁移和回退必须单独验证。

## 重访条件

若经过成对越权、并发停用与回放测试，能证明一种增量流既不泄漏未授权资料也不在完整校验前发布可执行建议，且等待完整结果严重降低帮助可达性，可考虑分段审阅输出。若同步授权检查造成不可接受的性能退化，先优化索引和只读授权查询，不改为信任过期缓存。
