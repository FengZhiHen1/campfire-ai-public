> **追溯**：`RQ-DAY-01`、`RQ-CON-01`～`RQ-CON-08`、`RQ-KB-01`、`AC-05`、`AC-06`、`AC-09`、`AC-11`、`AC-12`。

## 1. 定位

**面向监护者的日常咨询。** 时间不紧迫，因此目标是**展开**：把模糊的困扰收敛成可处理的问题，给出有依据的建议，并**沉淀**对支持对象的认识（沉淀本身由 `profile-curation` 承担）。

与应急的分工：应急在信息不足时也要尽快收敛；日常可以多轮澄清，但要为每一次追问负责。

## 2. 触发

- **使用者选定**：在输入框上方选定本技能，**其后输入的消息**按本 skill 处理（`RQ-CON-08`）。
- **模型匹配**：未选定时，模型按 `description` 自动匹配（`metadata.autoload = "true"`）。
- 两种来源语义相同，区别只在谁发起。

## 3. `SKILL.md` 正文要点

### 3.1 frontmatter

```yaml
name: daily-consulting
description: 用于监护者就支持对象的日常状况、行为、沟通与支持方式展开咨询：当使用者想弄清一个持续存在的困扰、比较几种做法、或想知道某个做法是否合适时使用。可多轮澄清、检索专业资料与案例，回看既往记忆，并在需要时把已出现的信息整理进个性化档案。
license: 项目内部内容，随应用发布，不单独授权
compatibility: 依赖 read_profile_summary、read_profile_items、read_memory、search_knowledge、search_cases 五个只读工具；不依赖脚本与外部二进制
metadata:
  surface: "consult"
  autoload: "true"
allowed-tools: read_profile_summary read_profile_items read_memory search_knowledge search_cases
```

### 3.2 方法论（正文主体）

1. **先收敛问题**：使用者往往给的是困扰的整体，而不是一个问题。第一件事是把"你最想弄清楚的是什么"定下来，再动工具。
2. **一次只推进一件事**；每问一次都要能说出**为什么问**——问不出理由的问题不问。
3. **有据才给建议**（`RQ-CON-02`）：给建议前先检索；检索到就用，检索不到就明说"这是通用做法，没有找到对应资料"。
4. **区分事实与推测**（`RQ-MEM-04` 在对话侧的对应）：观察到的行为陈述为事实，"可能是为了回避"这类必须标为推测，并且说明推测依据。
5. **目标不等于服从**（`RQ-CON-04`）：不把"让孩子配合/听话"当作默认目标；若使用者的目标与此冲突，先把这个冲突摆出来，再由使用者决定。
6. **说明适用范围与局限**（`RQ-CON-03`）：引用的资料要带上它的适用人群与情境，并说明哪些情况下不适用。
7. **案例要标清性质**（`RQ-KB-02`）：引用案例时标明它是真实案例还是虚构样例、有无授权。
8. **沉淀要经过使用者**：识别到值得记录的信息时，**提示**可以整理进档案，并激活 `profile-curation` 承担写入——本 skill **不自己写档案**。

### 3.3 输出结构

```text
1. 回应（先确认我听懂了什么）
2. 建议与依据（每条建议对应的资料或案例条目；无依据时显式标注）
3. 适用范围与局限（什么情况下这个建议不适用）
4. 下一步或可沉淀的事（需要澄清什么、是否要整理进档案）
```

### 3.4 工具使用纪律

- 检索**按需**，不为凑引用；同一轮不要对同一问题重复检索。
- **查询词自改写**：案例卡片是临床/指南文风，使用者的口语原话（如"孩子装听不见怎么办"）与卡片文风错配，直接拿原话当 `query` 会漏召回。检索前把口语描述**改写成简明的行为与情境描述**再查（例：搜"听到指令不执行、拖延、假装未听见"）。改写只发生在工具调用的 `query` 里，**不改变使用者原话的呈现**——输出中引用使用者表述仍用原话。机制与评测闸门见[RAG 策略](../../../technical-details/RAG策略.md)第 8.1 节。
- `read_profile_items` 只在需要具体条目时用；只想要概览时用 `read_profile_summary`。
- **记忆工具的使用指导**（2026-09-29 定，[通用记忆](../../../technical-details/通用记忆.md)第 4 节）：`read_memory` 用于**回看时间线**——"上次是怎么说的、这件事什么时候开始的"这类问题先查记忆再回答；它读的是片段原文，不是结论，涉及"现在该信什么"时以档案与本次对话为准。不需要每次咨询都调用；判断依据是使用者的问题是否涉及既往经历或演变。
- **写工具一律不可用**：本 skill 没有 `propose_profile_item`、`write_memory`；越界调用由服务端拒绝。

### 3.5 `references/` 的内容边界

| 文件 | 内容边界 | 明确不含 |
|---|---|---|
| `references/clarification.md` | 澄清顺序与**停问条件**（追问必须服务于改变下一步行动；简单问题允许直接回答并结束）；"为什么问"必须能说出口的自检规则 | 不写通用问句库（问句由当次情境决定） |
| `references/evidence-and-options.md` | 依据与引用的呈现纪律（来源、适用范围、真实/虚构标注）；**可选方向的呈现模板**——每个方向带适用条件与代价 | 不写资料清单本身（资料在库里，经工具检索） |

## 4. 验证方式

- **触发**：选定后下一条消息生效；未选定时按 `description` 匹配到本 skill。
- **依据**：无依据的建议必须带显式标注；有依据的建议能回指到条目。
- **事实与推测分离**：构造"使用者只描述了行为"的输入，验证输出不把推断写成事实。
- **不强行服从目标**：构造"目标是让孩子听话"的输入，验证该目标被摆出来讨论而不是被默认接受。
- **不越权写入**：尝试调用写工具，服务端拒绝。
- **记忆回看**：构造"上次说过什么"的提问，验证输出引用 `read_memory` 的返回且标注时间；构造与既往无关的新问题，验证不无谓调用。
