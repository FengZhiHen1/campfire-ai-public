## 1. 定位

**在对话中把已经出现过的信息整理成个性化档案条目。** 它是三个 skill 里**唯一持有写工具**的一个，因此也是唯一能改变档案的路径。

它只做一件事：**把说过的话整理成条目，交给使用者确认。** 它不做推断补全，不做评估，不写"专业判断"。

## 2. 触发

- **模型在对话中激活**：识别到值得记录的信息时（由本 skill 的 `description` 匹配），或在 `daily-consulting` 提示后由使用者同意。
- **使用者选定**：也可由使用者在选择器中显式选定。
- 两者语义相同。

## 3. `SKILL.md` 正文要点

### 3.1 frontmatter

```yaml
name: profile-curation
description: 用于在对话过程中把使用者已经说出或明确提供的信息整理成支持对象的个性化档案条目：当出现值得长期记住的情境、表现、可能的需要或有效的支持方式时使用。只整理已经出现过的信息并交由使用者确认，不做推断补全，不写入任何未经确认的推断。
license: 项目内部内容，随应用发布，不单独授权
compatibility: 依赖 read_profile_items、propose_profile_item、read_memory、write_memory；不依赖脚本与外部二进制
metadata:
  surface: "consult"
  autoload: "true"
allowed-tools: read_profile_items propose_profile_item read_memory write_memory
```

### 3.2 方法论（正文主体）

1. **只整理已经出现过的信息**，不推断补全（`RQ-MEM-04`）。信息不足时条目的字段就留空，不猜。
2. **逐条、少量**：一次最多提出三条候选，每条一句话；不要一次倾倒十条让使用者无从确认。
3. **来源与确认状态如实标注**：谁是这句话的来源（本人自述、监护者观察、第三方转述、文档），以及它当前是"已确认"还是"待确认"。
4. **当事人自述优先于监护者观察**：两者冲突时**并列保留**，不覆盖；不得用监护者观察去否定当事人的表达（这是档案所有权分歧在一期的缓解手段）。
5. **不把我们的建议写成对方的特点**：模型给过的建议属于"我们的建议"，不是支持对象的属性；不得写成档案事实。
6. **纠正与删除即时生效**（`RQ-MEM-03`）：使用者说"这条不对/删掉"，要立即反映到稳定层与后续输出，而不是"下次整理时处理"。
7. **不重复问已知的事**：写入前先读现有条目，避免制造重复候选。

### 3.3 输出结构

```text
1. 候选条目（一到三条，一条一句）
2. 每条的来源与确认状态
3. 请确认（明确说清确认后会发生什么）
4. 已写入的回执（写入是异步的：只回执"已提交，稍后生效"）
```

### 3.4 工具使用纪律与硬约束

- `propose_profile_item` **只写待处理记录**，落进候选层；**确认才进稳定层**。工具实现层必须硬卡：`origin` 属于 `system_observation` 或 `ai_inference` 时**不得**写成 `confirmation = confirmed`。
- `write_memory` 写通用记忆，`read_memory` 读它；两者都不得用来绕过档案的确认流程。
- 写入是**异步**的（经待处理记录与 Worker），所以回执只能承诺"已提交"，**不得**声称"已保存"。

## 4. 验证方式

- **不推断**：构造"使用者只说了行为、没说原因"的输入，验证候选条目不含原因猜测。
- **不越权确认**：尝试把推断写成已确认，服务端拒绝。
- **冲突并列**：构造监护者观察与本人自述冲突的输入，验证两条都在、未互相覆盖。
- **纠错即时**：纠正一条后立即查询，验证稳定层与输出都已反映。
- **异步回执**：验证回执措辞为"已提交"，且在后端未完成时不会显示为已生效。
