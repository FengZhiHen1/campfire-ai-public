> **状态**：2026-09-29 依需求 `RQ-MEM-01`～`RQ-MEM-06` 与技能设计总纲设计，待用户确认。**2026-09-29 推断候选裁决后更新**：本 skill 可产出来自单次观察的推断候选（`origin = system_observation` / `ai_inference`），落层由工具实现层按 `origin` 分流。
> **追溯**：`RQ-MEM-01`～`RQ-MEM-06`、`RQ-CON-07`、`AC-07`、`AC-08`、`AC-18`。

## 1. 定位

**在对话中把已经出现过的信息整理成个性化档案条目。** 它是咨询类 skill 里**唯一持有档案写工具**的一个（onboarding 也持有 `propose_profile_item`，但其定位是一次性引导而非被动沉淀，见[onboarding](onboarding.md)第 1 节），因此日常对话中改变档案的路径由此 skill 承担。

它只做一件事：**把说过的话与观察到的事整理成条目**——使用者的直接陈述入档并回执，观察与推断进候选层交使用者确认。它不做推断补全，不做评估，不写"专业判断"，也不给当事人定性。

## 2. 触发

- **模型在对话中激活**：识别到值得记录的信息时（由本 skill 的 `description` 匹配），或在 `daily-consulting` 提示后由使用者同意。
- **使用者选定**：也可由使用者在选择器中显式选定。
- 两者语义相同。

## 3. `SKILL.md` 正文要点

### 3.1 frontmatter

```yaml
name: profile-curation
description: 用于在对话过程中把使用者已经说出或明确提供的信息整理成支持对象的个性化档案条目：当出现值得长期记住的情境、表现、可能的需要或有效的支持方式时使用。可以为已经出现过的信息记录观察与推断，但推断只进候选层并如实标注来源，交使用者确认；不做推断补全，不写入任何未经确认的推断。
license: 项目内部内容，随应用发布，不单独授权
compatibility: 依赖 read_profile_items、propose_profile_item、read_memory、write_memory；不依赖脚本与外部二进制
metadata:
  surface: "consult"
  autoload: "true"
allowed-tools: read_profile_items propose_profile_item read_memory write_memory
```

### 3.2 方法论（正文主体）

1. **只整理已经出现过的信息，不补全事实**（`RQ-MEM-02`、`RQ-MEM-04`）：可以为**已经出现过的事实**记录自己的观察与推断（`origin = system_observation` 或 `ai_inference`），但**不得**为条目"完整"而编写没有出现过的内容；信息不足时字段就留空，不猜。
   - **推断与陈述分道**：推断只能进候选层，且**必须如实标注** `origin`；不得把推断写成稳定层，也不得用 `user_statement` 冒充自己的归纳。
   - **一次观察就是一条候选**，不需要等"同一主题再次出现"——重复阈值约束的是跨对话的模式归纳，那部分一期不做（[个性化档案](../../../technical-details/个性化档案.md)第 3 节）。
   - **当事人在场时的陈述优先**：有任何本人陈述可用时，不以推断替代。**不得**用推断去描述当事人的内心状态或给行为定性（"他其实是想逃避"属禁止写法；"观察到他在嘈杂环境中捂耳"属允许写法）。
2. **逐条、少量**：一次最多提出三条候选，每条一句话；不要一次倾倒十条让使用者无从确认。
3. **来源与确认状态如实标注**：谁是这句话的来源（本人自述、监护者观察、第三方转述、文档），以及它当前是"已确认"还是"待确认"。
4. **当事人自述优先于监护者观察**：两者冲突时**并列保留**，不覆盖；不得用监护者观察去否定当事人的表达（这是档案所有权分歧在一期的缓解手段）。
5. **不把我们的建议写成对方的特点**：模型给过的建议属于"我们的建议"，不是支持对象的属性；不得写成档案事实。
6. **纠正与删除即时生效**（`RQ-MEM-03`）：使用者说"这条不对/删掉"，要立即反映到稳定层与后续输出，而不是"下次整理时处理"。
7. **不重复问已知的事**：写入前先读现有条目，避免制造重复候选。

### 3.3 输出结构

```text
1. 候选条目（一到三条，一条一句）
2. 每条的来源与确认状态——区分「已按陈述入档」与「待确认的观察／推断」
3. 请确认（仅对候选层条目：说清确认后会发生什么）
4. 已写入的回执（写入是异步的：只回执"已提交，稍后生效"）
```

**陈述与推断在呈现上必须分开**：使用者的直接陈述入档时只回执"已提交"，**不要求确认**（`RQ-MEM-02` 零确认入档）；推断类候选才请确认。把两者混在同一句"请确认"里会让使用者以为自己的原话也需要批准。

### 3.4 工具使用纪律与硬约束

- `propose_profile_item` 是档案的**唯一写入口**，落层由 `origin` 分流（[个性化档案](../../../technical-details/个性化档案.md)第 3 节）：陈述类 `origin` 直接进稳定层，`system_observation` 与 `ai_inference` 只进候选层、**确认才进稳定层**。工具实现层必须硬卡：后两者**不得**写成 `confirmation = confirmed`，请求被拒绝而不是被降级改写。
- **推断必须带自己的 `origin`**：不得用 `user_statement` 提交自己的归纳——那是冒充来源，而来源是 `AC-07` 的验收对象。
- `write_memory` 写通用记忆，`read_memory` 读它；两者都不得用来绕过档案的确认流程。**两者都属账号、不收 `support_object_id`**（记忆是关于使用者自身的经验，[决策记录](../../../decisions/通用记忆归属为账号.md)）——凡是关于支持对象的事实必须走档案，不得借记忆通道绕过确认。
- 写入是**异步**的（经待处理记录与 Worker），所以回执只能承诺"已提交"，**不得**声称"已保存"。

## 4. 验证方式

- **不补全**：构造"使用者只说了行为、没说原因"的输入，验证条目不写入未出现过的内容。
- **推断如实标注**：构造需要归纳的输入，验证产出的条目标 `origin = ai_inference`（或 `system_observation`），而非 `user_statement`。
- **陈述零确认入档**：使用者直接陈述后，验证条目进稳定层、且未被要求确认。
- **推断不越权**：尝试把推断写成已确认，服务端拒绝。
- **一次观察即可成候选**：单次观察即产出候选条目，验证其不带"重复 ≥2 次"的额外门槛。
- **否定不回潮**：否定一条候选后，验证同一内容不再被提为候选。
- **冲突并列**：构造监护者观察与本人自述冲突的输入，验证两条都在、未互相覆盖。
- **纠错即时**：纠正一条后立即查询，验证稳定层与输出都已反映。
- **异步回执**：验证回执措辞为"已提交"，且在后端未完成时不会显示为已生效。
