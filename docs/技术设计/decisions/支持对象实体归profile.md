# 支持对象实体归 profile，生命周期为创建／改名／归档

> **决定**：**支持对象**立为独立实体（表 `campfire_support_object`），归 `modules/profile`；生命周期四操作一状态位——**创建、改名、归档、恢复，没有删除**（`archived_at` 为空即在用）。授权经 `core/authz` 的**两个具名函数** `require_owned`（读）与 `require_writable`（写，额外要求未归档）；协议与错误类型在 `core/authz`、一期实现（属主即允许）由 `profile` 提供、装配处注入。会话与对象的绑定另立 `campfire_session_object`，**主键是 `session_id`**，"默认沿用上一次的选择"由该表推导而不另存字段。**理由**：`RQ-MEM-07` 与 `AC-22` 的判定点已经存在（`pending_write.support_object_id` 的存储层 CHECK 早已在等这个实体），而被判定对象全库无定义；归档而非删除，是因为**删除会让在途写入产生"删后复活"歧义**——账号注销为此专门引入墓碑，归档让行始终存在，因此不需要第二个墓碑。**被否决项**：仅创建与切换（误建或错名永久留在切换器里，且没有给出"不删除"的理由）；可硬删除（需为对象再建一套墓碑或排空机制，成本与账号注销同量级）；把实体放 `core`（支持对象是业务实体，`core` 装的是跨切能力与投递机制，二者性质不同）；把"账号当前对象"存成字段（会与绑定记录构成两个可写真源）。
> **状态**：**2026-09-29 经用户裁决**（选定"创建 + 改名 + 归档"）。这填补了一个**下游已假定存在、上游从未定义**的实体；同时修正了两处既有缺陷（见下文）。不代表已实现。

## 上下文与证据

**这不是"补一个缺失的表"，是"判定点存在、被判定对象不存在"**：

| 位置 | 依赖方式 | 修正前现状 |
|---|---|---|
| [个性化档案](../technical-details/个性化档案.md) 第 2 节 | `profile_item.support_object_id` 归属键 | 字段已定义，实体无定义 |
| [个性化档案](../technical-details/个性化档案.md) 第 9 节 | "每次访问都要校验该对象属于当前账号" | 校验对象不存在 |
| `core/pending_write/models.py` | **存储层 CHECK**：`(kind='profile_item') = (support_object_id IS NOT NULL)` | 约束已在等这个实体（实测该文件 `__table_args__`） |
| [通用基座](../technical-details/通用基座.md) 与 `core/authz/__init__.py` | 唯一授权端口 | 空占位，其说明写着"端口的形状随第一个真实调用点落地" |

即：该实体是 `core/authz` 的**第一个真实调用点**，缺它则 `AC-22`（跨账号访问被拒、两个对象档案互不可见）与 `AC-02` 都无可判定。

### 本轮查出并修正的两处既有缺陷

**缺陷一：账号注销的真删清单遗漏了档案与对象。** [认证与账号](../technical-details/认证与账号.md)第 8 节原列五项（身份用户、会话、FalkorDB 图、待处理记录、删除账本行），而需求原文 `RQ-ACC-08` 要求删除"身份、会话、通用记忆、**档案**、待处理写入"，`AC-24` 写"其**档案**与待处理写入记录不再存在"——**清单与验收对不上**。已补入三项（支持对象含已归档者、会话‑对象绑定、全部档案条目），并声明第 3 步必须早于"删除身份用户"，否则 `account_id` 再也无法用于定位。

**缺陷二：`cli` 白名单到不了 `profile`，且文档与机械检查本身不一致。** [项目结构设计](../../项目结构设计.md)第 7 节给 `cli` 的白名单是 `core/*` 与 `modules/{library,accounts}`；而机械检查 `apps/api/tests/test_layer_boundaries.py` 的 `ALLOWED["cli"] = {"campfire.core", "campfire.modules.library"}`——**连 `accounts` 都不在其中**。这直接影响注销：注销经运营 CLI 执行，要删档案与对象就必须能 import `profile`；而 `modules/*` 之间**禁止互相依赖**，因此跨 `accounts`／`profile`／`memory` 的注销编排**没有任何单个模块能承担**，只能落在能同时 import 多个模块的 CLI 入口。这需要一次定调级修正（涉及 `accounts` 现有"账号注销编排"这一用例的归属），**未随本次修改**，登记于[设计待办](../../TODO.md)。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| 仅创建与切换 | 对象一旦建立就永不错误 | 误建与错名永久留在切换器里；未说明为何不能改 |
| 创建 + 改名 + **硬删除** | 必须能真正移除对象 | 在途 `pending_write` 无法区分"已删"与"从未存在"→ **删后复活**；须再建一套墓碑或排空机制，成本与账号注销同量级 |
| **创建 + 改名 + 归档（选定）** | 需要可逆、且不愿引入破坏性语义 | 多一个可空时间列与"归档对象不收写入"一条规则；已归档行永久留存 |
| 实体放 `core` | 若它是跨切机制 | 支持对象是**业务实体**（一个人），`core` 现有共用表 `pending_write` 是**投递机制**不是实体；让 `core` 装业务实体会与其身份相悖 |

## 决定与影响

**形状**（详见[支持对象](../technical-details/支持对象.md)）：`id`、`account_id`、`display_name`、`created_at`、`updated_at`、`archived_at`。索引两条；**不建唯一约束**（同账号两个同名对象是真实情形）；`display_name` 的非空判据落**存储层 CHECK**；`account_id` **不建外键**（身份服务的表由 core 拥有，跨进程外键不可靠）。

**`display_name` 与档案"偏好称呼"是两个事实**，不合并、不互相推导：前者是导航标签、不进咨询上下文、必填；后者是关于这个人的一条事实、进注入、选填。

**授权端口的两个函数**：`require_owned` 与 `require_writable`。用两个具名函数而非布尔参数，是因为布尔参数在调用点读不出语义，而读写写错方向的后果不对称；抛错而非返回 `bool`，是因为返回值可以被漏检，而 `AC-22` 的判定不能靠调用方自觉。

**失败语义**：对象不存在与不属于当前账号的**对外文案逐字相同**（区分二者等于提供对象枚举通道，与登录限流"不区分账号不存在与密码错误"同一条纪律）；已归档而走写路径则**明确区分**（属主自己的对象，告知归档状态不泄露信息，且使用者需要知道才能去恢复）。

**绑定表**：`campfire_session_object(session_id PK, account_id, support_object_id, bound_at)`。"默认沿用上一次的选择"由 `bound_at` 最大者推导、无历史时回退到创建最早的在用对象；**不新增"账号当前对象"字段**——那会成为第二个可写真源。

## 重访条件

- **`cli`／注销编排的依赖白名单**落地时（见"缺陷二"）→ 届时重估 `accounts` 的"账号注销编排"用例归属；这也可能牵动 `core/authz` 实现的位置。
