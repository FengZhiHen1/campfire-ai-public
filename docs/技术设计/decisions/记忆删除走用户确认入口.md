# 记忆的删除与纠正走用户确认入口，不做模型工具

> **决定**：通用记忆的「查看 / 纠正 / 删除」（`RQ-MEM-03`）由**用户确认入口**承载——记忆面的 HTTP 契约（查看列表 + 删除 + 纠正），**不新增 `delete_memory` 模型工具**。模型可见的写入工具只有 `write_memory`，与档案侧的 `propose_profile_item` 对称；`AC-08` 的验收对象是**读取路径**（删除后两条读路径都不再返回），不要求模型能触发删除。**理由**：与档案侧对同一问题的既有裁决定于同一分工——[个性化档案](../technical-details/个性化档案.md)第 8 节写明「`confirm`、`correct`、`delete` 的调用方是**档案面与对话页的确认入口**（HTTP），**不是模型可见工具**」，并给出「模型推断进候选、使用者确认才进稳定层」正是靠这条分工成立的理由；`RQ-MEM-03` 的施事者原文也是「**使用者**可查看、纠正与删除」，而非模型。**被否决项**：把 `delete_memory` 做成模型可见工具；「模型只能提议删除、用户确认后由 HTTP 执行」的两段式。
> **状态**：**2026-09-30 经用户裁决**。这是对 `TECH-22 ②`「删除/纠正的接口所有者」的关闭决定。不代表已实现。

## 上下文与证据

`AC-08` 要求「删除一条记忆后，两条读取路径（时间线回看与应急预注入）都不再返回」。机制层已落地：`modules/memory/deletion.py` 的 `delete_episode` / `correct_episode` 两个用例 + 端到端集成测试（含用消融验证两条读路径各自被独立钉住）。缺的是**谁调它**——[技能设计](../technical-details/技能设计.md)第 3 节的七个工具里只有 `read_memory` / `write_memory`，`tools/` 下无 `delete_memory` 契约，登记于 `TECH-22 ②`。

四条证据共同指向「用户确认入口」：

| 证据 | 原文要点 | 出处 |
|---|---|---|
| 同类问题的既有裁决 | `confirm`/`correct`/`delete` 的调用方是**档案面与对话页的确认入口（HTTP），不是模型可见工具**；「模型推断进候选、使用者确认才进稳定层」靠这条分工成立 | [个性化档案](../technical-details/个性化档案.md)第 8 节 |
| 需求的施事者 | 「**使用者**可查看、纠正与删除通用记忆与档案条目」 | [功能需求与验收](../../需求/功能需求与验收.md) `RQ-MEM-03` |
| 一期流程图 | 「登录 → 首页 → 应急/日常咨询 → 案例浏览 → **档案与记忆的查看 / 纠正 / 删除**」 | 同上，第 1 节 |
| 工具返回不含标识 | `read_memory` 每条只返回「时间、内容原文、来源会话标识、写入状态」，**没有 episode 标识**——模型无从指名要删哪条 | [read_memory](../面/consult/tools/read_memory.md)第 3 节 |

**第四条的推论很硬**：若要做成模型工具，必须**同时修改一个已确认的契约**（给 `read_memory` 的返回加标识），而该契约当前刻意为模型裁掉了它不需要的字段。

**顺带修正一处现存不一致**：`profile-curation` 第 3.2 节第 6 条写「使用者说『这条不对/删掉』，要立即反映到稳定层与后续输出」，但该 skill 的 `allowed-tools` 是 `read_profile_items propose_profile_item read_memory write_memory`——**不含任何删除工具**。该条是纯语义要求（「不得推迟到下次整理」），其机制承载是确认入口的 HTTP 路径，不是模型工具；本条裁决使这层含义显式。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **用户确认入口（HTTP），不做模型工具（选定）** | 删除是使用者的显式意图，且 `AC-08` 的验收对象是读路径 | 需要记忆面的 HTTP 契约与一个承载页面；对话里说「删掉那条」不能由模型直接办成，须引导到确认入口 |
| 模型可见的 `delete_memory` 工具 | 对话内直接办成最顺滑 | 与档案侧已记录的裁决定相反；必须给 `read_memory` 返回加标识（改已确认契约）；模型获得对用户数据的**不可逆删除权**，与「模型不得自行认定用户意图」的既有立场冲突 |
| 两段式：模型只提议、用户确认后 HTTP 执行 | 兼顾顺滑与安全，与「推断进候选」同构 | 新增一套「待确认删除」状态与机制（第三张状态表或复用候选层），概念数明显增加；一期删除量小，收益不抵成本 |

**为什么两段式被否决**：它与档案候候选层的类比看似成立，但档案候选之所以需要独立状态，是因为**推断的准确性本身不确定**（所以要让使用者裁决）；而「用户说删掉」的意图是确定的，缺的只是「哪一条」的指认——指认靠界面列表比靠模型转述更可靠。为一期低频操作引入一张状态表属过度工程。

## 决定与影响

**决定**：新增**记忆面**（HTTP 契约：列表 / 删除 / 纠正），模型工具清单**不变**（仍为七个）。

由此**新产生的未成文项**（登记于[设计待办](../../TODO.md)）：

- **记忆面的 HTTP 契约尚未成文**（列表返回是否暴露 episode 标识、删除与纠正的入参、二次确认的语义归属）。
- **记忆的查看/纠正/删除页面尚未成文**：`docs/design/pages/` 已有 `档案页.md`，无记忆页；tab 栏固定四项（首页 / 咨询 / 档案 / 我的，见[首页](../../design/pages/首页.md)），放置位置需一并决定。
- **标识暴露面的分层**：UI 需要稳定标识才能指名删除，而 `read_memory` 的工具返回刻意不含标识——HTTP 侧需要另定（不是简单地把工具返回加宽，否则等于把不变量让给了模型可见面）。

## 重访条件

- 出现「使用者希望**在对话中**直接删除记忆」的真实反馈，且引导到确认入口被实测证明不可接受（例如多轮对话中反复需要删除）——届时重估两段式，而不是直接给模型删除权。
- 记忆面的 HTTP 契约成文时，若发现「列表 → 指认 → 删除」的形状在移动端不成立（例如列表项无法稳定对应一条 episode），回到本条重新评价承载者。
