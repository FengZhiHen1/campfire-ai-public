# DSR-007：以支持对象与事项重定模块边界

> **决定**：目标模块按公开支持、私人事项、个人空间、记录、受限交接、计划、证据与演练划分，保留现有语言、Web、关系库及前端五层；旧 emergency/profiles 的一比一业务镜像不再是目标边界。**理由**：新需求把人、事、授权关系与发布责任分离，旧档案家属所有权及行为桶边界无法表达。**被否决项**：沿用旧模块与四层档案，只在每个模块局部加授权字段。
> **状态**：2026-09-26 用户授权自主收敛产品与架构；目标态待迁移，不宣称代码已实现（旧实现已归档）。

## 上下文与证据

原 `DSR-006` 的模块镜像建立在 emergency/crisis/profiles/cases/tickets/knowledge 与单角色、家属档案、行为桶会话之上。当时让 API 模块、Agent 扩展及前端特性完全一比一，确实减少归属选择。现已确认 `RQ-SP-01～05` 的支持对象与账号分离、`RQ-CTX-03/06` 的私人事项与空间分开、`RQ-PLAN-03` 的条目级停用；读到的 `profiles.caregiver_id` 与咨询 `bucket` 必填进一步证实旧对象不承载上述语义。新证据击败的是**旧边界轴适用性**，不是 Python/FastAPI 或物理五层的价值。

## 备选与评价

| 方向 | 保留的价值 | 代价或风险 |
|---|---|---|
| 沿用旧模块并增加授权字段 | 改动面看似小，可复用旧 API | 家属所有权、对象归属与输出契约仍贯穿旧模块，容易出现双权限真相、影子档案和草案误发布 |
| 重新划分业务域但保留技术栈与稳定层次（选定） | 授权、事项、记录与计划各有状态所有者，可按阶段迁移 | 需要新 schema、接口版本、数据清点与旧入口过渡 |
| 一并换成微服务或新前端 | 边界物理隔离显著 | 1–3 人团队引入分布式一致性与部署负担，不能解决合法授权证据缺口 |

## 决定与影响

目标项目级定调由 [技术栈设计](../../技术栈设计.md) 与 [项目结构设计](../../项目结构设计.md) 拥有；[机制](../technical-details/README.md)按新对象与失败语义落实。沿用 React Web 先行、小程序冻结、PostgreSQL/pgvector、Redis 与现有可重用 Agent 内核，但商业能力不以 Agent 扩展数量作为结构轴。`DSR-006` 的前端五层、厚包薄入口等经验证有用的部分继续适用；“所有模块 1:1 镜像旧机制”和“安全扩展首位即足以保证强制授权”的前提不再适用。接口迁移使用 `/api/v2`；旧 `/api/v1` 实现已归档，不参与新目标。

## 重访条件

若新的业务域在实践中始终共同修改、缺乏独立不变量，且跨模块事务导致大量重复协调，则合并实际相邻模块；若新的独立前端渠道产生真实需求，再重审共享包边界。重访应以变更耦合、越权测试和维护成本为证据，而非以旧目录先存在为理由。
