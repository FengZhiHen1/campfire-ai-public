# 账号注销：内容真删，保留不含内容的墓碑

> **决定**：一期**支持账号注销**，经运营 CLI 执行（不提供自助注销）。处置分三段——① 身份用户、全部会话、该账号的 FalkorDB 图、待处理写入记录、该账号的删除账本行**真删**；② **保留一条注销墓碑**（新表，归 `core/auth`，只含账号标识、时间、原因，**不含任何用户内容**）；③ 图库物理残留随整张图丢弃，不等增量清理。**理由**：内容必须真删（`RQ-MEM-03` 的删除语义）；但**不能删得无迹可寻**——在途写入需要一条"该账号已注销"的判据，否则 Worker 查不到账号时无法区分"已注销"与"从不存在"，会把数据写回已删账号的图。**被否决项**：连墓碑一起删（留下"删后复活"窗口，须另做排空队列来补）；整体软删除（数据物理上仍在，只是读不到，与"删除须覆盖检索与衍生"的验收口径冲突）。
> **状态**：**2026-09-29 经用户裁决**。这填补了一个**下游已假定存在、上游从未定义**的能力——[通用记忆](../technical-details/通用记忆.md)第 1 节把"账号注销时失效"写进不变量，`campfire_memory_deletion_ledger` 的 `reason` 词表也已预留 `account_deletion`（存储层已实现），而需求稿与认证文档此前**零条**关于账号注销。不代表已实现。

## 上下文与证据

**这不是"缺一个功能"，是"下游依赖不存在的上游事件"**：

| 位置 | 内容 | 问题 |
|---|---|---|
| [通用记忆](../technical-details/通用记忆.md)第 1 节 | "按账号缓存驱动（有界缓存 + **账号注销时失效**）" | 把不存在的能力当既成事实写进不变量 |
| `modules/memory/models.py` | `DELETION_REASON_ACCOUNT_DELETION = "account_deletion"` | 词表已预留，且有 CHECK 约束；但无触发方 |
| [通用记忆](../technical-details/通用记忆.md)第 7 节 | 表结构注释 `reason # user_request \| correction \| account_deletion` | 同上 |
| 需求稿 / 认证与账号 | **零条** | 能力无定义、无验收 |

**同时补齐登出**：这是另一类缺口——机制**已经存在**，只是文档没写。[认证与账号](../technical-details/认证与账号.md)第 5 节自己列出 `/auth/*` 含 signout；官方《Session Invalidation》原文写明 `revokeSession()` "will delete the session from the db and from the frontend (cookies)"。原第 10 节排除的是"会话管理界面（查看与登出**其他设备**）"，**当前设备的登出**从未被写下来，需求与验收也没有它。

**软删除为什么不是第三个选项**（本轮辨析）：软删除的两个常见动机——可恢复、保留审计——在本项目里分别不成立与已被覆盖。① 账号注销的用户意图是**永久的**，保留可恢复副本与 `RQ-MEM-03` 相悖；② "保留审计痕迹"**正是"墓碑"这条**，所以真正要选的只是"留不留、留什么"。而本项目删除记忆的常态**本身就是软删除**（账本过滤是唯一生效点，图库物理删除已延期），因此账号级如果再做软删除，等于在一个已经偏软的系统上再叠一层，却不解决任何新问题。

**账号级删除在技术上比单条删除更干净**：`group_id` 在 FalkorDB 后端**就是图名**（[通用记忆](../technical-details/通用记忆.md)第 1 节实测），`MemoryGraph.driver_for(account_id)` 按账号取图——**丢掉整张图是一次完整操作**，不受"共享边"与"物理清理延期"两条约束。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **内容真删 + 墓碑保留（选定）** | 需要"在途写入不复活"的判据 | 对外不能声称"已删除全部数据"；墓碑是第二个关于该账号的记录 |
| 全部真删（含墓碑） | 必须能字面承诺"删净" | Worker 无法区分"已注销"与"不存在"→ **删后复活**；须补"注销前排空队列"，成本更高 |
| 整体软删除（标记注销，不物理删） | 需要可恢复与完整审计 | 数据物理上仍在、不再可读；与 `RQ-MEM-03`"删除须覆盖检索与衍生"的验收口径需重新对齐 |

## 不变量

1. **顺序不可调换**：先写墓碑 → 删未领取的 `pending_write` → 撤销全部会话 → 删身份用户 → 丢弃账号图。**墓碑必须先写**，否则中间窗口内的消费会把数据写回。
2. **Worker 领取时必须重新判定账号是否已注销**（墓碑即为判据）。这是[写入路径](../technical-details/写入路径.md)第 6 节"授权在写入前被撤销 → 领取时重新判定"在注销场景下的落地。
3. **墓碑归 `core/auth`，不新建模块、不并入删除账本**。判据是依赖白名单而非偏好：Worker 只允许 import `core/*` 与 `modules/{profile,memory}` 且**禁止回查业务用例**（[项目结构设计](../../项目结构设计.md)第 7 节），故墓碑**不能**放 `modules/accounts`；而请求路径与 Worker **都要读**它。不放删除账本的理由是列约束：`episode_key` 为 `NOT NULL` 且 **UNIQUE**、语义为"某条 episode 被删"，墓碑不对应任何 episode。
4. **墓碑不含任何用户内容**：只有账号标识（不透明 UUID）、时间、原因。删除账本的 `episode_key` 是 UUID5 派生、不可反推原文。
5. **注销不可逆**：CLI 须要求显式确认，不提供撤销。它不是登出、也不是停用。

## 已知残余窗口（如实写明）

第 1 步与第 5 步之间仍有极窄竞态：Worker 可能在"读墓碑（尚无）"之后、图被丢弃之前完成写入，从而**重建**该账号的图。

**后果有界**：该账号已不存在、无人能以其身份登录，读路径一律按登录态取数，故重建的图**不可经应用读取**——属存储残留（`EVID-D` 范畴），**不是数据泄露**。彻底闭合需每账号锁或"写入后校验"，一期不做；**须实测确认窗口可接受**（登记于[设计待办](../../TODO.md)）。

## 重访条件

- 实测显示**残余窗口**（墓碑写入与图丢弃之间）可被触发且后果不可接受——届时不加锁，而是**优先改为"注销前排空队列"**（先停止该账号的写入、再删除），因为那消除的是竞态本身而非加一层互斥。
- 出现**自助注销**的真实需求（例如二期有了邮箱通道）——届时须补自助流程的身份确认与冷静期，而不是把运营 CLI 直接开放给使用者。
- 出现**字面承诺"已删除全部数据"**的合规要求——届时须一并删除墓碑，并同时落地排空机制，否则承诺不成立。
