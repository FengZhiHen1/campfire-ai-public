# 账号注销：内容真删，保留不含内容的墓碑

> **决定**：一期**支持账号注销**，经运营 CLI 执行（不提供自助注销）。处置分三段——① 身份用户、全部会话、该账号的 FalkorDB 图、待处理写入记录、该账号的删除账本行**真删**；② **保留一条注销墓碑**（新表，归 `core/auth`，只含账号标识、时间、原因，**不含任何用户内容**）；③ 图库物理残留随整张图丢弃，不等增量清理。**理由**：内容必须真删（`RQ-MEM-03` 的删除语义）；但**不能删得无迹可寻**——在途写入需要一条"该账号已注销"的判据，否则 Worker 查不到账号时无法区分"已注销"与"从不存在"，会把数据写回已删账号的图。**被否决项**：连墓碑一起删（留下"删后复活"窗口，须另做排空队列来补）；整体软删除（数据物理上仍在，只是读不到，与"删除须覆盖检索与衍生"的验收口径冲突）。
> **状态**：**2026-09-29 经用户裁决**。这填补了一个**下游已假定存在、上游从未定义**的能力——[通用记忆](../technical-details/通用记忆.md)第 1 节把"账号注销时失效"写进不变量，`campfire_memory_deletion_ledger` 的 `reason` 词表也已预留 `account_deletion`（存储层已实现），而需求稿与认证文档此前**零条**关于账号注销。不代表已实现。

**同时补齐登出**：这是另一类缺口——机制**已经存在**，只是文档没写。[认证与账号](../technical-details/认证与账号.md)第 5 节自己列出 `/auth/*` 含 signout；官方《Session Invalidation》原文写明 `revokeSession()` "will delete the session from the db and from the frontend (cookies)"。原第 10 节排除的是"会话管理界面（查看与登出**其他设备**）"，**当前设备的登出**从未被写下来，需求与验收也没有它。

**软删除为什么不是第三个选项**（本轮辨析）：软删除的两个常见动机——可恢复、保留审计——在本项目里分别不成立与已被覆盖。① 账号注销的用户意图是**永久的**，保留可恢复副本与 `RQ-MEM-03` 相悖；② "保留审计痕迹"**正是"墓碑"这条**，所以真正要选的只是"留不留、留什么"。而本项目删除记忆的常态**本身就是软删除**（账本过滤是唯一生效点，图库物理删除已延期），因此账号级如果再做软删除，等于在一个已经偏软的系统上再叠一层，却不解决任何新问题。

**账号级删除在技术上比单条删除更干净**：`group_id` 在 FalkorDB 后端**就是图名**（[通用记忆](../technical-details/通用记忆.md)第 1 节实测），`MemoryGraph.driver_for(account_id)` 按账号取图——**丢掉整张图是一次完整操作**，不受"共享边"与"物理清理延期"两条约束。

## 不变量

1. **顺序不可调换**：先写墓碑 → 删未领取的 `pending_write` → 撤销全部会话 → 删身份用户 → 丢弃账号图。**墓碑必须先写**，否则中间窗口内的消费会把数据写回。
2. **Worker 领取时必须重新判定账号是否已注销**（墓碑即为判据）。这是[写入路径](../technical-details/写入路径.md)第 6 节"授权在写入前被撤销 → 领取时重新判定"在注销场景下的落地。
3. **墓碑归 `core/auth`，不新建模块、不并入删除账本**。判据是依赖白名单而非偏好：Worker 只允许 import `core/*` 与 `modules/{profile,memory}` 且**禁止回查业务用例**（[项目结构设计](../../项目结构设计.md)第 7 节），故墓碑**不能**放 `modules/accounts`；而请求路径与 Worker **都要读**它。不放删除账本的理由是列约束：`episode_key` 为 `NOT NULL` 且 **UNIQUE**、语义为"某条 episode 被删"，墓碑不对应任何 episode。
4. **墓碑不含任何用户内容**：只有账号标识（不透明 UUID）、时间、原因。删除账本的 `episode_key` 是 UUID5 派生、不可反推原文。
5. **注销不可逆**：CLI 须要求显式确认，不提供撤销。它不是登出、也不是停用。

## 已知残余窗口（如实写明）

第 1 步与第 5 步之间仍有极窄竞态：Worker 可能在"读墓碑（尚无）"之后、图被丢弃之前完成写入，从而**重建**该账号的图。

**后果有界**：该账号已不存在、无人能以其身份登录，读路径一律按登录态取数，故重建的图**不可经应用读取**——属存储残留（`EVID-D` 范畴），**不是数据泄露**。彻底闭合需每账号锁或"写入后校验"，一期不做；**须实测确认窗口可接受**（登记于[设计待办](../../TODO.md)）。

## 排除理由：`campfire_citation`（引用索引）不随注销清除

**2026-10-07 用户裁决**：`campfire_citation` **没有删除路径**，但**不补**——它登记为
**审计凭据**，且**不含个人内容**，故**明确排除在注销的真删清单之外**。下面写的是
**为什么它不需要随注销清除**（不是「我们忘了删」，也不是一条改动记录）。

**它是什么**：表自述为「引用索引：注入项的可回指凭据（**不是对话的第二份真源**）」
（`core/db/citations.py` 的表注释）。它是**索引**，不是对话或使用者内容的副本；权威在
会话消息与业务条目本身（[通用基座](../technical-details/通用基座.md)第 2 节的同一口径）。

**它的列**：`citation_id` / `seq` / `run_id` / `source` / `reference` / `recorded_at` /
`summary`。★ **没有 `account_id`，也没有 `session_id`**——即这张表在形状上**没有一列
用来表达「这条引用属于谁」**。

**它装什么**：它装的是**指针**——「这轮引用了共享资料库的哪一条」，指向共享库条目
（`knowledge:<uuid>` / `case:<uuid>`），**不含使用者正文**。

**⚠ 关于「谁往这张表写」，两个写入者分属两个不同代码基线**（不标注就会自相矛盾）：

| 写入者 | 落点 | 基线 |
|---|---|---|
| 检索工具命中条目时发凭据 | `tools/library.py` 的 `_mint_citations` → `record(source=…, reference=f"{source}:{item_id}")` | **仅工作树**（`git show HEAD:tools/library.py` 对 `record(`/`_mint_citations` 命中 **0**；2026-10-07 随 T36/T38 在途） |
| 注入项渲染时逐条记录 | `agent/context/injection.py` 的 `InjectionBatch.render` → `recorder.record(...)` | **已在 HEAD**，但被 `if item.reference is not None` 守住 |

⇒ **在 HEAD 上这张表没有活的生产写入者**；在**当前工作树**上，**唯一会真正落行的是检索工具**
（实测 **8 处** `InjectionItem` 构造点**无一处**传 `reference`：`injection.py` 的
`injection-status` 项、`runner.py` 的当前时间／技能目录／技能激活三项、`scope.py` 的可用性项、
`surfaces/consult/injections.py` 的两项、`routes.py` 的 `_notice_item`）。

**它现在有几行**：3 行，全部来自探针（`run_id = probe-288142f1614242e39300fb12893a9e03`）。

### 为什么它不需要随注销清除（两条理由，判据都落在**注销动作**上）

**理由一（承重）：注销会真删 `campfire_session` 的归属行，而「`run_id` 走回账号」所依赖的
正是那一行 ⇒ 注销之后该关联断开。**

`agent_messages` 只有 `session_id`（无账号列），要走到账号必须经
`campfire_session.account_id`（`modules/accounts/session_repository.py` 的
`outerjoin(AgentSession, …)` 就是这条 join 的形状）。而注销第 4 步的 `SessionAccountPurger`
**真删该账号的全部归属行**（`delete(CampfireSession).where(account_id == …)`，
`session_repository.py:462`；清除者清单见 `cli/operator.py`）⇒ **join 的右端在注销后消失**。

**★ 已核第二处同类映射，同样被真删**（避免「只查了一处」的漏洞）：`campfire_session_object`
（`profile` 模块的 `SessionObjectBinding`，主键 `session_id`、带 `account_id`）是另一条
`session_id → account_id` 的通道，由 `ProfileAccountPurger` 在注销第 4 步一并真删
（`delete(SessionObjectBinding).where(account_id == …)`，
`modules/profile/repository.py`）⇒ **两处会话归属映射都在注销时消失**，无遗漏的旁路。

**⚠ 由此得到的分时结论（本节关键，不得压成一句）**：

- **注销之后**：承载归属的那一行已被真删 ⇒ **数据库侧没有任何可查询路径能从 `run_id`
  （或 `citation_id`）走到账号**。**这才是本排除理由站得住的依据。**
  **⚠ 但「注销之后」不等于「注销那一瞬间之后」**：Redis 的 `RunMeta`（含 `account_id`）
  是**独立于注销**的临时键，**TTL 600 秒**（`RUN_BUFFER_TTL_SECONDS`），而**注销侧对
  Redis 零引用**（`core/auth/deletion.py` 与 `cli/operator.py` 的清除者清单里
  `cache`/`redis` 命中数为 **0**），`meta_key` **没有任何删除点、也没有清扫任务**
  ⇒ **注销后的 ≤600 秒内，该键仍可能把 `run_id` 连到账号**。
  **⇒ 准确表述是「注销且运行缓冲到期之后」**，不是「注销之后」。
  **该窗口有界且自愈**（600 秒后 Redis 自行过期），**故不改变排除结论**；
  但**若将来要求「注销即刻断开一切关联」，须把 Redis 清理纳入注销编排**（列为待办）。
- **注销之前**：`run_id` ↔ 账号 的关联**确实存在**，但它**不是这张表的性质**：
  它活在 Redis 的 `RunMeta`（`surfaces/consult/runbus.py`，字段
  `run_id`/`session_id`/`account_id`/`status`）里，而那是**传输层**临时键、**TTL 600 秒**
  （`RUN_BUFFER_TTL_SECONDS`）；**此外引用载荷还有一条通道会随会话条目落库**（见下方边界 2）
  ⇒ **注销之前它确实可关联到账号**。
  ⇒ 本排除理由**不依赖**「注销前也无关联」，故**不受该通道影响**：
  **排除的判据是「注销后断开」，不是「从来无关联」。**

**理由二：删这些行是净损失。** 设计上它承担的不变量是
（[通用基座](../technical-details/通用基座.md)第 4 节）：「每条注入消息在引用索引表里留一条
对应记录……因为输出里的引用要靠它回指」；「**没有索引记录的注入消息不得成为可引用依据**」。
⇒ 删掉这些行**不会**让任何使用者内容留存，却会**破坏「输出里的引用可回指」这条不变量**。

### ⚠ 本排除理由的两条边界（如实标注，不得读成「它肯定不含个人数据」）

1. **「不含个人数据」是【依据列形状与写入点的推断】，不是实测结论。**
   证据是两条：**列清单里只有 `run_id`/`source`/`reference`**（无账号、无会话列），
   且 `reference` 由检索工具写成 `f"{source}:{item_id}"`、**指向共享库条目**。
   推断的强度依赖「写入者不往里写别的东西」——这是**对当前代码的观察**，不是对表的
   结构性保证（`summary` 是 `Text`、`reference` 是 `Text`，**结构上容得下自由文本**）。
2. **★ 「注销之前 `run_id` 与账号无关联」【不成立】，该通道此刻就在工作树里。**
   引用载荷的另一条通道是**会话条目**：`agent/runtime/session_annotations.py` 的
   `citation_annotation()` 把 `run_id` 一并写进注解，由 `CitationAnnotatingSession`
   挂在助手正文分片（`output_text`）的 `annotations` 上、**随会话条目落库**
   （装配点在 `agent/runtime/runner.py`）——**而 `agent_messages` 可经 `session_id`
   join 到 `campfire_session.account_id`** ⇒ **注销之前 `run_id` 可走回账号**。
   **该机制不在 HEAD 上**（`session_annotations.py` 是未跟踪文件、`runner.py` 的包装
   不在 `HEAD`），属 2026-10-07 的在途改动；**本仓在途探针已实测该载荷落库后逐字读回保真**
   （`docs/证据/probes/t38/probe_roundtrip.py` 用真 `SQLAlchemySession`，产物
   `docs/证据/probes/t38/probe_roundtrip.txt` 记「逐字保真: True」且 raw 里 `"run_id": "r-1"` 可见；
   **2026-10-07 由 `tmp/t38/` 迁出**，原 `tmp/` 已清空）。
   同一结论也写在 [HTTP/SSE 契约](../面/consult/HTTP与SSE契约.md)第 7.1 节
   （「引用载荷必须落在会话条目里」；同节还写明该载荷对模型不可见——输入转换器只取
   `text`、整段 `annotations` 被忽略）；读侧亦已按此口径实现
   （`modules/accounts/session_items.py` 的引用重建注明「**水合真源就是会话条目本身**」）。
   **⇒ 因此本条不是「将来才会失效的条件」，而是「此刻已成立的事实」，只是它由
   「注销删归属行」兜住**（理由一）。**若将来 `agent_messages` 不再随注销失去归属行
   （例如改成不删归属行、或另建可持久 join 的映射），本排除理由即失效。**
   另：本包**未在本机库中读到含 `run_id` 的会话条目**（两次读数均为 0 行；
   正控 `annotations` 字样在同一命令下命中），即**通道已通、当前尚无该载荷落库**。

### ⚠ 重访条件（本排除理由的失效条件）

- **若将来有别的写入者往这张表里写使用者私有内容，本排除理由即失效**，须重新裁决。
  **⚠ 这个条件不是假设：代码里已经存在第二处 `record(...)` 调用点**
  （`agent/context/injection.py` 的 `InjectionBatch.render`），它当前被
  `if item.reference is not None` 守住、而**生产侧 8 处 `InjectionItem` 构造点无一传 `reference`**
  ⇒ **此刻只有检索工具会真正落行**。一旦有人给其中某条注入项补上 `reference`，
  本排除理由的第 1 条边界就要重估。
- **若「注销后 `run_id` 走不回账号」不再成立**——即承载归属的 `campfire_session` 行
  不再被注销真删，或另建了一条**不随注销清除**的 `run_id` ↔ 账号 映射
  （落表、或让该载荷留在不随注销失去归属的载体里）⇒ 本条结论失效。

### ★ 对外口径：注销是「撤销不可达」，不是「删净」（2026-10-07 用户裁决）

**⚠ 这条与本决策文档原有的「内容真删」措辞有张力，如实记在这里以免被读成矛盾。**

**事实（三路独立核实）**：账号注销**不删除对话内容**——`agent_messages` / `agent_sessions`
是 SDK 拥有的两张表，注销的三个领域清除者**都不碰它们**；`SessionAccountPurger` 的
docstring 自述「**为什么不删 SDK 的两张表**：那两张表的内容由 SDK 拥有，且会话撤销
（经身份服务）已让它们**不可达**；本 purger 只负责业务侧的归属行，**不越界**」，
它实际执行的是 `delete(CampfireSession).where(account_id == …)`
（`modules/accounts/session_repository.py`）。**正控**：全仓 `delete(RetrievedNode` 命中
**5** 处（搜索方法有活性），而 `delete(AgentMessage)` / `delete(AgentSession)` **0 处**。
⇒ **使用者与模型的对话正文在注销后仍物理留在库里**，只是**经身份服务撤销会话后不可达**。
