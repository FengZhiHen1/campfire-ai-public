# 会话校验逐请求查证数据库，接受 core 进入鉴权关键路径

> **决定**：会话校验以 `check_database=True` **逐请求查证数据库**，该查证经 SuperTokens core 执行；**core 因此位于鉴权关键路径**，其不可用时全部受限操作不可用（fail-closed）。**理由**：已确认的 `AC-17` 要求"运营者重置密码后，重置前签发的所有会话立即失效"，而无状态校验下被撤销的 access token 在到期前仍然可用——即时撤销与"鉴权不经 core"不可兼得，`AC-17` 是已确认需求，因此放弃后者。**被否决项**：混合校验（敏感操作强校验、普通请求维持无状态——须改写 `AC-17` 为"有界延迟失效"）；保持无状态并把 `AC-17` 降级为"有界延迟失效"；由我们自行读取 SuperTokens 的会话表来绕开 core。
> **状态**：**2026-09-29 经用户裁决**。这是对[技术栈设计](../../技术栈设计.md)第 2 节"会话校验在 Python SDK 内完成、不经过 core……core 只在注册、登录、重置、刷新时被调用"的**实质修正**，并删除了由该表述派生的可用性承诺。不代表已实现。

## 上下文与证据

[认证与账号](../technical-details/认证与账号.md)原稿内部存在矛盾，两句话都写在同一份文档里：

| 位置 | 原文 | 蕴含 |
|---|---|---|
| 第 2 节组件表与可用性段 | 「每个请求的鉴权——**会话校验在 Python SDK 内完成，不经过 core**」「core 挂掉只影响注册、登录、重置与刷新，不影响已登录用户继续使用」 | 鉴权路径上无 core |
| 第 5 节 | 「**会话必须可由服务端即时撤销**（`RQ-ACC-06`）：这是"人工重置"能成立的前提」 | 鉴权必须能感知撤销 |

**为什么两者互斥**（读 `supertokens-python` 源码确认，非推断）：

1. `recipe/session/recipe_implementation.py` 的 `get_session` 调用 `session_functions.get_session(..., (check_database is True), ...)`，即把该开关透传为 `always_check_core`；`check_database` 为 `None`（默认）或 `False` 时该值为假。
2. `recipe/session/session_functions.py` 的 `get_session` 仅在 `access_token_info is not None and not always_check_core and access_token_info["parentRefreshTokenHash1"] is None` 时**本地构造响应返回**；否则 `ProcessState.add_state(CALLING_SERVICE_IN_VERIFY)` 并 `POST /recipe/session/verify` → **经 core**。

官方文档给出同向结论：《Access token blacklisting》原文 "By default, session verification is stateless... if you revoke a session, the user can still use its access token until the token expires"；《User management》删除用户页亦写明 "Without `checkDatabase: true`, that token can continue to pass session verification until it expires"。两条官方表述指向同一机制，且有源码对应。

**因此**：要让撤销即时生效，`check_database=True` 必须开；开了之后 SDK 不自己查会话表，而是经 core 查——**"鉴权不经 core"必然不成立**。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **逐请求 `check_database=True`（选定）** | `AC-17` 必须按原文成立；且"授权不可用时拒绝"（fail-closed）是已确立不变量 | core 成为鉴权单点：其可用性与容量决定全站受限操作；每次鉴权多一次 core 往返与一次数据库读；原"已登录用户不受 core 影响"的降级承诺作废 |
| 混合：敏感操作强校验、普通请求维持无状态 | 能接受"改密后旧会话在普通只读路径上仍可用，直到 access token 过期" | 须把 `AC-17` 从"立即失效"改写为"有界延迟失效"，是修改一条已确认需求；且"哪些算敏感操作"成为需要长期维护的清单 |
| 保持无状态，`AC-17` 降级为有界延迟失效 | 把 core 的可用性看得比即时撤销更重要 | 同上，且重置的实际效果被削弱——撤销 refresh token 只能把窗口压到 access token 有效期内，需另行给出该时长取值 |
| 我们自行读 SuperTokens 会话表绕开 core | 拒绝接受 core 进入关键路径，又必须即时撤销 | 让会话数据的写入者（core）与读取者（我们）分离，形成第二定义；core 的 schema 变动直接破坏鉴权 |

## 不变量（实现层据此校验）

- **每个受限操作都必须开启数据库查证**，不得只在部分端点开启："校验方式不一致"会造出"某些接口撤销生效、另一些不生效"的隐蔽缺口。
- 数据库查证失败（core 不可达、超时）一律**拒绝**，不得回退到无状态校验通过——回退等于在故障时静默关闭撤销能力。
- 会话有效期（access token 与 refresh token）**不再承担"撤销窗口"职责**：撤销即时成立与该取值无关。该取值仍待定，属另一件事。

## 决定与影响

会话校验改为逐请求查证数据库并接受 core 进入鉴权关键路径；`AC-17` 与 `RQ-ACC-06` **零改动**——本次改的是技术机制与由此派生的可用性表述。

被本次裁决直接推翻的既有表述：

- [技术栈设计](../../技术栈设计.md)第 2 节认证行："**会话校验在 Python SDK 内完成、不经过 core**，core 只在注册、登录、重置、刷新时被调用"。
- [认证与账号](../technical-details/认证与账号.md)第 2 节："core 挂掉只影响注册、登录、重置与刷新，不影响已登录用户继续使用"。
- 同文档第 7 节失败语义表："身份服务（core）不可用 → 注册、登录、重置、刷新不可用；**已登录用户的请求不受影响**"。
- 同文档第 11 节验证方式："另需验证：**core 不可用时已登录会话仍可用**"——该验证项本身已作废，替换为"core 不可用时不存在任何仍可达的业务路径"。

## 重访条件

- core 的**可用性、容量或重启窗口**被实测证明不可接受（例如它成为主要故障源，或其往返把应急首字时延推出 `RQ-EMG-03` 的预算）——届时评估混合校验，并同步改写 `AC-17`。
- SuperTokens 提供**不经 core 的即时撤销**机制（例如 SDK 侧可验证的撤销清单），且我们能在不读取其内部表的前提下使用。
- `TECH-07` 核实结果显示 Session 相关能力被企业许可门禁影响，使 core 的部署与升级成本实质上升。
