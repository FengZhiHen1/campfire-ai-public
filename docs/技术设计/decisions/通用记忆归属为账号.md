# 通用记忆归属为账号，与支持对象无关

> **决定**：通用记忆是**关于使用者自身**的时间线经验，归属**账号**——分区键 `group_id = account_id`。记忆**不随支持对象分区**，也不随对话切换对象而改变；`write_memory` / `read_memory` 的参数去掉 `support_object_id`。**理由**：需求 `RQ-MEM-01` 的原文就是「关于使用者自身的低风险信息」，而外部框架（应急预取的稳定信息、档案领域架构）已完整承担「关于支持对象」的认识；两者混在同一个图库分区里，会让「使用者的偏好」与「当事人的特征」无法分别纠正与删除。**被否决项**：`group_id = support_object_id`（2026-09-29 前设计稿的取值，把记忆当作「对象的时间线经验」）；`group_id = account_id` 但保留 `support_object_id` 作可选过滤标签（一期没有「同一账号下对象各自记忆」的消费面，是无人使用的参数）。
> **状态**：**2026-09-29 经用户裁决**。这是对[功能需求与验收](../../需求/功能需求与验收.md)既有确认内容的**实质修正**（`RQ-MEM-07`、`AC-22`、业务概念表），不是措辞润色。不代表已实现。

## 上下文与证据

需求稿在这一点上**自身矛盾**，且矛盾被登记成了「措辞修正」：

| 位置 | 原文 | 主语 |
|---|---|---|
| [功能需求与验收](../../需求/功能需求与验收.md) `RQ-MEM-01` | 「关于**使用者自身**的低风险信息随咨询自动累积」 | 使用者 |
| [功能需求与验收](../../需求/功能需求与验收.md) 业务概念表 | 「关于**某个支持对象**的…时间线经验；随支持对象分区」 | 支持对象 |
| [功能需求与验收](../../需求/功能需求与验收.md) 第五节 | 记「概念表原『关于使用者自身』的措辞已修正为『关于某个支持对象』」 | —— |

即：原稿先写「使用者自身」，随后在概念表中被改成「支持对象」并记为措辞修正，而 `RQ-MEM-01` 的正文从未同步。设计阶段据此把 `group_id` 定为 `support_object_id`，并把「关于使用者自身的偏好」写为一期不做（[通用记忆](../technical-details/通用记忆.md)第 1、11 节）——**这一步修改了需求的主语，却没有留下决策记录**。

用户 2026-09-29 裁决：「通用记忆就是最普遍的用户记忆，和支持对象无关」——即回到 `RQ-MEM-01` 的原文主语。

**为什么两者必须分开**（本次裁决的实质理由，非偏好）：

1. **纠正与删除的粒度不同**。`RQ-MEM-03` 要求使用者可纠正与删除；记忆里混着「使用者怕吵」与「当事人怕吵」两类事实时，删除其中一条必须先判定它属于谁——而派生事实层（EntityEdge）不携带这个归属，账本也无法按它过滤。
2. **授权主体不同**。记忆属使用者、可以跨对象复用（换一个支持对象仍适用）；档案属支持对象。把记忆挂在对象下，等于让「使用者的偏好」随对象删除而消失。
3. **写入方不同**。记忆由 `write_memory` 写入、`profile-curation` 是唯一持有写工具的 skill；档案由 `propose_profile_item` 写入。两者共用同一图库分区会让「谁的记忆」无法从写入路径区分。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| `group_id = support_object_id`（原设计稿） | 需要「同一账号下不同对象的经验严格隔离」时 | 与 `RQ-MEM-01` 原文冲突；「关于使用者自身」的一期消费面丢失；换对象回看消失；删除粒度需要额外归属字段才能判定 |
| `group_id = account_id` + 可选 `support_object_id` 过滤（折中） | 二期出现「同一账号多对象、各自记忆视图」的真实需求时 | 一期没有该消费面，参数与过滤分支无人使用；`support_object_id` 必填与否成为无意义的选择 |
| **`group_id = account_id`，无对象维度（选定）** | 记忆是使用者自身的时间线，档案已独立承担对象维度 | 不保留对象维度；二期若真的需要按对象切分，须新增维度并回填 |

**不变量（本次裁决确立，实现层据此校验）**：

- `group_id` 由**当前登录账号**决定，**不接受调用方传入**。这直接消掉「忘记传分区键落到默认值」这一整类缺陷——Graphiti 在 `group_id is None` 时会回落到默认分区（FalkorDB 分支为 `'_'`），那会把所有账号并进同一分区。
- `read_memory` / `write_memory` 的归属校验从「`support_object_id` 必须属于当前账号」改为「**会话所属账号即分区键**」，越权访问的判定点因此前移到会话/账号层。
- 记忆**不因支持对象被删除而删除**；也不因切换对话对象而不可见。

## 决定与影响

记忆归属账号、分区键为 `account_id`、工具不再收 `support_object_id`；「关于使用者自身」的消费面由「一期不做」改为**一期就有**（这正是本次裁决要恢复的）。

下游被这次反转绑定的既有内容必须同批修订，否则文档内部再次互相矛盾：

- `RQ-MEM-07`「每个对象一份独立**档案**与独立**记忆**」→ 记忆不再随对象独立。
- `AC-22`「各自的档案与**记忆**互不可见」→ 保留档案部分，记忆改为账号级。
- 业务概念表的记忆定义与第五节「已定」条目 → 回到 `RQ-MEM-01` 的主语。
- [通用记忆](../technical-details/通用记忆.md)第 1、2、3、6、7、10、11 节。
- [read_memory](../面/consult/tools/read_memory.md)、[write_memory](../面/consult/tools/write_memory.md) 契约参数。
- [写入路径](../technical-details/写入路径.md) `pending_write` 的 `support_object_id` 字段（记忆类记录不再需要，档案类仍需要）。
- [技能设计](../technical-details/技能设计.md)、[咨询面](../面/consult/README.md)、三个 skill 的取数与参数描述。
- [项目结构设计](../../项目结构设计.md)第 6 节 `memory` 模块的用例行（去掉对象维度）。

**未随本次裁决解决的问题**：记忆机制另有若干与归属无关的落地缺口（episode 幂等的身份依据、两条读路径的取数 API、`invalid_at` 过滤与多来源边的删除语义、删除/纠正的接口所有者）。它们**不由本条 ADR 承担**，登记于[设计待办](../../TODO.md)第五节 `TECH-22`。

## 重访条件

- 出现「同一账号下按支持对象分别查看/隔离记忆」的**真实消费面**（例如多个对象的经验确实互相干扰，或使用者要求按对象清理记忆）——届时在 `account_id` 分区之上新增对象维度并回填，而不是回退到对象即分区。
- 记忆的使用者侧记录与支持对象的记录需要**分别满足不同的保留或授权规则**时（`EVID-C`/`EVID-D` 相关条款落地）——届时复核分区键是否还够用。
