# 检索链归入 library 模块

> **决定**：检索链整体归 `modules/library`——节点投影、向量路、字面路、RRF 融合、条目聚合与检索用例；`core/retrieval` 取消，嵌入模型的配置值（模型名、端点、凭据）仍由 `core/config` 拥有。**理由**：检索机制与其领域模式在实践上不可分——过滤维度（库别、`status`、`withdrawn`、`risk_class`、`ebp_tags`…）与聚合键（`item_id`、`card_id`）全是 library 与案例库的领域字段；只有一个模式实例时「通用机制」没有真实消费者。**被否决项**：保留 `core/retrieval` 为领域无关机制、由 library 实现字面检索器、`core` 定义 Protocol 并在 `tools` 装配——其「领域无关」声明与检索必须消费的领域投影清单互相矛盾。
> **状态**：2026-09-29 经用户裁决，是对[项目结构设计](../../项目结构设计.md)的实质变更。不代表已实现。

## 上下文与证据

[项目结构设计](../../项目结构设计.md)把 `core/retrieval` 定为跨切能力，把资料与案例的录入、撤下与检索用例归 `modules/library`。对该模块做依赖分析时暴露四处问题，其中第三、四处是实测证据而非偏好：

1. **领域无关的声明与事实不符**：检索必须产出的过滤与聚合键全部来自 library 与案例库的领域投影（[RAG 策略](../technical-details/RAG策略.md)第 2 节）。
2. **为跨越自造边界而存在的缝**：原方案要求 `core` 定义 Protocol、library 实现、`tools` 装配，并需专门一节文档解释这条缝。
3. **同一事实两处声明所有权**：「两路检索与合并」同时写在[资料与案例检索](../technical-details/资料与案例检索.md)与 [RAG 策略](../technical-details/RAG策略.md)的权威范围里；该重叠已产生实际漂移——RRF 决定在其中一处退化为被否决的旧合并规则。
4. **只有一个模式实例**：一期只有资料库与案例库两个集合、且同属 library，检索机制没有第二个消费者。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| 保留 `core/retrieval`，library 实现字面检索器、`core` 定义接口（原方案） | 检索机制必须被 library 之外的主体复用时 | 「领域无关」声明与投影清单矛盾；保留 Protocol 缝与装配约定；除非改造成由 library 注入投影规格的参数化引擎——那服务单个实例，属为单一场景建抽象 |
| **检索链并入 `modules/library`（选定）** | 检索机制与领域数据同属一个限界上下文时 | 模块内关注点增多（两份表结构、两条检索路、融合、聚合、摄取）；出现第二个消费者时需重新抽出 |

消费者触点不因方向而改变：`cli`（摄取入口）、`tools`（工具包装）、`agent/context`（注入预算与引用索引）、`core/config`（嵌入配置）由「谁触发、谁消费、谁持有配置」决定，与检索代码放在哪个模块无关——因此并入并不减少整合度，只是让模块边界与聚合边界重合。

## 决定与影响

检索的机制与其领域模式同属一个模块：条目（真源）、节点（投影）、两路检索、融合、聚合、字面检索器与检索用例都在 `modules/library`。这同时消掉前述四处问题——不再有需要跨模块解释的接口缝，合并规则与投影清单回到单一权威文档域。

框架耦合随之收敛：LlamaIndex 只有 library 一个消费者，「框架耦合止于 library」成为可直接检查的事实，不必为它预留 `core` 模块——同时满足[项目结构设计](../../项目结构设计.md)第 1 节「没有消费者的依赖不预先声明」。`core/config` 仍持有嵌入模型名与凭据，因为[RAG 策略](../technical-details/RAG策略.md)第 11 节要求记忆侧的 Graphiti 嵌入器使用同一个 TokenHub 向量模型——共享的是配置值，不是检索代码。

## 重访条件

出现**第二个直接消费检索机制的主体**——第三个语料集合、绕过 `tools/` 直接调用检索的第二个面、或多租户 `spaces` 要求共享同一套检索内核——则重新评估把检索机制抽为独立模块：届时它才有真实消费者，参数化引擎也才有第二个实例。
