# 账号标识取身份服务的用户标识，认证不建面

> **决定**：① `account_id` **就是 SuperTokens 的用户标识**（UUID v4 字符串），不建映射表、不另设内部账号主键；② 认证**不新建 `surfaces/accounts/`**，其 HTTP 契约由[认证与账号](../technical-details/认证与账号.md)拥有；③ 前端引入官方前端 SDK `supertokens-web-js`（Apache-2.0）承担令牌刷新与 anti-CSRF 头注入；④ 注册入口**复写身份服务的 sign-up API**，邀请码作自定义表单字段。**理由**：这四项共同消掉"账号标识没有所有者"与"认证面没有契约所有者"两个缺口，且都不新增供应商、不自造轮子。**被否决项**：`user id mapping` 换取可读图名（收窄账号名到 `[a-zA-Z0-9_-]`，中文账号名不可用）；自建不透明 id + 映射表（即文档原列为风险的"第二定义"）；新建 `surfaces/accounts/`（掏空"面"的定义）；自写前端刷新逻辑（并发单飞刷新是隐蔽缺陷高发区）；自建注册端点并禁用 SDK signup 路由（须自行签发 session，与选型理由相悖）。
> **状态**：**2026-09-29 经用户裁决**。其中 ① 修正了原文档"我们自己的用户表与身份服务的表要通过明确的映射关联"的表述（该风险由此消解，而非被权衡接受）；② 修正了[项目结构设计](../../项目结构设计.md)第 9 节"前端不得读取或存储凭据"的绝对化措辞（为 anti-CSRF 令牌给出边界）。不代表已实现。

## 上下文与证据

原设计的缺口不是"选错方向"，而是**三个相关事实都没有所有者**：

| 缺口 | 原文证据 | 阻塞什么 |
|---|---|---|
| 账号标识形态未定 | [通用记忆](../technical-details/通用记忆.md)原文："账号标识的最终形态尚未决定（`accounts/` 仍是占位包）" | 记忆分区键、FalkorDB 图名、删除账本账号列、`pending_write.account_id` 全部无定值 |
| 认证面没有契约所有者 | `surfaces/` 下只有 `consult/`；[项目结构设计](../../项目结构设计.md)第 9 节已声明"会话凭据经 httpOnly Cookie 传递"，但 cookie 属性、anti-CSRF 模式、端点形状无任何文档拥有 | 前端无法实现登录；凭据传输的取值全靠实现者临场决定 |
| 前端如何维持会话未知 | 全库 grep `supertokens-web-js\|supertokens-auth-react\|前端 SDK` **零命中** | 令牌过期后谁刷新、anti-CSRF 头谁加，无答案 |

**已核实的关键事实**（决定 ① 成立）：

- SuperTokens 用户标识是 **UUID v4 字符串**（官方《User Object》示例 `3f23dca5-79da-4d84-9a72-90286ef6ea0d`），36 字符。
- Graphiti 的 `validate_group_id` 判据是 `^[a-zA-Z0-9_-]+$`，**连字符在字符集内**——UUID 直接满足，无需归一化。
- 宽度 36 落在 `identity.MAX_ACCOUNT_ID_LENGTH`（128）与账本 `varchar(128)` 之内。
- 官方《User Object》写明：*The primary user ID. **It can change if the user links to another user***——故账号链接成为必须排除的变更源。

**已核实的关键事实**（决定 ③ 成立）：

- cookie 鉴权下 **access token 不暴露给前端**（官方《Access Session Data》原文），与 [项目结构设计](../../项目结构设计.md)第 9 节的禁令**不冲突**。
- anti-CSRF 在 `sameSite=lax` 且同顶级域时默认 `VIA_CUSTOM_HEADER`；`sameSite=none` 会改变该行为，且官方《Security》原文指出 Safari 的第三方 cookie 限制会让 cookie 模式失效。
- `supertokens-web-js` 的 `LICENSE.md` 为 **Apache-2.0**（实测仓库原文核实）。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **`account_id` = 身份服务用户标识（选定）** | 接受与身份服务耦合、换供应商需迁移分区键 | 无映射层、无第二定义、不限定账号名字符集；代价由"重访条件"覆盖 |
| `user id mapping`（让 SuperTokens 返回自定义标识） | 需要可读图名以便运营排障 | 账号名被收窄到 `[a-zA-Z0-9_-]`，**中文账号名不可用**；只能在用户无任何数据前调用；主站文档缺失（社区回复"文档即将推出"）、免费归属未核实 |
| 自建不透明 id + 映射表 | 要求与身份服务彻底解耦 | 维护一张映射表——正是原文列为风险的那种"谁是谁的第二定义" |

| 方向（接入面） | 何时成立 | 代价 |
|---|---|---|
| **契约归认证文档、不建面（选定）** | 认证不经过 Agent 基座、不装配 skill 与工具池 | 认证面契约与咨询面契约不同址；靠 README 文档地图指明归属 |
| 新建 `surfaces/accounts/` | 认证也需要基座能力时 | 掏空"面 = 产品入口 + 基座运行装配"的定义，使"新增面复用基座"这条扩展缝失准 |
| 复写 SDK sign-up API 注入邀请码校验（选定） | 校验在我们的后端代码内 + 不自己实现会话签发，二者都要 | 注册路由仍是 SDK 的路由；须保证校验失败时**不留下用户记录** |
| 自建注册端点、禁用 SDK signup 路由 | 要求不存在可绕过的注册路径（防御纵深） | 须自行签发 session 与设置 cookie，与"换取不自己实现会话安全"的选型理由相悖 |

## 不变量（实现层据此校验）

- **`account_id` 是不可轻易变更的分区键**：它是记忆分区键、FalkorDB 图名与删除账本账号列。**不得启用会改写用户标识的身份服务特性**（账号链接）。
- **全库只有一个"谁是谁"的定义**：我们自己的表一律以 `account_id` 引用身份服务的用户标识，不出现第二个账号主键。
- **凭据禁令的边界**：前端不得读取或存储 **access/refresh 令牌**；**anti-CSRF 令牌是防伪令牌、不是会话凭据**，其读取与自定义头回传是机制要求，不构成权限证明。
- **邀请码校验失败不得留下用户记录**：复写法必须在调用原实现之前拒绝，不得先建号再回滚（`AC-15` 要求无效码"不建号"）。
- **前端 SDK 只做传输**：它不参与业务授权判定。

## 决定与影响

四项决定同时落地；其中两项**修正了原有措辞**，一项**消解了原有风险**：

- 原 [认证与账号](../technical-details/认证与账号.md)第 3 节把"我们自己的用户表与身份服务的表要通过明确的映射关联，不得各自成为第二定义"列为**风险**：决定 ① 使其**不再需要映射**，风险消解而非被接受。
- 原 [项目结构设计](../../项目结构设计.md)第 9 节"前端不得读取或存储凭据"是**绝对化表述**：决定 ③ 为其给出边界（anti-CSRF 令牌例外）。
- 原 [通用记忆](../technical-details/通用记忆.md)第 7 节"账号标识的最终形态尚未决定"**已过时**，改为指向本裁决。

## 重访条件

- 出现**更换身份服务**或**启用账号链接**的真实需求——届时 `account_id` 必须迁移，须评估记忆分区键与账本的迁移代价。
- 运营排障因**图名不可读**产生实际困扰，且已验证 `user id mapping` 属开源免费部分——届时可重估，但须接受账号名字符集限制。
- 认证开始需要**基座能力**（例如认证流程本身要调模型），使"不建面"的理由不再成立。
- 前端 SDK 与 assistant-ui 或 React 19 出现**阻塞性冲突**，或它引入的升级负担超过自写传输层的成本。
