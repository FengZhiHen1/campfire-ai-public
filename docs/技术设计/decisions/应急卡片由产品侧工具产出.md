# 应急 Action Card 由产品侧工具产出，基座只定通用信封

> **决定**：`action_card` 事件**改由产品侧工具 `emit_emergency_action_card` 产出**，不再由基座保留工具 `emit_action_card` 发出（原方案）。基座第 7.3 节只定义**通用信封**（`sections` / `states` / `annotations` 三种与领域无关的形状），领域词表（医疗风险三值、来源六类、置信四档）与它们的机械校验落在工具的参数模型上。工具池 9→10。**理由**：基座不得出现领域术语（第 1 节不变量），而"模型编不出第四种医疗风险"必须是**机械校验**而不是提示词约束——`RQ-LIM-05` 已明确提示词层可以绕过、不构成安全边界。**被否决项**：基座保留工具 + 自由 `key/value` 载荷（词表校验退化成提示词约束）；基座内联应急词表（违反不变量）。
> **状态**：**2026-09-30 经用户裁决**。这是对「三个事件未定义」中 `action_card` 一项的关闭决定。不代表已实现。

## 上下文与证据

定事件形状时撞上一处张力：`AC-21` 要求医疗风险只出现"稳定 / 未排除 / 高风险"三种表述，[emergency-consulting](../面/consult/skills/emergency-consulting.md)第 3.4 节也写明"状态字段由工具参数校验，模型编不出第四种"——但这句话没有一个落点：基座第 1 节的不变量禁止它出现领域术语，因此基座无法校验"医疗风险"的取值。

| 事实 | 出处 |
|---|---|
| 基座不得出现领域术语 | [通用基座](../technical-details/通用基座.md)第 1 节 |
| 原方案：基座提供 `emit_action_card`，"载荷形状由使用的 skill 定义" | 同文档第 7 节（原表述）——即基座发事件，但形状归 skill，两侧都不校验 |
| 卡片需要"结构可校验"这个卖点 | [咨询对话界面](../technical-details/咨询对话界面.md)第 6.2 节：**不解析模型 markdown 猜结构**，状态字段经工具参数校验 |
| 提示词层约束不构成安全边界 | `RQ-LIM-05` |

**关键判据**：`question` 与 `action_card` 在这一点上**不对称**，不能因为原方案写了"同构"就沿用。`question` 需要"结束本次运行"这一运行编排行为——只有基座能给，所以它是基座保留工具。`action_card` 不需要：工具返回后运行自然继续。因此它可以、也应该下沉到产品侧。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **产品侧工具 + 基座通用信封（选定）** | 领域词表必须机械校验，且基座不得含领域术语 | 工具池 9→10；应急的 `allowed-tools` 加一项 |
| 基座保留 `emit_action_card`，载荷为自由 `key/value` | 想要"零新增工具" | `medical_risk` 退化为自由字符串，三值校验只能写在 skill 指令里——**正是 `RQ-LIM-05` 说可以绕过的一层**；`AC-21` 的机械端消失 |
| 基座内联应急词表 | 追求一处校验 | 直接违反"基座不含领域术语"；且将来第二种卡片要再改基座 |
| 前端解析模型 markdown | 零工具零事件 | 与"不解析猜结构"的既定结论相反；半截文本无法校验；页面设计已按事件成稿 |

**为什么不选第三个**：把领域词放进基座换取"一处校验"，等于用一条不变量换一条便利。不变量（基座不含领域术语）保护的是"将来第二种面、第二种卡片不需要动基座"，这条比省一个工具更值钱——而且下沉方案同样拿到了机械校验，只是校验位置从基座移到了工具。

## 决定与影响

**决定**：

1. 基座第 7 节新增 7.1（`reasoning_delta`）、7.2（`question`）、7.3（`action_card` 通用信封）三小节，明确三个事件的形状与产生方式。
2. 新增产品侧工具 `emit_emergency_action_card`，契约见[该工具文档](../面/consult/tools/emit_emergency_action_card.md)；它由装配处注册，与 `finish_onboarding` 同一种做法。
3. 工具池 9→10；[技能设计](../technical-details/技能设计.md)第 3 节工具表补一行并说明"为什么不属业务模块"。

由此得到的两条性质（写在基座第 7.3 节）：

- **领域词表校验落在 `args_model` 的枚举上**，是参数解析期的机械拒绝，不是提示词约束。
- **基座不需要知道有哪些卡片**：新增一种卡片是新增一个产品侧工具，不改基座。

**连带修正**：原方案称 `question` 与 `action_card`「产生方式同构」，该表述已废——两者在"是否需要结束运行"上不对称，判据写入基座第 7.3 节。

## 重访条件

- 出现第二种结构化卡片（非应急）时，验证"新增一个产品侧工具即可、基座不动"是否真成立；若第二个卡片的形状无法装进通用信封（例如需要嵌套结构或表格），则重估信封形状，而不是往基座里加领域分支。
- 若将来发现产品侧工具无法承担某一类校验（例如需要跨字段的领域规则），回到本条重新划分校验位置。
