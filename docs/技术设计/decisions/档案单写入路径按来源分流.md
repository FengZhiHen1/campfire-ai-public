# 档案单写入路径，按来源分流

> **决定**：档案保留**一个写工具**（`propose_profile_item`）与一条写入路径（`pending_write.kind = profile_item`），**落层由 `origin` 决定**：`user_statement`、`guardian_observation`、`third_party_report`、`document` 直接进稳定层；`system_observation`、`ai_inference` 只进候选层，确认后进稳定层。判定在**工具实现层硬卡**，新增 `source` 与 `pending_id` 两个字段，`origin` 取值域补齐六个。**理由**：需求 `RQ-MEM-02` 的原文是「使用者的直接陈述零确认入档」，而原设计稿的硬约束写的是「只写候选层，稳定层由使用者确认后进入」——**直接把陈述也挡在稳定层外，与需求对撞**；同时在候选层一侧，原设计稿**没有任何产生者**，`AC-18` 与对话页"待确认"轻提示因此都无对象可指。**被否决项**：拆成两条写入路径（陈述一条、推断一条，新增第二个写工具或 `profile` 内部推断用例）；工具收全部六个 `origin` 但仍一律写候选层（落层判定缺位）；一期不产生推断候选（则须回退 `RQ-MEM-04` 与 `AC-18`）。
> **状态**：**2026-09-29 经用户裁决**。这是对[propose_profile_item](../面/consult/tools/propose_profile_item.md)与[个性化档案](../technical-details/个性化档案.md)既有设计内容的**实质修正**，不是措辞润色。不代表已实现。

## 上下文与证据

需求与设计稿在这一点上互相矛盾，且矛盾处此前未被登记：

| 位置 | 原文 | 后果 |
|---|---|---|
| [功能需求与验收](../../需求/功能需求与验收.md) `RQ-MEM-02` | 「**使用者的直接陈述零确认入档**；系统观察与归纳以候选状态存在」 | 陈述应进稳定层 |
| [propose_profile_item](../面/consult/tools/propose_profile_item.md) 第 4 节第 2 条（修正前） | 「**只写候选层**：本工具不直接改稳定层；稳定层由使用者确认后进入」 | 陈述也进不去 |
| [写入路径](../technical-details/写入路径.md) 第 3 节 | `origin` 四值：`user_statement`、`guardian_observation`、`system_observation`、`ai_inference` | 契约能传的 `third_party_report`、`document` **存不下** |
| [技能设计](../technical-details/技能设计.md) 第 3 节 | 一期七个工具里，档案写工具只有 `propose_profile_item` | 无第二个写入者（2026-09-30 后工具总数九个，**档案写工具仍只有它**——onboarding 经同一工具写种子，未新增写入者） |
| [profile-curation](../面/consult/skills/profile-curation.md) 第 3.2 节（修正前） | 「只整理**已经出现过的信息**，不推断补全」 | 模型被纪律挡住，**候选层永远为空** |

两处缺口合并成同一件事：**档案的写入路径到底有几条、落层在哪判定**。

**候选层没有产生者**是本轮的实测结论，不是推断：把上述五处逐条对照后，`system_observation` 与 `ai_inference` 两条 `origin` 在一期**没有任何调用方能产生**——模型侧被 skill 纪律禁止，系统侧没有推断用例；而 `freshness = stale` 的 90 天降权、`read_profile_items` 的 `include_candidates` 分支、`AC-18`、对话页"有 N 条待确认"轻提示全部依赖候选条目存在。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| 拆成两条写入路径（陈述一条、推断一条） | 两类写入的落层与失败语义真的不同时 | 新增第二个写工具或 `profile` 内部推断用例；`pending_write` 分流点从 `origin` 扩散到 `kind`；**新增的概念多于它消除的分支** |
| 单路径，工具收六个 `origin`，仍一律写候选层（原设计稿） | — | 与 `RQ-MEM-02` 直接对撞；陈述被要求二次确认 |
| **单路径 + 按 `origin` 分流（选定）** | 落层是 `origin` 的函数时 | 工具实现层承担落层判定；`origin` 语义变重（既是"谁说的"也是"落哪层"） |
| 一期不产生推断候选 | 若确认负担不可接受 | 须回退 `RQ-MEM-04`、`AC-18`，并删除 90 天降权与 `include_candidates` |

用户裁决（原文）：**「能否保持一个写入路径，按照不同分类触发不同后续？比如需要确认的，就在前端对话唤起确认卡片」**——即上表选定行，且把"需要确认的"呈现交给前端确认卡。

**推断的产生者同样由用户裁决**：模型可产出**来自单次观察**的推断候选；跨对话的**模式归纳一期不做**。

## 决定与影响

写入路径只有一条，落层是 `origin` 的函数；确认与不确认的分野由前端确认卡呈现，不由两条后端路径表达。

**`origin` 与需求的对齐**（本次修正的实质）：`user_statement`、`guardian_observation` 直接进稳定层且记 `confirmation = confirmed`（一期使用者即陈述人或监护人本人）；`third_party_report`、`document` 进稳定层但记 `unconfirmed`；`system_observation`、`ai_inference` 只进候选层。

**阈值口径的更正**（修正前设计稿的内部矛盾，两处口径不一致）：

| 位置 | 修正前 | 现取值 |
|---|---|---|
| [个性化档案](../technical-details/个性化档案.md) 第 3 节 | 「单次观察**只能作为单次记录存在**…90 天够长到不误伤**低频但真实的观察**」 | 保留：单次观察即一条候选，受 90 天降权约束 |
| 同文档第 5 节第 5 条 | 「`ai_inference` 与 `system_observation` **只在同一模式重复出现达到阈值后才生成候选条目**」 | 改：阈值为 `≥2` 次**跨对话**，约束的是**模式归纳**，不是候选条目的产生 |

判定依据：需求稿第五节原文即写「候选**模式**需同一主题在 ≥2 次不同对话中出现才可归纳」——阈值的作用域一直是**模式**。是设计稿把它**过度套用到了候选条目**上，从而与同一文档第 3 节自相矛盾。本次修正把设计改回与需求一致，**需求基线未修改**。

**新增字段的必要性**：`source`（来源定位）承载 `AC-07` 的"来源"，`pending_id` 承载第 7 节"档案条目对 `pending_id` 建唯一约束"的幂等承诺——原字段表两者皆无，使该承诺无处落地。

## 重访条件

- 确认负担成为真实问题（使用者抱怨候选过多），且评测证明按来源分级呈现比逐条确认更准 → 重估确认粒度。
- 出现**第二个**需要写档案的主体（二期共用的其他监护者、机构成员）→ 重估单写入口是否还成立。
- 跨对话模式归纳开放时（见[个性化档案](../technical-details/个性化档案.md)第 12 节）→ 重新定义它与单次观察候选的关系。
