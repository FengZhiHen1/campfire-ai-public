# 运营操作经 CLI，一期不做运营 web 后台

> **决定**：一期运营操作（邀请码发放/撤销、人工重置）**扩展既有的 `python -m campfire.cli`**，新增 `invite`、`account` 子命令；**不做运营 web 后台，不暴露任何运营 HTTP 端点**。运营者身份即**执行该 CLI 所需的服务器访问权**，本期**不引入应用层运营者身份与审计**。**理由**：一期运营量极小（`RQ-ACC-06` 的自助找回重访条件是"真实用户数 ≥50 或每周 ≥1 次找回请求"，反过来说明重置预期是个位数次数），为个位数操作建一个浏览器可达、能重置任意密码与建任意账号的界面，攻击面与收益不成比例；CLI 已存在，复用零新增攻击面。**被否决项**：一期即建运营 web 后台（须先过视觉契约那道门，且是首个管理界面，会引出范围蔓延）；用 SuperTokens 官方 Dashboard 充任（超 3 个 dashboard 用户付费、自托管需 license key 且条款未核实，且它管不了我们自己的邀请码表）。
> **状态**：**2026-09-29 经用户裁决**。这填补了[认证与账号](../technical-details/认证与账号.md)原"运营者入口"只有一句话、没有身份、没有边界、没有审计的缺口。不代表已实现。

## 上下文与证据

原设计对这一项的记载只有两句：`AC-15`/`AC-17` 把发放邀请码与重置密码交给"运营者"，[认证与账号](../technical-details/认证与账号.md)第 2 节决定运营操作"走 SDK 或 Management API，不依赖 Dashboard"。**由此可推出一个未被写下的结论**：运营者就是**持有 `SUPERTOKENS_API_KEY` 的人**——那把 key 能建号、能改密，而它原本只是"core 的 Management API 密钥"。

缺口因此有三层：**入口没有形态**、**身份没有定义**、**操作没有审计**。

**关键辨析（决定选项性质）**：一个"通过 key 登录的 web 后台"**不会**解决第三层。它把同一把共享静态 key 从服务器脚本搬到浏览器可达的界面，**仍然无法回答"哪位运营者重置了谁的密码"**。要做到追责必须有**具名运营者身份**——这与"选 CLI 还是选 web"是两件独立的事。本次裁决**有意**选择不做应用层追责，并把这一代价写明。

**本项目的既有模式**（同向证据，非本次决定的理由）：

| 位置 | 原文 |
|---|---|
| [写入路径](../technical-details/写入路径.md)第 6 节 | 死信的人工处理"由运营执行，**不做界面**" |
| [功能需求与验收](../../需求/功能需求与验收.md) `RQ-KB-03` | 知识库"**不提供任何服务端点与产品内界面**用于资料录入、审核或知识库管理" |
| [公共案例库](../technical-details/公共案例库.md)第 10 节 | 知识库管理与审核界面列为延期，"有真实运营需要与多人协作时" |
| [项目结构设计](../../项目结构设计.md)第 2 节 | `cli/` 是"本地运维入口（**不暴露成服务端点**）" |

**已核实的供应商事实**：SuperTokens 官方 Dashboard 由后端 SDK 挂载在 `<apiDomain>/auth/dashboard`，能看/改/删用户（[dashboard 仓库](https://github.com/supertokens/dashboard)，LICENSE 实测 Apache-2.0）；但官方《Dashboard initial setup》原文写 *"You can create **3 dashboard users** for free"*、自托管需 *"sign up to generate a license key"*——**license key 条款未核实**（同 `TECH-07` 类风险）。且它只覆盖身份服务的用户，**不覆盖我们自己的邀请码表**。

## 备选与评价

| 方向 | 何时成立 | 代价 |
|---|---|---|
| **扩展 CLI（选定）** | 运营者是项目所有者/少数技术人，能从服务器执行 | 每张邀请码都要登服务器；运营者身份=服务器访问权（**审计落在 OS 层，应用层无追责**） |
| 一期即建 web 后台 + 具名运营者 + 审计 | 有非技术运营者、多人协作，或需要应用层追责 | 需前端工程（**当前不存在**）、运营者身份存储、审计表；须先落地视觉契约；且是首个管理界面，必须同时划定"不做"边界 |
| 官方 Dashboard + 自建邀请码管理 | 想少写用户管理代码 | 依赖 license key（条款未核实）；邀请码仍自研；两处界面并存；CSP 需放行其 CDN |

## 不变量

- **运营操作不经 HTTP**：CLI 不挂路由、不对外；`account reset` 的撤销会话与改密**必须同时成立**，任一失败即整体失败并明确报错，**不得留下"密码已改但旧会话仍有效"**（第 8 节末行）。
- **`cli/` 的依赖白名单因此放行 `modules/accounts`**（[项目结构设计](../../项目结构设计.md)第 7 节）——该白名单由 `apps/api/tests/test_layer_boundaries.py` 机械检查，**新增子命令必须同步该表**。
- **只有 Nginx 对外监听**：api、worker 与**全部数据服务**（PostgreSQL、Redis、FalkorDB、SuperTokens core、MinIO）不得映射到公网接口，仅经 Compose 内网互联。官方原文警告自托管 core 暴露到互联网则"任何人都能创建或修改 dashboard 用户"；但**风险不止 core**——同一份编排里 PostgreSQL（全部业务数据与会话表）、Redis（队列与限流）、FalkorDB（全部记忆）、MinIO（默认 `minioadmin`）同样开着宿主端口。[docker-compose.yml](../../../docker-compose.yml) 已把全部端口绑到 `127.0.0.1`，完整约束见[技术栈设计](../../技术栈设计.md)第 6 节。

## 决定与影响

运营入口的形态、身份与边界一并落定；**代价如实记录**：本期无法回答"哪位运营者做了哪次操作"，追责依赖 OS 层日志。

## 重访条件

- 出现**非技术运营者**、多人协作，或需要**应用层追责**——届时按 web 后台方案重估，并须同时定义运营者身份、审计与权限边界。
- 运营操作频次上升到手执行不可接受（例如邀请码发放成为常态高频动作）——届时优先评估**批量/脚本化子命令**，而不是直接跳到 web 界面。
- 视觉契约（`docs/design/`）落地后，管理界面的实现前置条件才具备；在此之前即使决定做 web 后台也无法开工。
