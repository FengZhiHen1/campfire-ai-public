# 项目结构设计

> **权威范围**：目标仓库模块、目录职责、依赖方向、跨端契约组织与命名约定。业务语义和状态不由本文拥有。
> **状态**：2026-09-26 用户授权自主收敛的 v3.0 目标结构；不是当前代码目录已迁移的声明。

## 1. 结构原则与现状

保留 uv + pnpm 双工作空间、单仓和薄运行入口。已读 `pyproject.toml`、前端路由、`packages/py-db/py_db/models/`：目前业务模块仍按 emergency/profiles/cases 划分，前端同时有 `views/logics` 和少量 `view`，数据库档案按家属归属。目标不按旧“应急行为桶”复制一套新轴，而按**公开支持、情境辅助、用户事项、个人空间、记录、交接、共享计划、证据、演练**的业务职责划分。只迁移被新需求使用的能力；不创建未使用的空包。

依赖原则：业务用例持有授权、发布和停止决定；数据库/队列/模型/Agent 是可替换执行手段，不能反过来决定业务状态。每个跨模块操作只有一个状态所有者；读者不得从另一个模块的缓存推断权限。

## 2. 后端职责与依赖

| 目标业务模块（`apps/api-server/app/modules/`） | 拥有的用例 | 不得承担 |
|---|---|---|
| `auth` | 身份、凭证、账号状态；供关系核验的用户标识 | 对某个支持对象的实际访问授权 |
| `public_support` | 公开已审阅基础内容、真实求助路径和撤下 | 个性化生成或未经审阅的现场处置 |
| `assist` | 带作用域的情境澄清、受限模型调用、完整回答的核对与临时预览 | 在用户确认前持久化事项或替代授权判定 |
| `matters` | 私人与空间事项、用户明确保存、并发修订与逐项转入请求 | 因聊天而创建共享档案或长期标签 |
| `spaces` | 支持对象、授权主体、关系委托、撤销、争议与重复空间 | 以职业角色代替关系核验 |
| `records` | 带来源的观察、纠错、分歧及记录核对 | 将记录自动发布为计划 |
| `handoffs` | 接收者受限预览、明确发送与送达/失效状态 | 无权通知、以“已受理”冒充已送达 |
| `plans` | 分级确认、条目版本、安全异议及恢复 | 将审核权交给 AI 或访问管理员 |
| `evidence` | 研究/案例/安全内容的审阅、版本、撤下和依据索引 | 将私人记录自动用于公共检索 |
| `practice` | 审阅情景与演练反馈 | 冒充个人行为预测或专业诊断 |

`apps/api-server` 中模块包含薄路由、用例服务和端口；它们使用 `packages/py-db` 的 ORM/仓储与迁移、`py-schemas` 的对外 DTO、`py-auth` 的身份原语、`py-security` 的安全原语。**访问授权的判定入口由 `spaces` 一处提供**：其他模块从受信业务接口取得当前主体、空间、用途、范围与版本化决策，不自行读取角色枚举构造授权。跨模块共享可定义小型只读契约，不允许循环 import。保存事项转入空间的用例由 `matters` 发起，`spaces` 判定关系，`records` 写入来源明确的新记录；失败时要么全部不生效，要么保留私人事项并清楚报告未转入。

`apps/worker` 只处理可重试的证据索引、站内交接投递、专业审核通知和撤下后索引清理。授权、异议停用和计划确认必须先在主数据库事务内完成；Worker 不可在异步完成前把未确认内容作为当前有效内容发布。跨事务任务用持久化 outbox 或等价可恢复投递机制，消费者按业务键幂等。

## 3. Agent 与基础能力边界

`packages/py-agent-kernel` 继续承载通用模型运行、事件和工具适配；`py-agent-extensions` 只承载项目批准的整理、检索和演练工具。二者不是授权服务器：可用工具和检索上下文由 API 用例在调用前生成并校验，模型输出在写入记录或对外显示前再次按身份、内容类别、来源和当前状态校验。安全门不能只依赖“安全扩展优先加载”，即使扩展缺失、调用超时或模型拒绝配合，服务端仍阻断受限操作。`py-llm` 若仍被旧功能使用只作为迁移期现状，不为新能力扩展。

`packages/py-rag` 只索引当前被批准用于对应受众的研究、指南与案例；个人记录保留在带空间作用域的关系型数据中，按授权加载后再交给生成任务。`py-cache`、`py-storage`、`py-logger` 分别承载临时协调、受控附件及去敏审计，不能成为个人资料的隐式复制渠道。技术选型与版本仅由技术栈设计拥有。

## 4. 前端组织和接口接缝

`apps/react-web/src/` 沿用已在项目规范中的单向五层：`domain/`（无框架业务类型）←`application/`（用例与端口）←`viewModel/`（交互状态与 Hooks）←`view/`（页面与组件）；`infrastructure/` 实现 application 端口，经装配注入，不让 `view` 直接请求 HTTP、读取 JWT 或跨层导入仓储。按 `public_support`、`assist`、`matters`、`spaces`、`records`、`handoffs`、`plans`、`evidence`、`practice`、`auth` 在层内组织；跨特性元素只在确有第二消费者时进入 shared。

公开基础内容路由可在未登录时读取，AI 入口必须经过登录及真实服务端守卫；前端守卫只负责体验，不充当权限证明。选择当前空间与切换支持对象时，清除前一个人的可见缓存和正在运行的流；任一旧请求迟到的响应不得显示到新对象页。`packages/ts-shared` 限于跨端 DTO 与枚举，不复制业务规则；前后端契约须有实际序列化、错误与权限测试。

`apps/mini-program` 冻结：不为它新增页面、功能分叉或微信登录承诺；日后重启再从已验证的 Web 业务契约映射，而非复制 Web 的敏感客户端缓存。

## 5. 推荐目录骨架与迁移缝

```text
apps/api-server/app/modules/{auth,public_support,assist,matters,spaces,records,handoffs,plans,evidence,practice}/
apps/api-server/app/core/{dependencies,operations}/
apps/worker/src/worker/tasks/{evidence_indexing,notification,withdrawal}/
apps/react-web/src/{domain,application,viewModel,view,infrastructure}/<feature>/
packages/{py-db,py-schemas,py-auth,py-security,py-rag,py-cache,py-logger,py-storage}/
packages/{py-agent-kernel,py-agent-extensions}/
```

这里的路径是**目标归属**，不是要求一次迁移全部代码。已有 `emergency/profiles/cases` 保持可回滚的旧读路径，先建立新模型与权限服务，按业务入口逐段切换，再删除已经验证无调用的旧路径。旧 `profiles.caregiver_id` 与必填出生日期/诊断不能直接当作新空间权限；旧代码或生产数据未清点前，不做破坏性迁移。

## 6. 验证与失败边界

- 静态依赖检查应拒绝前端 view 直接访问 infrastructure、领域包反向依赖 app、跨 app import 与双模块各自维护授权规则。
- 集成用例覆盖用户同时参与两个空间、取消请求后切换对象、Token 有效但关系已撤销、Worker 重放任务与缓存落后数据库的情况；授权不一致时拒绝受限操作，公开内容仍可达。
- 先列迁移映射和回退点，逐阶段核对 API、schema 和资料权限；阶段切换不以“测试环境无真实用户”替代生产数据核查。未实现或未测试的路径标明差异，不宣称结构已落地。
