# 总体架构

> **本文唯一拥有**：技术选型、部署拓扑、安全设计、环境划分、监控告警、技术风险与后备方案。
> **来源**：原 `docs/篝火智答-技术栈设计.md`（v1.2，2026-05-24，存档于 docs/历史/）§1-3、§5-7。
> 各模块的机制与数据模型由机制设计文档拥有；产品需求由需求文档拥有。

## 1. 背景与约束

### 1.1 功能需求摘要

平台包含七大功能模块：智能应急咨询（P0）、个性化档案库（P0）、真实案例库管理（P0）、人工兜底通道（P2，延后）、事件趋势复盘（P1）、协作照护（P1）、科普查阅（P2）。需求项与优先级见需求文档。

### 1.2 技术性约束

| 维度 | 指标 |
|------|------|
| **数据规模** | 初期案例库 < 10 万切片，用户量级为垂直领域中小规模 |
| **预算约束** | 成本敏感，优先轻量模型与容器化自部署组件 |
| **性能约束** | 红线安全门命中即时响应（无 LLM 依赖）；应急咨询 TTFT 设计目标 P50 ≤ 3 秒、P95 > 5s 告警，不设全流程绝对时长（需求侧指标，归需求文档非功能需求） |

### 1.3 团队与运维现状

- **团队规模**：1-3 人小团队，无专职运维
- **技术背景**：具备 Python/FastAPI/LangChain 生态认知基础
- **部署环境**：云服务器（国内）+ Docker 容器化
- **运维能力**：需零运维负担方案，避免 K8s 等重运维基础设施

|----------|----------|----------|----------|
| 前端框架 | Taro（React 语法） | 4.x | 微信小程序跨端开发（需求侧终态；MVP 期冻结，需求侧由 react-web 承载，ADR-012/014） |

## 3. 架构设计

### 3.1 架构分层图

```mermaid
graph TB
    subgraph 客户端层
        MP[微信小程序<br/>Taro + React（需求侧终态，MVP 期冻结）]
        WEB[react-web<br/>React + Vite（供给侧/管理 + MVP 期需求侧内测）]
    end

    subgraph 网关层
        Nginx[Nginx 反向代理<br/>HTTPS / 静态资源 / API 路由]
    end

    subgraph 应用层
        API[API Server<br/>FastAPI + asyncio]
        AGENT[Agent 基座<br/>Pydantic AI + Skill 目录 + 工具注册]
        RAG[检索与切片<br/>pgvector 混合检索]
    end

    subgraph 数据层
        PG[(PostgreSQL + pgvector<br/>业务数据 + 向量检索)]
        Redis[(Redis<br/>缓存 / Session / 限流 / 队列)]
        MinIO[(MinIO<br/>对象存储)]
    end

    subgraph 外部服务
        DS[DeepSeek API<br/>LLM 生成服务]
    end

    MP -->|wx.request| Nginx
    WEB -->|HTTPS| Nginx
    Nginx -->|反向代理| API
    API -->|编排/安全前置| AGENT
    AGENT -->|rag_search 等工具| RAG
    AGENT -->|模型调用| DS
    RAG -->|向量检索| PG
    API -->|业务 CRUD| PG
    API -->|缓存/限流| Redis
    API -->|文件读写| MinIO
    API -.->|异步任务| Redis
```

> 客户端层分工按 ADR-006/012/014 收束：微信小程序（Taro）为需求侧终态（监护人/志愿者），react-web（React + Vite）为供给侧（老师/专家）与管理端；MVP 期小程序冻结、Web 全量承载供给侧与需求侧内测服务，终态分工不变。
> 应用层的 Agent 化运行方式（统一基座、工具与 Skill、分面自治）按 ADR-007 确立，执行策略由 Agent 基座文档拥有。

### 3.2 数据流向说明

**1. 应急咨询核心流程（同步 + 流式，Agent 应急面）**

```
家属点选行为桶（可附文字） → 需求侧客户端（MVP 期 react-web，终态小程序） → Nginx → FastAPI
  → 红线安全门判定（代码层纯规则，命中红线短路不经 Agent，出高危桶卡 + 就医指引）
  → 此刻安全层（代码层，零 LLM）：通用卡 → 桶卡 → 阶段单点问题
  → 编排代码并行预取（档案 + 案例检索）并预注入（含会话记录）
  → Agent 基座强制加载 emergency-consult Skill，单轮生成首份方案（SSE 逐 Token）
  → 追问轮：通用 Agent 会话（放行 rag_search）；确定性兜底信号后校验（代码层）触发 ticket_create（M4 后）
  → 需求侧客户端接收流式响应，逐句渲染
```

**2. 案例入库异步流程（Agent 异步面）**

```
老师提交案例（Web）→ FastAPI → PostgreSQL 写入元数据
  → 投递异步任务到 Redis 队列
  → 后台 Worker：case-extraction Skill 提取 L2 卡片（含 PII 检测/EBP 建议）
  → 专家终审通过 → 切片 + 向量化嵌入（阿里 text-embedding-v4）
  → 写入 pgvector 向量索引
  → 案例状态更新为「已索引入库」
```

**3. 工单兜底流程（同步触发 + 异步预组装）**

```
确定性兜底信号命中（检索质量不足/用户标记未解决/连续追问未解决） 或 用户主动触发
  → 代码层调用 ticket_create 工具生成工单（PostgreSQL INSERT）
  → 高风险标记自动标红
  → ticket-enrich Skill 异步预组装（上下文/档案摘要/专家匹配建议）
  → 专家接单（Web）
  → 专家回复写入工单记录
```

各模块的接口契约、数据模型与失败语义由机制设计文档拥有；Agent 化的运行方式（统一基座、工具与 Skill、分面自治）由 Agent 基座文档拥有。

## 4. 安全设计

| 维度 | 方案 |
|------|------|
| **传输安全** | HTTPS / TLS 1.3，Nginx 终端 SSL |
| **认证** | 身份-凭证分离 + JWT 双 token（Access 15min + Refresh 7d，python-jose 签发）；微信渠道（code2session 静默登录）预留，机制由认证与访问文档定义 |
| **鉴权** | 六角色显式 RBAC（家属/志愿者/老师/专家/管理员/维护人员），角色→能力显式映射 + 依赖注入守卫，矩阵由认证与访问文档定义 |
| **密码安全** | bcrypt 哈希（passlib），salt rounds ≥ 12 |
| **敏感数据** | 手机号仅管理员可见（RBAC 字段级控制）；案例/档案写入前自动 PII 检测脱敏 |
| **输入校验** | Pydantic v2 Schema 全量校验 + PostgreSQL 参数化查询（防 SQL 注入） |
| **防刷限流** | Redis 滑动窗口限流（用户级 30 req/min，IP 级 100 req/min） |
| **AI 输出安全** | 强制免责声明注入 Prompt 模板；高风险关键词（自伤/药物）后校验阻断 |
| **文件安全** | MinIO 预签名 URL 上传/下载，文件类型白名单校验 |

## 5. 部署与运维

### 5.1 环境划分

| 环境 | 方案 | 用途 |
|------|------|------|
| **开发** | 本地 Docker Compose（FastAPI + PostgreSQL + Redis + MinIO） | 日常开发与调试 |
| **测试** | 云服务器单实例 + Docker Compose | 集成测试、验收测试 |
| **生产（一期）** | 云服务器（4C8G 起）+ Docker Compose + Nginx | MVP 上线 |
| **生产（扩展）** | 托管 K8s（阿里云 ACK）+ 多副本 | 规模增长后扩展 |

### 5.2 关键配置

**环境变量清单（`.env`）**：

```
# 数据库
DATABASE_URL=postgresql+asyncpg://user:pass@postgres:5432/campfire
# Redis
REDIS_URL=redis://redis:6379/0
# DeepSeek API
DEEPSEEK_API_KEY=sk-xxx
DEEPSEEK_BASE_URL=https://api.deepseek.com/v1
# MinIO
MINIO_ENDPOINT=minio:9000
MINIO_ACCESS_KEY=xxx
MINIO_SECRET_KEY=xxx
# JWT
JWT_SECRET_KEY=xxx
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_DAYS=7
# 限流
RATE_LIMIT_USER_PER_MINUTE=30
RATE_LIMIT_IP_PER_MINUTE=100
```

**密钥管理**：

- 开发环境：`.env` 文件（不入 Git，`.gitignore` 防护）
- 生产环境：云厂商密钥管理服务（阿里云 KMS / 环境变量注入）

### 5.3 监控与告警

| 维度 | 方案 | 说明 |
|------|------|------|
| **日志收集** | Python logging → stdout → Docker logs → Loki（可选） | 结构化 JSON 日志，含 trace_id |
| **指标监控** | Prometheus + Grafana | FastAPI 内置 `/metrics` 端点（prometheus-fastapi-instrumentator） |
| **关键告警** | Grafana Alert + 钉钉/企业微信通知 | 5xx 率 > 1%、TTFT P95 > 5s、DeepSeek API 不可用 |
| **健康检查** | FastAPI `/health` + Docker HEALTHCHECK | 含 PostgreSQL/Redis/MinIO 连通性检查 |

生产部署的具体操作流程由远程服务器操作指引文档（docs/运营/）拥有。

## 6. 潜在风险与替代方案

| 风险点 | 影响 | 缓解措施 | 后备方案 |
|--------|------|----------|----------|
| **DeepSeek API 服务中断** | 核心应急咨询功能不可用 | 熔断降级 + 本地缓存通用建议模板；故障时返回预设安全指导 | 切换到通义千问 API（需提前适配接口，成本增加约 3x） |
| **pgvector 性能瓶颈（>100 万向量）** | 检索延迟增加，TTFT 超标 | 升级 pgvectorscale 插件（StreamingDiskANN 索引）；定期监控索引性能 | 迁移至 Milvus 或 Qdrant 专业向量库 |
| **微信小程序资质审核未通过** | 需求侧无法经小程序触达 | MVP 期暂缓小程序、Web 全量承载（ADR-012/014）；审核前自查医疗健康类目规范 | 公众号 H5 补位（可行性验证中）；资质路径明朗后重启小程序，回归 ADR-006 终态 |
| **冷启动无档案** | 新用户体验降级为纯案例检索 | 默认检索全部案例（无标签过滤），生成方案中注明「完善档案可获得更精准建议」 | 使用用户注册时填写的最少信息（年龄/诊断类型）做初步过滤 |
| **单机 Docker Compose 单点故障** | 服务不可用 | 云服务器自动快照 + 快速重建脚本；Nginx upstream 预留扩展节点 | 升级为 Docker Swarm（轻量）或托管 K8s |
| **RAG 幻觉风险** | 生成不存在的医疗建议 | Prompt 强制约束「仅基于提供的案例上下文回答，不要编造」；结构化输出经 Pydantic 契约校验，不合格阻断 | 降低温度参数 + 增加检索召回数量（Top-K 从 5 增至 10） |
| **Agent 行为不确定性** | 工具误调用、输出不可复现，影响验收与安全 | 应急面受限自治（单轮生成+白名单+代码持有控制流）；全部结构化输出契约校验；每 Skill 建评测集，变更后强制回归 | 应急面回退纯管线（编排开销门禁不达标时同样触发） |
| **Agent Token 成本膨胀** | 多轮工具调用导致成本超预算 | 应急面单轮生成零工具调用；异步面设重试上限；按 Skill/面维度 Token 追踪并告警 | 限制异步面并发与单日调用配额 |
