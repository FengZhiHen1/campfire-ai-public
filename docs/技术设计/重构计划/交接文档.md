## 三、S4 阻塞点（已解决——根因与教训，防止重蹈）

**现象**：`TestSlotFillingIntegration` 3 个槽位衔接测试永久挂起（300s+ 超时 exit=124），前 5 个用例通过。

**根因（已定位，faulthandler 铁证）**：starlette TestClient 的 transport（`_TestClientTransport.handle_request`）**同步等待整个 ASGI app 协程执行完毕**（`portal.call(self.app, ...)`），而非等待响应头。SSE 响应 = `StreamingResponse(hub.stream(...))`，app 协程要迭代完生成器才结束。`hub.stream()` 在**非终态会话**（桶卡发布后停在阶段问答等待，无 done/error）时 replay 完缓冲后进入 `condition.wait()` 循环——**永不结束** → `portal.call` 永不返回 → `client.stream().__enter__` 永久阻塞（**响应头都拿不到**）。

**为什么 S3 全绿**：S3 的 SSE 测试全部是终态会话（红线/走失直接发 done；非红线全链路推进问答后 `_generate_plan` 发 done）→ 生成器结束 → 正常返回。

**为什么此前的修复尝试（Kimi 3 长时间未果）失败**：旧交接文档误判挂点在 `iter_lines` 阻塞式读，stop_on / iter_lines 超时 / 客户端 deadline **全都在 `__enter__` 之后才生效**——死锁发生在更早的 transport 层，客户端侧任何修法都无效（stop_on 是无效设计，已回滚）。

**修复（已落地，`a3e36a8`）**：槽位测试**放弃 SSE 流断言，改直读 `ConsultStreamHub` 缓冲**——`get_stream_hub().get_or_create(session_id).events`。非红线 `start()` 同步顺序执行，POST /stream 返回时全部事件已在缓冲；直读断言同步、零阻塞、语义等价。

**诊断手段备忘**：pytest 内置 faulthandler——`-o faulthandler_timeout=45 -o faulthandler_exit_on_timeout=true` 可在挂起时 dump 全线程堆栈精确定位（主线程堆栈显示挂点调用链，portal 线程显示事件循环状态）。
