# 重构计划（v1.0 · 2026-08-04）

> **历史警示**：本计划以旧应急与四层档案目标为前提，已被[当前目标机制与迁移设计](../目标机制/迁移验证与发布.md)取代，不得按其中删库、`docker compose down -v`、占位安全卡公开等步骤执行；旧文声称“无真实用户数据”尚未经生产盘点证实。保留全文仅用于核对已实施代码与历史决策。

> **本文唯一拥有**：本次全库重构的目标、已确认决策、阶段划分与依赖、全局执行约定、完成定义。
> **依据**：本计划以 `docs/技术设计/` 体系（总体架构、Agent 基座、Agent 内核框架、机制设计、项目结构、决策记录）为准绳，与代码现状的差异即重构任务。
> **执行者**：pi（按阶段拆分为独立任务执行；每阶段完成后代码库必须可运行、验证通过）。
> **状态**：计划基线。各阶段文档的【未开始】标注在执行时逐项勾选。

## 一、重构目标

将当前 MVP 代码库（`consultation` 置信度路由时代 + 匿名演示轨 + views/logics 两层前端 + 无 Agent 基座）彻底重构至 2026-08-04 收束的技术基线：

1. **认证体系**：身份-凭证分离 + 六角色显式 RBAC + 邀请码 + 准入状态机，废除匿名演示轨（[ADR-013](../决策/ADR-013-用户认证体系重构.md)、[机制/认证与访问](../机制/认证与访问.md)）；
2. **Agent 化**：落地通用内核 `py-agent-kernel`（零 Campfire 依赖）+ 领域扩展 `py-agent-extensions`（单包多子包，扩展边界 = 机制模块边界），`py-llm` 退役（[ADR-011](../决策/ADR-011-Agent内核框架-内核加扩展与PydanticAI路线.md)、[Agent内核框架](../Agent内核框架.md)、[Agent基座](../Agent基座.md)）；
3. **应急链路**：时刻分层重构——此刻安全层（确定性安全卡 + 阶段单点问题）+ 完整方案层（Agent 单轮生成）+ 追问轮 + 确定性兜底信号，废除置信度路由（[ADR-009](../决策/ADR-009-应急链路时刻分层重构.md)、[ADR-008](../决策/ADR-008-二元安全门取代三级危机分级.md)、[机制/智能应急咨询](../机制/智能应急咨询.md)）；
4. **档案体系**：四层结构（身份基础/危机预案/事件时间线/专业评估）+ ABC 结构化事件 + 枚举统一（[ADR-010](../决策/ADR-010-档案四层结构与事件记录ABC标准化.md)、[机制/个性化档案库](../机制/个性化档案库/README.md)）；
5. **项目结构**：api-server 模块与机制模块 1:1（auth/emergency/crisis/profiles/cases），前端五层（domain/application/viewModel/view/infrastructure），Worker 扩展为异步面编排宿主（[DSR-006](../决策/DSR-006-项目结构v3目标态.md)、[项目结构](../项目结构/README.md)）。

## 三、阶段总览与依赖

```
S1 认证重构 ──→ S3 应急时刻分层 ──→ S5 扩展与异步面 ──→ S6 前端五层重组 ──→ S7 收尾
                  ↗                   ↗
S2 Agent 内核 ────┘                  │
S4 档案四层 ──────────────────────────┘
```

| 阶段 | 名称 | 核心产出 | 依赖 | 体量 |
|---|---|---|---|---|
| S1 | 认证重构 | User+Credential+InviteCode、六角色 RBAC、准入状态机、邀请码、全站守卫、前端 auth 特性 | 无 | 中 |
| S2 | Agent 内核 | `py-agent-kernel` 全组件 + 独立测试与文档 | 无 | 大（全新） |
| S3 | 应急时刻分层 | 红线安全门 + 此刻安全层 + 完整方案层 + 兜底信号；consultation→emergency | S2 | 大 |
| S4 | 档案四层 | 四层模型 + ABC 事件 + 枚举统一 + 双模式记录 | 无 | 中-大 |
| S5 | 扩展与异步面 | `py-agent-extensions` 六子包 + Skill 包 + agent_bootstrap + worker 任务面 + py-llm 退役 | S2/S3/S4 | 大 |
| S6 | 前端五层重组 | react-web 五层 + ts-shared 扩展 + 删除 mock | S1-S5（契约稳定） | 大 |
| S7 | 收尾与文档同步 | mini-program 冻结、CI 更新、机制文档同步、临时资产清理 | 全部 | 中 |

**顺序理由**：

- **S1 最先**：RBAC 守卫是全站路由前置（废除 `get_anonymous_user` 波及 8 个文件），且 ADR-013 是「设计基线完成、实施未开始」的明确任务，不依赖任何 Agent 能力；
- **S2 次之**：内核是全新独立包（零 Campfire 依赖），不触碰现有代码、每阶段绿态风险最低；早建使 S3/S5 直接以 Agent 目标态实现，避免「先管线后切换」的返工；
- **S3 先于 S4**：应急链路是 P0 核心；档案四层重构期间，安全卡槽位以「空档案回退纯模板」运行（机制明确冷启动兼容），S4 完成后槽位填充自动生效（衔接点见阶段文档）；
- **S6 最后**：后端契约稳定后，前端五层重组一次到位，避免两次改接口。

## 四、全局执行约定

### 4.1 每阶段通用验证门（DoD 前置）

```bash
uv run ruff check .                        # Python 代码检查（零告警）
uv run pytest                              # 后端测试全绿（含 packages 独立测试）
cd apps/react-web && pnpm lint             # 前端 lint（涉及前端的阶段）
cd apps/react-web && pnpm build            # 前端类型检查 + 构建（涉及前端的阶段）
```

### 4.2 数据库约定

- 从 S1 起废弃旧迁移链思路，**按目标态模型从零编写 Alembic 迁移**（`packages/py-db/py_db/migrations/versions/`，当前为空目录）；
- 每阶段涉及 schema 变更时：`uv run alembic revision --autogenerate` 生成 + 迁移文件内加中文业务意图注释（AGENTS.md 规范）；
- 开发库重建：`docker compose down -v && docker compose up -d && uv run alembic upgrade head && uv run python scripts/seed.py`（seed 脚本在 S1 建立，随阶段扩充）；
- ❌ 禁止手动改库不落迁移文件。

### 4.3 提交规范

- 每阶段按任务分组 commit，中文 message，说明「做了什么」和「为什么」；
- 一个 commit 只含一个主题的改动（AGENTS.md 规范）；
- 阶段完成时该阶段全部改动已提交，代码库处于可运行状态。

### 4.4 测试策略

- **测试先行**：每阶段先写契约级测试（py-schemas/py-auth/py-db 的单元测试 + 接口集成测试），再实现；
- 现有测试中与目标态冲突的（如置信度路由、匿名轨、旧 crisis 三级）**按阶段淘汰重写**，不与旧行为兼容；
- Agent 内核要求独立测试套件（S2 专用）；Skill eval 集在 S5 建立，作为质量门；
- 每阶段结束 `uv run pytest` 全绿。

### 4.5 文档同步义务

- 每个阶段完成后，若机制文档与代码出现偏差，**在该阶段内同步修订对应机制文档**（AGENTS.md：发现文档与代码不一致时停止编码并告知；本次重构为整体重构，文档同步任务集中在 S7 统一执行，但阶段内发现契约级矛盾应立即停下确认）；
- 重构期间新增/废弃的 API 契约同步更新对应机制文档的接口章节；
- S7 统一收口：机制文档一致性校订 + 项目结构文档状态标注更新 + docs/README 已知偏差清理。

### 4.6 执行说明（pi）

- 每个阶段是一个独立的 pi 任务：读本计划对应阶段文档 → 按任务清单执行 → 跑验证门 → commit；
- 阶段内任务按编号顺序执行；任务未完成前不进入下一任务；
- 遇到「设计文档与代码现状矛盾」立即停止并询问，不静默决策；
- 预算建议：S2/S3/S5 各按 2-3 个 loop 拆分（内核组件、扩展子包可再拆），其余阶段 1-2 个 loop。
