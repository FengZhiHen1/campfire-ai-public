# 写入路径

> **权威范围**：待处理记录的形状与状态、投递与消费、幂等与重试、死信与告警、以及档案与记忆两条写入路径的失败语义。档案条目的数据形状由[个性化档案](个性化档案.md)拥有；会话存储与运行由[通用基座](通用基座.md)拥有；队列选型由[技术栈设计](../../技术栈设计.md)拥有；模块边界由[项目结构设计](../../项目结构设计.md)拥有。
> **状态**：2026-09-29 依已确认的技术栈设计（Taskiq + Redis、独立 Worker、待处理记录是真相源）与各机制文档中的失败语义汇总成形，待用户确认。不代表已实现。
> **追溯**：`RQ-MEM-01`、`RQ-MEM-02`、`RQ-MEM-03`、`AC-07`、`AC-08`；
> **依据**：技术栈设计第 5 节三条不变量；个性化档案第 7 节；技能设计第 3.3 节的工具硬约束；Graphiti 需要 LLM 与 embedding 客户端（其写入无法在对话请求内完成）。

## 1. 为什么要离开请求路径

记忆与档案的写入要调用模型（Graphiti 的实体抽取与嵌入），在请求内同步做会直接冲击对话时延，而且图库失败会拖垮一次本来成功的咨询。

**因此**：请求只做一件与业务数据同事务的事——**写一条待处理记录**；真正的写入由 Worker 完成。这样图库写失败不回滚已完成的业务状态，也不需要把"写没写进去"混进对话的成败里。

## 2. 真源与状态所有者

| 事实 | 所有者 | 说明 |
|---|---|---|
| 待写入的事实（还没落进档案或记忆） | `pending_write` 表（我们的事务型数据库） | **真相源**；队列与 Worker 都不拥有它 |
| 投递 | Redis + Taskiq | 只负责把"有一条待处理记录"送到 Worker；**丢失可被兜底扫描补救** |
| 处理进度（pending → done/dead） | `pending_write` 表 | Worker 只推进状态，不另存状态 |
| 写入后的结果 | 档案表 / Graphiti 图库 | 各自的机制文档拥有其形状 |

**不变量**：**"没写进去"不得被当作"写进去了"。** 只有 `state = done` 才算写入成功；其余状态一律视为未写入。

## 3. 待处理记录的形状

```text
pending_write
├── id                 幂等键（请求事务内生成）
├── kind               profile_item | memory_episode
├── account_id         发起者
├── support_object_id  归属支持对象
├── payload            写入所需的最小载荷（JSON）：条目字段或 episode 内容
├── origin             生成方式：user_statement | guardian_observation | system_observation | ai_inference
├── source             来源：会话 id、消息 seq、工具名、时间
├── state              pending | processing | done | failed | dead
├── attempts           已尝试次数
├── next_attempt_at    下次可尝试时间（退避）
├── lease_owner        处理中的 Worker 标识（仅 processing 阶段）
├── lease_expires_at   租约到期时间
├── last_error         最后一次失败的摘要
└── created_at / updated_at / finished_at
```

- 记录**必须**与业务数据在同一事务内写入；事务回滚则记录不存在。
- `payload` 是**自足**的：Worker 只凭它与 `kind` 就能完成写入，不回查业务用例、不依赖请求上下文。

## 4. 投递与消费

1. **投递**：请求事务提交后再投递 Taskiq 任务，携带 `pending_id`。投递失败**不影响已提交的业务事实**——记录留在 `pending`，由兜底扫描重新投递。
2. **领取**：Worker 以租约方式领取（`state = processing` + `lease_owner` + `lease_expires_at`），不使用"先查后改"的无锁流程。
3. **消费**：按 `kind` 分派——
   - `profile_item`：写档案条目。**候选层与稳定层的判定在工具实现层硬卡**（`origin` 属于 `system_observation` 或 `ai_inference` 时不得写成已确认）。
   - `memory_episode`：写 Graphiti（实体抽取与嵌入），这是耗时与成本的主要来源。
4. **完成**：写入成功后置 `done`，记录 `finished_at`；同一事务内清理租约。

## 5. 幂等

- **幂等键就是 `pending_id`**：档案条目对 `pending_id` 建唯一约束。
- **图库侧必须由我们自建幂等**：已核实 Graphiti 对 episode 写入**没有任何官方的重试或幂等承诺**，源码中也没有重试装饰器。做法是——用**确定性 episode 标识**（由 `support_object_id` + `pending_id` 派生）写入，并在我们自己的表里记"该 pending 已写入图库"的标记；重试前先查该标记，标记的校验与状态推进在同一流程内完成。**不得**依赖图库去重。
- 重复投递、租约过期后重新领取、Worker 崩溃后重启——都不产生重复条目。
- 幂等**不**依赖队列的投递语义（at-least-once 是常态）。

## 6. 失败语义

| 情形 | 处置 |
|---|---|
| 待处理记录写入失败 | 请求失败并明确报错；**不得**返回"已记录" |
| 投递失败 | 记录保持 `pending`，由兜底扫描重投；不阻塞对话 |
| Worker 处理失败（可重试） | `attempts + 1`、`next_attempt_at` 按退避后移、`state` 回 `pending`、记 `last_error` |
| 超过重试上限 | 转 `dead` **并告警**；不得静默丢弃 |
| 图库写入失败 | 不回滚业务主事务；记录留在 `pending` 或 `dead`；**不得**当作已写入 |
| 租约过期（Worker 崩溃） | 视为可重新领取；靠幂等保证不重复写入 |
| 重复消费 | 幂等键去重 |
| 写入成功但摘要未刷新 | 允许滞后；注入时标注"摘要可能未含最新内容" |
| 授权在写入前被撤销 | 该记录在领取时按当前授权重新判定；不成立则转 `dead` 并记原因，**不写入** |

**最后一条需要特别说明**：待处理记录里带着发起时的 `account_id` 与对象标识，但**授权判定必须在领取时重新做一次**——记录排队期间授权可能已经变化。这条把"授权不靠缓存判断"落到了异步路径上。

## 7. Worker 的边界

照项目结构设计：Worker 只消费待处理记录里的**显式载荷**，不回查业务用例、不假定请求上下文；只允许 `import` `core/*` 与 `modules/{profile,memory}`。全异步（Taskiq），**不引入同步与异步之间的桥接**。

## 8. 可观测与告警

需要采集并可告警：队列深度、**最老 `pending` 记录的年龄**、`attempts` 分布、`dead` 数量与原因分布、处理时延分位。

`dead` 数量必须告警，并且**要用人为制造的失败验证告警真的会响**——否则它就是一个"坏了没人知道"的指标。一期的人工处理（查看与重放/丢弃）由运营执行，不做界面。

## 9. 一期不做（扩展缝）

- 优先级队列与任务路由（出现真实的优先级需求再说）。
- 批量合并写入（出现成本或吞吐压力再说）。
- 死信的人工重放界面（一期由运营直接操作）。
- 写入失败对用户的可见补偿（例如"这条没保存成功，点这里重试"）——**待确认是否需要**。

## 10. 待确认参数

重试上限 `N` 与退避曲线；租约时长；兜底扫描周期；`dead` 的保留时长。四项都登记于[设计待办](../../TODO.md)第四节。

## 11. 验证方式

- **投递失败**：人为让投递抛错，验证记录留在 `pending` 并被兜底扫描拾起。
- **Worker 崩溃**：处理中途杀掉进程，验证租约过期后可重新领取，且不产生重复条目。
- **重复投递**：同一 `pending_id` 投递两次，验证只写一次。
- **图库失败**：让 Graphiti 调用失败，验证业务主事务不受影响、记录状态正确、且不进入 `done`。
- **超限转死信**：持续失败，验证转 `dead` 且告警触发。
- **授权变化**：排队期间撤销授权，验证领取时重新判定并拒绝写入。
- **断言"未处理不被当作已写入"**：任何非 `done` 状态都不得出现在档案或记忆中。
