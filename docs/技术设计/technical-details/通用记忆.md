## 1. 记忆是什么、不是什么

通用记忆是**关于使用者自身的、在使用与照护中沉淀的时间线经验**：本人偏好的沟通方式、自己的表达习惯、自己常遇到的处境、对既往做法的回看。它是**时间线**，档案是**结论性条目**——两者不互相替代（`RQ-MEM-02` 管关于支持对象的事实，本机制管使用者自己的经验）。

**归属（2026-09-29 用户裁决修正）**：记忆归属**账号**——分区键 `group_id = account_id`，**不随支持对象分区**。一个账号持有多个支持对象时，记忆是**共享的**：换对象不丢、不各自独立。原文主语「关于使用者自身」即 `RQ-MEM-01` 的表述，此前设计稿改为「随支持对象分区」并记为措辞修正，该次修改已由本次裁决撤销（见[决策记录](../decisions/通用记忆归属为账号.md)）。授权即账号本身——记忆不另设授权规则，也不接受调用方传入分区键。

**分区在 FalkorDB 后端是「一个账号一张图」，不是同图内的属性过滤**（2026-09-29 实测，**此前所有文档都隐含假设后者**）：Graphiti 的 `_resolve_request_scope` 在 `group_id != driver._database` 时执行 `driver.clone(database=group_id)`——即**换一个图**。实测证实：在默认图写一条 `group_id='acct_x'` 的节点，再用 `select_graph('acct_x')` 查是 **0 条**（两处是不同的图）。直接后果，实现时必须遵守：

- 我方自建的时间线/预注入 Cypher **必须 clone 到同名库**（`driver.clone(database=account_id)`），否则读不到 Graphiti 写进去的数据——这是「写进去了但读不到」的静默失败。
- 账号 id 必须满足 **Graphiti 的 `validate_group_id`**（`^[a-zA-Z0-9_-]+$`，源码用 `re.match`）。**注意（2026-09-29 评审更正）**：此前此处写「还须满足 FalkorDB 的图名约束」——**该说法不成立**，FalkorDB 图名没有字符集限制（逐值实测 `acct.aaa`、`acct aaa`、`账号一号`、`acct:aaa`、`acct/aaa`、`_` 全部建图成功）；客户端唯一真实的限制是**空图名**（`falkordb/asyncio/falkordb.py` 抛 `TypeError: Expected a string parameter`）。因此约束的唯一来源是 Graphiti；我方用 `fullmatch`（比它的 `re.match` 更严，拒绝尾随换行），方向安全。
- **`group_id` 的三种取值在框架里是三件事**（实测）：`None` → 回落到**默认分区**（属性 `'_'`，图仍是配置库）；`''` → 放行校验但 `clone(database='')` 造出**空图名的坏驱动**（其建索引任务抛 `TypeError`），**不是**「默认分区」；`'_'` → 是 `FalkorDriver.default_group_id`，`clone(database='_')` 走特判分支**落到 `default_db`**，与我方写 `'_'` 那张图不是同一个图。因此实现层：拒绝空串（它只会得到坏驱动）、拒绝 `'_'`（会造成我方与框架写入不同的图），并显式传账号值而**不依赖 `None` 回落**。
- **图的数量随账号线性增长**：每个账号一张图，图不自动回收。这是与「FalkorDB 单图多分区」不同的运维形态，登记为运维待观察项（第 11 节）。
- **不要每次请求都 clone 驱动**（实测）：`FalkorDriver.__init__` 在构造时会**调度一个后台任务**建索引与约束，而 `clone(database=X)`（X 与当前库名不同时）会**构造新的 `FalkorDriver` 实例**——因此**每 clone 一次就多一个后台任务**（实测 pending task 计数 1→2→3→4，基准 1 个 + 每次 clone 各 +1）。落地时应**按账号缓存驱动**（有界缓存 + 账号注销时失效），不得在每条查询路径上 clone。补两点实测：`clone.client is base.client` 为真（共享连接，故只需关一次）；clone 出的初始化任务异常**无人 retrieve**（会打 `Task exception was never retrieved`）。同库名时 `clone` 返回自身（不新建），这点可用但不足以覆盖多账号。
- **这条已经踩过，不是假设**（2026-09-29 实现期自查）：`store.py` 最初把「切到账号那张图」写成裸 `driver.clone(database=account_id)`，于是**每条查询泄漏一个驱动 + 一个建索引后台任务**（实测同一账号连续两次调用返回两个不同对象、pending task 2→3→4）。现改为经装配层的 `MemoryGraph.driver_for(account_id)`：按账号缓存、上界 `MAX_CACHED_ACCOUNT_DRIVERS = 64`（账号数无上界，无界缓存只是换一种泄漏），`aclose()` 时清空缓存并**逐个取消**克隆驱动自己的后台任务（连接是共享的，`FalkorDriver.close()` 会关客户端——因此只对克隆驱动调 `close()`，不重复关客户端）。裸 `account_driver()` 仍保留但已在 docstring 标注「热路径调用即泄漏」。
- `episode`/`EntityEdge` 上的 `group_id` 属性**仍然会被写入**，因此同图内的属性过滤仍可作为辅助判据；但**不能**依赖它跨图取数。

**为什么与档案必须分开**：纠正与删除的粒度（`RQ-MEM-03`）、授权主体、写入方三者都不同——记忆属使用者、可跨对象复用；档案属支持对象。混在同一分区里会让「使用者的偏好」与「当事人的特征」无法分别纠正与删除。

不做的事：

- 不承载档案条目（`propose_profile_item` 的活）。
- 不承载**关于支持对象**的经验与特征（那属档案；`RQ-MEM-01` 的「使用者自身」与 `RQ-MEM-02` 的「支持对象信息」是两条不同的写入路径）。
- 不在对话请求内同步写图库（写入路径不变量）。

## 2. 时间模型：图库两层各管什么

Graphiti 写入一个 episode 后派生三层，本机制只消费其中两层：

| 层 | 形状 | 时间语义 | 谁消费 |
|---|---|---|---|
| **episode 原文**（EpisodicNode） | `write_memory` 提交的 content 原文 | `created_at`（入库）与 `valid_at`（发生时间 `occurred_at`） | 时间线回看（`read_memory`、使用者显式回看） |
| **派生事实**（EntityEdge） | 实体→关系→实体的三元组，带 `valid_at` / `invalid_at` 双时间窗 | 失效语义**只存在于这一层**：新事实推翻旧事实时旧边打 `invalid_at`，不删除 | 应急预注入（"当前有效认识"） |

**不变量**：`RQ-MEM-01` 的"过期或已被推翻的内容不得作为当前依据误导后续输出"由**派生事实层 + `invalid_at` 过滤**承载。episode 原文永远保留时间线原貌（被推翻的事实原文仍在时间线上，这就是回看语义）——派生层负责不误导，原文层负责不篡改历史。

## 3. 记忆单元：一次 `write_memory` 一个 episode

- **粒度（2026-09-29 定）**：episode = 一次 `write_memory` 提交的 content。**不额外切分**：模型提交时已按"一件值得记住的事"组织内容（`profile-curation` 的 skill 纪律负责提交质量），再切分只会让回看时不知道哪段是哪次。
- **幂等依据是 episode 的 `uuid`，不是 `name`**（2026-09-29 实测修正）：Graphiti 的 Episodic 落库是 `MERGE (n:Episodic {uuid: $uuid})`——**身份由 uuid 决定**，`name` 只是属性；`add_episode(uuid=None)` 每次生成随机 uuid，重复投递会产生**两条 episode**。但**不能**简单地「把确定性 uuid 传给 `add_episode(uuid=...)`」：
  - **实测约束一**：`add_episode(uuid=...)` 内部先做 `EpisodicNode.get_by_uuid(uuid)`，**节点不存在时抛 `NodeNotFoundError`**——即该参数只在"节点已预建"时可用，**首次写入会失败**。且该查找发生在**该 group_id 对应的那张图**里（第 1 节），预建节点也必须建在同一张图，否则照样找不到（实测踩过）。
  - **实测约束二**：同 uuid 的 `MERGE ... SET n = {...}` 会**整节点覆盖**（重跑后节点数仍为 1，`content` 被新值覆盖），没有"已存在则跳过"的语义。
  - **实测约束三（写入形状）**：`add_episode(uuid=X)` **完全忽略 `episode_body`**，只用从图库加载的 `content`——「预建节点」写法必须**把正文一起预写进节点**。实测：预建 `content='预建正文'`、传 `episode_body='参数正文'`，落库仍是 `预建正文`。
  - **实测约束四（自定义属性会被抹掉）**：Graphiti 保存 episode 用 `SET n = {...}` **整图替换**，因此**自定义属性会被清除**。实测：预建时 `n.campfire_marker='mine'`，`add_episode` 之后变为 `None`。**结论：我方「已写入」标记绝不能放在图节点上**，必须落在我们自己的 PostgreSQL（`pending_write.state`，[写入路径](写入路径.md)第 5 节）——这条把"自建幂等标记"的必要性从推断变成了证据。
  - **实测约束五（`episode_metadata` 不落库）**：`EpisodicNode.episode_metadata` 字段存在，但 FalkorDB 的 save query 里**没有它**（只落 uuid/name/group_id/source_description/source/content/entity_edges/created_at/valid_at）。因此工具契约要求的**来源会话标识只能经 `source_description` 承载**，不能指望 `episode_metadata`。
  - **因此可行写法**：确定性 uuid 由 `pending_id` 派生并作为**我方幂等键**；写入前先查我方"已写入"标记（同[写入路径](写入路径.md)第 5 节）。图库侧须**先按确定性 uuid 预建节点（含正文与 `source_description`，且建在该账号对应的那张图）**，再 `add_episode(uuid=...)` 追加派生物。幂等**不依赖**图库的 MERGE 语义。
- **必填**：`occurred_at`（发生时间，进 `valid_at`）、来源（会话 id、消息定位、时间）。没有时间的记忆无法回看（工具契约已有此约束）。
- **`source` 必须是合法 `EpisodeType`**（实测陷阱）：取值只能是 `message` / `json` / `text` / `fact_triple`。写入一个非法值不会在写入期报错，而会在**读取期**让 `retrieve_episodes` 抛 `NotImplementedError`——写入层必须显式传入合法值，不得留空。
- **`group_id` 由当前登录账号决定，不接受调用方传入**：Graphiti 在 `group_id=None` 时回落到默认分区（FalkorDB 分支为 `'_'`）——忘记传分区键会把所有账号并进同一分区，这是必须由实现层堵掉的失败模式，不是文档约定。
- **`store_raw_episode_content` 必须保持 `True`**（Graphiti 默认值）：置 `False` 会把 episode 的 `content` 清空，而时间线回看读的就是该字段。
- **实体抽取质量未实测**（missing evidence）：派生层的抽取依赖 TokenHub 的 OpenAI 兼容端点做结构化输出，其质量决定派生事实层的实际可用性；实测安排见第 9 节。

## 4. 两条读路径

两个消费面、两种语义，各走各的层（2026-09-29 定）：

| 路径 | 读什么 | 语义 | 服务的消费面 |
|---|---|---|---|
| **时间线回看** | episode 原文，按 `valid_at` 排序、时间区间与关键词过滤 | "上次是怎么说的、这件事什么时候开始的"——**回看**，不判失效 | `read_memory` 工具（日常咨询按需调用、使用者显式回看） |
| **应急预注入** | 派生事实（EntityEdge）+ `invalid_at` 时效过滤 + 近期全量 | "账号当前有效的经验认识"——**注入**，必须排除已失效 | 应急入口构造第一条消息时由应用取数注入 |

- **时间线回看**：模型拿到的就是片段原文（带时间与会话标识），不转译、不摘要——回看要的是"当时怎么说的"。
- **应急预注入**：应用侧取数，不走工具轮次（时延纪律，见第 6 节）。
- 两路的一致性由同一图库保证：写一个 episode，两条路各自可见；删一个 episode，两条路都被账本过滤（第 7 节）。
- **两路都必须落到账号对应的那张图**（第 1 节实测：`group_id` 在 FalkorDB 后端是图名）。自建查询一律先 `driver.clone(database=account_id)`，不得在默认图上按 `group_id` 属性过滤——后者会读成空。
- **两路的取数 API 都需自建查询**（2026-09-29 源码核实，**设计不能按"框架已提供"写实现**）：`retrieve_episodes(reference_time, last_n, group_ids, source, saga)` **只有**"某时间点之前最近 N 条"这一种形状——没有时间区间参数、没有关键词参数；`EpisodicNode.get_by_group_ids(group_ids, limit, uuid_cursor)` 只有 `limit` 与 `uuid_cursor`，排序为 `ORDER BY uuid DESC`。时间区间与关键词过滤必须由我们自己在 Cypher 上实现。
- **`invalid_at` 为空必须显式过滤**：`EntityEdge.get_by_group_ids(...)` **不**过滤 `invalid_at`，排序为 `ORDER BY e.uuid DESC`（不是时间倒序），且空结果会 `raise GroupsEdgesNotFoundError`——"该账号还没有记忆"会被抛成异常，实现层必须把"空"与"图库不可用"分开判定，否则第 6 节的降级语义会误报。

## 5. 注入预算与缓存纪律

- 记忆注入全部是**运行边界的消息**：应急预注入随应急上下文一起注入；日常的工具结果消息本身就是消息。**系统提示词保持静态**（[压缩策略](压缩策略.md)第 8 节），记忆内容不进系统提示词。
- **预算共享**：应急预注入的记忆条目与档案七组、RAG 注入共享同一条注入预算管道（基座第 4 节"组装顺序与预算由基座决定"），不另设记忆专属预算；具体数字沿用 RAG 策略第 10 节的注入预算（窗口 ≤8%，**待确认**）。
- **条数上限不等于预算**（2026-09-29 修正）：`emergency_memory_limit` 只限条数，而 `fact` 文本长度无界——20 条的字符量可以远超 RAG 应急注入 top-3 的量级。因此**字符上限必须与条数上限成对**：`emergency_memory_chars`（参数表）。两者都只是**兜底**，真正的预算闸门仍待 8% 那个数字确认；在它确认前，本机制给出的是"不会击穿"的硬边界，而不是"预算已被守住"的保证——后者需要 RAG 策略第 10 节的数字先定（同[TODO](../../TODO.md)第四节"基座两项已确认要求尚未落地"的处理纪律）。

## 6. 应急预注入（选路：近期全量，2026-09-29 定）

**为什么不是语义检索**：Graphiti `search()` 是嵌入+BM25+图遍历+重排的混合检索，每次应急入口运行前跑一次会引入不确定时延与嵌入调用，违背 `RQ-EMG-03`（首字 ≤10 秒）；且八项现场采集多为勾选短文本，嵌入质量存疑。**一期每账号的记忆量小**（真实数据量 missing evidence），"近期全量 + 让模型在注入内自行判断相关性"是零嵌入成本的确定性方案。

- **取数**：按 `group_id = account_id` 分区，取 `invalid_at` 为空的派生事实边，按 `valid_at` 倒序、上限 `emergency_memory_limit` 条与 `emergency_memory_chars` 字符（参数表）。**该查询须自建**（第 4 节：`EntityEdge.get_by_group_ids` 不过滤 `invalid_at`、不按时间排序）。
- **注入形状**：每条事实带 `fact` 文本、`valid_at`、来源 episode 指针；与档案七组一起注入（[个性化档案](个性化档案.md)第 8 节 `emergency_context` 同路），模型可见"这是记忆时间线沉淀的经验"。
- **降级**：图库不可用时**明确标注该来源不可用**（基座第 9 节），不得当作"没有记忆"静默处理；应急运行不因此失败。**"没有记忆"（查询返回空）与"图库不可用"（查询失败）必须区分**——前者是正常状态、不标注降级，后者必须标注。
- **归属校验**：分区键就是当前登录账号（第 1 节），应用侧取数不接受外部传入账号标识；跨账号读取在构造查询前即不可能发生。
- **语义检索为扩展缝**：重访条件——单账号派生事实数超过 `emergency_memory_limit` 的常态持续出现，或实测预注入时延不可忽略。

## 7. 删除账本（2026-09-29 定）

**问题**：Graphiti 的 `remove_episode` 只删该 episode **独占**的实体与边；共享实体的摘要不重算、被它强化过的边残留、它标记失效的边保留失效标记（源码实读）。纯 `remove_episode` 无法满足 `RQ-MEM-03`"删除须覆盖检索与衍生中的使用"。

**方案：我方删除账本**（与 `pending_write` 的"图库无幂等承诺→我方自建幂等标记"同构）：

```text
campfire_memory_deletion_ledger
├── episode_key        # 确定性 episode uuid（由 pending_id 派生，与写入路径第 5 节同源）
├── account_id         # 归属账号（分区键同源）
├── deleted_at
├── deleted_by         # 发起删除的账号
├── reason             # user_request | correction | account_deletion
└── derived_uuids      # 删除时已知的派生物清单（边与节点 uuid，尽力记录）
```

（表名遵循 [core/db](../../../apps/api/src/campfire/core/db/__init__.py) 的 `campfire_` 前缀约定，避免与 SuperTokens core 自建表、SDK 自建表撞名。）

- **`episode_key` 建唯一约束**：同一条记忆重复删除不得产生第二行——删除本身也须幂等（落在**存储约束**通道，不是应用层先查后写）。
- **`reason` 的词表落在 CHECK 约束上**（2026-09-29 评审发现后补，迁移 `760b797c8bab`）：此前 `pg_constraint` 里只有 PK 与 UNIQUE，探针 `INSERT ... reason='not_a_valid_reason'` **成功**——注释写着「取值见 `DELETION_REASONS`」，存储层却接受任意字符串。删除原因进审计，静默写入未知原因会让审计结论不可信。代价是词表变更需一次迁移，**有意接受**。
- **`derived_uuids` 是 JSONB 且插入时默认为 `[]`**：注意 `default=` **只在 flush/INSERT 时生效**（实测），构造后立刻读仍是 `None`——调用方若在持久化前需要空列表必须自己赋值（`ledger.record_deletion` 的 `derived_uuids or []` 就是这么做的）。
- **`episode_key` 的入口校验在 `identity.to_episode_key`**：必须是合法 UUID 并归一为规范小写连字符形式。账本按等值过滤，大小写/花括号形式不一致会让「同一条记忆」在写入与读取两侧看起来是两个 key——即删除记了却过滤不到（静默失效）。
- **`account_id` / `deleted_by` 是文本（`varchar(128)`），不是 `uuid`**（2026-09-29 评审修正）：账号键的判据是 Graphiti 的 `[a-zA-Z0-9_-]`、**不只 UUID**。此前定为 `uuid` 列与之直接冲突——实测 `'acct_aaa'::uuid` 报 `invalid input syntax`，即**合法账号键无法落库**，该类账号的删除不可实现。宽度与 `identity.MAX_ACCOUNT_ID_LENGTH` 一致。**账号标识的形态已于 2026-09-29 裁决**（见[认证与账号](认证与账号.md)第 3 节）：一期取 SuperTokens 的用户标识（UUID v4 字符串，满足该判据），故落库值就是 UUID 文本；**列仍保留文本宽度**，因为判据来源是 Graphiti 而非 UUID 本身，收窄成 `uuid` 列会把「合法账号键」的裁决权交给 PostgreSQL。回滚该迁移在含非 UUID 值时会失败（有意的失败而非静默丢数据）。

- **读取侧过滤（唯一生效点）**：两条读路径一律先查账本——episode 时间线按 `episode_key` 过滤；派生事实按**来源 episode**过滤。**账本过滤是语义删除的生效点**，图库物理删除不是。
- **多来源边的删除语义（2026-09-29 明确）**：`EntityEdge.episodes` 是**列表**，Graphiti 在命中既有事实时会 `episodes.append(episode.uuid)`——同一条边带多个来源 episode 是**常态**，不是边角。因此判据必须是「**该边引用的 episode 中至少一条在账本中**即不注入」，而不是「全部被删」：只删一条而边仍带着它时，若不排除就等于删除没生效（`RQ-MEM-03`）。
- **物理清理延期与账本过滤的组合约束**：残留边仍带着已删 episode 的 uuid。若后续写入**合法地复用/强化了这条残留边**，它会永久满足"至少一条来源在账本中"而被一直过滤——**新记忆被旧删除连带屏蔽**。故物理清理不能无限期延期：一旦启用（第 11 节），清理必须**同时从残留边的 `episodes` 列表移除已删 uuid**，而不是只删独占派生物。这是本条与"物理清理延期"之间必须成对成立的约束。
- **图库物理清理延期**：账本已保证语义删除即时生效；图库内残留（共享摘要、失效边）只是存储问题，与 G6 同源，登记为扩展缝（第 11 节）。物理清理另按**账号**批量执行，不在删除请求路径内。
- **纠正的语义**：使用者纠正一条记忆 = 删除旧 episode + `write_memory` 写新 episode（`occurred_at` 用纠正所指的发生时间）。**旧边的失效不能假定为自动发生**——已由**实测关闭**（2026-09-29，直接调用纯函数 `resolve_edge_contradictions`，环境 graphiti-core 0.30.2）：

  | 情形 | 旧边是否被自动置 `invalid_at` |
  |---|---|
  | 新事实 `valid_at` **更晚**（正常推进） | **是**（置为新边的 `valid_at`） |
  | 新事实 `valid_at` **更早**（纠正指向更早时间） | **否**（返回空列表，旧边 `invalid_at` 仍为 `None`） |
  | 两者同一时间 | **否** |

  源码依据：该函数只在 `edge_valid_at < resolved_edge_valid_at`（`edge_operations.py` 的 `elif` 分支）时置失效，否则 `continue`——**严格小于**，故同时间也不失效。而纠正恰恰允许新 episode 的 `occurred_at` 早于被纠正事实。
  **因此（落法已定）**：纠正必须以**账本过滤兜底**作为正确性保证（删除旧 episode 后，引用它的派生边一律不注入，见本节的多来源判据）；「显式删除旧边」是可选的补充手段，**不能**作为正确性的唯一依赖。
- **验证**（对齐 `AC-08`、`EVID-D`）：删除一条记忆后，`read_memory` 不再返回该 episode；应急预注入不再包含**引用该 episode 的**派生事实；图库内残留**不构成违反**——验收对象是读取路径，不是物理存储。
- **删除与纠正的接口所有者（缺口，2026-09-29 记录）**：`AC-08` 要求的"删除一条记忆后两条读路径都不再返回"目前**没有承载它的工具**——[技能设计](技能设计.md)第 3 节的七个工具只有 `read_memory` / `write_memory`，`tools/` 下无 `delete_memory` 契约。与之相对，档案侧有 `confirm` / `correct`（[个性化档案](个性化档案.md)第 8 节）。记忆侧的删除/纠正入口（工具契约与归属）**尚未成文**，登记于 [TODO](../../TODO.md) `TECH-22`。
  **实现现状（2026-09-29）**：`modules/memory/deletion.py` 已落地 `delete_episode` 与 `correct_episode` 两个用例（`AC-08` 的机制载体），并有端到端集成测试（`test_memory_deletion_integration.py`，含「删除后两条读路径都不返回」的主用例，并用消融验证两条路径各自被独立钉住）。**仍缺的是工具契约与 `tools/` 包装**——即模型还调不到它。在契约成文前，这两个用例没有产品侧调用方。
- **删除不调图库**（实现约定，2026-09-29）：删除的正确性由账本独自保证，因此 `delete_episode` **不碰图库**。理由：把图库操作放进删除路径会让一个正常的删除请求因基础设施故障而不可用；而账本写入是本库（PostgreSQL）事务。图库残留只是存储问题（本节下文的物理清理延期），不构成验收违反。
- **删除一条从未写入的记忆也会记账**（实现约定，2026-09-29）：因为写入路径是异步的——「记忆已排队但尚未写入」时若拒绝记账，之后写入完成就会把用户已要求删除的记忆写进去（**删除被写入覆盖**）。先记账则写入侧能按账本判断该不该写。这条把删除与[写入路径](写入路径.md)第 5 节的幂等标记连成一体。

| Graphiti 嵌入器与 FalkorDB 向量索引的接通（`TECH-13` 残留） | 维度一致性落地 |

**实测到的两个构造期行为**（影响装配，不是失败语义）：

- `FalkorDriver.__init__` 会在构造时**调度一个后台任务**建索引与约束（`build_indices_and_constraints`）——因此「驱动构造成功」不等于索引已建好，也意味着进程退出时可能留下未完成的初始化任务。
- `Graphiti.__init__` 只在**显式传入** `llm_client` / `embedder` 时才用我们的客户端，否则回落到 `OpenAIClient()` / `OpenAIEmbedder()`（读 `OPENAI_API_KEY`）。记忆侧必须显式传入，否则会绕过 TokenHub 去连 OpenAI。
- **`cross_encoder` 也必须显式传入**（实测）：默认值 `OpenAIRerankerClient()` 会立刻构造 `AsyncOpenAI(api_key=None)` 并抛 `OpenAIError: Missing credentials`——**连构造都会失败**，不是运行期问题。一期不用重排（第 6 节不做语义检索），因此传一个「保持原序」的空实现即可，但**不能不传**。
- **`graphiti-core` 未把 `httpx` 写进依赖**（实测 0.30.2 的 `requires` 只有 neo4j / numpy / openai / posthog / pydantic / python-dotenv / tenacity），但它 `import httpx`——缺它会在 `import graphiti_core` 时直接 `ModuleNotFoundError`。本项目本就依赖 httpx，故不缺。

**一个数据质量陷阱**（实测，写入层必须防）：episode 的 `source` 字段若不是 `EpisodeType` 的合法取值（`message` / `json` / `text` / `fact_triple`），`retrieve_episodes` 会在读路径上抛 `NotImplementedError`——**写入期的脏数据会在读取期才炸**，且异常类型与语义无关。写入层必须保证 `source` 合法，读取层须把它转成明确失败。

## 11. 一期不做（扩展缝）

- **语义检索预注入**：单账号记忆量常态超限或时延不可忽略时重访（第 6 节）。
- **图库物理清理**：定期按账号批量清理账本中已删 episode 的残留派生物——**启用时必须同时从残留边的 `episodes` 列表移除已删 uuid**（第 7 节的组合约束），否则会连带屏蔽复用该边的新记忆；与 G6 的会话增长清理同批设计。
- **episode 原文的保留策略**（G6）：一期数据量小，不设 TTL；记忆量成为真实问题后再定。
- **按支持对象切分记忆的视图**：一期记忆属账号、对象间共享（第 1 节）；出现「按对象分别查看/隔离记忆」的真实消费面时重访，见[决策记录](../decisions/通用记忆归属为账号.md)的重访条件。

## 12. 验证方式

- **时间线回看**：写入三条记忆后按时间区间查询，验证返回带时间与会话标识的原文。**同时验证**：无过滤条件时的返回量有界（`retrieve_episodes` 只有"最近 N 条"形状，时间区间与关键词由自建查询承担）。
- **失效不误导**：写入 A 再写入推翻 A 的新记忆，应急预注入只含新事实边（`invalid_at` 过滤生效，且该过滤是自建查询的一部分）。
- **删除生效**（`AC-08` / `EVID-D`）：删除后两路读取都不再返回；图库残留不判失败。**多来源边单测**：一条被两个 episode 共同引用的边，删其一后必须不再注入。
- **纠正落地**：纠正后 `read_memory` 返回新原文、旧原文不返回；**旧边是否失效按实测结论处理**（`occurred_at` 早于被纠正事实时不假定自动失效）。
- **幂等**：同一确定性 uuid 重复写入只产生一条 episode（不得用 `name` 去重冒充）。
- **归属**：`group_id` 取自登录态；构造调用时无法传入他人账号标识。两个支持对象之间记忆**可见**（共享），档案**不可见**（`AC-22`）。
- **空与失败可区分**：新账号（无记忆）返回空且**不**标注降级；停图库时返回明确"记忆不可用"标注——覆盖 `GroupsEdgesNotFoundError` 被误当作故障的情形。
- **应急预注入时延**：实测取数路径（一次分区查询）对首字时延的影响可忽略（毫秒级）。
- **降级标注**：停图库后应急入口仍可运行，注入中含明确"记忆不可用"标注。
