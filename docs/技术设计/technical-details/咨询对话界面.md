## 1. 机制总览

```text
后端 SSE（RunEvent）                          前端
─────────────────                ────────────────────────────────────────
run_started ─┐                    infrastructure/sse.ts
text_delta   │ 解析、校验、  →     裸 RunEvent 异步流（AsyncIterable<RunEvent>）
progress     │ 错误映射               │
tool_call_*  │                      ▼
citation ────┘               features/consult/application/usecases.ts
candidate                   用例层：sendMessage / loadHistory / listSkills
run_finished / run_failed         │  端口定义（domain 层的 TS 类型）
                                  ▼
                             features/consult/viewModel/
                             状态归属（详第 4 节）：会话级 store（Zustand）、
                             运行状态机（useRunState）、assistant-ui 适配
                                  │
                                  ▼
                             features/consult/view/
                             对话页（Composer、Thread、MessageList）、
                             消息自定义 part 渲染器、应急表单页
```

一句话分工：**infrastructure 只做"事件解码"，application 只做"用例编排"，viewModel 做"状态与形状"，view 只做"渲染"**。SSE 事件到 UI 状态的映射规则是本层的核心机制，全部在 viewModel 层成文（第 4 节）。

## 2. runtime 选型：assistant-ui LocalRuntime

**结论**：对话 UI 采用 assistant-ui，走 `useLocalRuntime + ChatModelAdapter`（官方自定义 runtime 路径，[技术栈设计](../../技术栈设计.md)第 2 节已定）。

**为什么是 LocalRuntime 而不是 ExternalStoreRuntime**：

| 评价维度 | LocalRuntime | ExternalStoreRuntime |
|---|---|---|
| 消息状态归属 | runtime 内部管理 | 我们的 store 全量持有 |
| 需要写的代码 | 一个 `ChatModelAdapter.run` | messages + convertMessage + onNew/onEdit/onReload/onCancel |
| 分支/编辑/重生成 | runtime 免费提供 | 每个回调都要自己实现 |
| 与 SSE 的适配 | adapter 内逐事件 yield，天然映射 | 需在 store 里手动模拟流式追加 |

**取舍说明**：LocalRuntime 内部管理消息状态，看起来与"Zustand 管状态"的定调有张力——但对话消息不是业务状态，**后端会话存储才是它的真源**（基座第 2 节单真源）；前端 runtime 持有的只是呈现态。选择 LocalRuntime 后，Zustand 只管**会话级状态**（当前对话 id、激活 skill、待确认候选计数、连接状态），两者不重叠。

**DSH 对照**：本设计参考了 DSH 的消息流模型（事件驱动、流式渲染、引用与消息绑定呈现），但 DSH 的 web 端自行实现完整消息状态机；本项目用 assistant-ui 承担这一层，adapter 只做"后端事件 → 前端 chunk"的纯映射——**状态机逻辑被库承接，映射逻辑归我们**。

**风险已核实**：`ChatModelRunOptions` 里的 `unstable_getMessage`、`unstable_threadId` 字段带有不稳定性风险——本设计**不使用这两个字段**，adapter 只依赖稳定的 `messages`、`abortSignal` 与我们自己的闭包状态。

## 3. 事件流映射（SSE → UI 状态）

基座第 7 节定义了 8 种流式事件。映射规则：

| 事件 | viewModel 动作 | UI 呈现（view 层消费） |
|---|---|---|
| `run_started` | 初始化运行状态 `running`；记录激活 skill、注入项清单 | **输入框保留**、发送按钮置灰（可继续打字草稿，不可发送）；顶部状态条 |
| `reasoning_delta` | adapter yield reasoning part 增量 | 可折叠思考区（详第 6.3 节）：流式期间活动、结束后收起 |
| `text_delta` | adapter yield text part 增量 | 消息流式渲染 |
| `progress` | 更新进度文案（不改消息内容） | 状态条文案（"正在检索资料…"） |
| `tool_call_started` / `tool_call_finished` | 更新工具调用段（可折叠） | 工具调用指示器（名称+摘要，默认收起） |
| `citation` | 追加到当前 assistant 消息的 citations 数组 | 消息尾引用区（详第 5 节） |
| `question` | 追加 `data-question` part 到当前消息 | 提问卡片（详第 6.1 节）：选项按钮 + 自由输入 + 跳过 |
| `action_card` | 追加 `data-action-card` part 到当前消息 | 行动卡片（详第 6.2 节）：分区渲染，旧卡标失效 |
| `candidate` | 写入 profile 候选列表（Zustand，不进消息流） | 对话页轻提示"有 N 条待确认" |
| `run_finished` | 置 `idle`；保留引用清单 | 发送按钮恢复可用 |
| `run_failed` | 置 `failed` + 错误码映射为用户可读文案 | 错误 toast + 重试按钮 |

**三条不变量**：

1. **失败不得伪装成功**（基座第 9 节）：`run_failed` 到达时，已有 partial text 保留但消息标注"本次回答中断"；不得静默截断为完整回答。
2. **两路检索失败不得被解读为"没有资料"**（检索失败语义）：`run_failed` 的错误码若为检索类失败，toast 文案明确"检索暂时不可用"，不得写"未找到相关内容"。
3. **事件顺序防御**：`citation` 先于 `run_finished` 到达属正常；任何在 `run_finished` 之后到达的事件忽略（SSE 重连场景），丢弃计一条 debug 日志（不静默吞）。

**adapter 的实现形状**（viewModel 层，非完整代码）：

```typescript
// ChatModelAdapter.run 内：SSE 事件 → assistant-ui chunk
async *run({ messages, abortSignal }) {
  // 两段式（见 HTTP/SSE 契约第 4 节）：
  // 1. POST /consult/sessions/:id/messages（携带 pendingSkill）→ 取 run_id
  // 2. GET  /consult/runs/:run_id/stream 订阅
  //    for await 逐事件：
  //    text_delta → 累积文本，yield { content: [{ type: "text", text }] }
  //    citation   → yield data-citation part（第 5 节）
  //    run_failed → throw（runtime 置错误态）
  // 3. abortSignal 触发时调 POST /consult/runs/:run_id/cancel
}
```

| 应急表单页 | `/consult/emergency` | 八项现场采集（多数为勾选，一只手可完成）；提交即构造第一条消息并程序激活 |

### 4.2 状态归属三分（项目结构第 9 节既有定调）

| 状态 | 归属 | 说明 |
|---|---|---|
| 当前对话 id、激活 skill、技能目录、候选计数、连接状态 | viewModel 的 Zustand store | 跨页面、跨组件 |
| 输入框草稿、折叠展开、滚动位置 | view 组件内 `useState` | 纯视觉 |
| 对话消息与运行状态 | assistant-ui runtime | 真源在后端会话存储；前端是呈现态 |

**技能选择器**（`RQ-CON-08`）：选择只作用于下一条消息——发送时把 pendingSkill 作为参数传给 `sendMessage`，发送后立即清空选择器（视觉回归默认"自动"）。**授权口径（2026-10-01 授权语义重写后）**：选择消费的是"本次运行的激活写入"，不是授权——激活记录落会话历史后授权跨运行持续、会话内只增不减（[技能设计](技能设计.md)第 4 节）；因此选择器回归"自动"不代表已激活的技能失效，页头技能标签（`activated_skills`，多技能串联呈现）才是授权状态的可视面。选择器候选值 = 模型可见目录集（`daily-consulting`、`profile-curation`）；应急不进选择器（入口唯一，[HTTP/SSE 契约](../面/consult/HTTP与SSE契约.md)第 4.1 节值域裁决）。

### 4.4 历史水合（刷新后恢复）

对话 id 在 URL 中（React Router）。刷新或直链进入时：

1. `useConsultPage` 读 URL 的 `sessionId`，调 `loadHistory(sessionId)`（application 层）。
2. 后端返回该会话的消息列表（含每条消息的 part 序列——文本、工具调用摘要、引用）。
3. `history.ts` 把后端消息形状转换为 `ThreadMessageLike` 数组（含 `data-citation` part），经 `ThreadHistoryAdapter` 或直接注入 runtime。
4. 水合完成前显示骨架屏；**水合失败显示错误与重试**，不显示空对话冒充成功。

## 5. 引用与消息的绑定（citation as custom part）

[项目结构设计](../../项目结构设计.md)第 9 节定调"citation 跟消息走"。落地机制：

- citation 作为 assistant 消息 content 里的自定义 part：`{ type: "data-citation", data: { ... } }`——已核实 `data-*` 前缀 part 被自动转为 `DataMessagePart` 并可注册渲染器。
- `data` 载荷（对齐[资料与案例检索](../../技术设计/technical-details/资料与案例检索.md)第 3 节返回契约）：`item_id`、`library`、`title`、`source`、`applicable_scope`、`status`、`locator`、`ranking`，案例另带 `evidence_level`、`review_status`、`interview_at`、`makes_claims_high_risk`、`inferred_fields`、`authorization`。
- 渲染为消息尾部的"依据"区，默认收起，展开显示来源与适用范围（应急 skill 3.5 节"依据清单默认收起"的前端对应）。
- **绑定不变量**：citation part 与所属消息同生命周期，滚动、重放、历史水合都不错位——因为它是消息 content 的一部分，不是外部索引。

**candidate 不进消息流**（项目结构第 9 节）：进 Zustand 的候选计数，对话页只显示轻提示，点击跳转 profile 特性的候选确认页。

## 6. 应急路径的前端机制

应急表单页提交后：

1. 构造 `emergencyStart(payload: EmergencyFormPayload)`（application 用例）——POST 后端应急入口，后端组装三段输入（档案预取 + 八项 + 程序注入 skill）并启动运行。
2. 前端收到的仍是标准 `RunEvent` 流——**应急与日常共用同一对话页与同一 adapter**，差别只在：进入方式（表单 vs 输入框）、时延预期（`RQ-EMG-03`：首字 ≤10 秒——UI 有"正在分析现场情况…"进度提示，超 10 秒未首字显示降级提示）。
3. 八项现场采集全部可跳过（`RQ-EMG-01`）；跳过项在 payload 里显式标 `skipped: true`，**不得默认为正常**——前端只传"跳过"这个事实，解释权在后端与 skill。

**页面切换**：应急表单提交后 `navigate` 到 `/consult/sessions/:newId`，表单页即弃。

### 6.1 结构化提问（question part）

借鉴 DSH 的 `ask_user_question`（选项 + 自由回答 + 跳过三通道），但机制适配本项目的运行模型（基座第 2 节：一次运行跑到结束，没有运行中暂停）：

- **现有单题草案形状**：`question` 事件映射为当前 assistant 消息 content 里的 `{ type: "data-question", data: { question, options: [{ label, description? }], allowSkip } }` part（与 citation 同为 `data-*` 机制）。模型侧拟由基座 `ask_user` 工具产生（事件设计见[通用基座](通用基座.md)第 7 节）——工具参数即载荷，前端无需做任何文本解析。**多题接入尚未就绪**：下述统一多题交互已确认，但此单题形状不能表达一个批次；工具参数、事件载荷、历史记录与回答关联须同步对齐，登记于[设计待办](../../TODO.md)。单题在视图内按长度为 1 的问题组呈现，不改动现有运行契约；本地多题预览不代表真实事件已接通。
- **运行结束于提问**：`question` 事件后本次运行正常结束（`run_finished`）——**不是暂停等待**。回答作为下一条使用者消息发送，走与普通消息完全相同的 `sendMessage` 路径。
- **三条回答通道**：① 选项回答——点选暂存该题的 `label`，提交前允许改选；② 自由回答——暂存该题文本；③ 跳过——暂存该题的显式跳过状态。三种通道均不在逐题操作时发送消息，整组处理完毕后点击「提交」统一发送。多题回答须逐题保留题目与答案的对应关系；跳过必须保留显式标记（如"（跳过）"），**后端与 skill 按 `RQ-EMG-02` 的"未排除"语义处理，不得默认为正常**。
- **交互裁决（2026-09-30 用户再次确认）**：只保留一种提问结构，借鉴 DSH 支持一次提出多题、逐题切换、保留答案与最终统一提交；单题使用同一组件的 1/1 状态，日常和应急结构与行为相同。此裁决取代此前应急点选即发送规则；事实类问题仍不预选、不推荐答案。
- **组件**：`QuestionCard`（`MessageParts/` 内）——题干 + 编号选项与说明 + 自由回答 + 题号与处理进度 + 上一题/跳过/下一题或提交；切换题目保留各题作答，跳过只影响当前题，返回可以修改。最终提交后整组置为静态已提交记录，禁止重复作答；历史水合也使用同一记录形态。未提交即发送其他消息时，旧卡保留未提交草稿，不能冒充已回答。
- **输入区互斥（2026-09-30 用户确认）**：当前问题组等待作答时收起普通 Composer、SkillPicker 与发送按钮，保留各自的草稿和暂存选择；题卡收起、逐题切换仍属于等待作答，不恢复 Composer。整组提交（包括全部显式跳过后提交）或待回答组被移除后恢复。历史已提交记录不占用待作答状态；运行期间的进度与停止操作仍可用。可见性由当前待作答状态派生，不清空草稿，也不改变问题事件或回答发送机制。
- **应急追问**（`RQ-EMG-02`"一键选择、可跳过"）：同样经统一提问卡呈现，每题保留 2–4 个选项（如"有 / 没有 / 不确定"）及 `allowSkip: true`。一键选择只暂存该题答案，整组完成后提交；不增加新的提问组件或直接发送分支。

### 6.2 应急 Action Card 的卡片渲染

应急输出**不是一段流式散文，是一张结构化的行动卡**（应急 skill 3.4 节七节）。卡片渲染不是视觉偏好，是 `RQ-EMG-03` 的可读性要求——慌乱中的使用者需要"立即做"最先被看到，而不是在三百字里找。

- **产生方式与 `question` 不同构（2026-09-30 裁定）**：模型侧经**产品侧工具** `emit_emergency_action_card` 产出卡片（[工具契约](../面/consult/tools/emit_emergency_action_card.md)），基座把工具返回的信封翻成 `action_card` 事件（形状见[通用基座](通用基座.md)第 7.3 节）。前端映射为消息 content 里的 `{ type: "data-action-card", data: { … } }` part，字段取该节的通用信封（`sections` / `states` / `annotations`），**不再**是 `sections/sources/confidences` 这种领域专属形状——领域词表与校验落在工具参数上。**不解析模型 markdown 猜结构**——医疗风险等状态字段由参数模型的枚举在解析期拒绝越界值（`stable` / `uncertain` / `high_risk`），模型编不出第四种。
- **载荷形状**（对齐应急 skill 3.4/3.5 节）：七节各一条目（`当前状态`/`立即怎么沟通`/`立即做`/`不要做`/`需要的医疗检查`/`安全措施`/`何时升级`，第五节仅在医疗层未排除时出现）；每条动作带来源标注（六类）与置信等级（`confirmed/likely/possible/unknown`）；`medical_risk` 取值硬校验为三值。**七节的枚举标识符与中文小标题的对应见工具契约第 2 节**，前端按 `key` 分派、按 `heading` 显示。
- **组件**：`ActionCard`（`MessageParts/` 内）——按节分区渲染、状态字段（医疗风险、沟通水平）以可扫读的形式突出；依据清单（citation parts）默认收起挂在卡尾。
- **重复评估**（应急 skill 3.6 节）：新一轮评估产生**新卡**，旧卡不删除但渲染为"已过期，见最新卡片"的失效态——可区分、可回看，不在旧结论上打补丁。
- **流式关系**：卡片到达前的 partial text 保留（如"正在分析现场情况"的过渡文字）；卡片之后模型还可继续输出（如追问），同一消息内多 part 并存。
- **不做逐节流式渲染（2026-09-29 定，含核实结论）**：进度感知由首字文本流 + `progress` 事件 + 超时降级提示承担。技术核实（SDK 0.22.x 源码）：Chat Completions 的 tool-call 参数增量确实逐 token 到达，但 SDK 的 `buffer_tool_call_stream` 把 function 增量**缓冲到流结束**才产出 `tool_called` 事件，`RunItemStreamEvent` 无参数增量事件——要拿增量只能在 SDK 边界前自建 tee 拦截；且流式期间半截 JSON 无法做载荷校验（`medical_risk` 三值校验只能延后到整卡），"结构可校验"卖点与流式渲染天然错位。**重访条件**：实测卡片生成段 >10 秒，或使用者反馈等待焦虑。

### 6.3 思考过程的呈现（reasoning part）

**为什么要呈现**（2026-09-29 核实后定）：DeepSeek-V4.1-Flash 思考模式**默认开启**（effort=high），思考段经 `reasoning_content` 流式输出且回传由 SDK 自动处理（`reasoning_content_replay.py` 对 deepseek 模型自动回传，400 风险已覆盖）——不呈现它，思考期间界面就是白屏等待，直接伤 `RQ-EMG-03` 的时延体验。

- **机制**：`reasoning_delta` 事件 → adapter yield reasoning part（assistant-ui 原生支持，其 reasoning disclosure 组件自带"运行中自动展开、结束收起"行为）；历史水合时思考区默认收起。
- **呈现纪律**：思考是**模型中间态，可能含未定论内容，不是结论**——与正文视觉区隔（折叠形态）、不得作为依据引用、不参与 citation。应急场景默认收为一行"正在分析…"（慌乱中不需要看思维链，只需要知道在动）；日常默认收起、可手动展开。
- **与工具调用的交替**：思考与工具调用可交替多轮（DeepSeek 思考模式支持工具间思考）——每次思考段是独立的 reasoning part，按到达顺序渲染。

## 7. 失败语义与降级

失败一律显式标注，不静默：

| 情形 | 前端行为 |
|---|---|
| SSE 连接失败 | 带 `Last-Event-ID` 自动重连（指数退避，上限 3 次；耗尽、409 `run_not_resumable`、或运行流 **404** 一律改走历史水合）；重连期间输入框置灰并显示"连接中断，正在重连" |
| 重连耗尽 | 错误提示 + 手动重试按钮；**不显示空对话** |
| 会话过期/未登录（401） | 清理本地状态，跳转登录页（`RQ-ACC-01`） |
| 无档案（`AC-02`） | 非错误——正常进入，输出由后端标注"未使用个性化档案" |
| 发送中途取消 | 调 `POST /consult/runs/:run_id/cancel`；已渲染 partial text 保留并标"已中断" |
| 应急首字 >10 秒 | 显示"正在生成…建议先按通用安全措施行动"类降级提示（不替代、不伪造输出） |

## 8. 验证方式

- **单元（vitest）**：`chatAdapter` 的事件→chunk 映射（含失败、乱序防御）；`history.ts` 的后端消息→ThreadMessageLike 转换；`runStore` 的状态迁移。
- **组件测试**：citation part 渲染（默认收起、展开含来源）；QuestionCard 单题与多题共用结构、三通道逐题暂存、切换与返回保留答案、跳过可修改、未完成禁用提交、整组只发送一次且成为静态记录、未提交即发送后续消息不能冒充已回答；ActionCard 七节分区渲染、`medical_risk` 越界载荷被拒、重复评估后旧卡显示失效态；ReasoningDisclosure 默认收起、应急场景收为一行、思考内容不渲染为正文；技能选择器"发送即消费"；应急表单可全跳过提交。
- **E2E 级验收对照**（需后端就绪）：`AC-19`（选定技能后下一条消息按该 skill 作答）、`AC-03`（应急最小输入可完成）、`AC-02`（无档案不阻断）。
- **时延实测**：`AC-13`——记录提交到首字、到完整的时延分布（非单次演示值）。
- **失败注入**：断开 SSE（开发者工具 offline），验证重连与降级提示真实出现，而非纸面承诺。

## 9. 一期不做与重访条件

## 已知偏差与证据边界

- **assistant-ui 版本未锁定**：技术栈设计只定了库与 runtime 路径，具体版本在 `pnpm install` 时锁定；`data-*` part、`ThreadHistoryAdapter` 等 API 已于 2026-09-29 对照官方文档核实存在，但**未在本地跑过**——落地前以实际版本为准复核。
- **三个事件尚无承载（2026-09-30）**：`question`（第 6.1 节多题提问卡）、`action_card`（第 6.2 节行动卡）、`reasoning_delta`（第 6.3 节思考区）由[通用基座](通用基座.md)第 7 节声明，但 `agent/runtime/events.py` 的 `RunEvent` 联合里**都没有**。交互与页面设计均已确认，事件未定——三处组件无数据来源。载荷形状归基座，[HTTP/SSE 契约](../面/consult/HTTP与SSE契约.md)不发明；登记于[设计待办](../../TODO.md)。
- **后端契约已成文（2026-09-30）**：[HTTP/SSE 契约](../面/consult/HTTP与SSE契约.md)已定端点形状与传输，且**发送与订阅分两段**（`POST /consult/sessions/:id/messages` 取 `run_id` → `GET /consult/runs/:id/stream` 订阅，支持 `Last-Event-ID` 续传），本文第 3 节的 adapter 形状与第 7 节的重连语义已同步改写。**仍缺**：`question`、`action_card`、`reasoning_delta` 三个事件的载荷未定义（见下方第二条）。
