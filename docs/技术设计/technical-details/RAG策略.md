# RAG 策略

> **权威范围**：检索链的**内部机制与参数**——语料输入形态与分块、嵌入与向量存储、索引、融合与候选取值、条目聚合、上下文装配预算、时延预算与评测。**对外行为**（两库边界、返回契约、撤下传播、失败语义）由[资料与案例检索](资料与案例检索.md)拥有；供应商与框架选型由[技术栈设计](../../技术栈设计.md)拥有；`search_*` 的参数与返回由[咨询面 `tools/`](../面/consult/tools/)拥有。
> **状态**：2026-09-29 依用户确认的"全量引入 LlamaIndex"（`B`）、"合并改用 RRF"与"一期不直接导入 PDF"三项决定，以及已核实的供应商与框架事实重写，待用户确认。不代表已实现。
> **追溯**：`RQ-KB-01`、`RQ-KB-02`、`RQ-KB-04`、`RQ-CON-02`、`RQ-CON-03`、`RQ-EMG-03`、`AC-05`、`AC-06`、`AC-09`、`AC-11`。
> **依据（已核实）**：
> - **TokenHub 向量模型**：`POST /v1/embeddings` 兼容 OpenAI Embeddings；`Kinfra-Text-Embedding-0.6b` 1024 维、`Kinfra-Text-Embedding-4b` **2560 维**（维度固定），均 32k 上下文，`encoding_format` 仅 `float`，**单条文本 ≤2000 字符**、单请求建议 ≤128 条，支持中文等 30+ 语言（标注 CMTEB）。TokenHub 模型列表共八类，**无重排模型**。
> - **pgvector**：`vector` 建索引上限 **2000 维**、`halfvec` **4000 维**（此限只作用于建索引，不限制列类型）；**近似索引下过滤在索引扫描之后应用**，0.8.0 起支持 iterative index scan。
> - **LlamaIndex**（MIT；最新 0.14.25 / 2026-09-21；近一年约 21 个版本，节奏明显放缓；仍在 1.0 之前；`llama-index-core` wheel ≈11.9 MB、**29 个直接依赖**，Python ≥3.10,<4.0，可只装 core 加个别集成包）：`PGVectorStore` **把 metadata 过滤下推到 SQL**（`MetadataFilters` 可嵌套、`indexed_metadata_keys` 可建索引），支持自定义 `table_name`/`schema_name`/`perform_setup`/`use_jsonb` 与 `hnsw_kwargs`（m、ef_construction、ef_search、dist_method），`hybrid_search=True` 走 **tsvector** GIN；`QueryFusionRetriever` 有四种模式含 **`reciprocal_rerank`（RRF）**，入参是检索器列表、可混合自定义检索器；`IngestionPipeline` 有 docstore 去重与 `IngestionCache`（可用我们已有的 Redis）；`RetrieverEvaluator` 内置 `hit_rate`/`mrr`/`precision`/`recall`/`ndcg`；`MarkdownNodeParser` 按 `#` 层级切并写 `metadata["header_path"]`；`SentenceSplitter` 的 `chunk_size` 以 **token** 计、**不识别表格与列表**、不做超长二次切分。

## 1. 语料输入与分块

### 1.1 一期输入格式：处理后的 Markdown 或 HTML

- **系统不解析 PDF**（2026-09-29 定）。一期只接收**已处理好的 Markdown 或 HTML**。
- 理由：我们的"结构优先分块"依赖**标题层级**，而普通 PDF 读取器只给页码（`page_label`）、不保标题层级；同时保住"标题层级 + 表格结构 + 页码"需要官方的付费解析服务 **LlamaParse**，那会新增一个供应商与一套凭据，与"少供应商"相悖。
- 因此**资料准备流程在链外**：PDF → Markdown（外部工具 + 人工核对标题与表格）→ 才进系统。这一步属于 `EVID-F`（首期资料与案例的收集与录入），**责任人承担结构保真度**。
- **HTML 同样在链外清理**：只保留正文与标题层级，去掉导航、页脚与脚本残留。

### 1.2 分块：框架切 + 我们两层后处理

- **先用 `MarkdownNodeParser`**：按 `#` 层级切分，写出 `metadata["header_path"]`（如 `/H1/H2/`），代码块内的 `#` 不会误判为标题。
- **我们补两层后处理**（框架开箱不保证，这是引入后仍必须自己写的部分）：
  1. **表格与列表保护**：表格整块成节点（交给 `MarkdownElementNodeParser` 或我们的规则）；列表项不跨节点切断——切断了就直接制造错误依据。
  2. **超长二次切分**：框架**不对超长 section 再切**，而嵌入接口**单条硬上限 2000 字符**。超限节点按**句边界**二次切；仍超限的**不可分单元**（例如整页表格）标记为"未嵌入"并进人工处理队列，**不静默截断**。
- 目标块长 **400–800 字符**。注意 `SentenceSplitter` 的 `chunk_size` 以 **token** 计，中文下**不能直接当字符数用**，换算后仍受 2000 字符硬限约束。
- **结构边界处不重叠**（重叠会让同一内容在引用里出现两次，也让 `locator` 含混）。
- 每个节点携带：`item_id`、`chunk_index`、`header_path`（框架给）、`locator`（章节路径；**一期没有 PDF，所以没有页码**）、`char_count`。

### 1.3 案例卡片（2026-09-29 定）

卡片是结构化 JSON，不走 Markdown 分块链；**整卡一节点**（与[公共案例库](公共案例库.md)第 2 节"检索单位是卡片"一致）：

- **嵌入文本 = 全字段结构化拼接**：按"字段名：值"逐字段拼接（保留字段边界，比自由文本拼接的语义命中更准）；`_inferred` 的内容**不参与嵌入**（同公共案例库第 4 节"保留但不参与检索注入"的既有先例——推断依据不应驱动命中），`card_id`、`case_id` 等标识字段不嵌。
- **高风险字段参与嵌入**（`immediate_action`、`medical_criteria` 等）：`makes_claims_high_risk` 是返回时的标记而非检索层过滤（公共案例库第 5 节），呈现约束在 skill 层——不嵌入高风险字段，应急查询反而命不中对应卡片，分层支持策略就落空了。
- **超长处理复用第 1.2 节规则**：超 2000 字符按句边界二次切分，切出的多个节点同 `card_id`，聚合时归回卡片（与第 4 节条目聚合同一机制，不为卡片新造规则）。
- **`locator`**：卡片节点取卡片 `title`，回指靠 `card_id`；narrative 小节走五节标题路径（`场景背景` 等，等价于 `header_path` 语义）。

### 1.4 条目侧字段

- **`keywords`** 与 **`aliases`**：导入时填写（机构名、缩写、常见俗称、英文原名）。**字面路只查 `title` + 这两个字段，不查正文**——中文正文的 trigram 噪声很大，而真正需要字面命中的恰是这类短词。

## 2. 嵌入与向量存储

| 项 | 取值 |
|---|---|
| 嵌入服务 | TokenHub `POST /v1/embeddings`，经 LlamaIndex 的 OpenAI 兼容嵌入适配接入 |
| 模型 / 维度 | `Kinfra-Text-Embedding-4b` / **2560**（固定，不可自定义） |
| 单条上限 | 2000 字符（因此分块后处理是硬需求） |
| 批量 | 单请求建议 ≤128 条 |
| 节点存储 | `PGVectorStore`，**自带表结构**，`table_name` 自定义、`use_jsonb` 存 metadata |
| 索引 | 一期不建（见第 3 节） |

**真源划分（重要）**：

- **条目（`knowledge_item` / `case_item`）仍是事实真源**，留在我们自己的表里：状态（`published`/`internal`/`fictional`）、`withdrawn`、来源、适用范围、授权状态、`keywords`/`aliases` 都由它拥有，录入与审阅流程也走它。
- **节点表是它的投影**：需要在 **SQL 层过滤**的字段（状态、`withdrawn`、库别、授权）**同时写进节点的 metadata**，否则过滤会掉到应用层，违反"过滤在 SQL 内完成"的不变量。投影不是第二真源——它的权威仍是条目表。
- **案例库节点的投影清单（2026-09-29 定）**：在四项通用投影之上，卡片级节点再带——① 返回契约消费的字段（[资料与案例检索](资料与案例检索.md)第 3 节案例必带五项：`source_type`、`evidence_level`、`review_status`、`interview_at`、`makes_claims_high_risk`，加 `inferred_fields`）；② 聚合依赖：`card_id`；③ 结构化过滤维度（[公共案例库](公共案例库.md)第 2、5 节明说"元数据过滤/过滤维度"）：`risk_class`、`age_range`、`severity_level`、`behavior_type`、`ebp_tags`、`parent_category`。其余字段（`subject_type`、`consent_*`、`transcript_ref` 等）无过滤或返回消费，**从窄不投影**。
- **资料库节点的投影清单**：通用投影中适用于资料侧的是**状态、`withdrawn`、库别**（授权为案例侧维度；资料来源的许可是 `EVID-B` 的入库前置，不是查询期过滤）；节点再带——① 返回契约消费的字段（[资料与案例检索](资料与案例检索.md)第 3 节 `KnowledgeResult` 必带）：`title`、`source`、`applicable_scope`——`applicable_scope` 同时是 `search_knowledge` 的 `scope` 参数下推到 SQL 的依赖；`status` 已在通用投影、`locator` 已是节点结构字段（第 1.2 节），无需重复投影；② 聚合依赖：`item_id`（第 1.2 节已列）。一期资料侧无其他结构化过滤维度；其余字段（版本号、`keywords`、`aliases`）**从窄不投影**——字面路直接查条目表（第 3.1 节），不经节点投影。
- **两者同库同事务**（pgvector 就在主库）：因此**撤下可以在一个事务里同时改条目状态与删除该条目的节点**，不需要"最终一致"的窗口，`RQ-KB-04` 的"撤下即刻不可检索"得以成立。

**配置与 DDL 归属**：

- **嵌入模型名唯一配置处是 `core/config`**：`agent/model` 只拥有 LLM 模型名，而 `core/*` 不得依赖 `agent/*`（[项目结构设计](../../项目结构设计.md)第 7 节白名单），嵌入模型名（`Kinfra-Text-Embedding-4b`）经 `core/config` 注入，复用 `tokenhub_base_url`/`tokenhub_api_key`——嵌入服务同为 TokenHub，不引入第二套凭据。**维度不做成可配置项**：2560 与模型绑定，作为 `modules/library` 内的常量——可配置的维度会诱发「配错维度混库」（第 7 节纪律 4）。
- **连接串必须给两条**（2026-09-29 实测）：`PGVectorStore._connect()` **无条件同时建同步引擎（psycopg2）与异步引擎（asyncpg）**，因此 `connection_string` 与 `async_connection_string` 都必须提供——检索路径用原生 async 的 `aquery`/`aretrieve`，摄取写入用同步 `add`。
- **节点表 DDL 走 Alembic、`perform_setup=False`**：pgvector 扩展与节点表结构由迁移建立，与「schema 变更必须经迁移文件」的全局约定一致（[项目结构设计](../../项目结构设计.md)第 10 节），处置先例同 SDK 自建表（[设计待办](../../TODO.md)第五节）。**已实测（2026-09-29）**：`perform_setup=False` + 自建表下写入与 `aquery` 均正常，metadata 过滤**确实下推到 SQL 的 `WHERE`**（实测 SQL：`WHERE metadata_->>'item_id' = 'item-1' ORDER BY distance asc`），符合「过滤在 SQL 内完成」的不变量。迁移必须匹配框架的两条约定：**表名是 `data_<table_name>`**（框架加 `data_` 前缀），且 **`id` 为 `bigint` + sequence 自增**——缺 sequence 会写入失败。setup 期的静默吞错（`TECH-14`（b））随 `perform_setup=False` 不再适用。

## 3. 索引

### 3.1 字面路：我们自己的 GIN trigram

- 对**条目表**的 `title`、`keywords`、`aliases` 建 GIN trigram 索引。
- 查询用 `LIKE` / `ILIKE '%词%'`，**不得用 `~` / `~*`**（中文不走索引）。
- **需 ≥3 个连续汉字**：1–2 字的查询**不走字面路**，只走向量路与元数据过滤。
- 部署 locale **不得为 `C`**（`C` 下汉字被全部丢弃、相似度恒为 0）；本部署的 `en_US.utf8` 已实测可用（见下条）。
- **不要用框架的 `hybrid_search`**：它建的是 **tsvector** GIN（全文检索），中文没有分词器时基本不可用——这与 `pg_trgm` 是两回事。
- **字面检索器的实现归属（2026-09-29 定）**：整条链归 `modules/library`——`title`/`keywords`/`aliases` 是它自己的条目表列，节点投影、向量路、字面路、RRF 融合与条目聚合也都消费它的领域字段（状态、库别、`item_id`、案例卡片维度），机制与模式同属一个模块；`core/retrieval` 因此取消，不存在需要跨模块解释的接口缝。LlamaIndex 只有 library 一个消费者，**框架耦合止于 `modules/library`**；装配（工具注册）仍在入口按[项目结构设计](../../项目结构设计.md)第 7 节完成。
- **中文约束已实测**（2026-09-29，`pgvector/pgvector:pg17` = PostgreSQL 17.10，库 locale `en_US.utf8`）：`show_trgm('孤独症')` 产出 4 个三元组、相同文本 `similarity` 为 1、相关文本 0.45 vs 无关 0——**汉字被认作词字符**；索引行为：`LIKE '%孤独症儿童%'` 走 **Bitmap Index Scan**（GIN trigram），`~` 正则走 **Seq Scan**。上面三条约束（≥3 汉字、必须 `LIKE`、locale 不得为 `C`）全部成立。

### 3.2 向量索引（现在不建，条件触发）

- 一期不建：几千个节点下精确检索既足够快又保证召回 100%，而 2000 维的索引上限**只作用于建索引**，不建就不受限。
- **切换条件**：节点数超过**约 5 万**，或单次向量检索 SQL 超过 **100 毫秒**。
- 届时用框架的 `hnsw_kwargs` 建 HNSW（`m=16`、`ef_construction=64`、查询侧 `ef_search`），**并且我们自己设置会话级 `hnsw.iterative_scan`**（框架不负责这一项）——因为 pgvector 的过滤在索引扫描**之后**应用，而我们每条查询都带过滤。

## 4. 融合检索与候选

- **融合用 RRF**（2026-09-29 定）：`QueryFusionRetriever` 的 `reciprocal_rerank` 模式，检索器列表 = **pgvector 向量检索器 + 我们自研的 pg_trgm 检索器**。
- **为什么改用 RRF**：它只用**名次**、不用原始分数，因此不存在跨路分数量纲不一致的问题，也没有需要调的神秘权重；这比先前自拟的"路内排名 + 命中路数"更有依据。**不做跨路分数加权归一化。**
- **一期不用 LLM 多查询生成**（`QueryFusionRetriever` 支持，但会加一次模型调用，且应急时延吃紧）。
- 候选取值：向量路 **top-30**（节点）、字面路 **top-30**（按条目计；**待确认**）、融合后取 **top-8 条目**。
- 过滤（库别、状态、撤下、授权）**在 SQL 内完成**（metadata 过滤已核实可下推）。
- **条目聚合仍是我们自己写**：框架返回的是节点与分数，我们需要把同一 `item_id` 的多个节点**聚合为条目**、只保留名次最高的节点作为 snippet、并把条目名次上提；**同一轮不重复注入同一条目**。
- **两路在同一粒度上得名次**：`QueryFusionRetriever` 融合的单位是节点。向量路的候选自然是节点；字面路的检索单位是**条目**（条目表行），参与融合前展开为该条目的节点——同一条目的节点共享其名次，聚合时归回条目。RRF 只用名次、聚合取最佳节点，因此节点数多的条目不会获得名次优势；字面路候选槽位被长条目占满是已知代价，一期语料量小不构成问题，评测若显示字面路覆盖不足则重访候选数（第 10 节）。
- **一期不做重排**（2026-09-29 定）：TokenHub 没有重排模型，接外部重排会新增供应商，且加一次调用会吃掉应急的时延预算。

## 5. 上下文装配

- 注入形状与返回契约一致：标题、snippet、来源、适用范围、状态、`locator`。
- **预算：检索结果占模型窗口不超过 8%**（**待确认**）；超出时按名次截断并标注"未全部注入"。
- **应急路径更紧**：只注入 **top-3**，且不为凑依据追加检索（`RQ-EMG-03`）。
- 每条注入进**引用索引**（[基座](通用基座.md)第 4 节），以便输出回指。
- 顺序按最终名次；**不按库别分组**（避免"资料先于案例"这类隐含偏好）。

## 6. 时延预算

- 一次检索 = **一次 query 嵌入（网络往返）+ 一次融合 SQL**（一期无向量索引，几千节点的顺序扫描）。
- 日常路径不设单独指标；**应急路径首字 ≤10 秒**（`RQ-EMG-03`）→ 嵌入调用必须与**档案预注入并行**，不串行等待。

## 7. 摄取流水线

**摄取不暴露在应用里**（2026-09-29 定）：没有上传接口、没有知识库管理页、没有审核工作流 UI。资料与案例在**本地**处理入库，检索才在运行时由两个工具使用。

- **入口形态**：应用包内的**一个 CLI 入口**（`python -m campfire.cli ingest <路径>`），**跑在同一镜像里**、连同一个库。**不是**仓库根 `scripts/` 下的独立脚本——它必须复用同一份依赖与同一套写入逻辑（条目表、幂等、嵌入适配），独立脚本一定会漂移。「本地」指的是**运行环境与触发方式**（不暴露成服务端点），不是「独立代码」。CLI 只是入口：摄取流水线、分块链与嵌入适配的实现归 `modules/library`（检索链与摄取同属一个模块，见第 3.1 节的实现归属）。
- **流水线**：`IngestionPipeline`，transformations = 我们的分块链（`MarkdownNodeParser` + 两层后处理）+ 嵌入。
- **去重与增量**：docstore 按 doc_id + hash 判断（未变跳过、变了重新 upsert）；`IngestionCache` 用我们已有的 Redis，避免重复嵌入同一文本。
- **导入是一次链外准备 + 一次链内摄取**：链外产出 md/html，链内负责切分、嵌入与写入。
- 导入失败要么整份成功、要么明确失败并留下可见记录；**不留下「一半进去了」的静默状态**。不受 HTTP 超时约束，因此**一份文件一个事务**。

**四条必须与「本地跑」一起成立的纪律**：

1. **凭据与环境**：脚本要连生产库——必须明确**谁能在哪台机器上、用哪套凭据**执行；凭据经环境注入，不入版本库（`AGENTS.md` 的密钥纪律同样适用）。
2. **可复现性**：必须**在同一镜像与同一 lockfile 里跑**（例如容器内执行），否则本地与线上的依赖差异会让**分块与嵌入结果不一致**。
3. **摄取记账**：没有应用内审计，就由脚本自己写**导入记录**——批次、文件、条目数、操作者、时间、脚本版本。否则将来撤下某条资料时无法回溯它是从哪份文件、哪一版进来的。
4. **换嵌入模型必须整库重建**：维度固定（2560），混入不同维度的向量会让检索静默失准。

## 8. 评测

- 用 `RetrieverEvaluator`（`hit_rate`、`mrr`、`recall`、`ndcg`），**配合我们手工构造的 20–30 条查询与期望条目**；覆盖五类：机构名与缩写、1–2 字短词、纯语义改写、跨语言术语、**家长口语改写**（用自然口语表述的咨询问题，如"孩子装听不见怎么办"，期望命中临床文风卡片——案例卡片的文风与使用者查询的口语鸿沟是嵌入检索的脆弱点，2026-09-29 实读上游 L2 卡片确认卡片为临床/指南腔，但鸿沟幅度与模型改写能否弥合**均无证据**，由本类量化）。
- **一期没有语料**（`EVID-F` 未完成），所以先建用例集与指标，不跑分数；任何"效果良好"的判断在此之前都不成立。
- `generate_question_context_pairs` 可合成评测集（需模型调用），但**合成集不能替代手工基准**，只用于扩充。
- 另记：两路各自贡献的命中数（RRF 下用于判断某一路是否在拖后腿）、单次检索耗时、注入 token 数。

### 8.1 案例检索的查询改写桥（评测闸门后落地，2026-09-29 定方向）

**问题**：案例卡片是临床/指南文风（实读上游 L2 卡片确认），使用者查询是口语描述——查询与文档之间的文体鸿沟是嵌入检索的脆弱点；且行为维度存在**值域外案例**（上游 `_inferred` 自证"被动任务拒绝/拖延不在标准行为类型枚举中"），口语行为描述只能靠语义路命中。

**归属**：改写由**咨询模型在工具调用内完成**——`query` 本来就是模型生成的字符串，skill 引导它"查询词用简明的行为与情境描述，不用使用者原话转写"（例：不搜"孩子装听不见怎么办"，搜"听到指令不执行、拖延、假装未听见"）。零新增模型调用、零新组件，应急时延预算不受冲击；与第 4 节"一期不用 LLM 多查询生成"不冲突（该条禁的是检索器内部加模型调用，此处是 skill 层引导、同一帧生成）。

**闸门（已写入 skill，评测验证、无效则回退）**：第 8 节第五类评测（家长口语改写）量化两件事——① 鸿沟实际幅度（口语直接搜 vs 标准措辞搜的召回差）；② 模型自改写是否弥合。**检索引导已按用户 2026-09-29 指令写入两个咨询 skill**（[日常](../面/consult/skills/daily-consulting.md) 3.4 节、[应急](../面/consult/skills/emergency-consulting.md)第 6 节）；评测若显示改写无效，则回退该引导——不留未经验证仍生效的提示词。

**条件项**：入库侧为案例补口语别名（写进 `keywords`/`aliases`，喂字面路）只在评测显示字面路在口语查询上系统性漏召时考虑；`ebp_tags` 反向映射查询需先核验 NCAEP 值域（上游 23–28 项自称补充项、未独立核验）。

## 9. 一期不做与重访条件

| 不做 | 重访条件 |
|---|---|
| **重排** | 评测显示向量路 recall@30 尚可但 top-8 精排明显差——说明是排序问题而非召回问题 |
| LLM 多查询生成 | 评测显示同一问题换说法后召回骤降 |
| 向量索引 | 节点数 >5 万，或单次向量检索 SQL >100 毫秒 |
| **PDF 解析**（含引入付费解析服务） | 一期链外准备的成本被证明不可持续，且数据处理条款核实通过 |
| 条目摘要嵌入、父子块 | 评测显示长文档的局部细节检索不到 |

## 10. 参数表

| 参数 | 取值 |
|---|---|
| 输入格式 | 处理后的 Markdown / HTML（**不接 PDF**） |

| 注入预算 | 窗口的 ≤8%（**待确认**）；应急 top-3 |

## 11. 记忆侧的嵌入（Graphiti）

- Graphiti 的嵌入器必须配置为**同一个 TokenHub 向量模型**——否则会引入第二个供应商的凭据。
- 维度一致性：Graphiti 侧与 FalkorDB 向量索引的维度必须匹配（2560）；FalkorDB 向量索引**已核实支持 1–4096 维**（2560 在范围内，`TECH-13`），Graphiti 嵌入器与其索引的接通方式仍须实测。
- 记忆写入在 Worker 内异步执行（[写入路径](写入路径.md)），嵌入调用计入 Worker 的成本与重试预算；嵌入失败按记忆写入失败处理，不回滚业务主事务。

## 12. 依赖代价（照实记）

- `llama-index-core` wheel ≈11.9 MB、**29 个直接依赖**（含 `nltk`、`tiktoken`、`networkx`、`sqlalchemy`、`numpy`），间接依赖通常上百；Python ≥3.10,<4.0。
- 只装 `llama-index-core` 与所需集成包，**不装全家桶 `llama-index`**（它只是 starter bundle）。
- 这是"全量引入"的真实代价，登记在此以便日后复核是否值得。
