# RAG 策略

> **权威范围**：检索链的**内部机制与参数**——语料输入形态与分块、嵌入与向量存储、索引、融合与候选取值、条目聚合、上下文装配预算、时延预算与评测。**对外行为**（两库边界、返回契约、撤下传播、失败语义）由[资料与案例检索](资料与案例检索.md)拥有；供应商与框架选型由[技术栈设计](../../技术栈设计.md)拥有；`search_*` 的参数与返回由[咨询面 `tools/`](../面/consult/tools/)拥有。
> **状态**：2026-09-29 依用户确认的"全量引入 LlamaIndex"（`B`）、"合并改用 RRF"与"一期不直接导入 PDF"三项决定，以及已核实的供应商与框架事实重写；**同日按实现期实测修订四处**——融合自实现（框架 RRF 要求同步检索器）、摄取不经框架 `IngestionPipeline`（要同事务）、嵌入用 `model_name=` 接入、分块保护与超长切分的确切行为。**检索链已实现**（`modules/library/`），真实语料与真实嵌入调用未验证（`EVID-F` 与 `TECH-20`）。
> **追溯**：`RQ-KB-01`、`RQ-KB-02`、`RQ-KB-04`、`RQ-CON-02`、`RQ-CON-03`、`RQ-EMG-03`、`AC-05`、`AC-06`、`AC-09`、`AC-11`。
> **依据（已核实）**：
> - **实现期实测（2026-09-29，真实容器、真实 TokenHub 调用与安装产物）**：`OpenAIEmbedding` 必须用 `model_name=` 传自定义模型名（`model=` 走枚举校验会抛错）；**且必须显式传 `encoding_format="float"`**（SDK 默认填 `base64`，TokenHub 只接受 `float`，实测错误码 `400001`）；真实嵌入**维度 2560**、语义可区分（相关文本 0.54 vs 无关 0.36）；`PGVectorStore.add()` 自建并提交事务（不能参与外部事务）、`aquery`/`adelete` 为原生 async、`engine`/`async_engine` 必须成对注入；**框架 `TextNode.hash` 由「文本 + metadata」共同决定**（两路节点仅文本一致时哈希不同，RRF 无法合并——见第 4 节）；**框架 `header_path` 只含父级路径、不含当前标题**（`## 一、服务对象` 的节点 header_path 只有 `/规范/`），`locator` 必须自行补上章节标题；`MetadataFilter.value` 不含 `bool`；`gin_trgm_ops` 不接受 `text[]`；`MarkdownNodeParser` 不切进表格/列表内部、也不对超长 section 二次切分。
> - **TokenHub 向量模型**：`POST /v1/embeddings` 兼容 OpenAI Embeddings；`Kinfra-Text-Embedding-0.6b` 1024 维、`Kinfra-Text-Embedding-4b` **2560 维**（维度固定），均 32k 上下文，`encoding_format` 仅 `float`，**单条文本 ≤2000 字符**、单请求建议 ≤128 条，支持中文等 30+ 语言（标注 CMTEB）。TokenHub 模型列表共八类，**无重排模型**。
> - **pgvector**：`vector` 建索引上限 **2000 维**、`halfvec` **4000 维**（此限只作用于建索引，不限制列类型）；**近似索引下过滤在索引扫描之后应用**，0.8.0 起支持 iterative index scan。
> - **LlamaIndex**（MIT；最新 0.14.25 / 2026-09-21；近一年约 21 个版本，节奏明显放缓；仍在 1.0 之前；`llama-index-core` wheel ≈11.9 MB、**29 个直接依赖**，Python ≥3.10,<4.0，可只装 core 加个别集成包）：`PGVectorStore` **把 metadata 过滤下推到 SQL**（`MetadataFilters` 可嵌套、`indexed_metadata_keys` 可建索引），支持自定义 `table_name`/`schema_name`/`perform_setup`/`use_jsonb` 与 `hnsw_kwargs`（m、ef_construction、ef_search、dist_method），`hybrid_search=True` 走 **tsvector** GIN；`QueryFusionRetriever` 有四种模式含 **`reciprocal_rerank`（RRF）**，入参是检索器列表、可混合自定义检索器；`IngestionPipeline` 有 docstore 去重与 `IngestionCache`（可用我们已有的 Redis）；`RetrieverEvaluator` 内置 `hit_rate`/`mrr`/`precision`/`recall`/`ndcg`；`MarkdownNodeParser` 按 `#` 层级切并写 `metadata["header_path"]`；`SentenceSplitter` 的 `chunk_size` 以 **token** 计、**不识别表格与列表**、不做超长二次切分。

## 1. 语料输入与分块

### 1.1 一期输入格式：处理后的 Markdown 或 HTML

- **系统不解析 PDF**（2026-09-29 定）。一期只接收**已处理好的 Markdown 或 HTML**。
- 理由：我们的"结构优先分块"依赖**标题层级**，而普通 PDF 读取器只给页码（`page_label`）、不保标题层级；同时保住"标题层级 + 表格结构 + 页码"需要官方的付费解析服务 **LlamaParse**，那会新增一个供应商与一套凭据，与"少供应商"相悖。
- 因此**资料准备流程在链外**：PDF → Markdown（外部工具 + 人工核对标题与表格）→ 才进系统。这一步属于 `EVID-F`（首期资料与案例的收集与录入），**责任人承担结构保真度**。
- **HTML 同样在链外清理**：只保留正文与标题层级，去掉导航、页脚与脚本残留。**加工工具是应用包内的 CLI**（2026-09-29 实现）：
  - `python -m campfire.cli convert <input.html> --out <output.md>` —— 实现归 `modules/library/html_extract.py`（数据加工属检索链）。**与 ingest 分成两条命令**：设计要求「加工后＋人工核对标题与表格」才进系统，convert 是**纯转换**（不连库、不调模型、零成本），产物可先审再喂；把转换并进 ingest 会跳过"审"这一步。
  - **正文容器按优先级选**：`section.body.main-article-body` → `article .body` → `article` → `main` → `body`。按优先级而非"取文本最多"（实测教训：PMC 的 `<article>` 有 87,195 字符、比正文容器 80,523 **更大**，多出的是 front-matter 的作者与单位；按大小选会把作者名渲染成 `###` 标题并错误嵌套后续正文）。退回 `body` 时 CLI 显式告警，**不假装选到了正文**。
  - **元信息容器整体剔除**：`front-matter`/`author-notes`/`history` 等（作者、单位、投稿史、版权声明）。它们在页面里常被标成 `h3`，留在正文会与真正的章节标题混进同一棵 `header_path` 树。
  - **`h1–h6` → `#`–`######`**、**`<table>` → Markdown 表格**（单元格数不一致的行按列补齐并**留痕**）。标题层级是分块链的硬依赖。
  - **块级链接保留文本，界面控件丢弃**：实测「Supplementary file1 (PDF 160 KB)」这类补充材料链接在早先实现里**整条消失**（真实内容丢失，由守恒对账抓出）。控件判据是 `target="_blank"` 或位于 `<figure>` 内——**通用网页约定而非站点特定 class**，按 class 判会随站点改版失效。
  - **图片不接线但必须留痕**：一期不支持图片，原位写「（此处原件有图片，一期不支持图片，未接入）」，**不静默丢弃**。
  - **元数据从出版方标注抽取**（`citation_*`/`DC.*`/`og:*`）：标题、DOI、期刊、日期、作者、URL、许可声明。**用出版方元数据而非人工转写**——它同时是**内容身份校验**的材料（采集过程出现过"PMC 编号猜错、抓回完全无关文献且 HTTP 200"，只看状态码会静默污染语料库）。
  - **守恒对账要求**：HTML→Markdown 的质检用**逐文本节点核对**（不是逐行比对——HTML 是树，一行可能是整段）。实测 PMC：正文容器内 ≥25 字符的文本节点 364 个，缺失 0 个。
- **语料件的元数据写在文件头部的 YAML frontmatter**（2026-09-29 实现期定）：`source`、`applicable_scope`、`title`、`keywords`、`aliases`、`license` 等键与正文**同文件**，由摄取链解析为条目字段。理由：出处与适用范围写在文件里比命令行参数更不易错配（一次导入几十份时尤其明显），而许可与出处**必须随语料存活**——它们是一期发布闸门 `EVID-B` 的判据。frontmatter **不参与分块**（进正文会污染检索内容，实测过：YAML 会成为一个可检索节点）。**缺 `source` 或 `applicable_scope` 即拒绝入库**（不变量，`RQ-KB-02`）：可在文件里给，也可由命令行 `--source`/`--scope` 给，显式参数优先。
- **原件常含无关内容，加工时要裁剪并留痕**：例如《国家卫健委公报》是整期刊物，同期刊载食品安全、网络安全、人才规划等其他公文。整份入库会让无关内容进入检索（`header_path` 相同的节点混在一起尤其难筛）。裁剪范围与理由写进 frontmatter 的 `derivation` 键——**不静默丢弃**。

### 1.2 分块：框架切 + 我们两层后处理

- **先用 `MarkdownNodeParser`**：按 `#` 层级切分，写出 `metadata["header_path"]`（如 `/H1/H2/`），代码块内的 `#` 不会误判为标题。
- **我们补两层后处理**（框架开箱不保证，这是引入后仍必须自己写的部分；实现见 `modules/library/chunking.py`）：
  1. **表格与列表保护**：实测框架按标题边界切分，**不会切进表格或列表内部**（表格整块成节点、列表项不跨节点）——但它不保证结构，因此我们的切分仍**只在段落/句子边界进行**；结构单元**不做中间切断**（不把一行切开）。
  2. **超长二次切分**：框架**不对超长 section 再切**（实测一个 2248 字符的 section 原样成为一个节点），而嵌入接口**单条硬上限 2000 字符**。超限内容按**段落边界** → **句边界** 依次切分。
     - **超长表格按行切分、每片重复表头**（2026-09-29 定，实测教训）：保护的本意是不切断**行内**，而按行分段并重复表头产出的每片仍是**合法且自解释**的 Markdown 表格（表头决定列义）。早先一律判"以表格为主，切断会破坏结构"导致 PMC 论文的 27 种循证实践清单（Table 2，8,487 字符）**不进检索**——而"有哪些循证实践"恰是最可能的提问，等于丢掉论文的核心交付物。表头识别要求首两行是「列名行 + `|---|` 分隔行」；识别不出时**仍交人工**（宁可漏嵌，也不产出列义不明的碎片）。
     - 仍不可分的单元（无标点的超长串、缺分隔行的畸形表格）标记 `needs_manual_review` 并计入人工处理队列，**不静默截断**。
  3. **小段落合并**：切出的碎片合并回目标区间，减少语义不完整的块。
- 目标块长 **400–800 字符**，硬上限 2000 字符。**字符计数用 Unicode 码点**（`len(str)`）而非框架 `SentenceSplitter` 的 token 计数——嵌入接口的限制是**字符**，中文下 token 与字符不是一回事。标题路径会拼入块文本（保留层级语义），因此**计入长度预算**。
- **结构边界处不重叠**（重叠会让同一内容在引用里出现两次，也让 `locator` 含混）。
- 每个节点携带：`item_id`、`chunk_index`、`header_path`（框架给）、`locator`（章节路径；**一期没有 PDF，所以没有页码**）、`char_count`。
- **`locator` 必须自己补上当前章节标题**（2026-09-29 实测）：框架的 `header_path` 语义是**父级路径，不含当前标题**——节点 `## 一、服务对象` 的 `header_path` 只有 `/规范/`。直接拿它当 `locator`，同一章下所有块会指向同一位置（实测 23 个块只产出 3 种 `locator`），引用回指 `AC-05` 失准。因此 `locator = header_path + 当前章节标题`（实测可区分度从 3 种升至 19 种）。**章节标题要在切分前取好并传给每一块**：超长 section 被切成多块后只有首块还带标题行，若从块文本现取，后续块的章节名会丢。节点 metadata 存补齐后的 `locator`，`header_path` 原样保留框架语义。

### 1.3 案例卡片（2026-09-29 定）

卡片是结构化 JSON，不走 Markdown 分块链；**整卡一节点**（与[公共案例库](公共案例库.md)第 2 节"检索单位是卡片"一致）：

- **嵌入文本 = 全字段结构化拼接**：按"字段名：值"逐字段拼接（保留字段边界，比自由文本拼接的语义命中更准）；`_inferred` 的内容**不参与嵌入**（同公共案例库第 4 节"保留但不参与检索注入"的既有先例——推断依据不应驱动命中），`card_id`、`case_id` 等标识字段不嵌。
- **高风险字段参与嵌入**（`immediate_action`、`medical_criteria` 等）：`makes_claims_high_risk` 是返回时的标记而非检索层过滤（公共案例库第 5 节），呈现约束在 skill 层——不嵌入高风险字段，应急查询反而命不中对应卡片，分层支持策略就落空了。
- **超长处理复用第 1.2 节规则**：超 2000 字符按句边界二次切分，切出的多个节点同 `card_id`，聚合时归回卡片（与第 4 节条目聚合同一机制，不为卡片新造规则）。
- **`locator`**：卡片节点取卡片 `title`，回指靠 `card_id`；narrative 小节走五节标题路径（`场景背景` 等，等价于 `header_path` 语义）。

### 1.4 条目侧字段

- **`keywords`** 与 **`aliases`**：导入时填写（机构名、缩写、常见俗称、英文原名）。**字面路只查 `title` + 这两个字段，不查正文**——中文正文的 trigram 噪声很大，而真正需要字面命中的恰是这类短词。
- **两者是文本列（空格分隔多值），不是数组**（2026-09-29 实测）：`pg_trgm` 的 `gin_trgm_ops` **不接受 `text[]`**（报 `operator class "gin_trgm_ops" does not accept data type text[]`），而 `array_to_string` 表达式索引又不被允许（非 `IMMUTABLE`）。设计要求在这两个字段上直接建 GIN trigram 索引，因此用文本列最贴合。

## 2. 嵌入与向量存储

| 项 | 取值 |
|---|---|
| 嵌入服务 | TokenHub `POST /v1/embeddings`，经 LlamaIndex 的 `OpenAIEmbedding` 接入（**必须用 `model_name=` 而非 `model=`**，见下） |
| 模型 / 维度 | `Kinfra-Text-Embedding-4b` / **2560**（固定，不可自定义） |
| 单条上限 | 2000 字符（因此分块后处理是硬需求） |
| 批量 | 单请求建议 ≤128 条 |
| 节点存储 | `data_campfire_node`：DDL 由 Alembic 迁移拥有，取用方 `perform_setup=False` + `use_jsonb` |
| 索引 | 一期不建（见第 3 节） |

**真源划分（重要）**：

- **条目（`knowledge_item` / `case_item`）仍是事实真源**，留在我们自己的表里：状态（`published`/`internal`/`fictional`）、`withdrawn`、来源、适用范围、授权状态、`keywords`/`aliases` 都由它拥有，录入与审阅流程也走它。
- **节点表是它的投影**：需要在 **SQL 层过滤**的字段（状态、`withdrawn`、库别、授权）**同时写进节点的 metadata**，否则过滤会掉到应用层，违反"过滤在 SQL 内完成"的不变量。投影不是第二真源——它的权威仍是条目表。
- **案例库节点的投影清单（2026-09-29 定）**：在四项通用投影之上，卡片级节点再带——① 返回契约消费的字段（[资料与案例检索](资料与案例检索.md)第 3 节案例必带五项：`source_type`、`evidence_level`、`review_status`、`interview_at`、`makes_claims_high_risk`，加 `inferred_fields`）；② 聚合依赖：`card_id`；③ 结构化过滤维度（[公共案例库](公共案例库.md)第 2、5 节明说"元数据过滤/过滤维度"）：`risk_class`、`age_range`、`severity_level`、`behavior_type`、`ebp_tags`、`parent_category`。其余字段（`subject_type`、`consent_*`、`transcript_ref` 等）无过滤或返回消费，**从窄不投影**。
- **资料库节点的投影清单**：通用投影中适用于资料侧的是**状态、`withdrawn`、库别**（授权为案例侧维度；资料来源的许可是 `EVID-B` 的入库前置，不是查询期过滤）；节点再带——① 返回契约消费的字段（[资料与案例检索](资料与案例检索.md)第 3 节 `KnowledgeResult` 必带）：`title`、`source`、`applicable_scope`——`applicable_scope` 同时是 `search_knowledge` 的 `scope` 参数下推到 SQL 的依赖；`status` 已在通用投影、`locator` 已是节点结构字段（第 1.2 节），无需重复投影；② 聚合依赖：`item_id`（第 1.2 节已列）。一期资料侧无其他结构化过滤维度；其余字段（版本号、`keywords`、`aliases`）**从窄不投影**——字面路直接查条目表（第 3.1 节），不经节点投影。
- **两者同库同事务**（pgvector 就在主库）：因此**撤下可以在一个事务里同时改条目状态与删除该条目的节点**，不需要"最终一致"的窗口，`RQ-KB-04` 的"撤下即刻不可检索"得以成立。

**配置与 DDL 归属**：

- **嵌入模型名唯一配置处是 `core/config`**：`agent/model` 只拥有 LLM 模型名，而 `core/*` 不得依赖 `agent/*`（[项目结构设计](../../项目结构设计.md)第 7 节白名单），嵌入模型名（`Kinfra-Text-Embedding-4b`）经 `core/config` 注入，复用 `tokenhub_base_url`/`tokenhub_api_key`——嵌入服务同为 TokenHub，不引入第二套凭据。**维度不做成可配置项**：2560 与模型绑定，作为 `core/config` 的常量 `EMBEDDING_DIM`——可配置的维度会诱发「配错维度混库」（第 7 节纪律 4）。**常量归属 2026-09-29 从 `modules/library` 移到 `core/config`**：记忆侧（Graphiti 嵌入器，第 11 节）必须共用同一维度，而 `modules/*` 之间不得互相 import（项目结构设计第 7 节）——留在 library 会逼出「越白名单导入」或「第二处定义」二选一，故与模型名同处唯一配置点；两个模块各自转出同一个对象。
- **嵌入适配的接入方式**（2026-09-29 实测）：框架的 `OpenAIEmbedding` 用 `model=` 会把值当作 `OpenAIEmbeddingModelType` **枚举**校验，我们的 `Kinfra-Text-Embedding-4b` 不在枚举内，构造即抛 `ValueError: ... is not a valid OpenAIEmbeddingModelType`。**改传 `model_name=`** 即可承载自定义模型名（框架 `base.py` 内有 `if "model_name" in kwargs` 分支直接采用该值）——因此「经 OpenAI 兼容嵌入适配接入」成立，不需要自研嵌入客户端。超时与重试上界（30 秒 / 2 次）定得比对话模型低：嵌入失败可降级到字面路，不值得吃掉应急时延预算。
- **两条连接串 + 注入自己的引擎才能与业务同事务**（2026-09-29 实测）：`PGVectorStore` 要求 `connection_string`（同步）与 `async_connection_string`（异步）**同时提供**，且 `engine`/`async_engine` 必须成对注入（只给一个会抛 `ValueError: Both engine and async_engine must be provided`）。检索用原生 async 的 `aquery`/`adelete`。**摄取不能走框架的 `add()`**：它内部自建并提交 session（`with session.begin()`），无法参与我们的外部事务，而「条目表与节点表同事务」是撤下语义的前提（第 2 节末条）。因此摄取用**我们自己的 session** + 框架的 `_table_class` 写节点行——框架耦合收敛到这一处，由集成测试守护。
- **布尔过滤必须以字符串存**（2026-09-29 实测）：`MetadataFilter.value` 的类型联合是 int/float/str/列表，**不含 `bool`**——传 `value=False` 会被 pydantic 严格模式拒绝。因此节点 metadata 的 `withdrawn` 等布尔语义**存成 `"true"`/`"false"` 字符串**（框架的 `->>` 把 JSON 值渲染为文本，字符串取值可正确匹配）；`status`、库别本就是字符串，不受影响。
- **表结构与命名由迁移拥有**（已落地）：业务表用 `campfire_` 前缀（避让 SuperTokens core 自建表与 SDK 自建表），节点表名为 `data_campfire_node`——框架把 `table_name` 渲染成 `data_<table_name>`。**迁移必须匹配框架的三条约定**：表名带 `data_` 前缀；`id` 为 `bigint` + sequence 自增（缺 sequence 会写入失败）；列名为 `text`（`varchar`）/`metadata_`（jsonb）/`node_id`/`embedding`。取用方一律 `perform_setup=False`，pgvector 扩展与两张表都由迁移建立（与「schema 变更必须经迁移文件」一致，先例同 SDK 自建表，见[设计待办](../../TODO.md)第五节）。**已实测**：`perform_setup=False` + 迁移建表下写入与 `aquery` 均正常，metadata 过滤**确实下推到 SQL 的 `WHERE`**（实测 SQL：`WHERE metadata_->>'item_id' = 'item-1' ORDER BY distance asc`），符合「过滤在 SQL 内完成」的不变量；setup 期的静默吞错（`TECH-14`（b））随 `perform_setup=False` 不再适用。集成测试 `apps/api/tests/test_library_schema_integration.py` 锁住这些约定。

## 3. 索引

### 3.1 字面路：我们自己的 GIN trigram

- 对**条目表**的 `title`、`keywords`、`aliases` 建 GIN trigram 索引。
- 查询用 `LIKE` / `ILIKE '%词%'`，**不得用 `~` / `~*`**（中文不走索引）。
- **查询词闸门：中文需 ≥3 连续汉字，非中文需 ≥3 连续字母/数字**（2026-09-29 放宽）。不满足则**不走字面路**，只走向量路与元数据过滤。
  - **放宽缘由**：原闸门只数汉字，导致**英文查询永远走不了字面路**（实测 `"autism"` 被判不可用）。语料加入英文文献后这条开始有实际影响，而 `pg_trgm` 对英文同样有效。
  - **阈值依据是"选择性"而非"有无三元组"**（2026-09-29 在 2 万行临时表 + 与生产一致的三列 trigram 索引上实测）：`show_trgm('ab')`（2 字符）**同样产出 3 个三元组**（pg_trgm 会填充边界），但那些三元组太常见，规划器宁可全表扫描。实测计划——

    | 查询 | 规划器自选 | `SET enable_seqscan=off` 强制 |
    |---|---|---|
    | `autism`（6 字符） | Bitmap Index Scan | 走索引 |
    | `asd`（3 字符） | Bitmap Index Scan | 走索引 |
    | `ab`（2 字符） | **Seq Scan** | 走索引 |
    | `孤独症`（3 汉字） | Bitmap Index Scan | 走索引 |
    | `筛查`／`干预`（2 汉字） | **Seq Scan** | 走索引 |

    3 字符是分界点，故非中文取 ≥3。**判据取"最长连续字母/数字段"而非总长度**：`"a b"` 总长 3 但每段 1 字符，用总长会让这类噪声查询通过闸门。
  - **实测方法说明**：首轮探测只给 `title` 建了索引，而查询条件是 `title OR keywords OR aliases`——OR 里的未索引列让规划器放弃全部索引，得到**假的 Seq Scan 结论**。三列都建索引后结论才正确。生产表已对三列各建一个 trigram 索引。
- 部署 locale **不得为 `C`**（`C` 下汉字被全部丢弃、相似度恒为 0）；本部署的 `en_US.utf8` 已实测可用（见下条）。
- **不要用框架的 `hybrid_search`**：它建的是 **tsvector** GIN（全文检索），中文没有分词器时基本不可用——这与 `pg_trgm` 是两回事。
- **字面检索器的实现归属（2026-09-29 定）**：整条链归 `modules/library`——`title`/`keywords`/`aliases` 是它自己的条目表列，节点投影、向量路、字面路、RRF 融合与条目聚合也都消费它的领域字段（状态、库别、`item_id`、案例卡片维度），机制与模式同属一个模块；`core/retrieval` 因此取消，不存在需要跨模块解释的接口缝。LlamaIndex 只有 library 一个消费者，**框架耦合止于 `modules/library`**；装配（工具注册）仍在入口按[项目结构设计](../../项目结构设计.md)第 7 节完成。
- **中文约束已实测**（2026-09-29，`pgvector/pgvector:pg17` = PostgreSQL 17.10，库 locale `en_US.utf8`）：`show_trgm('孤独症')` 产出 4 个三元组、相同文本 `similarity` 为 1、相关文本 0.45 vs 无关 0——**汉字被认作词字符**；索引行为：`LIKE '%孤独症儿童%'` 走 **Bitmap Index Scan**（GIN trigram），`~` 正则走 **Seq Scan**。上面三条约束（≥3 连续汉字、必须 `LIKE`、locale 不得为 `C`）全部成立。
- **跨语言检索已实测**（2026-09-29，真实 TokenHub 嵌入）：**中英跨语言对齐成立**——中文查询与对应英文段落的相关度明显高于无关英文段落：术语直译「孤独症谱系障碍的循证干预实践」相关 0.679 vs 无关 0.244（差距 +0.435），纯术语 0.483 vs 0.210（+0.273），口语化症状描述 0.374 vs 0.158（+0.217）；同语言基线（英文查询）为 0.816 vs 0.306（+0.510）。**结论：英文语料值得入库**。注意**口语化查询的区分度明显弱于术语直译**（+0.217 vs +0.435）——这与第 8.1 节的"口语改写桥"是同一关切，属已登记待确认项。

### 3.2 向量索引（现在不建，条件触发）

- 一期不建：几千个节点下精确检索既足够快又保证召回 100%，而 2000 维的索引上限**只作用于建索引**，不建就不受限。
- **切换条件**：节点数超过**约 5 万**，或单次向量检索 SQL 超过 **100 毫秒**。
- 届时用框架的 `hnsw_kwargs` 建 HNSW（`m=16`、`ef_construction=64`、查询侧 `ef_search`），**并且我们自己设置会话级 `hnsw.iterative_scan`**（框架不负责这一项）——因为 pgvector 的过滤在索引扫描**之后**应用，而我们每条查询都带过滤。

## 4. 融合检索与候选

- **融合用 RRF**（2026-09-29 定，同日实现期修订）：**RRF 本身照旧**（`score = Σ 1/(rank + k)`，k=60，与框架同值，源自 RRF 原论文）；但**不由 `QueryFusionRetriever` 执行**——实测它的融合发生在 `_retrieve` 内部，两路输入必须是**同步**检索器，而我们的两路都是异步 SQL；塞进去需要线程池包装，会钝化失败语义（单路失败要能降级并标注）。融合公式只有几行，由 `modules/library/retrieval.py` 自实现。
- **合并键是 `node.hash`（文本 + metadata 的哈希），不是 `node_id`**（2026-09-29 实测，含一次已修缺陷）：框架的 `TextNode.hash` **把 metadata 一并纳入计算**。字面路展开节点时若只带文本、不带 metadata，两路即便 `text` 完全一致，哈希也不同，RRF 因此永远判不出「两路都命中」——实测 23 个节点 text 全同、hash 全不同，融合退化成只有向量路。**因此字面路展开的节点必须照搬库中存的那份 metadata**。这条已由集成测试 `test_both_paths_merge_when_text_matches` 守护（两路合并时 `fused_score` 约为单路的两倍）。
- **命中来源要记账**：返回契约的 `ranking` 要求「哪几路命中」（[资料与案例检索](资料与案例检索.md)第 3 节），实现里由 `ranking["hit_paths"]` 给出 `vector`/`literal`/`both`。它是调试与第 8 节评测判断「某一路是否在拖后腿」的依据。
- **为什么改用 RRF**：它只用**名次**、不用原始分数，因此不存在跨路分数量纲不一致的问题，也没有需要调的神秘权重；这比先前自拟的"路内排名 + 命中路数"更有依据。**不做跨路分数加权归一化。**
- **一期不用 LLM 多查询生成**（会加一次模型调用，且应急时延吃紧）。
- 候选取值：向量路 **top-30**（节点）、字面路 **top-30**（按条目计；**待确认**）、融合后取 **top-8 条目**。
- 过滤（库别、状态、撤下、授权）**在 SQL 内完成**（metadata 过滤已核实可下推）。
- **条目聚合仍是我们自己写**：框架返回的是节点与分数，我们需要把同一 `item_id` 的多个节点**聚合为条目**、只保留名次最高的节点作为 snippet、并把条目名次上提；**同一轮不重复注入同一条目**。
- **两路在同一粒度上得名次**：融合的单位是节点。向量路的候选自然是节点；字面路的检索单位是**条目**（条目表行），参与融合前展开为该条目的节点——同一条目的节点共享其名次，聚合时归回条目。RRF 只用名次、聚合取最佳节点，因此节点数多的条目不会获得名次优势；字面路候选槽位被长条目占满是已知代价，一期语料量小不构成问题，评测若显示字面路覆盖不足则重访候选数（第 10 节）。
- **一期不做重排**（2026-09-29 定）：TokenHub 没有重排模型，接外部重排会新增供应商，且加一次调用会吃掉应急的时延预算。

## 5. 上下文装配

- 注入形状与返回契约一致：标题、snippet、来源、适用范围、状态、`locator`。
- **预算：检索结果占模型窗口不超过 8%**（**待确认**）；超出时按名次截断并标注"未全部注入"。
- **应急路径更紧**：只注入 **top-3**，且不为凑依据追加检索（`RQ-EMG-03`）。
- 每条注入进**引用索引**（[基座](通用基座.md)第 4 节），以便输出回指。
- 顺序按最终名次；**不按库别分组**（避免"资料先于案例"这类隐含偏好）。

## 6. 时延预算

- 一次检索 = **一次 query 嵌入（网络往返）+ 一次融合 SQL**（一期无向量索引，几千节点的顺序扫描）。
- 日常路径不设单独指标；**应急路径首字 ≤10 秒**（`RQ-EMG-03`）→ 嵌入调用必须与**档案预注入并行**，不串行等待。

## 7. 摄取流水线

**摄取不暴露在应用里**（2026-09-29 定）：没有上传接口、没有知识库管理页、没有审核工作流 UI。资料与案例在**本地**处理入库，检索才在运行时由两个工具使用。

- **入口形态**：应用包内的**一个 CLI 入口**（`python -m campfire.cli ingest <路径>`），**跑在同一镜像里**、连同一个库。**不是**仓库根 `scripts/` 下的独立脚本——它必须复用同一份依赖与同一套写入逻辑（条目表、幂等、嵌入适配），独立脚本一定会漂移。「本地」指的是**运行环境与触发方式**（不暴露成服务端点），不是「独立代码」。CLI 只是入口：摄取流水线、分块链与嵌入适配的实现归 `modules/library`（检索链与摄取同属一个模块，见第 3.1 节的实现归属）。
- **流水线**（2026-09-29 实现期修订）：分块链 = `MarkdownNodeParser`（框架）+ 我们的两层后处理，**由 `modules/library` 直接编排**，不经框架的 `IngestionPipeline`——原因见第 2 节：摄取必须与条目表同事务，而框架的写入路径自建事务。嵌入经第 2 节的 `OpenAIEmbedding` 适配器批量调用。
- **去重与增量**：按 `source_path` + `doc_hash`（内容 SHA-256）判断——**未变跳过、变了先删该条目的旧节点再写新节点**，同一事务内完成。一期不用框架的 docstore/`IngestionCache`（Redis 缓存重复嵌入），重访条件见第 9 节。
- **导入是一次链外准备 + 一次链内摄取**：链外产出 md/html，链内负责切分、嵌入与写入。
- 导入失败要么整份成功、要么明确失败并留下可见记录；**不留下「一半进去了」的静默状态**。不受 HTTP 超时约束，因此**一份文件一个事务**（已实测覆盖：失败在嵌入阶段、以及条目已写入后节点写入失败，两种情形都整份回滚）。

**四条必须与「本地跑」一起成立的纪律**：

1. **凭据与环境**：脚本要连生产库——必须明确**谁能在哪台机器上、用哪套凭据**执行；凭据经环境注入，不入版本库（`AGENTS.md` 的密钥纪律同样适用）。
2. **可复现性**：必须**在同一镜像与同一 lockfile 里跑**（例如容器内执行），否则本地与线上的依赖差异会让**分块与嵌入结果不一致**。
3. **摄取记账**：没有应用内审计，就由脚本自己写**导入记录**——批次、文件、条目数、操作者、时间、脚本版本。否则将来撤下某条资料时无法回溯它是从哪份文件、哪一版进来的。
4. **换嵌入模型必须整库重建**：维度固定（2560），混入不同维度的向量会让检索静默失准。

## 8. 评测

- 用 `RetrieverEvaluator`（`hit_rate`、`mrr`、`recall`、`ndcg`），**配合我们手工构造的 20–30 条查询与期望条目**；覆盖六类：机构名与缩写、**不达闸门的短词**（1–2 汉字／1–2 字符，验证不被当成零结果）、纯语义改写、**跨语言查询**（中文问英文文献——阶段 0 实测总体成立，但**口语化查询的区分度明显弱于术语直译**，见第 3.1 节，须由本类量化）、**家长口语改写**（用自然口语表述的咨询问题，如"孩子装听不见怎么办"，期望命中临床文风卡片——案例卡片的文风与使用者查询的口语鸿沟是嵌入检索的脆弱点，2026-09-29 实读上游 L2 卡片确认卡片为临床/指南腔，但鸿沟幅度与模型改写能否弥合**均无证据**，由本类量化）、英文术语（英文语料入库后的同语言基线）。
- **一期没有语料**（`EVID-F` 未完成），所以先建用例集与指标，不跑分数；任何"效果良好"的判断在此之前都不成立。
- `generate_question_context_pairs` 可合成评测集（需模型调用），但**合成集不能替代手工基准**，只用于扩充。
- 另记：两路各自贡献的命中数（RRF 下用于判断某一路是否在拖后腿）、单次检索耗时、注入 token 数。

### 8.1 案例检索的查询改写桥（评测闸门后落地，2026-09-29 定方向）

**问题**：案例卡片是临床/指南文风（实读上游 L2 卡片确认），使用者查询是口语描述——查询与文档之间的文体鸿沟是嵌入检索的脆弱点；且行为维度存在**值域外案例**（上游 `_inferred` 自证"被动任务拒绝/拖延不在标准行为类型枚举中"），口语行为描述只能靠语义路命中。

**归属**：改写由**咨询模型在工具调用内完成**——`query` 本来就是模型生成的字符串，skill 引导它"查询词用简明的行为与情境描述，不用使用者原话转写"（例：不搜"孩子装听不见怎么办"，搜"听到指令不执行、拖延、假装未听见"）。零新增模型调用、零新组件，应急时延预算不受冲击；与第 4 节"一期不用 LLM 多查询生成"不冲突（该条禁的是检索器内部加模型调用，此处是 skill 层引导、同一帧生成）。

**闸门（已写入 skill，评测验证、无效则回退）**：第 8 节第五类评测（家长口语改写）量化两件事——① 鸿沟实际幅度（口语直接搜 vs 标准措辞搜的召回差）；② 模型自改写是否弥合。**检索引导已按用户 2026-09-29 指令写入两个咨询 skill**（[日常](../面/consult/skills/daily-consulting.md) 3.4 节、[应急](../面/consult/skills/emergency-consulting.md)第 6 节）；评测若显示改写无效，则回退该引导——不留未经验证仍生效的提示词。

**条件项**：入库侧为案例补口语别名（写进 `keywords`/`aliases`，喂字面路）只在评测显示字面路在口语查询上系统性漏召时考虑；`ebp_tags` 反向映射查询需先核验 NCAEP 值域（上游 23–28 项自称补充项、未独立核验）。

## 9. 一期不做与重访条件

| 不做 | 重访条件 |
|---|---|
| **重排** | 评测显示向量路 recall@30 尚可但 top-8 精排明显差——说明是排序问题而非召回问题 |
| LLM 多查询生成 | 评测显示同一问题换说法后召回骤降 |
| 向量索引 | 节点数 >5 万，或单次向量检索 SQL >100 毫秒 |
| **PDF 解析**（含引入付费解析服务） | 一期链外准备的成本被证明不可持续，且数据处理条款核实通过 |
| 条目摘要嵌入、父子块 | 评测显示长文档的局部细节检索不到 |
| 框架的 `IngestionPipeline` 与 docstore/`IngestionCache` | 摄取量与重复嵌入成为成本问题，或出现跨运行的增量摄取需求——届时需先解决「框架写入自建事务」与「条目表/节点表同事务」的冲突（第 2 节） |

## 10. 参数表

| 参数 | 取值 |
|---|---|
| 输入格式 | 处理后的 Markdown / HTML（**不接 PDF**） |
| 分块 | `MarkdownNodeParser` + 表格列表保护 + 超长二次切分 |
| 块目标长度 | 400–800 字符 |
| 块硬上限 | 2000 字符（嵌入接口限制） |
| 块重叠 | 0（结构边界切分） |
| 嵌入模型 / 维度 | `Kinfra-Text-Embedding-4b` / 2560 |
| 节点存储 | `PGVectorStore`（自定义 `table_name`、`use_jsonb`） |
| 向量索引 | 一期不建；条件触发时 `hnsw_kwargs` + 自设 `hnsw.iterative_scan` |
| 字面索引 | 我们自己表上的 GIN trigram（`title`/`keywords`/`aliases`；**文本列**，`gin_trgm_ops` 不接受 `text[]`） |
| 融合 | 我们自实现 RRF（k=60，按内容哈希合并）；**不用 `QueryFusionRetriever`**——它要求两路是同步检索器，与我们的异步 SQL 不合（见第 4 节） |
| 候选 | 向量 top-30（节点）、字面 top-30（按条目计；**待确认**） |
| 融合后 | top-8 条目 |
| 重排 | 无 |
| 注入预算 | 窗口的 ≤8%（**待确认**）；应急 top-3 |

## 11. 记忆侧的嵌入（Graphiti）

- Graphiti 的嵌入器必须配置为**同一个 TokenHub 向量模型**——否则会引入第二个供应商的凭据。
- 维度一致性：Graphiti 侧与 FalkorDB 向量索引的维度必须匹配（2560）；FalkorDB 向量索引**已核实支持 1–4096 维**（2560 在范围内，`TECH-13`），Graphiti 嵌入器与其索引的接通方式仍须实测。
- 记忆写入在 Worker 内异步执行（[写入路径](写入路径.md)），嵌入调用计入 Worker 的成本与重试预算；嵌入失败按记忆写入失败处理，不回滚业务主事务。

## 12. 依赖代价（照实记）

- `llama-index-core` wheel ≈11.9 MB、**29 个直接依赖**（含 `nltk`、`tiktoken`、`networkx`、`sqlalchemy`、`numpy`），间接依赖通常上百；Python ≥3.10,<4.0。
- 只装 `llama-index-core` 与所需集成包，**不装全家桶 `llama-index`**（它只是 starter bundle）。
- 这是"全量引入"的真实代价，登记在此以便日后复核是否值得。
