# 认证与账号

> **权威范围**：账号形态、注册（邀请码）、接入面与凭据传输、登录与会话、人工重置、身份服务的集成边界与降级语义。**认证面的 HTTP 契约归本文拥有**（认证不经过 Agent 基座，因而不建 `surfaces/accounts/`，见第 5 节）。技术选型由[技术栈设计](../../技术栈设计.md)拥有；模块归属由[项目结构设计](../../项目结构设计.md)拥有；档案与记忆的访问判定由授权端口拥有，不在本文。
> **状态**：2026-09-29 依已确认的需求与技术选型设计，待用户确认。第 5 节的会话校验方式已经用户 2026-09-29 裁决（见[决策记录](../decisions/会话校验逐请求查证数据库.md)），该裁决同时修正了[技术栈设计](../../技术栈设计.md)第 2 节的可用性表述。不代表已实现。
> **追溯**：`RQ-ACC-01`～`RQ-ACC-06`、`AC-01`、`AC-02`、`AC-14`、`AC-15`、`AC-16`、`AC-17`。
> **依据**：SuperTokens core 仓库 README（core 为独立 Java HTTP 服务，用户数据 100% 在自己的库；`ee/` 之外为 Apache-2.0）；SuperTokens 官方文档《Implement username login》（复写 email 校验器实现账号名登录）；SuperTokens 官方文档《Access token blacklisting》（**默认无状态校验下撤销不即时生效**——原文：the user can still use its access token until the token expires，须开 `checkDatabase`）；`supertokens-python` 源码（`recipe/session/recipe_implementation.py` 的 `get_session` 把 `check_database is True` 透传为 `always_check_core`；`session_functions.get_session` 仅在 `not always_check_core` 且无父刷新令牌哈希时本地返回，否则 POST `/recipe/session/verify` 经 core）。

## 1. 目标与边界

身份只回答三件事：**你是谁、属于哪个组织、当前会话是否有效**。它不回答"你能看哪个支持对象的档案"——那是授权端口的事。

- 全应用必须登录（`RQ-ACC-01`）：不存在匿名内容页、匿名接口或未登录可达的业务路径。**唯一例外是运维探针端点 `GET /health`**——它必须未登录可达（Nginx 上游检查与容器健康检查不持会话），但只回报组件状态与异常类型，**不复述连接串、凭据或内部拓扑**，且不构成业务能力（`AC-01`）。
- 登录本身不授予任何个人资料的访问权。
- 认证不可用时**拒绝受限操作**，不降级为放行。

## 2. 组件与职责

| 组件 | 职责 | 不承担 |
|---|---|---|
| SuperTokens core（独立 Java 容器） | 注册、登录、重置、会话刷新，**以及逐请求的会话数据库查证** | 业务授权判定 |
| SuperTokens Python SDK（在我们进程内） | 请求解析与令牌结构校验、**以 `check_database=True` 发起数据库查证**、与我们的存储交互 | 业务授权判定 |
| 我们的 PostgreSQL | 身份与会话数据的存放（core 使用我们的库） | 授权真相 |
| `accounts` 模块 | 邀请码注册编排、人工重置编排 | 任何档案可见性判定；组织与成员管理（**一期不存在**，见第 3 节） |

**一条关键的可用性事实**：会话校验**逐请求查证数据库**，该查证由 Python SDK 发起、**经 Java core 执行**（SDK 自身不直连会话表）。因此 **core 在鉴权关键路径上**：core 不可用时，注册、登录、重置、刷新**以及全部受限操作**都不可用并明确报错，不存在"已登录用户不受影响"的路径。这是 `AC-17`（重置后旧会话立即失效）成立的必要代价——无状态校验下，被撤销的 access token 在到期前仍然可用（见[决策记录](../decisions/会话校验逐请求查证数据库.md)）。

**三条运营与成本边界**（已核实）：① SuperTokens 的 **Dashboard 超过 3 个用户即需付费**，因此一期运营操作（建号、人工重置）**走 SDK 或 Management API**，不依赖 Dashboard；② **攻击防护套件属付费特性**，因此登录限流与防爆破由我们自己实现；③ **Multitenancy 与 SSO/SAML 属付费**（定价计算器显示 $0，与文档表述不一致，故标为**不确定**），二期若要做机构多租户，需评估付费许可或自建。

## 3. 账号形态

- **账号名登录，不要求邮箱**（`RQ-ACC-05`）。按官方文档的做法实现：复写 email 校验器使账号名通过校验。
  **已知偏差**：标识在内部**仍存放于 `email` 字段**（`TECH-08`）。这带来一处风险，需在实现时显式处理：以后真要加邮箱时"登录名"与"联系方式"会冲突。
- **账号标识 `account_id` 就是身份服务的用户标识**（2026-09-29 用户裁决），**不建映射表、不另设内部账号主键**。判据：SuperTokens 的用户标识是 UUID v4 字符串（36 字符），满足 Graphiti `group_id` 的 `^[a-zA-Z0-9_-]+$`——连字符在字符集内，**无需归一化或映射层**；宽度 36 亦落在 `identity.MAX_ACCOUNT_ID_LENGTH`（128）与账本 `varchar(128)` 之内。
  **因此「谁是谁」全库只有一个定义**：我们自己的表一律以 `account_id` 外键引用它，不出现第二个账号主键，也不存在"我们的用户表与身份服务的表各成一套"的第二定义。
  **不可轻易变更的约束**：该值是记忆分区键、FalkorDB 图名（`group_id`）与删除账本的账号列——改它等于迁移全部记忆与账本。故**不得启用会改写用户标识的身份服务特性**（账号链接 `Account Linking` 会使主用户 ID 变更，官方《User Object》原文：*The primary user ID. It can change if the user links to another user*；该项目属付费且一期不启用）。
  **为何不用 `user id mapping` 换取可读图名**（该 API 能让 SuperTokens 返回自定义标识）：它使账号名被收窄到 `[a-zA-Z0-9_-]`，**中文账号名将不可用**；且该特性只能在用户尚无任何数据（session、roles）之前调用，其文档在主站缺失（社区回复"文档即将推出"）、是否属开源免费部分未核实（同 `TECH-07` 类风险）。收益仅为运营排障时图名可读，代价是产品级限制，不采用。
- **一期只做个人账号**（`RQ-ACC-03`，**2026-09-29 用户裁决收窄**）：**不支持以组织名义注册或使用**，账号上**不存在**组织字段或组织标识；组织与机构协作整体推迟到二期。二期的授权缝落在既有的**唯一授权端口**上（第 9 节），**不落在账号结构上**——因此一期不预建组织表、不预留组织字段，二期接入时认证与账号的形状不变。
- **一期账号没有可主动触达的联系通道**（无邮箱、无手机号）：这影响告知、条款变更通知与二期机构协作时的成员确认。属于已知限制，不是默认设计。

## 4. 注册（邀请码）

- **不开放自由注册**（`RQ-ACC-04`）。注册须凭有效邀请码。
- **校验在我们自己的后端**，不依赖身份服务是否原生支持邀请码：**我们持有邀请码表**，校验通过后才经 SDK 建号。字段：

  | 字段 | 说明 |
  |---|---|
  | `code` | 8 位随机码，**主键**；比较须恒定时间，避免计时旁路 |
  | `state` | `issued` \| `used` \| `revoked`（词表落 CHECK 约束，与删除账本同法） |
  | `expires_at` | 有效期截止（签发时按 30 天计） |
  | `used_at` | 被使用的时间；`state = used` 时必填 |
  | `used_by_account_id` | 使用它的账号（`account_id`，见第 3 节） |
  | `revoked_at` | 撤销时间；`state = revoked` 时必填 |
  | `created_by` | 创建者标识（运营者，见第 7 节） |
  | `created_at` | 签发时间 |

  **唯一约束落在 `code` 上**，`state` 的取值由 CHECK 约束保证——两者都放在**存储层**而非应用层先查后写。
- **注册入口的落地形状**（2026-09-29 定）：**复写身份服务的 sign-up API**，把邀请码作为该 API 的自定义表单字段，在复写法内先校验邀请码、通过后调用原实现建号。理由：这是"校验在我们的后端代码里"与"不自己实现建号与会话签发"同时成立的唯一低成本形状；自建注册端点并禁用身份服务的 signup 路由，要求我们自己签发 session 与设置 cookie，与[技术栈设计](../../技术栈设计.md)第 2 节"换取不自己实现会话安全"的选型理由相悖。
- **可用性不变量**（**2026-09-29 修正**，原文写"同一事务"，**该写法不成立**）：建号发生在 SuperTokens core 这个独立进程内，**我们本库的事务无法跨进程覆盖它**。可实现且必须遵守的形状是：

  1. **先在本库原子占用邀请码**——以条件更新（`UPDATE ... WHERE code = ? AND state = 'issued' AND expires_at > now()`）判定成败，**不先查后写**；
  2. 占用成功后才调用建号；
  3. **建号失败则补偿释放**（把该码回退为 `issued` 并清空 `used_at`/`used_by_account_id`）。

  它保证的是"**无效码绝不建号**"（第 1 步就拒绝，不触碰身份服务）与"**一码只用一次**"（并发下由条件更新的原子性保证），而**不是**跨进程原子性。第 2 步成功而第 3 步之前崩溃，会留下"码已占用但账号未建"的状态——该状态**安全**（拒绝二次使用），由运营在撤销/重发时处理，不在请求路径内自动回收。
- 邀请码的发放与撤销由运营控制；撤销后**立即不可再用**。
- 提交内容：账号名、密码、邀请码。不要求邮箱，不要求填写任何支持对象信息。
- **邀请码参数**（2026-09-29 定）：**8 位随机、一次性使用、有效期 30 天**。一次性最安全；30 天覆盖正常发放节奏。发放与撤销由运营执行。
- **密码策略**（2026-09-29 定）：**采用身份服务的默认校验器**——至少 8 字符、且含至少一个小写字母与一个数字（官方默认校验器行为）。一期不自定更严或更宽的规则：自定规则要自己维护，且默认值已被官方测试覆盖。

## 5. 接入面与凭据传输

**身份服务的路由与我们的端点不是两套东西**：身份服务按固定的 `apiBasePath`（`/auth`）挂载注册、登录、刷新等路由，它们运行在我们的 FastAPI 应用内。因此认证面的接入点由两部分组成——**身份服务挂载的路由**（`/auth/*`）与**我们自己定义的业务端点**。

| 部分 | 内容 | 归属 |
|---|---|---|
| `/auth/*`（身份服务挂载） | signup、signin、session refresh、signout 等由 SDK 提供的路由；注册路由的校验逻辑经复写注入 | SDK 形状 + `accounts` 模块的复写实现 |
| 我们自建的认证端点 | 账号信息查询、未来的会话管理等 | `accounts` 模块，契约由本文拥有 |

**运营操作不在 HTTP 面上**：邀请码发放/撤销与人工重置经 `campfire.cli` 执行（第 7 节），**不提供 HTTP 端点**——它们因此不出现于上表。

**不新建 `surfaces/accounts/`**（2026-09-29 定）：本项目的"面"指**产品入口与 Agent 基座运行装配**（[项目结构设计](../../项目结构设计.md)第 5 节），而认证不经过 Agent 基座、不装配 skill 与工具池。为它建一个"面"会掏空该概念的含义，也会让"新增面复用基座"这条扩展缝失准。认证的 HTTP 契约因此**由本文拥有**，模块归属仍按第 2 节的表。

**凭据传输**（2026-09-29 定）：

- **cookie 型会话**，凭据**不可被前端 JavaScript 读取**（官方《Access Session Data》原文：使用 cookie 鉴权时，access token 默认不暴露给前端 SDK，因为它存放在 httpOnly cookie 里）。这与[项目结构设计](../../项目结构设计.md)第 9 节"前端不得读取或存储凭据"一致，不冲突。
- **anti-CSRF 取 `VIA_CUSTOM_HEADER`**：它在 `sameSite=lax` 且 API 与站点同顶级域时是身份服务的默认值，前端须随请求携带一个自定义头。**一期前后端同顶级域部署**（经同一 Nginx 暴露），因此该默认值成立；`sameSite=none` 是**禁用**条件——它会使 anti-CSRF 自动切到 `VIA_CUSTOM_HEADER` 之外的路径，且 Safari 的第三方 cookie 限制会让 cookie 模式直接失效（官方《Security》原文），故一期不使用 `none`。
- **前端引入官方前端 SDK（`supertokens-web-js`，Apache-2.0 已核实）负责两件事**：令牌过期时的刷新重试循环（并发请求遇 401 的单飞刷新是自写 HTTP 层的常见缺陷来源），以及随请求注入上述 anti-CSRF 头。**它只做传输与会话维护，不做业务授权**——前端守卫只负责体验，不构成权限证明（[项目结构设计](../../项目结构设计.md)第 9 节）。
- **本地开发**：前端与 API 端口不同但同为 `localhost`，属 same-site，`VIA_CUSTOM_HEADER` 与 `lax` 均成立，不需要为开发期放宽 cookie 策略。

**令牌时长**（2026-09-29 定）：采用身份服务的默认值——**access token 3600 秒（1 小时）**、**refresh token 144000 分钟（100 天）**（core `config.yaml` 默认值，已实读该文件）。**这两个数值不再承担"撤销窗口"职责**（撤销已由逐请求数据库查证做到即时，见第 6 节），因此不因安全理由收窄。

**已知风险**：一轮咨询的 SSE 流**可能长于 access token 有效期**（`RQ-EMG-03` 只约束首字 ≤10 秒，不约束流的总时长）。若令牌在流中途到期，前端 SDK 的刷新会发生在一段进行中的流上。**这不构成设计缺陷但必须实测**：登录后发起一次超过 1 小时的流式咨询，验证刷新不打断流、或流能正确恢复；若实测会中断，则为长流设置续期策略。

**登录限流与防爆破**（2026-09-29 定）：**core 自身不提供登录限流**（官方《Rate limit policy》原文：the core has no rate limit other than for the `/hello` API），而攻击防护套件属付费特性，因此由我们在**两层**实现：

| 层 | 防什么 | 实现位置 |
|---|---|---|
| 按 IP 限流 | 单 IP 的快速爆破与邀请码枚举 | **Nginx**（官方自托管建议即此，并给出 `limit_req_zone` 示例配置）；它本就在部署拓扑内，且请求在该层被挡掉、**不消耗 core 往返** |
| 按账号失败计数 | 多 IP 打同一账号的慢速爆破 | 应用层，计数落 Redis（[技术栈设计](../../技术栈设计.md)第 2 节"缓存与限流"行的既定归属） |

- **计数维度必须是账号**而不是仅 IP：否则分布式慢速爆破可以绕过。计数键用**账号名经过不可逆处理后**的值，不把账号名明文写进 Redis 键。
- **限流触发时的对外行为**与第 8 节的失败语义一致：明确拒绝，且**不区分"账号不存在"与"密码错误"**（否则限流本身变成账号枚举渠道）。
- **具体阈值留待实现期实测确定**：需在真实登录时延与误伤率之间校准，一期不写死数字——未经实测的阈值会让后续判断误以为限流已被验证。

## 6. 登录与会话

- 每个请求由服务端重新查证会话，且**逐请求查证数据库**（`check_database=True`）：**客户端凭据不得作为权限证明**，令牌的结构与签名校验也不足以证明会话仍然存在。
- **会话必须可由服务端即时撤销**（`RQ-ACC-06`）：这是"人工重置"能成立的前提——重置后旧会话若仍有效，重置形同虚设。即时性**完全依赖上一条的数据库查证**：撤下无状态校验就不再即时。
- 会话与业务授权分离：会话有效只说明"你是某个账号"，不说明"你能看什么"。
- **登出（当前设备）**：撤销当前会话并清除浏览器 cookie，由前端 SDK 的 `signOut()` 触发——它调用身份服务的 signout API，**"删除数据库中的会话与前端 cookie"**（官方《Session Invalidation》原文）。因为会话校验逐请求查证数据库，**登出后旧 access token 立即失效**，不存在"登出后仍可用到过期"的窗口。
  - 前端随后**清空本地状态并回到登录页**（与 401 的处理同路，见[咨询对话界面](咨询对话界面.md)第 6 节）。
  - **登出只撤当前会话，不动其他设备**——"登出其他设备"属会话管理界面，一期不做（第 10 节）。
  - **登出不需要服务端自建端点**：signout 路由由身份服务挂载（第 5 节 `/auth/*`），前端 SDK 直接调用。
  - **登出不是会话撤销的唯一入口**：人工重置（第 7 节）与账号注销（第 8 节）都必然包含它。

## 7. 运营者入口与人工重置

**运营者入口的形态**（2026-09-29 用户裁决）：**扩展既有的 `python -m campfire.cli`**（`apps/api/src/campfire/cli/`），新增账号与邀请码子命令；**一期不做运营 web 后台**。理由：一期的运营量极小——`RQ-ACC-06` 的自助找回重访条件是"真实用户数 ≥50，或每周 ≥1 次找回请求"，反过来说明一期重置是**个位数次数**；为个位数操作建一个浏览器可达、能重置任意密码与建任意账号的界面，攻击面与收益不成比例。CLI 已有（`convert`/`ingest`），复用零新增攻击面。

| 子命令 | 用途 |
|---|---|
| `invite issue` / `invite revoke` / `invite list` | 邀请码的发放、撤销与查看（表结构见第 4 节） |
| `account reset` | 为指定账号重置密码，**并在同一操作内撤销该账号全部会话** |

**运营者身份就是"能执行该 CLI 的人"**，即**服务器的操作系统访问权**——本期不引入应用层运营者身份与审计表。这是**有意的选择**，代价如实写明：**无法回答"是哪位运营者重置了谁的密码"**，追责只能依赖 OS 层日志。若出现非技术运营者、多人协作或需要应用层追责，须重估为 web 后台方案（见重访条件）。

- **`account reset` 的顺序与失败语义**：撤销会话与改密**必须同时成立**（第 9 节末行）——CLI 须保证任一失败即整体失败并明确报错，**不得留下"密码已改但旧会话仍有效"**。
- **运营者入口不得暴露成服务端点**：CLI 不挂路由、不经 HTTP 对外，与 `cli/` 既有禁令一致（[项目结构设计](../../项目结构设计.md)第 7 节 `cli` 入口白名单）。
- **一期不承诺自助找回。** **重访条件**（2026-09-29 定）：真实用户数 **≥50**，或出现**每周 ≥1 次**找回请求，即重估邮箱选填或一次性恢复码。

**网络边界（与运营入口同样重要）**：**只有 Nginx 对外监听**——api、worker 与全部数据服务均不得映射到公网接口。官方文档原文警告：自托管的 core 若暴露到互联网，**任何人都能创建或修改 dashboard 用户**；而 core 自带的 `/auth/dashboard` 由后端 SDK 挂载，同样在它之后。风险不止 core：同一份编排里 PostgreSQL 的 `5432` 承载全部业务数据与会话表、Redis 的 `6379` 承载队列与限流、FalkorDB 承载全部记忆（且默认无密码）、MinIO 默认凭据为 `minioadmin`。完整约束见[技术栈设计](../../技术栈设计.md)第 6 节"网络暴露面约束"；[docker-compose.yml](../../../docker-compose.yml) 已把全部数据服务端口绑到 `127.0.0.1`。

**官方 Dashboard 不作为本期运营界面**：它由后端 SDK 挂载在 `<apiDomain>/auth/dashboard`，能看/改/删 SuperTokens 用户，但 ① 超 3 个 dashboard 用户需付费，且自托管需申请 license key（条款**未核实**，同 `TECH-07` 类风险）；② 它**只管身份服务的用户，管不了我们的邀请码表**——邀请码在第 4 节是我们自己的表。因此它即便启用也无法覆盖主要运营操作。

## 8. 账号注销

**能力归属**（2026-09-29 用户裁决）：一期**支持**账号注销，**经运营 CLI 执行**（第 7 节的入口形态），**不提供自助注销**——一期账号没有邮箱与手机号（第 3 节），使用者没有可自助触达的通道，因此注销请求由使用者口头提出、运营者执行。

**为什么必须定义它**：不是"应该有"，而是下游已把它当既成事实——[通用记忆](通用记忆.md)第 1 节的驱动缓存失效与图库清理都写着"账号注销时失效"，删除账本的 `reason` 词表也已预留 `account_deletion`（存储层实现见 `modules/memory/models.py`）。上游从未定义，属"下游设计依赖不存在的上游事件"。

**三段处置**（2026-09-29 定，不是一刀切）：

| 数据 | 处置 | 理由 |
|---|---|---|
| 身份服务的用户、全部会话、该账号的 FalkorDB 图、该账号的待处理记录、该账号的删除账本行 | **真删** | 账号级删除能删干净：`group_id` 在 FalkorDB 后端**就是图名**，丢掉整张图是一次完整操作，不受单条删除的"共享边"牵连（[通用记忆](通用记忆.md)第 1、7 节） |
| 该账号的**支持对象**（含已归档的）、**会话与对象的绑定**、**全部档案条目** | **真删** | `RQ-ACC-08` 与 `AC-24` 的原文都要求"其**档案**……不再存在"。归档是生命周期状态，**不是注销的豁免**——见[支持对象](支持对象.md)第 7 节（该项此前遗漏于本清单） |
| **注销墓碑**（新表，归 `core/auth`） | **保留**：账号标识（不透明 UUID）、注销时间、原因 | 见下方"为什么保留墓碑" |

**为什么保留墓碑**：

- **在途写入会"删后复活"**：注销时可能已有 `pending_write` 在排队，甚至已被 Worker 领取。若账号删得无迹可寻，Worker 写入时查不到账号——而"查不到"与"账号从不存在"**无法区分**，于是数据被写回已注销账号的图（[写入路径](写入路径.md)第 6 节"授权在写入前被撤销 → 领取时重新判定"，注销正是该判定的输入）。墓碑是 Worker 识别"已注销"的**唯一**依据。
- **形状**：只含账号标识、时间、原因，**不含任何用户内容**——删除账本的 `episode_key` 是由 `pending_id` 派生的 UUID5，不可反推原文。
- **它落在哪**：**`core/auth`**，不新建模块。判据是依赖白名单而非偏好——Worker 只允许 import `core/*` 与 `modules/{profile,memory}` 且**禁止回查业务用例**（[项目结构设计](../../项目结构设计.md)第 7 节），故墓碑**不能**放 `modules/accounts`；而请求路径与 Worker **都要读**它，跨界可读是它的唯一归属理由。
  **为什么不放删除账本**：该表 `episode_key` 是 `NOT NULL` 且 **UNIQUE**、语义是"某条 episode 被删"，而账号墓碑不对应任何 episode（实测 `models.py` 的列约束）。塞进去会破坏该列不变量。
- **代价如实写明**：墓碑保留 `account_id`，因此对外**不能声称"已删除全部数据"**——准确表述是"已删除全部内容，并保留一条不含内容的注销记录"。若将来要求字面删净，须补"注销前排空队列"的机制，成本更高（见重访条件）。

**顺序与失败语义**：顺序**不可随意调换**，第 1 步必须先于最后一步。

1. **先写墓碑**——使在途记录立即失去写入资格；
2. 删除该账号**未领取**的 `pending_write` 记录；
3. 删除该账号**全部档案条目、支持对象与会话‑对象绑定**（[支持对象](支持对象.md)第 7 节；若档案条目对对象有外键，先删条目再删对象）；
4. 撤销该账号**全部会话**；
5. 删除身份服务的用户；
6. 丢弃该账号的 FalkorDB 图。

第 3 步**必须早于第 5 步**：身份用户一旦删除，就再也无法按 `account_id` 定位这些行。

任一步失败即整体失败并明确报错，**不留"用户已删但数据仍在且可读"的中间态**。

**一处残余窗口，如实写明**：第 1 步与第 6 步之间仍有极窄竞态——Worker 可能在"读墓碑（尚无）"之后、图被丢弃之前完成写入，从而**重建**该账号的图。**后果有界**：该账号已不存在、无人能以其身份登录，读路径一律按登录态取数，因此重建的图**不可经应用读取**——它是存储残留（`EVID-D` 范畴），**不是数据泄露**。彻底闭合需额外的每账号锁或"写入后校验"，一期不做，须实测确认窗口可接受。**第 3 步的档案写入不受此竞态影响**：档案写入经 `pending_write` 且有对象归属判定，第 2 步已删未领取记录、墓碑已使在途记录失去资格。

**不可逆**：注销不是登出、也不是停用。CLI 须要求显式确认（如输入账号名），且**不提供撤销**。

## 9. 失败语义

| 情形 | 处置 |
|---|---|
| 注销过程中任一步失败 | 整体失败并明确报错；不留"用户已删但数据仍可读"的中间态（第 8 节） |
| 邀请码无效、过期或已撤销 | 明确拒绝，不建号；不泄露"该码是否存在"以外的信息 |
| 账号名已被占用 | 明确拒绝 |
| 身份服务（core）不可用 | 注册、登录、重置、刷新**与全部受限操作**均不可用并明确报错（fail-closed）；core 在鉴权关键路径上，**不存在不受影响的路径** |
| 会话存储不可用 | 拒绝受限操作（fail-closed）；全应用无匿名可达路径，故不存在"公开基础内容仍可用"的例外 |
| 重置过程中撤销失败 | 整个重置失败并报错；不得留下"密码已改但旧会话仍有效"的中间态 |

## 10. 授权缝（不在这里）

档案的访问判定经项目的**唯一授权端口**；一期实现为"属主即允许"。二期机构协作在同一端口增加维度，认证与账号的形状不变。

**通用记忆的判定不走端口**（2026-09-29 归属裁决）：记忆归属**账号**、分区键取自登录态（`group_id = account_id`），不存在"某条记忆属于哪个支持对象"的判定——因此它没有跨对象授权维度，也不经 `core/authz`（[决策记录](../decisions/通用记忆归属为账号.md)）。登录态本身就是它的边界。

|---|---|---|
| 邮箱与邮箱验证、邮件找回 | 不实现 | 有可用的邮件通道且用户规模需要自助找回 |
| 社交登录、2FA、Passkey | 不实现 | 有真实需求，且评估过身份服务的对应能力 |

| 微信小程序登录 | 不实现 | 小程序上线；它是服务端用 code 换 `openid`，作为**第三种登录方式**接入同一账号体系 |
| 会话管理界面（查看与登出其他设备） | 不实现 | 用户提出需求。**注意**：当前设备的登出**一期就有**（第 6 节），本条只指多设备管理 |
| 自助注销 | 不实现 | 一期无邮箱/手机号，无自助通道；账号注销经运营 CLI 执行（第 8 节） |

## 12. 未核实与待确认

- `TECH-07`：SuperTokens 的**付费特性清单**——门禁机制在 `ee/`，被门禁的功能代码可能在主源码树，需确认我们要的 EmailPassword 与 Session 不被企业许可门禁。
- `TECH-08`：账号名存放于 `email` 字段带来的歧义。
- core 的版本与 Python SDK 的兼容矩阵：**待核实**。
- **限流阈值**（第 5 节两层的具体数值）：**待实测确定**，须在真实登录时延与误伤率之间校准。
- **长流与令牌刷新的交互**（第 5 节"已知风险"）：access token 1 小时，而一轮咨询的 SSE 流可能更长——须实测刷新是否会打断进行中的流。
- **注销残余竞态的窗口宽度**（第 8 节）：须实测"墓碑写入"与"图被丢弃"之间重建该账号图的概率与后果是否可接受。

## 13. 验证方式

对齐验收：`AC-01`（未登录访问任意业务路径被拒，不存在匿名接口，**运维探针端点除外**）、`AC-02`（无档案也能完成应急咨询并标明未使用档案）、`AC-14`（注册与登录只提供个人账号形态，不存在组织账号入口、组织字段或机构访问档案的路径）、`AC-15`（无码或无效码拒绝注册；撤销后不可用；校验在自己的后端）、`AC-16`（只要求账号名与密码）、`AC-17`（重置后旧会话立即失效）、`AC-23`（登出后当前会话立即失效）、`AC-24`（账号注销后内容真删、墓碑保留、无残留可读）。

另需验证：

- **`check_database=True` 确实生效**：撤销会话后用同一 access token 立即重放请求，必须被拒——这条要把"开了开关"与"删了数据库行且查证真的发生"区分开，不能只看配置值。
- **core 不可用时全部受限操作被拒绝**：人为制造 core 故障，验证不存在任何仍可访问的业务路径（fail-closed），并据此确认健康检查与告警覆盖 core。
- **无效邀请码不留下用户记录**：用无效/已撤销的码走注册，除被拒外还须确认身份服务侧**没有**新建用户（复写法必须在调用原实现之前拒绝）。
- 重置过程中撤销失败不留中间态。
- **登出后旧令牌不可用**：登出后立即用登出前的 access token 重放请求，必须被拒（与 `check_database` 项同源，但入口不同）。
- **注销的在途写入不复活**：注销前先写入一条 `pending_write` 并**阻止其被消费**，执行注销后放行消费，验证该记录**不写入**、图未被重建（消融：去掉墓碑后该记录会写入，用此证明墓碑真的在起作用）。
