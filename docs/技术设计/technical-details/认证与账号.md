# 认证与账号

> **权威范围**：账号形态、注册（邀请码）、登录与会话、人工重置、身份服务的集成边界与降级语义。技术选型由[技术栈设计](../../技术栈设计.md)拥有；模块归属由[项目结构设计](../../项目结构设计.md)拥有；档案与记忆的访问判定由授权端口拥有，不在本文。
> **状态**：2026-09-29 依已确认的需求与技术选型设计，待用户确认。不代表已实现。
> **追溯**：`RQ-ACC-01`～`RQ-ACC-06`、`AC-01`、`AC-02`、`AC-14`、`AC-15`、`AC-16`、`AC-17`。
> **依据**：SuperTokens core 仓库 README（core 为独立 Java HTTP 服务，**会话校验在后端 SDK 内完成、不经过 core**，用户数据 100% 在自己的库；`ee/` 之外为 Apache-2.0）；SuperTokens 官方文档《Implement username login》（复写 email 校验器实现账号名登录）。

## 1. 目标与边界

身份只回答三件事：**你是谁、属于哪个组织、当前会话是否有效**。它不回答"你能看哪个支持对象的档案"——那是授权端口的事。

- 全应用必须登录（`RQ-ACC-01`）：不存在匿名内容页、匿名接口或未登录可达的业务路径。
- 登录本身不授予任何个人资料的访问权。
- 认证不可用时**拒绝受限操作**，不降级为放行。

## 2. 组件与职责

| 组件 | 职责 | 不承担 |
|---|---|---|
| SuperTokens core（独立 Java 容器） | 注册、登录、重置、会话刷新时的身份操作与数据库操作 | 每个请求的鉴权——**会话校验在 Python SDK 内完成，不经过 core** |
| SuperTokens Python SDK（在我们进程内） | 会话校验、按请求重新查证、与我们的存储交互 | 业务授权判定 |
| 我们的 PostgreSQL | 身份与会话数据的存放（core 使用我们的库） | 授权真相 |
| `accounts` 模块 | 邀请码注册编排、人工重置编排、组织标识 | 任何档案可见性判定 |

**一条关键的可用性事实**：登录之后的每个请求**不依赖 Java core**——它依赖我们的数据库。core 挂掉只影响注册、登录、重置与刷新，不影响已登录用户继续使用。

**三条运营与成本边界**（已核实）：① SuperTokens 的 **Dashboard 超过 3 个用户即需付费**，因此一期运营操作（建号、人工重置）**走 SDK 或 Management API**，不依赖 Dashboard；② **攻击防护套件属付费特性**，因此登录限流与防爆破由我们自己实现；③ **Multitenancy 与 SSO/SAML 属付费**（定价计算器显示 $0，与文档表述不一致，故标为**不确定**），二期若要做机构多租户，需评估付费许可或自建。

## 3. 账号形态

- **账号名登录，不要求邮箱**（`RQ-ACC-05`）。按官方文档的做法实现：复写 email 校验器使账号名通过校验。
  **已知偏差**：标识在内部**仍存放于 `email` 字段**（`TECH-08`）。这带来两处风险，需在实现时显式处理：以后真要加邮箱时"登录名"与"联系方式"会冲突；我们自己的用户表与身份服务的表要通过明确的映射关联，不得各自成为"谁是谁"的第二定义。
- **组织账号只作账号形态**（`RQ-ACC-03`）：组织标识作为账号属性存在；**一期不产生任何机构内的成员管理，也不存在机构访问支持对象档案的路径**。
- **一期账号没有可主动触达的联系通道**（无邮箱、无手机号）：这影响告知、条款变更通知与二期机构协作时的成员确认。属于已知限制，不是默认设计。

## 4. 注册（邀请码）

- **不开放自由注册**（`RQ-ACC-04`）。注册须凭有效邀请码。
- **校验在我们自己的后端**，不依赖身份服务是否原生支持邀请码：我们持有邀请码表（码、状态、可用次数或一次性、有效期、撤销时间、创建者），校验通过后才经 SDK 建号。
- 邀请码的发放与撤销由运营控制；撤销后**立即不可再用**。
- 提交内容：账号名、密码、邀请码。不要求邮箱，不要求填写任何支持对象信息。

## 5. 登录与会话

- 每个请求由服务端重新查证会话；**客户端凭据不得作为权限证明**。
- **会话必须可由服务端即时撤销**（`RQ-ACC-06`）：这是"人工重置"能成立的前提——重置后旧会话若仍有效，重置形同虚设。
- 会话与业务授权分离：会话有效只说明"你是某个账号"，不说明"你能看什么"。

## 6. 人工重置

- 运营者入口：为指定账号重置密码 → **同一操作内撤销该账号的全部会话**（两件事必须同时发生，不允许只做一件）。
- 一期**不承诺自助找回**。二期重访条件：有真实用户规模后，评估邮箱选填或一次性恢复码。

## 7. 失败语义

| 情形 | 处置 |
|---|---|
| 邀请码无效、过期或已撤销 | 明确拒绝，不建号；不泄露"该码是否存在"以外的信息 |
| 账号名已被占用 | 明确拒绝 |
| 身份服务（core）不可用 | 注册、登录、重置、刷新不可用并明确报错；**已登录用户的请求不受影响** |
| 会话存储不可用 | 拒绝受限操作（fail-closed）；公开基础内容的可达性不由本文决定 |
| 重置过程中撤销失败 | 整个重置失败并报错；不得留下"密码已改但旧会话仍有效"的中间态 |

## 8. 授权缝（不在这里）

档案与记忆的访问判定经项目的**唯一授权端口**；一期实现为"属主即允许"。二期机构协作在同一端口增加维度，认证与账号的形状不变。

## 9. 一期不做（扩展缝）

| 缝 | 一期状态 | 启用条件 |
|---|---|---|
| 邮箱与邮箱验证、邮件找回 | 不实现 | 有可用的邮件通道且用户规模需要自助找回 |
| 社交登录、2FA、Passkey | 不实现 | 有真实需求，且评估过身份服务的对应能力 |
| 组织成员管理 | 不实现 | 二期机构协作 |
| 微信小程序登录 | 不实现 | 小程序上线；它是服务端用 code 换 `openid`，作为**第三种登录方式**接入同一账号体系 |
| 会话管理界面（查看与登出其他设备） | 不实现 | 用户提出需求 |

## 11. 验证方式

对齐验收：`AC-01`（未登录访问任意业务路径被拒，不存在匿名接口）、`AC-02`（无档案也能完成应急咨询并标明未使用档案）、`AC-14`（组织账号能登录，且不存在机构访问档案的路径）、`AC-15`（无码或无效码拒绝注册；撤销后不可用；校验在自己的后端）、`AC-16`（只要求账号名与密码）、`AC-17`（重置后旧会话立即失效）。

另需验证：**core 不可用时已登录会话仍可用**（用人为制造故障证明这条降级真的成立，而不是写在纸上）；重置过程中撤销失败不留中间态。
