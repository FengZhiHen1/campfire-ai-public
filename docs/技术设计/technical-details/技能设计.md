# 技能设计（一期总纲）

> **权威范围**：一期的 **skill 清单与定位**、每个 skill 的**工具范围**、**激活与工具范围的关系**、以及**共用纪律的一致性维护方式**。每个 skill 的方法论与 `SKILL.md` 正文要点在[咨询面 `skills/`](../面/consult/skills/)，每个工具的契约在[咨询面 `tools/`](../面/consult/tools/)；skill 机制由[通用基座](通用基座.md)拥有。
> **状态**：2026-09-29 依用户确认的划分与激活语义设计；**2026-10-01 依用户裁决重写激活语义**（激活记录即授权真源、授权跨运行只增不减、`skill` 参数值域收敛），见第 4 节。不代表已实现：实现与本文存在已知偏差，落地时须按本文修正。
> **追溯**：`RQ-CON-01`～`RQ-CON-04`、`RQ-CON-06`、`RQ-CON-08`、`RQ-EMG-01`～`RQ-EMG-03`、`RQ-DAY-01`、`RQ-MEM-02`、`RQ-MEM-04`、`RQ-ACC-09`、`AC-11`、`AC-12`、`AC-13`、`AC-18`、`AC-19`、`AC-25`。
> **标准依据**：Agent Skills 开放标准——`name` 须与目录名一致且仅小写字母、数字与连字符；`description` 是选择键；主体建议不超过 500 行；`references/` 一层深；**每个 skill 是自包含目录，且标准不支持 skill 之间互相依赖**。

## 1. 一期的四个 skill

| `name`（目录名） | 定位 | 激活来源 | 工具范围 | `references/` |
|---|---|---|---|---|
| [emergency-consulting](../面/consult/skills/emergency-consulting.md) | 时间紧迫情境下的即时咨询：**固定顺序的六层闸门**（医疗→基线偏离→沟通→环境→既往策略→安全），输出一张现场 Action Card | 程序注入（应急表单入口，`autoload: "false"`）；**不可经 `skill` 参数手选**（2026-10-01 裁决，见第 4 节） | 只读：资料、案例；输出：应急行动卡（档案八组稳定信息由应用预注入，不走工具） | `gates.md`、`action-card.md` |
| [daily-consulting](../面/consult/skills/daily-consulting.md) | 日常咨询，目标是**展开**：澄清问题、给出带依据的建议 | 模型按 `description` 匹配；使用者也可选定（`skill` 参数合法值） | 只读：档案摘要、档案条目、记忆时间线（账号级）、资料、案例 | `clarification.md`、`evidence-and-options.md` |
| [profile-curation](../面/consult/skills/profile-curation.md) | 把对话中已出现的信息整理成档案候选，交使用者确认 | 模型在对话中激活；使用者也可选定（`skill` 参数合法值） | 对象创建 + 读档案条目 + 写候选与记忆（`create_support_object` 于 2026-10-01 裁决加入，跨会话建对象的授权来源） | `extraction-rules.md`、`source-and-status.md` |
| [onboarding](../面/consult/skills/onboarding.md) | 账号首次日常会话的**一次性引导**：告知、创建第一个支持对象、以应急八组为纲的档案种子、使用者认知、使用说明跳转（2026-09-30 定，机制见第 4 节） | 程序注入（仅首次日常会话，应用查 `campfire_onboarding` 状态表决定），`autoload: "false"`；**不可经 `skill` 参数手选**（2026-10-01 裁决，见第 4 节） | 对象创建 + 读档案条目 + 写档案与记忆 + `finish_onboarding` | `seed-questions.md`、`telling-first.md` |

前三个 skill 的分工理由（应急为什么不能与日常合并、沉淀为什么独立）见[咨询面概览](../面/consult/README.md)第 2 节；onboarding 为什么独立于 profile-curation（主动结构化提问 vs 被动整理、触发准确性互不污染）见[该 skill 第 1 节](../面/consult/skills/onboarding.md)。

**三条共同纪律**（咨询类三份 `SKILL.md`——emergency、daily、profile-curation——都必须含）：

1. 有据才给可执行建议；依据不足、资料冲突或超出能力时明确限制；**需要寻求专业帮助时，按各 skill 的边界声明处理**（`RQ-CON-02`）。
2. 目标不等于服从：不把"让他听话、安静、别丢脸"转成控制当事人的建议（`RQ-CON-04`）。
3. 专业判断与可读解释并给：涉及专业概念时在当次输出内解释到不需要专业背景即可理解（`RQ-CON-06`）。

另有一条只在咨询类 skill 出现的纪律：**只把注入的稳定层内容当事实**，候选层内容只能以"待确认"呈现（`RQ-MEM-04`）。**onboarding 不含共用标记块**（豁免一致性检查）：三条共同纪律的语义前提是"产出咨询输出"，引导不产出咨询建议，语义前提不成立（见[该 skill 第 3.3 节](../面/consult/skills/onboarding.md)）。

> **2026-09-29 两次裁决的最终形态**：共用纪律不统一要求"给出真实求助路径"。应急按外部调研框架改为**医疗危险优先**（`RQ-EMG-04`）：输出「医疗风险：稳定 / 未排除 / 高风险」并给「何时升级」，**但不做诊断、不给用药建议、不含已发生自伤或伤人时的处置流程**（见[该 skill 第 5 节](../面/consult/skills/emergency-consulting.md)）；日常可按需说明何种情况下应寻求专业帮助，措辞同样保守。

## 2. 共用纪律的一致性维护

标准不支持 skill 间依赖，且每个 skill 必须自包含，所以共用段落必然有多份拷贝。用标记块 + 工程检查防漂移：

```text
<!-- shared:evidence-discipline -->
…共用纪律正文…
<!-- /shared:evidence-discipline -->
```

检查规则：**同名标记块在全部 skill 中必须逐字一致**；不一致即工程检查失败。标记块之外的正文各自不同。

**第十个工具为什么不属业务模块**：它不读也不写任何业务数据——它把应急输出的七节与四个状态字段校验后交给基座事件通道，语义归应急 skill，不归 `modules/*`。放在产品侧而不做成基座保留工具，是为了让**领域词表的机械校验落在这一侧**（医疗风险只取三值由参数枚举保证），同时保持基座不含领域术语（基座第 1 节不变量）。它与 `finish_onboarding` 一样经装配处注册，不是某个 skill 的特权工具。

**五个 `profile` / `memory` 工具的参数差异**（2026-09-29 归属裁决）：档案侧工具收 `support_object_id`；**记忆侧两个工具不收**——记忆归属账号，分区键取自登录态（见[决策记录](../decisions/通用记忆归属为账号.md)）。`memory` 一侧因此没有对象维度的越权判定点。`create_support_object` 与 `finish_onboarding` 也不收 `account_id`：属主与状态键都取登录态（各自的契约硬约束）。

**未激活任何 skill 时的默认可用工具集**：一期只含 `read_profile_summary` 与 `search_knowledge`（只读）。

**应急上下文不是工具**：`emergency_context(support_object_id)` 由应用在构造第一条消息时取数并注入（[基座](通用基座.md)第 4 节"面可提前代跑工具注入"），以满足应急时延目标，因此**不出现在工具清单里**。**应急记忆预注入同路**：近期派生事实也由应用侧取数并随应急上下文一起注入，同样不是工具（[通用记忆](通用记忆.md)第 6 节）——注意**记忆侧的取数分区键是账号**（`account_id`），不是 `emergency_context` 的 `support_object_id`（2026-09-29 归属裁决，见[决策记录](../decisions/通用记忆归属为账号.md)）。

**每个 skill 能用的工具**见第 1 节表格；`SKILL.md` 的 frontmatter 以 `allowed-tools` 声明同一集合。

## 4. 激活与工具范围的关系

**2026-10-01 用户裁决：激活记录即授权真源。** 无论激活由谁发起（模型匹配、使用者手选、程序注入），其落库形态统一为会话历史中的 skill 工具调用记录（function_call + 携带 `<skill_content>` 的结果对——模型侧真实调用，应用侧合成同形记录）；授权从历史激活记录推导、跨运行持续、**只增不减**。机制细节归[通用基座](通用基座.md)第 3、5 节拥有，本文只定业务侧的三件事：

- **`skill` 参数的合法值域 = 模型可见目录集**（`daily-consulting`、`profile-curation`）：使用者手选只能选模型自己也能选的。`emergency-consulting` 与 `onboarding` 传入即 **422**——应急只走应急表单入口（入口唯一性由「应急是分秒必争的场景，选择器入口会让使用者明知应急却被迫浏览目录」支撑）；onboarding 由引导状态表触发，手选等于绕过触发条件（「无行即注入」的判定会被一个载荷字段推翻）。值域之外的名字同样 422——静默忽略会让使用者以为选中的技能起了作用。
- **程序注入的把关者**：`autoload: "false"` 的两个 skill（应急、引导），其合成记录只能由应用在触发条件成立时写入——应急的触发条件是应急表单入口，引导的是 `campfire_onboarding` 状态表判定。`autoload` 门（拒绝模型发起的调用）与应用侧触发条件是同一授权的两道互不代写的关卡。
- **一次性引导的触发（2026-09-30 定，`RQ-ACC-09`）**：账号首次创建**日常**会话时，应用查 `campfire_onboarding` 状态表（归 `modules/accounts`，表形状见[认证与账号](认证与账号.md)第 8 节）——无行或 `in_progress` 即程序注入 onboarding skill；`completed`（模型经 `finish_onboarding` 工具写入）或 `skipped`（UI 跳过入口写入）即不注入。**应急会话永不触发**（`RQ-EMG-03` 时延硬约束）；「首次」由状态表判定，不从档案或会话推导。引导会话延续为日常对话，会话中创建的第一个对象补建该会话绑定（[支持对象](支持对象.md)第 6 节）。

**授权语义（纯并集、只增不减）的既有依据与代价**：一次对话先后激活多个 skill（现场问答后模型激活 `profile-curation` 沉淀候选）本来就是设计过的场景；三个 skill 中两个含共用纪律标记块，方法论共存有机械检查防漂移。代价是引导完成后其工具在本会话内不回收——`finish_onboarding` 之后同会话仍可建对象、写档案，这与档案工具「对话式创建是一等入口」的产品定调相容，接受它。原「同时激活数量上限待确认」一项随之关闭：纯并集下没有「同时激活」概念，只有集合成员关系；并集天然封顶于池内已注册白名单。

**其他既有事实的落地口径**：

- 工具范围的**主手段**是"声明保持稳定 + 可用性用消息告知 + 服务端拒绝越界调用"（基座第 5 节）。
- 应急表单入口构造第一条消息时**就是**一次程序注入的激活；它带来合成激活记录，此后该会话的后续轮次无需（也不能）经 `skill` 参数续授权。
- **暴露范围不是安全边界**：服务端仍按请求与参数校验权限。

## 5. 验证方式

- **标准校验**：四个 skill 均通过 `skills-ref validate`；`name` 与目录名一致。
- **一致性检查**：同名共用标记块逐字一致（onboarding 无标记块，豁免由第 1 节的裁决承担）。
- **触发准确性**：`daily-consulting` 与 `profile-curation` 各准备"应为触发"与"不应为触发"的提示集；应急验证"注入即激活"且不被自动匹配；onboarding 验证"仅首次日常会话注入、状态表驱动、应急会话与二次日常会话不注入"。
- **工具范围**：断言应急激活时写工具被服务端拒绝；`profile-curation` 无法把推断写成已确认；onboarding 未激活时 `finish_onboarding` 被服务端拒绝。
- **授权跨运行（2026-10-01 裁决）**：引导会话「首次注入 → 提问中止 → 回答续跑」全程 onboarding 工具可用；应急会话后续轮次无需重选技能；`skill` 参数传 `emergency-consulting` / `onboarding` / 未知名 → 422。
