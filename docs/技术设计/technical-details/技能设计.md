# 技能设计（一期总纲）

> **权威范围**：一期的 **skill 清单与定位**、每个 skill 的**工具范围**、**激活与工具范围的关系**、以及**共用纪律的一致性维护方式**。每个 skill 的方法论与 `SKILL.md` 正文要点在[咨询面 `skills/`](../面/consult/skills/)，每个工具的契约在[咨询面 `tools/`](../面/consult/tools/)；skill 机制由[通用基座](通用基座.md)拥有。
> **状态**：2026-09-29 依用户确认的划分与激活语义设计，待用户确认。不代表已实现。
> **追溯**：`RQ-CON-01`～`RQ-CON-04`、`RQ-CON-06`、`RQ-CON-08`、`RQ-EMG-01`～`RQ-EMG-03`、`RQ-DAY-01`、`RQ-MEM-02`、`RQ-MEM-04`、`AC-11`、`AC-12`、`AC-13`、`AC-18`、`AC-19`。
> **标准依据**：Agent Skills 开放标准——`name` 须与目录名一致且仅小写字母、数字与连字符；`description` 是选择键；主体建议不超过 500 行；`references/` 一层深；**每个 skill 是自包含目录，且标准不支持 skill 之间互相依赖**。

## 1. 一期的三个 skill

| `name`（目录名） | 定位 | 激活来源 | 工具范围 | `references/` |
|---|---|---|---|---|
| [emergency-consulting](../面/consult/skills/emergency-consulting.md) | 时间紧迫情境下的即时咨询：**固定顺序的六层闸门**（医疗→基线偏离→沟通→环境→既往策略→安全），输出一张现场 Action Card | 程序注入（应急卡片构造的第一条消息），`autoload: "false"` | 只读：资料、案例（档案八组稳定信息由应用预注入，不走工具） | `gates.md`、`action-card.md` |
| [daily-consulting](../面/consult/skills/daily-consulting.md) | 日常咨询，目标是**展开**：澄清问题、给出带依据的建议 | 模型按 `description` 匹配；使用者也可选定 | 只读：档案摘要、档案条目、记忆时间线（账号级）、资料、案例 | `clarification.md`、`evidence-and-options.md` |
| [profile-curation](../面/consult/skills/profile-curation.md) | 把对话中已出现的信息整理成档案候选，交使用者确认 | 模型在对话中激活；使用者也可选定 | 读档案条目 + 写候选与记忆 | `extraction-rules.md`、`source-and-status.md` |

三个 skill 的分工理由（应急为什么不能与日常合并、沉淀为什么独立）见[咨询面概览](../面/consult/README.md)第 2 节。

**三条共同纪律**（三份 `SKILL.md` 都必须含）：

1. 有据才给可执行建议；依据不足、资料冲突或超出能力时明确限制；**需要寻求专业帮助时，按各 skill 的边界声明处理**（`RQ-CON-02`）。
2. 目标不等于服从：不把"让他听话、安静、别丢脸"转成控制当事人的建议（`RQ-CON-04`）。
3. 专业判断与可读解释并给：涉及专业概念时在当次输出内解释到不需要专业背景即可理解（`RQ-CON-06`）。

另有一条只在咨询类 skill 出现的纪律：**只把注入的稳定层内容当事实**，候选层内容只能以"待确认"呈现（`RQ-MEM-04`）。

> **2026-09-29 两次裁决的最终形态**：共用纪律不统一要求"给出真实求助路径"。应急按外部调研框架改为**医疗危险优先**（`RQ-EMG-04`）：输出「医疗风险：稳定 / 未排除 / 高风险」并给「何时升级」，**但不做诊断、不给用药建议、不含已发生自伤或伤人时的处置流程**（见[该 skill 第 5 节](../面/consult/skills/emergency-consulting.md)）；日常可按需说明何种情况下应寻求专业帮助，措辞同样保守。

## 2. 共用纪律的一致性维护

标准不支持 skill 间依赖，且每个 skill 必须自包含，所以共用段落必然有多份拷贝。用标记块 + 工程检查防漂移：

```text
<!-- shared:evidence-discipline -->
…共用纪律正文…
<!-- /shared:evidence-discipline -->
```

检查规则：**同名标记块在全部 skill 中必须逐字一致**；不一致即工程检查失败。标记块之外的正文各自不同。

**每个 skill 能用的工具**见第 1 节表格；`SKILL.md` 的 frontmatter 以 `allowed-tools` 声明同一集合。

## 4. 激活与工具范围的关系

- 工具范围的**主手段**是"声明保持稳定 + 可用性用消息告知 + 服务端拒绝越界调用"（基座第 5 节）；激活的两种落地形态由基座第 3 节拥有，本文不复述。
- 应急卡片构造的第一条消息**就是**一次程序注入的激活；它只带来只读工具。
- 一次对话可先后激活多个 skill：例如现场问答结束后，模型激活 `profile-curation` 把这次对话沉淀为候选。同时激活的数量上限**待确认**。
- **暴露范围不是安全边界**：服务端仍按请求与参数校验权限。

## 5. 验证方式

- **标准校验**：三个 skill 均通过 `skills-ref validate`；`name` 与目录名一致。
- **一致性检查**：同名共用标记块逐字一致。
- **触发准确性**：`daily-consulting` 与 `profile-curation` 各准备"应为触发"与"不应为触发"的提示集；应急验证"注入即激活"且不被自动匹配。
- **工具范围**：断言应急激活时写工具被服务端拒绝；`profile-curation` 无法把推断写成已确认。
