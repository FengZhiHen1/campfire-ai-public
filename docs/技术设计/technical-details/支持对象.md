# 支持对象

> **权威范围**：支持对象的实体形状、生命周期（创建、改名、归档、恢复）、归属与访问判定契约、会话与对象的绑定、以及账号注销时必须一并处置的数据。档案条目与稳定层由[个性化档案](个性化档案.md)拥有；授权端口的组织地位与依赖白名单由[项目结构设计](../../项目结构设计.md)拥有；账号注销的编排、顺序与墓碑由[认证与账号](认证与账号.md)拥有；模块归属由[项目结构设计](../../项目结构设计.md)拥有。
> **状态**：2026-09-29 依用户对生命周期的裁决（创建 + 改名 + 归档）设计，待用户确认。不代表已实现。
> **追溯**：`RQ-MEM-05`、`RQ-MEM-07`、`RQ-ACC-08`、`AC-02`、`AC-22`、`AC-24`。
> **依据**：需求业务概念表与 `RQ-MEM-07` 原文；`apps/api/src/campfire/modules/profile/__init__.py`（占位，只声明用例）、`core/authz/__init__.py`（空占位）、`core/pending_write/models.py`（`support_object_id` 的存储层 CHECK 已在等这个实体）、`apps/api/tests/test_layer_boundaries.py`（依赖白名单的机械检查，决定实体**不能**放哪一层）。

## 1. 目标与边界

支持对象是**平台围绕提供支持的具体孤独症人士**，是个性化档案的归属主体。一期它同时是三个机制的锚点：

| 锚点 | 谁依赖 |
|---|---|
| 档案条目的归属键 | 档案条目、待处理写入记录（`kind = profile_item` 时必填）、两个档案读取工具 |
| 会话的绑定目标 | 咨询面的应急与日常两条入口、会话列表的对象名 |
| 授权判定的被判定对象 | `core/authz` 唯一端口（"属主即允许"） |

**它不承载关于这个人的事实**——那是档案（[个性化档案](个性化档案.md)）；也不承载使用者自身的经验——那是通用记忆。它只有"这个对象是谁的、叫什么、是否仍在用"这三件事。

明确不做的事：

- **不设关系字段**（监护、亲属、代理人…）。一期账号只有个人形态，持有者即监护者（`RQ-MEM-05`），关系没有第二个取值；二期共用时才有区分，届时按[项目结构设计](../../项目结构设计.md)第 8 节的授权缝增加维度，本文第 3 节的形状不变。
- **不设权限与分享字段**（谁可编辑、医疗可见、紧急状态可见…）。一期共享不存在。
- **不承载可识别身份信息**（法定姓名、出生日期、性别、照片、联系方式）。理由与字段清单见[个性化档案](个性化档案.md)第 6.3 节。
- **不是档案的第二份真源**：对象上没有摘要、没有条目计数、没有"最近咨询时间"等派生值。

## 2. 为什么必须先有这个实体

这不是"补一个缺失的表"，而是**判定点已经存在、被判定对象不存在**：

| 位置 | 依赖方式 | 现状 |
|---|---|---|
| [个性化档案](个性化档案.md) 第 2 节 | `profile_item.support_object_id` 归属键 | 字段已定义，实体无定义 |
| [个性化档案](个性化档案.md) 第 9 节 | "每次访问都要校验该对象属于当前账号" | 校验对象不存在 |
| [写入路径](写入路径.md) 第 3 节 | `pending_write.support_object_id` | **存储层已建 CHECK**：`(kind = 'profile_item') = (support_object_id IS NOT NULL)` |
| [emergency-consulting](../面/consult/skills/emergency-consulting.md) 第 4.1 节 | `emergency_context(support_object_id)` 取数键 | 取数键的合法性无处校验 |
| [read_profile_summary](../面/consult/tools/read_profile_summary.md) 第 5 节 | "支持对象不存在或不属于当前账号 → 明确失败" | 判定依据不存在 |
| [认证与账号](认证与账号.md) 第 8 节 | 账号注销须删除该账号全部内容 | 档案与对象的删除项缺失（见第 7 节） |

`core/authz` 是空占位，其说明写着"端口的形状随第一个真实调用点落地"——**本实体就是那个第一个调用点**。

## 3. 实体形状

```text
campfire_support_object
├── id             主键（UUID，由 core/db.new_uuid 生成）
├── account_id     属主账号（= 身份服务的用户标识，见认证与账号第 3 节）
├── display_name   对象名（使用者自己起的称呼，用于切换器与列表）
├── created_at
├── updated_at
└── archived_at    归档时间；为空表示仍在用（第 4 节的唯一状态位）
```

| 字段 | 类型与约束 | 说明 |
|---|---|---|
| `id` | `UUID` 主键 | 业务主键，**不外露为账号或分区键**——它是档案的归属键，不是任何图库分区键 |
| `account_id` | `String(128)` 非空 | 宽度与 `core/pending_write` 的 `MAX_ACCOUNT_ID_LENGTH`、删除账本的 `account_id` 列一致；**不建外键**——身份服务的表由 core 拥有，跨进程外键不可靠（同[认证与账号](认证与账号.md)第 3 节"不建映射表"的取向） |
| `display_name` | `String(64)` 非空，CHECK `length(btrim(display_name)) > 0` | 使用者填写的名字。非空判据落**存储层**（同 `pending_write` 词表与删除账本 `reason` 的既有做法）：空名会让切换器出现无法辨认的条目，而"先查后写"挡不住并发与直连写入 |
| `created_at` / `updated_at` | `DateTime(timezone=True)` 非空 | `updated_at` 随改名与归档更新 |
| `archived_at` | `DateTime(timezone=True)` 可空 | 唯一的生命周期状态位：空 = 在用，非空 = 已归档 |

索引：

- `ix_campfire_support_object_account_archived (account_id, archived_at)` —— 切换到某账号的对象列表，且默认只取在用对象。
- `ix_campfire_support_object_account_created (account_id, created_at)` —— 默认排序（创建先后），也是"上次选择"推导的回退路径（第 6 节）。

**不建唯一约束**：同一账号下可以有两个同名对象（两个人都叫"小宝"是真实情形）。同名由使用者自己辨认，不靠数据库拒绝。

### 3.1 `display_name` 与档案"偏好称呼"的分工

这两者**不是同一个事实**，实现时不得合并：

| | `support_object.display_name` | 档案条目的"偏好称呼" |
|---|---|---|
| 是什么 | 使用者给这个对象起的**操作标签** | 关于这个人的一条**事实** |
| 归谁 | 本文（对象实体） | [个性化档案](个性化档案.md)第 6 节领域一 |
| 用在哪 | 切换器、会话列表、对象管理 | 咨询输出与注入 |
| 是否进咨询上下文 | **不进**——它是导航用标签，不是关于这个人的认识 | 进（稳定层） |
| 是否必填 | 必填（新建时要有个名字） | 选填（不知道就留空，不猜） |

**判据**：若一条信息会出现在咨询输出里作为对这个人的描述，它属档案；若它只是让使用者在界面上认出这个对象，它属对象。**同一个值在两边都存在是允许的**（使用者可以把切换器里的名字填成对方喜欢的称呼），但**任何一边都不得从另一边自动推导或回写**——那会产生两个可写的真源。

## 4. 生命周期

四个操作，一个状态位。**没有删除。**

| 操作 | 前置 | 效果 | 不变量 |
|---|---|---|---|
| **创建** | 已登录（`RQ-ACC-01`） | 插入一行，`archived_at` 为空 | 账号由登录态决定，**不接受调用方传入**（同记忆分区键的做法：忘记传就落到别人名下这类缺陷要由实现层堵掉） |
| **改名** | 对象属主 = 当前账号，且**未归档** | 更新 `display_name` 与 `updated_at` | 改名**不触碰档案**——历史条目里的来源与内容不随改名变化 |
| **归档** | 对象属主 = 当前账号，且未归档 | 置 `archived_at` | **不删除任何数据**：档案条目全部保留，仍可读取 |
| **恢复** | 对象属主 = 当前账号，且已归档 | 置 `archived_at` 为空 | 恢复后重新接受写入 |

**为什么是归档而不是删除**（2026-09-29 用户裁决）：

1. **删除会让在途写入产生歧义**。`pending_write` 里可能已有一条 `profile_item` 在排队，Worker 领取时按[写入路径](写入路径.md)第 6 节重新判定归属——若对象已被删得无迹可寻，"查不到"与"从未存在"无法区分。账号注销为这个问题专门引入了墓碑（[认证与账号](认证与账号.md)第 8 节）；**归档让行始终存在，因此不需要墓碑**。
2. **误建与误归档都可逆**。归档与恢复是同一个状态位的两次赋值，使用者不必承担不可逆的后果。
3. **档案是历史**。该对象过往的条目是已经发生的记录，不因"这个人现在还用不用这个对象"而消失。

**归档的语义边界**（必须明确，否则实现者会自行发挥）：

- 归档对象**可以读**：档案条目仍可查看、纠正、删除（`RQ-MEM-03` 不因归档而失效）。
- 归档对象**不接受新增写入**：`propose_profile_item` 在该对象上明确失败（第 5 节），已排队的 `pending_write` 在领取时同样被拒。
- 归档对象**不出现在新建会话的对象选择里**，但**仍可从档案页切换器进入**（标注"已归档"）以便查看或恢复。
- **归档不等于停用账号，也不等于注销**：它只作用于一个支持对象，不影响账号与其他对象。

**一期不设对象数量上限**：`RQ-MEM-07` 只说"可有多个"，没有给出需要限制的证据；限制会引入"达到上限怎么办"的新分支。

## 5. 归属与访问判定契约

### 5.1 端口在 `core/authz`，一期实现由 `profile` 提供

[项目结构设计](../../项目结构设计.md)第 8 节已定调：`core/authz` 是唯一授权判定端口，一期只有"属主即允许"一个实现，二期由 `spaces` 模块实现同一端口、**调用点不变**。本文落实这句话的形状：

```text
core/authz 提供（协议与错误类型，不依赖任何业务模块）
    require_owned(account_id, support_object_id) -> None
        # 读路径：对象存在且属主为 account_id 则返回，否则抛 AuthorizationError
    require_writable(account_id, support_object_id) -> None
        # 写路径：在 require_owned 之上再要求对象未归档

modules/profile 提供（一期的唯一实现：属主即允许）
    实现上述两个函数；装配处在 main.py / worker.py 注入
```

**为什么是两个具名函数而不是一个带布尔参数**：布尔参数在调用点读不出语义（`require(x, y, False)` 是不是"允许归档对象"看不出来），而读写两类调用点都要用，写错方向的后果不对称——把归档对象当可写会污染档案，把可写对象当只读只是行为不变。

**为什么抛错而不是返回 `bool`**：返回布尔值时"忘了检查返回值"是一条静默失效路径；抛错让漏检不可能通过（`AC-22` 的判定不能靠调用方自觉）。

### 5.2 调用点

| 调用方 | 用哪个 | 依据 |
|---|---|---|
| `read_profile_summary`、`read_profile_items` | `require_owned` | 越权读取必须失败，且**不得**返回空摘要冒充"没有档案" |
| `propose_profile_item` | `require_writable` | 已归档对象不得接受新增 |
| 咨询面构造应急上下文 | `require_owned` | `emergency_context(support_object_id)` 的取数键 |
| 咨询面建立会话绑定 | `require_writable` | 不应把新会话绑定到已归档对象（第 6 节） |
| Worker 领取 `profile_item` | `require_writable` | [写入路径](写入路径.md)第 6 节"授权判定必须在领取时重新做一次" |
| 档案面的纠正、删除 | `require_owned` | 归档对象仍可纠正与删除条目（第 4 节） |

**Worker 能读端口，是因为它只依赖 `core/*`**（[项目结构设计](../../项目结构设计.md)第 7 节）：协议与错误类型在 `core/authz`，实现经装配注入——若端口定义在 `modules/profile`，Worker 就得 import 业务用例，那是白名单禁止的。

### 5.3 失败语义

| 情形 | 对外行为 | 理由 |
|---|---|---|
| 对象不存在 | `AuthorizationError`，文案与"不属于你"**完全相同** | 区分二者等于提供对象枚举通道——与登录限流"不区分账号不存在与密码错误"同一条纪律 |
| 对象属于其他账号 | 同上 | 同上 |
| 对象已归档而调用方是写路径 | 明确失败，**文案区分**："该对象已归档，不能新增记录" | 属主自己的对象，告知归档状态不泄露任何信息，且使用者需要知道原因才能去恢复 |
| 端口实现不可用（如库不可达） | 明确失败，**不降级为放行** | [技术栈设计](../../技术栈设计.md)第 5 节：认证或授权不可用时拒绝受限操作 |

## 6. 会话与对象的绑定

`RQ-MEM-07` 要求：绑定在**会话开始时确定**，**默认沿用该账号上一次的选择**，且**可切换**；每次访问都要校验该对象属于当前账号。

**"可切换"的作用范围**（本节的判定，与已定页面设计一致）：切换影响的是**后续新建的会话**，不是进行中的会话——[档案页](../../design/pages/档案页.md)已写明"本页切换不影响进行中会话"。因此每个会话的绑定在建立时确定后**不再改变**。

```text
campfire_session_object
├── session_id        主键（对话标识；一个会话恰好一个对象）
├── account_id        建立绑定时所属账号
├── support_object_id 绑定的支持对象
└── bound_at
```

- **主键是 `session_id`**：一个会话只有一个对象，切换是"下一个会话换一个对象"，不是"同一会话内改绑"。
- **首对象补绑（2026-09-30 定，`RQ-ACC-09`）**：会话建立时账号**没有任何在用对象**的，该会话先落"无绑定"；引导对话在该会话中创建第一个对象（或会话中建立了账号的第一个对象）时，**补建为该会话的唯一绑定**——这是从无到有的首次绑定，不是改绑，不违反"绑定不可变"的本意（该不变量禁止的是既有绑定的变更，见上方"可切换"的作用范围）。补绑**只发生一次**：会话已有绑定后再建新对象不改绑。
- **索引** `ix_campfire_session_object_account_bound (account_id, bound_at)`：用于推导"上一次的选择"。
- **"默认沿用上一次的选择"由本表推导，不另存字段**：取该账号 `bound_at` 最大的那条绑定的对象；没有历史时回退到 `campfire_support_object` 里创建最早的在用对象（第 3 节索引）。**不新增"账号当前对象"字段**——那会成为第二个可写的真源，与绑定记录冲突时无法判断谁对。
- **不写进 SDK 的会话表**：对话真源是 SDK 的会话存储（[通用基座](通用基座.md)第 2 节），它的两张表尚未登记（见[设计待办](../../TODO.md)）。归属映射是**我们的业务事实**，不是对话内容；混进 SDK 表会让"对话真源"这个概念被掏空，也会让 SDK 升级时的表结构变更牵连业务数据。
- **本表不回答"会话属于哪个账号"**（2026-09-30 定）：它只在会话**已绑定对象**时才有行，而无对象账号的会话按上一行先落"无绑定"。归属判定因此另立 `campfire_session`（归 `modules/accounts`，见[决策记录](../decisions/会话归属单立表归accounts.md)）。两表回答两个不同的问题，不互斥、不互相推导——不得用本表有无行来推断会话是否存在或属于谁。
- **归档对象与新会话**：归档后**不再被选为默认对象**（默认对象只从在用对象里取）；已绑定到归档对象的既有会话仍可查看其内容。

## 7. 账号注销时的处置

账号注销的编排、顺序与墓碑归[认证与账号](认证与账号.md)第 8 节，本文只声明**必须一并处置的数据**（该节的真删清单此前遗漏了档案与对象，与 `RQ-ACC-08`、`AC-24` 的原文不一致）：

| 数据 | 处置 | 依据 |
|---|---|---|
| `campfire_support_object` 中该账号的全部行（**含已归档的**） | **真删** | 归档是生命周期状态，**不是注销的豁免**；`AC-24` 要求"其档案与待处理写入记录不再存在" |
| `campfire_session_object` 中该账号的全部行 | **真删** | 同上；它不构成对外内容，但属该账号的数据 |
| 该账号全部档案条目 | **真删** | `AC-24` 原文"其档案……不再存在" |

**顺序约束**：三项都必须在**墓碑写入之后**执行（墓碑先写，在途记录立即失去写入资格），并在**删除身份用户之前**完成——身份用户一旦删除，就再也无法按 `account_id` 定位这些行。若档案条目对 `campfire_support_object.id` 声明了外键，须**先删条目再删对象**。

## 8. 失败语义

| 情形 | 处置 |
|---|---|
| 创建时 `display_name` 为空或全空白 | 明确失败（存储层 CHECK 亦兜底），不静默填默认名 |
| 改名或归档一个已归档对象 | 改名明确失败；归档**幂等**（重复归档不报错，只刷新 `archived_at`） |
| 恢复一个未归档对象 | 幂等：不报错，`archived_at` 保持为空 |
| 对象不存在或不属于当前账号 | `AuthorizationError`，文案与越权不可区分（第 5.3 节） |
| 归档对象收到新增写入 | 明确失败并说明已归档；**不静默丢弃**，也不降级为"写入候选层" |
| 默认对象推导时该账号一个对象都没有 | 不是错误：返回"无对象"，由入口引导新建（`AC-02` 无档案不阻断咨询的同类形态） |

## 9. 验证方式

对齐 `AC-02`（无对象/无档案不阻断咨询并标注）、`AC-22`（两个对象的档案互不可见；跨账号访问被拒）、`AC-24`（注销后档案与对象不再存在）。

另需验证：

- **归属**：账号 A 建立对象 X 后，用账号 B 的登录态请求 X——读与写两条路径都必须失败，且**失败文案与"对象不存在"逐字相同**（消融：让文案区分二者，测试须失败，以证明"不泄露存在性"真被断言）。
- **归档边界**：归档对象后，① 读取仍成功；② `propose_profile_item` 失败且原因是"已归档"而非"越权"；③ 队列里已存在的 `pending_write` 在领取时被拒（构造一条排队记录，归档后放行消费）。
- **归档不删数据**：归档前后档案条目数与内容一致。
- **恢复**：恢复后重新接受写入。
- **默认对象推导**：同一账号建立 X、Y 两个对象并分别开过会话，验证新会话默认绑定到最近一次使用的那个；全部对象归档后验证不再有默认对象（而不是回退到归档对象）。
- **绑定不可变**：同一会话内尝试改绑，验证被拒绝或无效；新建会话才换对象。
- **首对象补绑**：无对象账号建立会话后在该会话中创建第一个对象，验证补建为该会话唯一绑定；同一会话再建第二个对象，验证绑定不改变（`RQ-ACC-09`）。
- **注销**：按第 7 节构造数据（含一个**已归档**对象）执行注销，验证三张表都没有该账号的行；**消融**：先不删对象，验证 `AC-24` 的断言会失败。
- **空名拒收**：直连数据库插入空白 `display_name`，验证 CHECK 拒绝（证明不变量落在存储层而不是只靠应用层）。

## 11. 已知偏差与证据边界

- **`cli` 白名单到不了 `profile`（实现前置缺口）**：第 7 节要求注销删除档案与对象，而注销经运营 CLI 执行；但[项目结构设计](../../项目结构设计.md)第 7 节给 `cli` 的白名单是 `core/*` 与 `modules/{library,accounts}`，而机械检查（`apps/api/tests/test_layer_boundaries.py` 的 `ALLOWED["cli"]`）**实际只放行 `core` 与 `modules.library`**——连 `accounts` 都不在其中，**文档与检查本身不一致**。且 `modules/*` 之间禁止互相依赖，因此跨 `accounts`／`profile`／`memory` 的注销编排没有任何单个模块能承担，只能落在能同时 import 多个模块的 CLI 入口。这需要一次定调级修正（涉及 `accounts` 的"账号注销编排"这一用例归属），**未随本次修改**，登记于[设计待办](../../TODO.md)。
- **SDK 会话表未登记**：`campfire_session_object` 与会话真源分表存放（第 6 节），但 SDK 自建的两张表（`agent_sessions`／`agent_messages`）至今未登记归属与命名，已在[设计待办](../../TODO.md)登记；两张表接入迁移时须同时确认绑定表的外键取向（本文未声明外键，因为会话标识由 SDK 表持有）。
- **对象数量与档案规模无真实数据**：`missing evidence`——一期允许无限多个对象，而"多对象"的实际使用形态未经真实数据检验。
- **不设关系与权限字段是有意收窄**，不是遗漏：一期属主即监护者、无共用，二者都没有第二个取值（第 1 节）。二期机构协作时由授权端口增加维度，本节形状不变。
