# 压缩策略

> **权威范围**：上下文压力的判定、压缩的范围选择与摘要生成、压缩结果的落地方式、保留尾部、锁与失败语义，以及本项目附加的**前缀缓存纪律**。会话存储与运行方式由[通用基座](通用基座.md)拥有；工具声明与激活由基座与[技能设计](技能设计.md)拥有；业务数据形状由各自机制拥有。
> **状态**：2026-09-29 依用户确认的四项参数与 DeepSeek Harness 的压缩设计（作为对照实现）设计。**2026-09-29 经用户指示落地实现**：机制与摘要调用已实现（`agent/context/compaction.py` 与 `agent/runtime/summarizer.py`），运行编排在派生窗口之前接入。实现期发现与两处落地形状的澄清记入第 5 节与「已知偏差」；本文第 10 节的参数仍是唯一真源。
> **追溯**：`RQ-EMG-03`（应急时延：压缩必须低频，否则每轮都在重算）、`AC-11`（压缩后引用仍须可回指）。
> **依据**：DeepSeek 上下文缓存文档（命中要求完整匹配一个已持久化的前缀单元）；腾讯云 TokenHub《提升 Cache 命中率指南》（只在末尾追加、系统提示保持稳定、`prompt_cache_key` 与 `X-Session-ID`）；DeepSeek Harness `compaction-basic`（阈值比例、范围选择、摘要检查点结构、摘要调用回放热前缀）。

## 1. 目标与两条硬约束

两条约束方向相反：

- **上下文预算**是硬的：模型窗口有限，历史不能无限发送。
- **前缀缓存**要求前缀逐字不变：TokenHub 的请求结构原则是"只在末尾追加，不要在中间插入或修改已有消息"；DeepSeek 的命中要求完整匹配一个已持久化的前缀单元，改了中间或结尾只能退回到更短的前缀单元，而且在系统学会那个更短单元之前并不命中。

**由此只有一条路**：压缩**低频、成段**发生，每次接受一次全量重算，之后的新前缀长期不变。压缩不是"每轮微调"，而是"偶尔重写一次前缀"。

## 2. 触发

触发时机：**每次运行之前、派生窗口之前**（等价于 DSH 的 `agent/pre-step`）。压缩轮次会明显更慢（一次摘要调用 + 随后一次全量重算），这正是它必须低频的原因。

| 触发 | 条件 | 行为 |
|---|---|---|
| 压力 | 窗口占用越过阈值 `floor(min(W × 0.8, W − O − headroom))` | 选择最旧的可安全压缩范围并摘要 |
| 溢出 | 提供方明确报上下文窗口溢出 | **绕过阈值与保留策略**，做一次最大头部缩减后重试 |
| 手动 | 显式入口，低于阈值也执行 | **仅供运维与调试，不暴露给使用者**（2026-09-29 定）——一期压缩基本不触发，暴露它只会制造误解 |

`W` 取**模型的上下文上限**（**2026-09-29 经用户确认：实际可用上下文为 1024k = 1,048,576**），`O` 取**我们请求上实际设置的输出上限**（不是模型 384k 的上限）。按 `O = 8192` 与 `headroomTokens = 65536` 代入：`min(1,048,576 × 0.8, 1,048,576 − 8192 − 65,536) = min(838,860.8, 974,848)` → 触发阈值 **838,860 token**（约 83.9 万）、逐字保留 `(1,048,576 − 8192) × 0.16 =` **166,461 token**（约 16.6 万）。

> 后果要说清：以 1024k 为预算时，**一期基本不会触发压缩**，它退化为"防溢出的保险"，而不是日常节流手段。这是用户 2026-09-29 的选择——照 DSH 公式、不另设更小的对话预算。若将来长对话确实需要节流，重访这一条。

## 3. 范围选择

- 取**最旧的工具配对平衡范围**：工具调用与结果成对，但不要求整轮——超大轮次里较早关闭的步骤可以被压掉。
- **系统提示永不被遮蔽**：范围从第一个非 system 消息开始。
- 没有可安全压缩的范围（例如整个对话就是一个不可分单元）→ **不做任何改变**并明确报告，不留假成功。

## 4. 摘要

- **由模型写**：一次独立调用，**必须与主调用同一模型与路由**——否则不会共享前缀缓存。
- **逐字回放热前缀**：把系统提示、上次路由请求的工具声明、被遮蔽范围的消息逐字回放，**压缩指令作为最后一条 user 消息追加**。这样提供方的热前缀缓存可复用至尾随指令之前，只有指令与摘要输出未缓存。
- **检查点结构固定**（换成我们的领域，空节写 `(none)`，不得省略任何一节）：
  1. 使用者目标与诉求（原文重要处逐字保留）
  2. 已确认的情境与**显式未知**
  3. 已给出的建议及其**依据引用**（保留业务条目标识与来源定位，`AC-11` 依赖它）
  4. 未决问题
  5. 下一步
  6. 必须继续遵守的约束（当事人意愿、安全边界、来源与适用范围）
- **已有 `<compacted-summary>` 时要求合并**，不是照抄：保留仍成立的事实，丢掉已过时的，合并进同一结构。
- 摘要输出受 `maxTokens` 限制；只有返回文本进入检查点，推理与工具调用一律排除。

## 5. 落地方式（与 DSH 的差异点）

- 摘要作为**一条消息追加**进会话（用 `<compacted-summary>` 标签框定）；**不改写、不删除任何已存消息**。
- 此后**窗口 = `[系统提示]` + `[最后一条摘要消息起的全部历史]`**。
- 这条规则**可完全从会话历史推导**，因此不需要另存"窗口配方"——单真源性质保住。
- 与 DSH 的差别：DSH 用 surface `replace` 原地遮蔽一段范围，且支持任意区域压缩；我们只能**从摘要处开始取窗口**（前缀裁剪）。因为范围选择本来就"从第一个非 system 消息开始取最旧平衡范围"，实际效果一致；差异只在"不能只压缩中间某段"。

### 5.1 落地形状（2026-09-29 实现期澄清，三条约束合起来只有一个形状）

本节三条要求看似冲突，实现时必须先解开：

| 出处 | 要求 |
|---|---|
| 第 5 节 | 窗口 = `[系统提示] + [最后一条摘要起的全部历史]`（**从摘要处取**） |
| 第 6 节 | 保留的尾部**原样跟在摘要之后** |
| 第 8 节第 1 条 | **只在末尾追加**；不改写、不插入、不重排（插入等于移动前缀，每轮缓存全量击穿） |

三者同时成立的唯一形状是：**在末尾追加「检查点 + 尾部原文」**。

```text
历史：… [旧尾部] [检查点] [尾部原文]      ← 只追加；前缀一字未动，缓存可复用
窗口：[系统提示] [检查点] [尾部原文]      ← derive_window 从最后一条检查点起取
```

**代价必须写明**：被保留的尾部在历史里因此存在**两份**，摘要之前那一份成为死重量——它不再进入窗口，也不会被删除（第 5 节禁止删除）。这与「会话存储会持续增长」同源；清理属会话级压缩重写，第 11 节明确一期不做。选择这个形状而不是「把摘要插在尾部之前」，是因为后者违反第 8 节第 1 条，而前缀缓存是本项目附加的硬纪律（违反即视为缺陷）。

## 6. 保留尾部

逐字保留最近 `(W − O) × 0.16` 的对话，或用绝对 `retainTokens`（必须低于解析出的阈值）。保留的尾部**不参与摘要**，压缩后原样跟在摘要之后。

## 7. 锁与失败语义

- 压缩是一条**有开始/结束记录的事务**；中途崩溃留下可检测的未闭合标记，而不是一个假装压缩完成的结束记录。
- **摘要失败不改动窗口**：记录警告，继续使用未压缩的窗口。压缩失败**不得让对话不可用**。
- 达到 `maxTokens` 造成摘要截断，按同一规则处理。
- 溢出恢复只在提供方明确分类窗口溢出时触发，且仅在"替换确实推进了"之后才重试，避免死循环。
- 取消优先于上述一切。
- 不可分单元（例如一次超大的工具调用）仍在预算之外：此时**明确失败并提示**，不静默截断。

## 8. 缓存纪律（本项目附加，违反即视为缺陷）

1. **只在末尾追加**；不改写、不插入、不重排历史消息。**不得做滑动窗口**——从头部裁剪等于移动前缀，每轮全量击穿。
2. **系统提示保持静态**：技能目录、档案摘要、检索结果、时间、活跃技能一律不得进入系统提示，只能作为尾部消息。
3. **工具声明在对话内保持稳定**（见基座第 5 节）。
4. **请求标识**：`prompt_cache_key` 用 `conversation_id`（TokenHub 明确要求"整体上下文总 ID"，不是单一会话 ID）；`X-Session-ID` 对同一用户保持不变。
5. **压缩低频成段**；压缩后新前缀长期不变。
6. **发版若改系统提示**：预热、灰度，并盯住缓存命中率。

## 9. 计量与度量

- **用提供方返回的 usage 计量，不用字符数折算。** DSH 的 token meter 是"4 字符 ≈ 1 token"的启发式，它自己的开发备注承认对 CJK 与 JSON Schema 低估——而我们的内容全是中文。
- 每次压缩记录：压缩前后窗口 token、释放 token、`prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`、摘要调用耗时与用量、压缩了多少历史项、保留了多少。

## 10. 参数

| 字段 | 默认 | 含义 |
|---|---|---|
| `thresholdRatio` | `0.8` | 触发阈值 = `floor(min(W × thresholdRatio, W − O − headroomTokens))` |
| `headroomTokens` | `65536` | 输出预留之外的额外压力余量；非负整数 |
| `retainRatio` | `0.16` | 逐字保留的近期对话 = `(W − O) × retainRatio`；与 `retainTokens` 互斥 |
| `retainTokens` | — | 绝对保留预算；与 `retainRatio` 互斥，且必须低于解析出的阈值 |
| `maxTokens` | `headroomTokens` | 摘要输出上限 |
| `compactionRetries` | `1` | 压缩后仍高于阈值时的额外尝试次数 |
| `maxOverflowRetries` | `1` | 确认溢出后的最大重试次数 |
| `auto` | `true` | 关闭后仅手动压缩 |

加载时校验：保留比例必须小于阈值比例；未知字段、两种保留形式并存、非法 token 数一律拒绝加载。

## 11. 一期不做（扩展缝）

- **工具结果剪枝**（DSH 的可选组件）：若要做，必须与压缩在**同一事务**内发生，否则会额外制造一次缓存失效。
- **任意区域压缩**（DSH 的 `compactRegion`）：与"窗口从摘要处开始"不兼容，需要先解决缓存代价。
- **SDK 的压缩重写**：不使用（它会清空并重写历史，违反单真源与缓存纪律）。

## 12. 验证方式

- **配置校验**：保留比例小于阈值比例；非法配置在加载时失败。
- **落地形状**：压缩后窗口恰为 `[系统提示 + 摘要 + 保留尾部]`，且引用仍可回指（`AC-11`）。
- **缓存行为**：用 `prompt_cache_hit_tokens` / `miss` 断言——压缩后首轮命中率下降、其后回升；**不以"感觉更快"作证**。
- **失败注入**：摘要调用失败、摘要截断、取消、不可分单元超预算、无可压缩范围——逐一验证其降级与提示，且都不让对话不可用。

## 13. 不在本文范围

- 会话存储与运行方式、注入项与工具可见性（基座）。
- 工具声明与激活（基座、技能设计）。
- 档案、记忆、资料与案例的数据形状。

## 已知偏差与证据边界

- **模型上限经用户确认**（实际可用上下文 1024k = 1,048,576；输出上限 384k），但**阈值实际不会触发**：按 1024k 预算，压缩在一期基本不发生，只防溢出。若长对话需要节流，重访"自设预算"。
- **`headroomTokens = 65536` 是 DSH 在其窗口规模下的取值**，我们照抄；`O` 取我们自设的输出上限（默认按 8192 计）。
- **已核实 SDK 会话没有任何内建清理**：所以"存储持续增长"不是猜测，需要我们自己定保留与清理策略。
- DSH 自述其 `thresholdRatio` 与 `retainRatio` 是"固定默认值、尚无语料依据"——我们沿用比例，但不把它当最优值。
- **我们只能做前缀压缩**，不能替换中间范围；这是缓存纪律的代价。
- 手动压缩是否作为用户可见能力：**待确认**，登记于[设计待办](../../TODO.md)第四节。

### 实现期发现（2026-09-29，均为实测或 SDK 实读，不是推断）

- **摘要截断只能靠用量启发式判定**。SDK 的 `ModelResponse` 实测字段只有
  `output`/`usage`/`response_id`/`request_id`/`raw_usage`，**不暴露 `finish_reason`**，
  因此拿不到「因长度而停」的官方信号。实现取 `output_tokens >= maxTokens` 即视为疑似截断并
  **拒绝落检查点**。判错代价不对称：误判为截断只是不改窗口（安全方向），误判为完整会把半截
  摘要写进检查点、丢掉没被摘要的历史。若将来能从提供方拿到明确信号，应换成它。
- **摘要调用带工具声明但 `tool_choice="none"`**。第 4 节要求逐字回放「上次路由请求的工具声明」
  以复用热前缀，于是声明必须照旧带上；而第 4 节又要求「工具调用一律排除」。两者用
  `tool_choice="none"` 同时满足：前缀一致、模型不可能发起工具调用（也就不需要事后过滤）。
  该参数是否被 TokenHub 支持**未核实**，登记于[设计待办](../../TODO.md)第五节。
- **溢出恢复的重试会再交一次本轮新增项**：首轮尝试可能已把注入消息与使用者消息部分落库，
  重试时再传一次就可能在会话里留下重复。彻底消除需要会话事务，而会话级重写属第 11 节
  一期不做；溢出路径在一期几乎不会触发（阈值约 83.9 万 token），因此接受并在此登记。
- **压缩事务的账在端口之外**：第 7 节要求「有开始/结束记录的事务」，实现只到「端口 + 固定的
  调用顺序」（先记开始、再动手、最后记结束），**表与迁移尚未落地**，与 `core/db`、Alembic 同批。
- **触发阈值在一期几乎不会生效**（见上一条「阈值实际不会触发」）：机制的全部参数因此只有
  单测证据，**没有真实长对话的实测证据**。若要在真实数据上验证，需要先造出约 83.9 万 token 的
  对话或临时下调 `thresholdRatio`。
