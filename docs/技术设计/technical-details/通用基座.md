# 通用基座

> **权威范围**：基座的产品无关职责与机制——真源划分与运行模型、开放标准 skill 机制的落地、注入项、工具池与权限、模型路由、流式事件、可观测钩子及其失败语义。skill 内容由各 `SKILL.md` 拥有；工具实现由产品侧拥有；模块边界由[项目结构设计](../../项目结构设计.md)拥有；技术选型由[技术栈设计](../../技术栈设计.md)拥有。
> **状态**：2026-09-29 依用户确认的项目结构设计、运行方式（三档：由 SDK 管会话）与开放标准设计，待用户确认。不代表已实现。
> **追溯**：`RQ-CON-01`、`RQ-CON-02`、`RQ-CON-03`、`RQ-CON-06`、`RQ-CON-08`、`RQ-EMG-02`、`RQ-EMG-03`、`RQ-LIM-04`、`AC-11`、`AC-12`、`AC-13`、`AC-18`、`AC-19`。
> **依据**：Agent Skills 开放标准（frontmatter 六字段、渐进披露三层、`skills-ref validate`）；OpenAI Agents SDK 官方文档的会话（`Session` 协议、`RunConfig.session_input_callback`、`call_model_input_filter`）与工具（`is_enabled`、`tool_namespace`、`defer_loading`、`ToolSearchTool`）机制；DeepSeek Harness 的消息流模型作为对照。**思考链核实（2026-09-29）**：DeepSeek-V4.1-Flash 思考模式默认开启（effort=high），`reasoning_content` 与 `content` 同级流式输出，带 `tools` 的请求须回传（官方思考模式文档）；SDK 0.22.x 的 `chatcmpl_converter` 捕获 `reasoning_content` 为 `ReasoningItem`、`reasoning_content_replay` 对 deepseek 模型自动回传（安装产物源码实读）。

## 1. 定位与边界

一句话判定标准：**基座知道自己如何运行，不知道自己被用在哪件事上。**

| 基座拥有 | 基座不含 |
|---|---|
| 真源划分与运行编排 | 任何领域术语（咨询、档案、案例、支持对象…） |
| skill 机制：发现、目录、激活、资源、校验 | skill 内容本身 |
| 注入项的组织与引用索引 | 记忆、档案、检索的语义与生命周期 |
| 工具池与权限系统 | 工具的具体实现 |
| 模型网关与路由 | 面向用户的输出结构与呈现 |
| 流式事件与可观测钩子 | 业务授权判定 |

不变量：基座不得 import 业务模块；出现领域术语即位置错误；基座不自行判定业务授权，也不自行发明事实。

## 2. 真源划分与运行模型

**一个事实一个真源。**

| 事实 | 真源 | 说明 |
|---|---|---|
| 对话（用户消息、助手消息、工具调用与结果、注入的消息） | **SDK 的会话存储**（本地，落在我们的 PostgreSQL） | **唯一，不另存副本**。应用读它做呈现与审计 |
| 模型当轮看到的上下文 | 由对话真源**派生的窗口** | 用 `RunConfig.session_input_callback` 在运行前决定裁剪、重排与前置；**只影响本轮模型输入，不影响落库** |
| 档案条目、通用记忆、资料与案例、待处理写入记录 | 各自的表（关系库 / 图库） | 与对话真源不重叠、不双写；会话里只有消息 |
| 引用的业务回指 | 我们的一张引用索引表 | 它是索引，不是对话的第二份真源；权威在会话消息与业务条目本身 |

**不使用 SDK 的压缩重写**（`OpenAIResponsesCompactionSession` 会清空并重写历史；在单真源下那等于改写用户可见的历史）。上下文压力由窗口策略处理：**存储不动，只裁模型窗口**。

一次**运行**（run）：

| 阶段 | 谁做 | 说明 |
|---|---|---|
| 入口 | 面 | 构造本轮 `input`（含初始激活消息与注入项）、指定 `session`、按激活集合决定 Agent 的工具集 |
| 派生 | 基座 | SDK 运行前取会话历史并前置；`session_input_callback` 决定本轮模型窗口 |
| 运行 | SDK | 模型调用 → 工具调用 → 回填，循环至结束或触顶 |
| 输出 | 基座 | 流式事件（第 7 节） |
| 落库 | SDK 与面 | 本轮新增项由 SDK 写入会话；业务写入经待处理记录（第 9 节） |

**上限**（2026-09-29 定）：**只设一条通用响应上限 180 秒**。不另设步数上限与 token 上限——步数上限是防死循环的手段，而调用次数与单轮成本由工具契约与压缩阈值约束；token 上限由压缩阈值与模型窗口兜底。超时按第 9 节以明确原因结束，并保留已产生的引用。

**运行内注入的边界**（已核实）：SDK **没有**在 hook 中写会话的官方做法。两条官方替代是——`RunConfig.call_model_input_filter` 可在**每次模型调用前**修改模型输入（可注入 system prompt，但**不落库**）；`RunState.add_input()` 会落库，但**仅用于暂停或恢复之后、下一次模型调用前**。因此"在某一步骤边界往流里追加消息"在 SDK 层没有直接对应物：**我们的注入都发生在运行边界**。

## 3. skill 机制的落地

| 环节 | 行为 |
|---|---|
| 发现 | 扫描配置根目录下的 `*/SKILL.md`；解析 frontmatter；**不合法即拒绝加载并在启动时失败**，不得以空元数据静默加载 |
| 目录注入 | 技能目录作为一条**只含 `name` 与 `description`** 的消息注入；目录变化时**追加一条新的目录消息**——SDK 会话不支持原地替换，旧目录会留在历史里。**目录预算上限 4000 token**（2026-09-29 定）：超出时按 `metadata.surface` 分组，只注入当前面可见的 skill |
| 激活（模型侧） | 模型调用 `skill({ name })` 工具；工具结果消息携带 `<skill_content>`（`SKILL.md` 正文）与资源指引，正文由此进入对话 |
| 激活（应用侧） | 应用读取**同一份** `SKILL.md`，把同形内容作为消息放进本轮 `input`；与模型调用的结果同形，差别只在发起者 |
| 资源 | `references/`、`assets/` 按需读取；相对路径、一层深，不做多级引用链。**读取经 `read_skill_resource(name, path)` 工具**（2026-09-29 定）：基座保留名、恒可用（与 `skill` 激活工具同为机制本身的工具）；**只允许读已激活 skill 的资源**——未激活的 skill 连正文都读不到，资源却可读会让渐进披露的第三层形同虚设（尤其 `autoload=false` 的 skill，模型侧激活被拒、资源更不该被旁路），未激活时返回明确错误并提示先激活；边界校验（一层深、防越界、体积上限、UTF-8）复用资源模块的同一套判据，读取结果作为工具结果消息落库——资源内容由工具调用进入对话，与激活正文同路 |
| 校验 | `skills-ref validate` 纳入工程检查 |
| `metadata` 自有键 | 基座读取但不送入模型。本项目约定 `autoload`（是否允许模型自动匹配）与 `surface`（所属面，供目录预算分组用） |

**一期不做**：skill 的安装、市场与运行时下发（skills 随应用发布）；`scripts/` 执行（保留运行器端口，见第 10 节）。

## 4. 注入项

注入项就是**消息**，没有单独的装配端口。

- 档案摘要、检索到的资料与案例、技能目录、激活内容、候选提示，全部以消息形式进入对话。
- 每条注入消息在**引用索引表**里留一条对应记录（来源、时间、指向的业务标识），因为输出里的引用要靠它回指。
- **不变量**：没有索引记录的注入消息不得成为"可引用依据"；注入失败必须显式标注该来源不可用，不得静默当作没有该信息。
- 组装顺序与预算由基座决定，但**受窗口策略约束**（第 2 节）。

## 5. 工具池与权限

工具注册形状：

```text
ToolSpec:
    name
    description
    parameters      # JSON Schema
    handler         # 由产品侧注册
    risk            # low | medium | high（一期全为 low）
    requires_approval: bool
```

- **权限在执行前校验**，不靠隐藏 schema；工具不可见不是安全边界。
- skill 的 `allowed-tools` 是**预授权**，交宿主权限规则匹配；它不限制工具池本身。
- 一期没有高风险动作，因此不实现人工审批流程（HITL 延后，见第 10 节）。
- 失败语义：工具自身错误作为结果回给模型（可恢复）；权限拒绝返回明确错误码，**不静默降级为其他工具**。

### 工具范围随激活集合变化

- **声明保持稳定**：请求里的 `tools` 数组在一条对话内**不变**（超集）。这是缓存纪律的要求——声明一变前缀就变，缓存从变化处失效。
- **可用性用消息告知**：激活集合变化时追加一条消息，告诉模型此刻可用哪些工具（与技能目录同形）。
- **服务端拒绝越界调用**：这是硬边界，与 SDK 和模型供应商都无关。
- **不变量**：激活前，该 skill 的工具虽已声明，但模型被明确告知不可用；未激活任何 skill 时只有面配置的默认可用集（一期只含只读类）。
- **延后加载已排除**：`ToolSearchTool`、`tool_namespace`、`@tool(defer_loading=True)` 属 **OpenAI Responses-only**（官方 models 页的清单明列），而本项目走 TokenHub 的 OpenAI 兼容端点、其文档无 `tool_search` 任何条目 → **整条路不通**。此项由"可选省 token 手段"改为**排除项**。
- **`is_enabled` 只作待验证的增强**：它不在 Responses-only 清单里，文档定位为 runner 侧的可见性与派发过滤，但**文档未声明它在第三方 Chat Completions 端点上是否生效**（`TECH-12`），因此不作为依赖。
- **暴露范围不是安全边界**：SDK 文档原文即为此——`is_enabled` controls visibility and dispatch; it does not replace authorization。服务端仍按请求与参数校验权限。
- 与开放标准的对应：`allowed-tools` 既作为本次激活的可用集合来源，又保留其"预授权"语义；标准只定义后者，本条属**超集用法**。

## 6. 模型路由

- 统一配置入口，**业务代码不得硬编码模型名**；接口保留用途分档（一期只有一个值）。
- 失败语义：超时、限流与供应商错误按策略重试；重试耗尽则本次运行失败并给出原因。**不得**用缓存或旧结果冒充当前结果。

## 7. 流式事件

事件类型（一期经 SSE 传输，名称与语义对齐 AG-UI 以便升级）：

| 事件 | 含义 |
|---|---|
| `run_started` | 运行开始，含本次激活的 skill 与注入项清单 |
| `reasoning_delta` | 模型思考过程的文本增量（中间态，非结论）。见第 7.1 节 |
| `text_delta` | 文本增量 |
| `progress` | 进度提示（用于长等待，例如检索中） |
| `tool_call_started` / `tool_call_finished` | 工具调用与其结果摘要 |
| `citation` | 一条可引用依据（对应引用索引中的记录） |
| `candidate` | 档案候选条目（未确认，供面呈现为"待确认"） |
| `question` | Agent 向使用者发起的**一组**结构化提问。**运行结束于提问而非暂停**——发出后本次运行正常结束，回答作为下一条使用者消息到达（与第 2 节"注入只发生在运行边界"的运行模型相容）。形状与产生方式见第 7.2 节 |
| `action_card` | 一次结构化的卡片段输出。**运行不因此结束**（卡片之后可继续输出，如追问或收尾文字）；同一会话内可出现多张，按时间顺序排列。形状与产生方式见第 7.3 节 |
| `run_finished` | 正常结束，含结束原因与引用清单 |
| `run_failed` | 异常结束，含错误码 |

### 7.1 `reasoning_delta`

```text
delta: string    # 思考文本增量
```

来源是 DeepSeek 思考模式的 `reasoning_content` 流式增量（第 6 行已核实：默认开启、`reasoning_content` 与 `content` 同级流式输出、SDK 捕获为 `ReasoningItem` 并自动回传）。

**待验证**（登记于[设计待办](../../TODO.md)）：SDK 的 `RawResponsesStreamEvent` 里思考增量对应的 `raw.type` 取值未实测——文本增量的 `response.output_text.delta` 已在 `_translate` 中确认，思考增量的等价键名须在真实端点上确认后才能接入；取不到时该事件不产出（思考区无内容），**不得**用文本增量冒充。

### 7.2 `question`：一组题，不是一道题

```text
batch_id: string          # 本次提问批次的标识（运行内唯一；回答回传时凭它关联）
items:                    # 一组题，按数组顺序呈现
    id: string            # 题标识（批次内唯一）
    prompt: string        # 题干
    options:              # 可为空数组（纯自由回答的题）
        label: string
        description: string?
    allow_skip: bool      # 该题是否允许跳过
```

**为什么是"组"而不是"题"**：一次性可提出多题、逐题作答、整组统一提交已经用户确认。若事件只能表达一道题，前端要靠多次事件自行拼组，而"整组提交"就失去服务端可校验的对象——组是提交单位，因此是事件单位。单题即长度为 1 的组，不另设形状。

**产生方式**：基座提供 `ask_user` 工具，参数即上述载荷；模型调用它即结束本次运行并发出该事件。它经 `register_base` 注册、**恒可用**（与 `skill`、`read_skill_resource` 同为机制本身的工具，不进 `allowed-tools` 的并集）——提问是运行的中止方式之一，不是某个 skill 的特权。不靠解析自由文本猜提问，保证选项形状可校验；skill 在指令里约束何时使用与选项的措辞纪律。

**回答怎么回来**（两段式下的形状，属[咨询面契约](../面/consult/HTTP与SSE契约.md)第 4.1 节）：回答经发消息端点的结构化 `answers` 字段回传（逐题 `id` + 选项 label 或自由文本或显式跳过），由服务端渲染成一条使用者消息落进会话。渲染保留**逐题对应关系**与**显式跳过标记**——跳过必须由服务端写成可判定的事实，不能靠前端措辞或模型推断（应急"跳过即未排除"的语义由此成立）。

### 7.3 `action_card`：通用信封，不含领域词

```text
card_id: string
title: string
sections:   { key: string, heading: string, lines: string[] }[]
states:     { key: string, value: string }[]          # 可为空
annotations:{ target: string, kind: string }[]        # 可为空；target 指向某条 line 的序号
```

**为什么是通用信封**：基座不得出现领域术语（第 1 节不变量），而卡片的取值词表（医疗风险三值、来源六类、置信四档）是领域事实。因此基座只承载"分节文本 + 键值状态 + 逐条标注"这三种与领域无关的形状，领域词汇与词表由产品侧定义并校验。

**产生方式（与第 7.2 节不对称，判据在此）**：卡片**由产品侧工具产出**，不是基座保留工具。理由是 `question` 需要"结束本次运行"这一运行编排行为，只有基座能给；而卡片不需要——工具返回后运行自然继续。产出路径复用既有的工具结果通道（与 `citations`、`candidates` 同一种做法）：工具在 `ToolResult` 上带回一张上述信封的卡片，基座把它翻成 `action_card` 事件。

由此得到的两条性质：

- **领域词表校验落在产品侧工具的 `args_model` 上**（如医疗风险只取三值），是机械校验而不是提示词约束——"模型编不出第四种"由参数模型保证，不由基座检查。
- **基座不需要知道有哪些卡片**：新增一种卡片是新增一个产品侧工具，不改基座。

卡片的使用者（哪个 skill 声明它、词表取值、旧卡失效的呈现）由[咨询面](../面/consult/README.md)与各 skill 拥有，基座不复述。

## 8. 可观测与评测钩子

- 每次运行记录：模型、token、时延、激活的 skill、注入项来源与数量、工具调用、引用、错误、结束原因。记录写在**我们自己的表**里，**不改写会话**。
- **触发准确性与输出质量分开测**（标准建议）：前者用"应为/不应为触发"的提示集测触发率，后者用对齐 `AC-11` 的独立评价判定。

## 9. 失败语义与不变量

| 情形 | 处置 |
|---|---|
| 注入项取数失败 | 标注该来源不可用并继续；不得假装已获取 |
| skill frontmatter 不合法 | 拒绝加载并在启动/校验时报错；不得静默加载 |
| 工具失败 | 作为结果回给模型；重试耗尽则以明确失败结束本次运行 |
| 模型不可用 | 本次运行失败并给出原因；不返回缓存内容冒充当前结果 |
| 触顶（步数/token/时间） | 以明确原因结束，保留已产生的引用 |
| 运行被取消 | 立即停止调用；业务侧的幂等由面与待处理记录承担 |
| 会话写入失败 | 本次运行明确失败；**不得**把未落库的对话当作已保存继续下一轮 |

## 10. 扩展缝

| 缝 | 一期状态 | 启用条件 |
|---|---|---|
| 脚本运行器 `ScriptRunner`（`scripts/`） | 不实现，仅保留端口 | 出现必须自带脚本的 skill，且有受限执行环境 |
| 人工审批（HITL） | 不实现 | 出现 medium/high 风险工具 |
| 子代理与并行研究 | 不实现 | 出现上下文隔离或并行调研的真实需求 |
| 会话级压缩重写 | 不实现 | 存储增长成为真实问题且找到不改写用户历史的做法 |
| 按面分组或按需筛选的目录装载 | 不实现 | 目录触及上下文预算 |
| AG-UI 传输 | 不实现 | 需要结构化状态同步时 |

## 11. 验证方式

- **标准一致性**：`skills-ref validate` 通过；非法 frontmatter 有拒绝加载的测试用例。
- **单真源**：窗口裁剪与重排**不影响落库**；下一轮仍能读到完整历史。
- **激活**：模型侧 `skill` 工具与应用程序注入产生同形内容；激活前写入类工具不可派发。
- **触发准确性**：每个 skill 准备"应为触发"与"不应为触发"的提示集。
- **引用**：每条引用可回指到引用索引中的业务标识。
- **失败注入**：制造注入失败、模型失败、工具失败、会话写入失败、触顶与取消，验证事件与降级信号真的出现。

## 12. 不在本文范围

- 各 skill 的内容与其 `references/` 组织。
- 工具的具体实现与检索策略。
- 业务授权判定。
- 档案与记忆的数据形状。

## 已知偏差与证据边界

- **对话日志的格式与所有权归 SDK**：我们接受其条目形状，不在自己的库里另存对话副本。呈现与审计都读它。
- **无逐条删除**：Session 协议只有 `get_items`、`add_items`、`pop_item`（最近一条）与 `clear_session`（全部），**没有按 id 删除**。因此对话历史的逐条处置做不到，需要时只能靠自建 Session 或整段清除。
- **不使用压缩重写，也没有重新注入兜底**：上下文压力由窗口策略处理，被裁掉的内容当次就是看不到。**已核实 SDK 会话没有任何内建裁剪、TTL 或清理**（`SessionSettings.limit` 只限制读回数量、不减存储），所以**会话存储会持续增长**，需要我们自己的窗口与保留策略。
- **注入消息无法原地替换**：技能目录变化以"追加新目录消息"表达，历史里会留下多份目录。
- **读回顺序**：顺序契约存在，但官方未把 `limit=None` 的读回顺序写成硬保证；因此定位"最后一条摘要消息"靠它内容里的 `<compacted-summary>` 标签，而不是靠顺序。
- **条目 content 有两种形状**（2026-09-29 实现期实测，用 SDK 0.22.3 + 假 Chat Completions 服务跑通）：使用者消息是字符串，而 **SDK 落库的助手消息是分片数组**（形如 `[{"type": "output_text", "text": "…"}]`）。窗口派生不能只认字符串——只认字符串会让检查点在分片形状上永远漏检（方向安全：不裁剪历史，但压缩静默失效）。实现里两种形状统一取文本，遇到不认识的部件（如图片）返回"取不到"而不猜。
- `TECH-12`（`is_enabled`、`session_input_callback`、`call_model_input_filter` 在 TokenHub 的 Chat Completions 端点上是否真生效）未核实，登记于[设计待办](../../TODO.md)第五节。
