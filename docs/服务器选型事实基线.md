## 1. 产品与一期规模

【文件】一期形态：面向监护人的**手机端 H5 咨询工具**，核心链路是"登录 → 首页 → 应急咨询 / 日常咨询 / 案例浏览 → 档案与记忆的查看·纠正·删除"。来源：`docs/需求/功能需求与验收.md` 第 1.1 节。

【文件】与容量直接相关的业务约束：

| 约束 | 内容 | 出处 |
|---|---|---|
| 全应用必须登录 | 不存在匿名内容页、匿名接口或未登录可达的业务路径；唯一例外是运维探针 `GET /health` | `RQ-ACC-01`、`AC-01` |
| 注册不开放 | 须凭邀请码，注册入口与校验在自己的后端；一期不要求邮箱 | `RQ-ACC-04`、`RQ-ACC-05` |
| 运营无 Web 后台 | 邀请码发放/撤销、人工重置密码、账号注销**全部经本地 CLI** 执行，不暴露 HTTP 端点 | `RQ-ACC-06`、`RQ-ACC-08`、决策记录《运营操作经CLI》 |
| 资料录入无服务端点 | 语料摄取只能经应用内 CLI（跑在同一镜像、连同一个库），无上传接口、无知识库管理页 | `RQ-KB-03`、`AC-29` |
| 一期不做附件 | 需求无附件；MinIO 一期无消费者 | 技术栈设计第 2 节"附件"行 |
| 一期不含机构协作 | 账号只有个人形态，不预建组织表 | `RQ-ACC-03`、`AC-14` |

【文件】**"50"这个数字在项目里的既有含义**：`docs/技术设计/technical-details/认证与账号.md` 第 7 节把"真实用户数 **≥50**"定为**重估自助找回（邮箱/恢复码）的重访条件**；决策记录《运营操作经CLI》用它说明"一期人工重置预期是个位数次数"。即：**≥50 人被视为"一期试点结束、进入下一阶段"的门槛**，而不是系统的容量上限。

【文件】一期明列的**非目标**（不产生服务器负载，列此以免高估）：机构协作、事项与记录对象、支持计划、受限交接、情景演练与复盘、面向志愿者/一线老师/专业人员的路径、微信小程序（远期形态）。

## 2. 部署形态：必须跑哪些进程

【文件】部署目标：**Docker Compose v2 单机**，明确"不引入 Kubernetes、消息总线或通用工作流引擎"。来源：`docs/技术栈设计.md` 第 2 节"部署"行与第 6 节。

【文件】服务清单（技术栈设计第 6 节的部署口径）：

```text
api       —— FastAPI（HTTP，SSE 流式）
web       —— React H5 静态产物
worker    —— Taskiq Worker（独立进程，全异步）
postgres  —— PostgreSQL 17 + pgvector + pg_trgm
redis     —— Redis 7（缓存、限流、队列 broker）
falkordb  —— FalkorDB（Graphiti 的图库后端）
supertokens —— SuperTokens core（独立 Java HTTP 服务）
nginx     —— 唯一对外监听的进程（反代 api、托管 web）
```

【文件】两处**口径不一致**，调研时请注意（不是笔误，是仓库现状）：
1. 技术栈设计第 2 节的"部署"行把 **MinIO** 列进了 8 个单元；而第 6 节明说"**MinIO 不进部署编排**"（一期无附件）。`docs/TODO.md` 又写"部署单元从 8 个加到 9 个（技术栈设计第 6 节明列 8 个）"。三个说法互相冲突。
2. ~~**部署编排尚不存在**~~ **【2026-10-15 订正】生产装配已落地**：`infrastructure/docker/`（`Dockerfile.api`、`Dockerfile.web`、`nginx.conf`、`app-locations.conf`、`entrypoint-api.sh`）与仓库根 `docker-compose.prod.yml` 均存在。旧文称「`infrastructure/{docker,nginx}/` 只有 `.gitkeep`、当前仓库里没有任何 app 侧 Dockerfile」，该判断已不成立（当时的依据是 `archive/**` 下的旧实现，而归档树不随本公开仓分发）。仓库根 `docker-compose.yml` 仍是**开发编排**，技术栈设计第 6 节明令"不得直接用于服务器部署"。

【文件】网络暴露面硬约束（技术栈设计第 6 节，安全约束）：

- **只有 Nginx 对外监听**；api、worker 与全部数据服务**不得映射到公网接口**，仅经 Compose 内网互联。
- SuperTokens core 与它自带的 `/auth/dashboard` **必须不可公网可达**（官方警告：core 暴露到互联网则"任何人都能创建或修改 dashboard 用户"）。
- 部署前必须替换全部模板占位符（`POSTGRES_PASSWORD=changeme`、`SUPERTOKENS_API_KEY=change-me-...`、`MINIO_*`）；`FALKORDB_PASSWORD` 在模板里被注释掉，**部署必须设置**。
- 前后端同顶级域部署（经同一 Nginx），否则 cookie 的 `sameSite` 判定与实际站点不符（认证与账号第 5 节）。

【实测 · 需要注意的偏差】开发编排文件已写成回环绑定（commit `6cb0a39`，2026-09-30，提交信息为"安全：数据服务端口绑回环"），但**本机正在运行的容器是更早创建的**，实测端口绑定与文件不一致：

```text
campfire-postgres     127.0.0.1:5432   （与文件一致）
campfire-supertokens  127.0.0.1:3567   （与文件一致）
campfire-redis        0.0.0.0:6379     ← 文件写 127.0.0.1，运行容器是 0.0.0.0
campfire-falkordb     0.0.0.0:6380     ← 文件写 127.0.0.1，运行容器是 0.0.0.0
```

测量命令：`docker inspect campfire-postgres campfire-redis campfire-falkordb campfire-supertokens --format '{{.Name}}: {{json .NetworkSettings.Ports}}'`。
含义：**要得到加固后的绑定必须重建容器**（`docker compose up -d --force-recreate`）。调研 Agent 若把"数据服务已绑回环"当既成事实，会低估当前开发环境的暴露面。

## 3. 实测资源占用

### 3.1 四个数据服务（空闲态，无业务负载）

【实测】采样条件：无本项目压测、无业务请求，容器运行 10–11 小时。

> ⚠️ **采样期间该 FalkorDB 与 PostgreSQL 上有并发活动**（不是本次测量造成的）。已确认原因：**同一台机器上有另一个进程正在跑本项目的集成测试**——测量时捕获到 `python -m pytest -p no:warnings apps/api/tests/test_memory_re...`（进程 138952，启动于 19:14:46）。旁证：`CLIENT LIST` 显示外部客户端（`lib-name=FalkorDB lib-ver=1.7.1`，来自 172.20.0.1）持续 `graph.QUERY`；FalkorDB 图数量在数秒内从 244 → 275 → 276 持续增长；工作区有 24 个 `apps/api/tests/*.py` 处于已修改状态。
>
> **因此**：下表 FalkorDB 与 PostgreSQL 的绝对值只是瞬时值，且**含测试负载**，不可当作稳定基线。第 3.1 节后半段的"干净容器标定表"用的是本次**新起的独立容器**（未挂载项目卷、测完已删除），不受此影响，**应以它为准**。

【补充实测（同一现象的另一处证据）】图名前缀分布（同一时刻）：`it_*` **213 张**、`probe*` **29 张**、`q[0-9]*` **9 张**——绝大多数是测试残留产物，**不是业务数据**。这对选型有直接含义：**本机 FalkorDB 的内存数字不能代表试点负载**，只代表"测试残留 + 分配器 arena 未归还"。

【顺带实测】FalkorDB 数据目录 `du -sh /data` = **4.0 KB**（图数据全在内存，RDB 未落盘）；Redis `/data` = 8.0 KB；PostgreSQL `/var/lib/postgresql/data` = **163 MB**。→ **图库的持久化磁盘占用当前无法从本机测得**（需触发 RDB/AOF 或给图库配持久化策略，本次未做）。

两种口径都给，因为它们的差值是页缓存：

| 容器 | `docker stats` 工作集 | cgroup `memory.current` | 容器内进程 RSS | 说明 |
|---|---|---|---|---|
| campfire-supertokens | **306–310 MiB** | 312.7 MiB | java 310,252 kB + java 43,920 kB（两个 JVM 进程） | JVM 常驻，与业务量无关 |
| campfire-postgres | **122–146 MiB** | 145.8 MiB | — | `shared_buffers=128MB`（=16384×8kB） |
| campfire-falkordb | **148–160 MiB** | 227.0 MiB | `used_memory_rss` 112–116 MiB | 三口径差异最大，见下方说明 |
| campfire-redis | **6.4–14.1 MiB** | 14.1 MiB | `used_memory` 1.08 MB，`used_memory_rss` 7.81 MB | 几乎可忽略 |

测量命令：`docker stats --no-stream`；`docker exec <c> cat /sys/fs/cgroup/memory.current`；`docker exec campfire-supertokens sh -c 'for p in /proc/[0-9]*; do ...'`。

**FalkorDB 的口径差异必须说清（否则会误判内存档）**：同一个容器上同时读到三个差一倍以上的数字——

- `used_memory` = **348–368 MB**（Redis 分配器自己的记账）
- `used_memory_rss` = **112–116 MB**（进程实际驻留）
- `docker stats` = **148–160 MiB**（cgroup 计费口径，已扣掉非活跃页缓存）
- `mem_fragmentation_ratio` = **0.32**（小于 1，说明分配器持有但内核未实际占用的页很多）

【推断】这些图绝大多数是**空图**（测试残留；测量期间数量本身在持续变化，见上方警告），`used_memory` 高企主要来自分配器 arena 而非真实数据。因此**不建议**用 348 MB 作为单账号/多账号的内存基准。下面给出干净的标定实验。

【实测】**干净 FalkorDB 容器的规模标定**（本次新起一个空容器，逐级建图，每张图 1 个 `Episodic` 节点；跑完删除容器）：

| 图数量（≈账号数） | cgroup `memory.current` | `used_memory_rss` |
|---|---|---|
| 0 | 86.1 MiB | 22.8 MiB |
| 50 | 95.5 MiB | 32.2 MiB |
| 150 | 100.4 MiB | 36.9 MiB |
| 350 | 110.4 MiB | 45.9 MiB |
| 650 | 114.1 MiB | 61.4 MiB |
| 1000 | 132.1 MiB | 78.3 MiB |

【实测】**"一账号一张图"是设计事实**，不是实现细节：Graphiti 在 FalkorDB 后端用 `driver.clone(database=group_id)` 切换**图**，因此分区键就是图名。来源：`docs/技术设计/technical-details/通用记忆.md` 第 1 节（含实测证据），代码 `apps/api/src/campfire/modules/memory/graph.py` 的 `driver_for(account_id)`。

【实测】**单图数据成本**：在空图上写入 1000 个 `Entity` 节点（各带 200 字符 `summary`）+ 1 条 `RELATES_TO` 边 + 20 个 `Episodic` 节点（各 1500 字符 `content`）后，整库 `used_memory` 增加 **1.95 MB**。

【推断】按上表边际值外推 **50 个账号**：50 张近空图 ≈ 基线 86 MiB + 约 9 MiB（cgroup 口径，约 46 KB/图）。**真实值取决于每账号的记忆条数，本次没有 50 个真实账号的数据。**

【实测】**按账号缓存驱动的上界**：代码常量 `MAX_CACHED_ACCOUNT_DRIVERS = 64`（`modules/memory/graph.py`），配合 `falkordb_max_coroutines = 20`（`core/config.py` 默认值）。即：客户端侧的图驱动缓存有界，但**图的物理数量随账号线性增长、且不自动回收**（通用记忆第 1 节把"一账号一张图"的运维形态列为待观察项）。

### 3.2 应用进程内存与冷启动

【实测】本机测量（Windows + CPython 3.12，`uv run python`，导入完成即读数）。口径为**导入后的常驻工作集**：

| 进程 | 导入耗时 | 常驻工作集 (Working Set) | 说明 |

【未知】`campfire.main` 的导入值（153 MiB）低于"全套重依赖"（207 MiB），说明 HTTP 入口并未在导入期拉起全部重依赖（`modules/library` 等按需导入）。**未测**：实际处理一次咨询请求后的稳态内存，以及并发 N 路 SSE 流下的内存。

【实测】uvicorn **没有配置多 worker**：`apps/api/src/campfire/main.py` 里只有 `app = FastAPI(...)` 与一条 `@app.get("/health")` 路由，仓库内无 `--workers` 配置。即**当前设计默认单进程 api**。

【实测】数据库连接池为 SQLAlchemy 默认值（**未显式配置**）：`pool_size=5`、`max_overflow=10`、`pool_timeout=30s`、`pool_pre_ping=True`。验证命令：


## 4. 存储增长模型（可推算的公式与实测单价）

### 4.1 向量与检索节点（决定 PostgreSQL 磁盘与内存）

【实测】`data_campfire_node` 真实行成本（本机 98 行测试数据，`pg_column_size` 逐列求和）：

| 列 | 单行字节 | 说明 |
|---|---|---|
| `embedding` | **10,240 B** | `vector(2560)` × float4(4B) = 固定 10,240 B |
| `text` | 平均 910 B | 分块后的正文（设计目标块长 400–800 字符） |
| `metadata_` | 平均 780 B | jsonb：`item_id`/`chunk_index`/`header_path`/`locator`/`char_count`/状态/撤下等投影 |
| **合计** | **≈ 11.9 KB/行** | |

【实测】`vector` 是 pgvector 的 USER-DEFINED 类型；扩展版本 `vector 0.8.2`、`pg_trgm 1.6`、PostgreSQL **17.10**。

【实测】**50,000 节点的表体积 = 597 MB**（无索引、无 halfvec 列）。

【推断】知识库规模换算（用实测 11.9 KB/行，**不含索引与膨胀**）：

| 节点数 | 表体积（外推） | 对应语料量级（按 600 字符/块，外推） |
|---|---|---|
| 1,000 | ≈ 12 MB | 约 40 份中等文档 |
| 10,000 | ≈ 119 MB | 约 400 份 |
| 50,000 | ≈ 597 MB（**实测值**） | 约 2,000 份 |

【文件】设计认为一期"几千个节点"即可满足两库检索需求，并据此**一期不建向量索引**；切换条件是"节点数超过约 **5 万**，或单次向量检索 SQL 超过 **100 毫秒**"（RAG 策略第 3.2 节）。**这个 5 万阈值经本次实测落在 230 ms 量级，见第 5 节。**

【实测】**pgvector 的 2000 维建索引上限会挡住原计划的 HNSW**：在 `vector(2560)` 列上执行

```sql
CREATE INDEX ... USING hnsw (embedding vector_cosine_ops) WITH (m=16, ef_construction=64);
```

直接报错：**`column cannot have more than 2000 dimensions for hnsw index`**（本机 pgvector 0.8.2）。设计文档第 3.2 节原写"届时用框架的 `hnsw_kwargs` 建 HNSW"，按现状**在 2560 维的 `vector` 列上不可能成功**；技术栈设计第 2 节已记"`vector` 建索引上限 2000 维、`halfvec` 4000 维"。

【实测】**可行的替代路径已跑通**：先把列转成 `halfvec(2560)`，再建 HNSW——

- 建索引耗时（5 万行）：**20.9 秒**，并伴随提示 `hnsw graph no longer fits into maintenance_work_mem after 11466 tuples`（`maintenance_work_mem=64MB`，本机默认）
- 索引体积：**256 MB**（5 万行）
- 查询耗时：**0.51 ms**（`hnsw.ef_search=40`，走 `Index Scan`）
- 代价：多一列 `halfvec(2560)` = 5,120 B/行；同样 5 万行的表体积从 597 MB 涨到 **1,138 MB**

【文件】字面匹配用 `pg_trgm` 的 GIN trigram 索引，建在条目表（非节点表）的 `title`/`keywords`/`aliases` 三列上；查询词闸门为"中文 ≥3 连续汉字、非中文 ≥3 连续字母/数字"（RAG 策略第 3.1 节）。

## 5. 检索性能实测（决定 CPU/内存档位的关键数据）

【实测】在真实 PostgreSQL 17.10 + pgvector 0.8.2 容器内的临时表上跑 `ORDER BY embedding <=> q LIMIT 30`（`vector(2560)`，`EXPLAIN ANALYZE`，最后 `ROLLBACK` 不留数据）：

| 节点数 | 精确顺序扫描耗时 | 计划 |
|---|---|---|
| 2,000 | **9.8 ms** | Seq Scan + top-N heapsort |
| 20,000 | **77.4 ms** | Seq Scan |
| 50,000（默认并行度 2） | **263.8 ms** | Seq Scan |
| 50,000（强制单核 `max_parallel_workers_per_gather=0`） | **257.1 ms** | Seq Scan |

【实测】第 3 行与第 4 行的结论值得单列：**在 5 万节点这一档，并行并没有帮上忙**（263.8 ms vs 257.1 ms，噪声级）。本次未做更细的并行归因，只如实报告这两个数字。

【实测】对照：`halfvec(2560)` + HNSW 在同一 5 万行上为 **0.51 ms**（约 500×）。

【实测】缓存影响：50,000 行那次扫描 `local hit=324,182 read=76,187`——即**表远超 shared_buffers 时会大量读盘**（`shared_buffers=128MB` 对 597 MB 的表）。2 万行那次 `local read=30,471`。**本机是本地 NVMe 且为临时表（local buffers）；生产冷缓存下的表现未测。**

【未知】没有做任何**并发**检索压测（N 路同时检索的时延与 CPU 占用），也没有测**写入路径的实际耗时**（摄取一份文档的总时长、记忆 episode 的实体抽取耗时）。这两个是选型最直接缺失的数据，已在第 9 节列出。
