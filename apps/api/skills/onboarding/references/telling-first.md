# 告知文本的措辞纪律

本文件是 `onboarding` 的 `references` 之一，由该 skill 正文按需读取。它只写**告知怎么写**，不含页面视觉。

## 1. 三件事的固定表述

告知必须覆盖三件事，一件不少。落地措辞与设置页「数据说明」卡同源（下表三行即该卡的成稿文案，逐字一致）：

| 要告知的事 | 落地表述 |
|---|---|
| 内容会用于什么 | 「本次输入的内容用于生成回答，并按你的确认累积到档案与记忆」 |
| 谁可见 | 「只有你的账号可以看到；登录才能使用全部功能」 |
| 是否送往外部模型 | 「咨询内容会发送给模型服务处理后返回」 |

**为什么必须三件都讲**：三件事分别回答使用者最可能担心的三个问题——我的话被拿去做什么、谁能看见、出了这个应用没有。少讲任何一件，都会让使用者在不知道边界的情况下开始提供关于第三人的信息。

**为什么不细写供应商名**：口径与技术栈文档一致——如实告知「会发送给模型服务」，不展开供应商与地域细节。**不展开不等于可以含糊**：「会不会送出去」这个问题必须被明确回答「会」，不能用「可能会被用于改进服务」这类模糊句代替。

## 2. 先告知，后询问

- 告知文本由**应用**作为静态消息注入，**先于任何询问到达**。
- `onboarding` **不得在告知前发起提问**——包括「为了方便，先问一下怎么称呼他」这类看似无害的开场问句。
- 首条 assistant 消息之前**不存在任何结构化提问事件**。这是一条可机械验证的顺序约束，不是措辞偏好。

**为什么顺序是硬约束**：告知的价值在于「使用者在知情的前提下决定给什么」。先问后告知拿到的是同一批信息，但使用者已经失去了拒绝的机会——那不是告知，是事后补票。

## 3. 措辞纪律

- **说「你的内容」，不说「数据」**：前者是使用者的东西，后者是系统的资产。整段告知不使用「收集」「采集」「用于优化」这类把主动权说在系统一侧的词。
- **明确回答，不留悬空**：三个问题都给出直接的「是/否/怎么做」，不使用「可能」「视情况」「一般来说」。
- **不承诺做不到的事**：不写「绝对安全」「完全匿名」「不会被任何人看到」。一期能承诺的是「只有你的账号可以看到」，这正是要写的原话。
- **不用免责腔**：不写「请仔细阅读以下条款」「本应用不对……负责」。告知是说明，不是免责声明。
- **不弱化一期边界**：涉及能力边界时如实说（例如专业审阅状态），不把边界句写小写淡。

## 4. 与设置页「数据说明」卡的一致性

两处必须**同源同口径**：

| 维度 | 要求 |
|---|---|
| 三件事的覆盖 | 两处都是三件，缺一即不一致 |
| 每件的表述 | 逐字一致（见第 1 节的表） |
| 供应商展开程度 | 两处都不展开 |
| 能力边界的表述 | 两处都不弱化 |

**为什么不各写一份**：两处是同一个告知在两个时点（首次引导、事后回看）的呈现。任一处偏乐观或偏含糊，使用者按哪一处理解都合理，而两处不一致本身就是误导。因此**改动任一处即需同步另一处**——这条纪律由本文件与设置页设计共同承担。

## 5. 与后续提问的衔接

- 告知之后才进入对象创建；回执只确认收到了使用者的回应，**不重复念一遍告知全文**。
- 使用者在引导中提出真实咨询问题时，**先完成或跳过引导段**，再由后续消息走日常咨询路径作答——不在引导段内给具体照护建议。

## 6. 本文件不含的内容

- 页面视觉与组件的呈现方式（属页面设计）。
- 通用的隐私政策或法律条款文本。
