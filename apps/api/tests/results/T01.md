## 1. 实现说明

### 1.1 三个事件类（基座 7.1／7.2／7.3）

在 `agent/runtime/events.py` 新增三个 `@dataclass(frozen=True, slots=True)` 事件类并加入
`RunEvent` 联合，载荷**平铺**、字段名逐字对齐设计文档（未改任何既有事件类）：

| 事件 | 载荷字段 | 依据 |
|---|---|---|
| `ReasoningDeltaEvent` | `delta` | 基座 7.1 |
| `QuestionEvent` | `batch_id`、`items`(`id`/`prompt`/`options`(`label`/`description`)/`allow_skip`) | 基座 7.2 |
| `ActionCardEvent` | `card_id`、`title`、`sections`(`key`/`heading`/`lines`)、`states`(`key`/`value`)、`annotations`(`target`/`kind`) | 基座 7.3 |

新增 `agent/tools/payloads.py` 承载这些载荷的值对象（`Question`／`QuestionItem`／
`QuestionOption`／`ActionCard`／`ActionCardSection`／`ActionCardState`／`ActionCardAnnotation`）。

**关键决策**：

1. **载荷对象放 `tools/` 而非 `runtime/events.py`**：事件类与 `ToolResult` 两边都要用，
   而 `agent.runtime` 已 import `agent.tools`（事件类用 `Candidate`／`ToolErrorCode`），
   反向 import 即成环。与既有 `Candidate` 同一种安排。
2. **形状约束写在 `__post_init__`，不在工具 args 里重写一遍**：如此工具参数模型（模型来路）
   与事件构造点（编排来路）共用同一份定义。实测 pydantic 会把 dataclass 抛出的 `ValueError`
   收成正常校验错误（`loc` 落在 `items.0` 这样的路径上），事件构造点则直接得 `ValueError`。
   若两处各写一遍，漂移方向恰是最坏的：事件侧放行工具侧拒绝的载荷。
3. **平铺而非嵌套**：以 T09 的消费者类型 `apps/web/src/shared/types/sse.ts` 为准
   （`QuestionEvent {type, batch_id, items}`、`ActionCardEvent {type, card_id, title, sections,
   states, annotations}`），并佐以 `docs/design/pages/对话页.md:53` 的「通用信封」。面侧
   HTTP 契约第 4.2 节把事件的 `data` 定义成该事件对象的 JSON（恒等映射），故字段名即线上契约。

### 1.2 `ask_user` 基座保留工具（基座 7.2）

新增 `agent/runtime/ask_user_tool.py`：

- `ASK_USER_TOOL_NAME = "ask_user"`，加进 `tools/pool.py` 的 `RESERVED_TOOL_NAMES`
  （产品侧走 `register` 占用它会被拒 `ToolRegistrationError`；保留名注册走 `register_base`）。
- 参数模型 `AskUserArgs` **只有 `items`**，**刻意不含 `batch_id`**：`question` 的

### 1.3 运行编排接线

- `assembly.py`：`ToolBridge` 新增 `gate` 参数，在工具调用边界把 `ToolResult.cards` 翻成
  `ActionCardEvent`、把 `ToolResult.question` 翻成 `QuestionEvent`，并与既有 `citations`／
  `candidates` 一致地把载荷事件排在 `tool_call_finished` **之前**。新增 `QuestionGate` 与
  `stop_after_question()`；`build_agent` 新增 `tool_use_behavior` 参数（默认 `"run_llm_again"`）。
- `runner.py`：每次运行新建 `QuestionGate`，桥与 agent 共用同一个 gate（于是「发出
  `question`」与「结束运行」由同一事实触发，不会只有其一发生）；`ask_user` 注册后进
  `_always_active`（恒可用，不进 `allowed-tools` 并集）；`_translate` 新增 `reasoning_delta` 翻译。
- `observability/records.py`：为新事件补显式分流并新增 `reasoning_deltas`／`question_batches`／
  `action_cards` 三个**只记条数**的字段——该模块文档承诺「`RunEvent` 每种类型都有明确处置」，
  不补就等于静默丢弃。

**关键决策——为何不用 `stop_at_tool_names`**：实测该机制**只看工具名，失败也停**。给一组
不合法参数（`items: []`）时它照样结束运行，事件流里没有任何 `question`，使用者表现为
「回复突然断掉、界面上什么都没有」。因此改用可调用 `tool_use_behavior`，判据取自
`QuestionGate`（「本次调用是否真的产出了提问」）。此差异有专门用例钉住
（`test_an_invalid_ask_user_call_does_not_end_the_run`）。

**关键决策——`reasoning_delta` 来源**：实测 SDK 0.22.3 + `chatcmpl_converter`，
`reasoning_content` 增量走 `response.reasoning_summary_text.delta`，第三方 `reasoning`
字段走 `response.reasoning_text.delta`，两条都携带增量文本故都翻译。保留「取不到就不产出」
兜底：任何其它 `raw.type` 返回空，**绝不用 `response.output_text.delta` 冒充**（基座 7.1 明令）。
故 7.1 的「待验证」项在本实现下**可产出**（非仅兜底），兜底路径仍有用例钉住。

### 5.1 结论「既有失败与本包无关」的采集通道验证

- **通道**：`git stash push --include-untracked`（把本包全部改动移出工作树）→

- **结果**：该用例在**基线**上同样失败，故「既有」结论有对照支撑，非仅凭 import 关系推断。

  命令的退出码或日志文本。

  （`campfire=68`、`t02=12`、`t03=8`、`t05=7`、`t06=12`、`t09=0`、`t10=0`、`review2=7`），

- **通道**：初次运行 `test_action_cards_from_a_tool_result_become_events_and_the_run_continues`
