## ★ v16：时长扩到 175s + 全部镜头改为比例派生时间

### 为什么要改时间点的写法（一个静默的失效模式）

目标规格要求九段共 **175s**（原 145s）。但只改 `timeline.ts` 的数字**不够**：
每个镜头内部原先用**绝对帧号**写时间点（`interpolate(frame, [150, 170], ...)`）。
段长一变，这些帧号全部失配，后果有两种且**都不报错**：

- 动作提前发生 → 段尾多出「什么都不发生」的时间 = 拖沓；
- 动作被挤到段边界外 → 该动作根本看不到。

`tsc` 不报、`check-sfx.ts` 也不报（它只验「cue 在镜头区间内」，验不了「cue 落在正确动作上」）。
**音效同理**：`shot('S4').from + 120` 这种绝对偏移会与画面事件脱钩。

### 改法

新增 `src/lib/shotTiming.ts`：`t.at(0.5)` / `t.span(0.2, 0.5)`，从**本段时长**按比例算帧号。
`src/sfx.ts` 同步改为 `at('S4', 0.16)`，两边用同一套比例，音画自动对齐。

> **先验证再依赖**：`useVideoConfig().durationInFrames` 在 `<Sequence durationInFrames={90}>` 内
> 到底返回 90 还是整个 Composition 的 300？我做了探针实测（渲染一帧把值印到画面上），
> 确认返回 **90**，比例方案才成立。当时若猜错，九个镜头会全部按错误基准排布。

### 新增时间全部给演示段

用户原话两条：①「时长不够 3 分钟」②「很多环节显得很拖沓，这部分拖沓的时间就可以给核心功能演示」。

### ★ 流式输出验证（用户明确要求的那一条）

用户原话:「对于 AI 对话演示,我希望能有那种**流式输出**的演示」。

|---|---|---|
| ① 裁正文 ROI,数「非纸色像素数」随时间的增长 | 数值**不单调**(4242→6002 但中间有 -981、-1296 的回退) | ✗ **不可信**:被两个因素污染 —— 相机推近(scale 1.0→1.16,墨迹数随 scale² 增长)+ 屏内滚动把内容移出 ROI。它既不能证明是、也不能证明不是 |
| ② 直接读组件的**计算式** | `text.slice(0, ⌊elapsed / framesPerToken⌋)` | ✓ 可信:与相机、滚动完全无关 |

② 的确定值(S5 段内,判断句 138 字):

```
段内帧   已揭示字符数
   90         0
  190        26
  290        53
  390        80
  490       108
  590       135
  600       138   ← 打完
```

**单调递增、约每 3.68 帧一字**,打完时刻恰好落在设计的 `at(0.5)`。

### ★ SFX 可听性（A6）—— 三个口径，前两个都失败

`final-review` A6 要求「每条 SFX 在**渲染产物**里是否真的听得见(不看预览)」。
这个检查我错了两次,值得留档:

### ★ 第四轮：全片空帧扫描（我自己的方法，不是审查提的）

前几轮都是「审查发现问题 → 我修」。这一轮我换了个做法:**用一个新的度量口径去扫全片**,
结果抓到前四轮都没看到的一类缺陷 —— **整屏只有一个颜色的帧**。

口径:PIL 逐帧读 160×90 缩略图的灰度标准差,**std < 0.5 视为「视觉上与空白无异」**。
为什么需要这个口径:帧差(YAVG)测的是「前后两帧的差」,而空帧常常**前后都很空**,
所以差值也小,在静止率里被当成「一段静止」而不是「一段空白」—— 两者严重程度完全不同。

| 位置 | 帧数 | 成因 |
|---|---|---|
| f300(S3 首帧) | 1 | S2 末尾内容已淡净,而 S3 首页 `frameIn` 从 opacity 0 起 |
| f4950-4957(S9 开头) | 8 | S8 末尾淡净,而 S9 第一句 0.02 才起;开场光扫此时在画外 |
| f5061-5065(S9 中段) | 5 | 边界句淡净之后,字标还等 0.02(6 帧)才开始 |
| f118-119(S1 末尾) | 2 | S1 `brandOut` 淡到 0,而 S2 首行也从 0 淡入 |

修法**不是**统一加淡入,而是按「接缝两侧不能同时为空」逐处处理:

- S3 首页 `frameIn` 起点 0 → **0.35**(f0 即有内容)
- S9 第一句 `b1` 从淡入改为 **f0 就在场**(免责声明越早出现越好)
- S9 字标起点 `BOUNDARY_END_R + 0.02` → **−0.02**(与边界句淡出**搭接**,不是首尾相接 ——
  正好接上会在衔接帧产生一个「两边都是 0」的瞬间,我第一版这么改时 f5061 的 std 恰好 0.0000)
- S1 `brandOut` 淡出终点 1 → **0.55**(不再淡到全空,硬切前仍明显变淡)
- S2 首行改为 **t=0 就在场**

**结果:5250 帧中 std<0.5 的帧 = 0**(修改前 16 帧)。

> **这一轮的教训**:**换一个度量口径,就能看见旧口径看不见的东西。**
> 帧差口径下这些帧是「静止」,标准差口径下它们是「空白」。前四轮之所以没抓到,
> 不是没扫全片,而是**扫的方式决定了能看到什么**。这也说明「我已经全片扫过了」这句话
> 只有在说明**用什么口径扫**时才有意义。

> **这轮最值得记住的教训**：第 13 条抓的是**我用来证明自己合规的那两条证据本身**。
> 两处都不是"算错"，而是**读证据的方式错了** —— 看输出的最后一行、抽三帧撞上周期。
> 指标本身没问题，是引用指标的方法有问题。**举证方式也要被审查**，否则它会替错误背书。


### S2 的「三次淘汰」（指标与观感冲突的实例）

## ★ v14 的重要说明：这一版换了画面做法

上一版（v11/v13）用「页面截图 PNG + 手写绝对定位叠加层」做画面。用户指出了 5 个结构性缺陷，我确认它们**都源于同一个根因**——截图路线里「画面」与「真实界面」是两份东西，凡需精确对位处只能猜坐标，而猜必然出错：

| # | 用户原话 | 根因 |
|---|---|---|
| 1 | 「文字为什么放在背景交界线的位置？」 | 渐变块与文字各自绝对定位，两套坐标 |
| 2 | 「滑到空白的地方」 | 截图是定高图片，滚动超过图片高度必然露空白 |
| 3 | 「√ 的位置和复选框没有匹配上」 | 在 PNG 上按猜的坐标叠 ✓ |
| 4 | 「我要的是仿佛原生的逐 token 输出」 | 截图是死图，流式只能伪造 |
| 5 | 「这里的框没匡准」 | 高亮只能另画一层，同样是猜的 |

**v14 改为直接用真实产品 React 组件当画面主体**（用户方案：「就用组件在 remotion 中制作动画，截图只用来参考」）。详细设计与消除机制见 [DESIGN_SPEC.md](DESIGN_SPEC.md) 的「★★ v14」节。

### 五个缺陷的消除情况

| 缺陷 | 机制 | 我的验证方式 |
|---|---|---|
| 1 文字压边 | `Shot.tsx` 统一版式常量；设备右缘 847 < 说明区左界 1000 | 抽帧目视 |
| 2 滚出空白 | 滚动量 = 进度 × **实测** maxScroll（`page-metrics.json`），进度夹紧 [0,1] | 量出各页 maxScroll（首页 0 / 应急 344 / 档案 4194 / 案例 1204）；S8 旧值 1680 超界 476px 正是用户看到的空白 |
| 3 ✓ 不对齐 | 渲染真实 `<input type=checkbox>` + `.check-box`，由产品 CSS `.selection:has(input:checked)` 驱动 | 抽帧目视：✓ 落在「明显疼痛」框内 |
| 4 假流式 | 真实文本节点按帧增长（`text.slice(0, ⌊elapsed/framesPerToken⌋)`） | 抽帧对比 f40/f90：文字真实增长、换行随之变化 |
| 5 框不准 | 高亮是元素自身 `::after`，选择器命中真实 DOM（`.list-row.candidate-record`） | 抽帧目视：框精确贴合真实「确认」按钮 |

两版出自同一时间线（`src/timeline.ts` 的 SHOTS 是唯一真源）。**画面一致性已用像素级证据实测**：

```
ffmpeg -i out/promo-final.mp4 -i out/promo-final-nobgm.mp4 \
  -lavfi "[0:v][1:v]psnr=stats_file=-" -f null -
→ 4350 帧全部 psnr_avg:inf, mse_avg:0.00
```

即**逐帧解码后的像素完全相同**。两版的**字节**流并非逐字节相同（视频轨 bit_rate 3163544 vs 3163326）—— 那是编码器在相同画面下做的 B-frames/码率控制决策差异，不代表画面差异。

> ★ **本段是 v15（145s）时期的记录，结论已被 v16 复算推翻，保留以备对照。**
> v16 逐帧统计后发现：**并非全部帧都是 `psnr_avg:inf`**（v16 实测约 3700/5250 为 inf，
> 约 1550 帧 `mse_avg>0`，最大 1.96）。所以「PSNR=inf ⇒ 像素完全相同」在**全片尺度上不成立**，
> 只在**大部分帧**上成立。当时的错因是只读了 PSNR 输出的最后一行。
> 正确的表述见本文档上方「成片 → 画面一致性」一节。

> 口径说明：早期版本我写的判据是「两版视频流 MD5 完全相同」。这条在某些编码配置下成立、某些下不成立（同一份源码重渲也可能变），因此**改用量化指标 PSNR** 作为画面一致性的判据。
> ★ 但 `psnr=inf` 的**逐帧计数**才是可引用的数字；只看输出的最后一行会得出「全部相同」的错误结论（我犯过）。


**确定性渲染验证**：同帧双次独立渲染的 PNG SHA256 相同（如 f3400 = `F21C86B395B27FCE…`）。

**满足 LIGHT 提交要求**：3 分钟以内（145s）；以真实产品运行演示为主。

### 一个关键的技术判定（原生滚动不可用）

审查建议「保留产品的原生 `overflow-y:auto`，写 `scrollTop`」。我照做并做了**决定性 A/B 对照**：

- 诊断探针实测 commit 阶段 `scrollTop=300` **确实写进去了**（`screen.scrollH=1144 clientH=844 top=300 ovY=auto`）
- 但 **A/B（同组件、同帧、只改 scrollY）输出 SHA256 完全相同** → Remotion 的截图流程会重置滚动位置
- 改回 transform 后 A/B **SHA256 不同** → transform 是唯一可用于帧捕获的滚动机制

因此 v14 用 transform；原生滚动的结论与证据一并留档，避免以后重复踩。

## 关键技术决策（含踩坑记录）

1. **滚动镜头必须用长图**。产品会话页内容在**内部滚动容器**里（`.thread`，`scrollHeight=7820 / clientHeight=608`），`fullPage` 截不出长图。解法：`capture/stitch-full.mjs` 按步长滚动容器逐屏截取后纵向拼接。**用视口截图滚动会露出空白**——这是 v2「设备框内空白」的根因。

2. **流式输出是纯 `f(t)`**（`src/lib/StreamText.tsx`）：`text.slice(0, ⌊elapsed/charFrames⌋)`，同一帧永远同一内容，满足确定性渲染。光标 8 帧周期闪烁。已用连续帧验证（逐字流出 + 光标 + 完成）。

3. **overlay 一律作为 `PhoneStage` 的 `children` 渲染在屏内坐标系**，自动跟随 `scale`/`translateY`。早期手工换算画布坐标的做法在加运镜后必然错位。

4. **坐标必须实测，不能猜**。手猜的坐标出过 5 次错：
   - 第 1 题勾选标记：猜 `(100, 320+i*71)`，实测 `x=50, 首行 y=380, 行距 61.5`
   - 待确认卡片按钮：我以为有「纠正」，实测是「**确认**」(`x=54,y=2216`) 与「删除」；「纠正」只在**已确认**条目上
   - 实测脚本：`capture/measure-q1-options.mjs`、`capture/measure-profile-actions.mjs`

5. **「拖沓」的量化与正解**。v2 静止率 56.5%。**我第一次用「缓慢连续微动」修补，静止率反而升高**——连续缓动幅度约 0.05px/帧，帧差测不出、观众也看不出，那是更精致的拖沓。正解两条：① 包装段时长让给核心演示（S5 30s→36s）；② 用**有实际幅度的相机运镜**（推近 1.00→1.16、横移 ±26px）与**离散节拍**（字标逐字、切题硬切、光扫）。结果 **17.9%**。

6. **段间用硬切，不用交叉溶解**。20 帧叠化会让两段文字同时可见（已在 f700 观察到重影）。

7. **SFX 边界自检**（`scripts/check-sfx.ts`，`npx tsx` 运行）：机械校验每条 `from` 落在所属镜头区间内、长样本不越界、每段至少 2 条。首次运行抓到 **14 个错误**（3 条 SFX 落在片尾之后，永远不会播放）+ 1 个素材缺失（`data-stream.mp3` 不存在，该音效一直静默失败）。
