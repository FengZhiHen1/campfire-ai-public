# 04｜执行操作与报告规范

> 目标：任何团队成员可以在不询问评测设计者的情况下复现一次运行；评委可以知道“数字从哪里来”。不绑定特定平台，不额外造重型评测框架。

## 1. 准备步骤

- [ ] 工程负责人核对当前 V3 实际功能、部署模型、Skills/Tools、输出 Schema，以及 V2 对照是否还可用。
- [ ] 领域专业人员审核关键危险信号和 `must_check/must_not`，对存在分歧的案例做替换或标 `needs_review`，形成审核记录。
- [ ] 审核样本来源及开源许可；正式公开集仅含合成或经明确许可的信息。
- [ ] 校准集独立运行，确认 A/B/C 能读取相同上下文、日志可保存、人工评分判据被共同理解。
- [ ] 冻结正式案例、版本号及 SHA256，记录在实验 manifest，后续改动另启评测批次。

## 2. 每次运行的最小证据包

建议一个 `run_id` 一个文件夹，保存：
- `manifest.json`：日期、模型ID、系统版本、知识/Skill快照摘要、组别、运行设置、案例集哈希、操作人员、错误重试策略；
- `outputs.jsonl`：逐案 `case_id`, `system_id`, `turn`, `raw_output`, `completion_status`, `latency_ms`，以及可追溯的工具日志文件引用；
- `ratings.csv`：两位独立评分者的原始分、硬失败类型、说明、适用核查数、实际通过数；
- `adjudication.csv`：分歧的复核与裁定（原始 ratings 不覆盖）；
- `summary.md`：原始计数、分母、组别差异、反例、工程限制、首次报告日期。

隐私数据与原始用户文本不得混入公开数据包。涉及个人资料的真实评测结果，应隔离存储与授权控制。

## 3. 工程执行规则

- 优先单次顺序运行 A→B→C，下一用例交替 B→C→A 或 C→A→B，避免系统性顺序偏差。
- 每例独立新会话和无关记忆清空；如果测试档案功能，则为三组构建对等背景文本版本，另做真实产品体验副实验。
- 同一知识快照、底座模型、提示长度预算、可用工具边界均记录；无法一致则单独说明。
- 工具失败必须保留，模型重试不得无限次；重试前设定规则和次数（推荐最多 1 次自动网络重试），首次失败原始日志照样保存。
- `raw_output` 与评分数据分离，防止把评分后的改写误当原始输出。
- 不要收集、传给第三方模型或提交到公开仓库任何未经授权的儿童真实案例。

## 4. 推荐执行节奏

**赛前最小演示**：
1. 8例校准场景检查设计与人工标准；
2. 12例冒烟跑通 A/B/C 记录链路，只做探索，不与最终40例合并；
3. 如果审查资源允许，冻结40例并正式盲评；否则先公开可复现的方法、合成样例、失败分析和未完成事项；
4. 所有赛事实测内容都必须能定位到明确的 `run_id`、配置和案例版本。

**后续产品迭代**：
- 失败案例进入回归集；每次代码变更后跑回归；
- 每次发布新增未见场景以检验泛化，不把回归集分数当作唯一总体效果；
- 每轮复盘优先问：“失败集中在场景理解、知识不准、错误路由、工具故障还是行动组织？”将结果反馈到具体 Skill 或工具。

## 5. 结果如何在比赛中展示

一页最有效的图：A/B/C 三组**危险失败例数** + **情境约束覆盖（分子/分母）** + **行动可执行性评分**，配一个失败到改进的真实运行案例。只展示实测数据；没做完的指标写“待验证”。

技术报告推荐附：测试集设计原则、测试样本结构及来源、完整评判依据、盲评与专业复核说明、仓库提交号、关键失败案例、开源许可边界。公开仓库 README 应给出运行方式，但不能为了公开而泄露全部密封测试集与真实家长资料。

## 6. 目前绝对不能宣称的结论

“40个场景全通过”“专业安全率99%”“已获第三方医学认证”“临床验证有效”“V3全面领先通用模型”等——本目录尚未保存任何实际运行结果，不能用候选案例或校验脚本得出这些结论。
