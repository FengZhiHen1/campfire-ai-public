# 01｜评测目标与实验协议

> 权威设计 v0.1（2026-10-27）。性质：研究方案；未实施。相关用例、指标和报告详见本专题其他文件，避免在多个文件重复维护定义。

## 1. 评测对象与问题边界

**系统对象**：篝火智答 V3 的应急咨询与日常咨询全链路，涵盖 Agent 运行时、领域 Skills、必要的检索/档案工具及行动卡输出。尚需工程实查哪些组件在当前部署中可稳定运行。

**目标人群**：以照护孤独症儿童的家长/监护人咨询情境为主要范围。测试模拟“用户向系统寻求信息理解、现场行动组织与求助判断”，不评估疾病诊断、治疗效果、真实危机救援能力或临床疗效。

要回答三个可证伪问题：
1. **H1 安全边界**：面对高风险、信息不足、来源不足或系统失败，能否避免不恰当确定性建议，并及时指向有资质的专业帮助？
2. **H2 情境适配**：相对于通用问答或领域 RAG，V3 是否更好地遵守已知约束（在场人数、场地、沟通方式、可用资源），并给出可执行的步骤？
3. **H3 系统价值**：V3 的组合工作流能否带来明确改善；如果改善，出自知识、档案、工作流还是界面组织？如果没有改善，暴露的故障路径是什么？

临床/专业适用性由独立领域评审而非模型自行判定。公开展示中，只能报告实际测试的版本与样本。

## 2. 评测分层：避免混淆四种不同证据

| 层级 | 观察对象 | 可证明什么 | 不能证明什么 |
|---|---|---|---|
| L0 工程 | API可达、Schema、Skill和工具轨迹、异常回退、延时/成本 | 是否按设定运行 | 建议专业正确 |
| L1 离线场景 | 固定合成输入，专业/人工评分，危险失误 | 指定用例中的质量与风险 | 真实家庭效果、临床安全 |
| L2 可用性 | 独立模拟任务中的任务完成、阅读理解、操作困惑 | 指定交互的可用程度 | 长期效果或治疗收益 |
| L3 实地 | 在授权、伦理审查和专业监督下的受控应用 | 真实流程中的初步可用性与风险 | 不经充分研究就推广成普遍疗效 |

**本专题首期仅实施 L0 + L1。** L2/L3 作为后续验证，不把历史 V2 七人引导体验当作 V3 的独立结果。

## 3. 方案规模与测试分组

- **校准**：8 例，只用于校准标注、调试工作流与评分分歧，不进入正式成绩。
- **正式候选**：40 例，五类各8例：日常照护、情境化应急、个体约束、明显风险/需专业转介、系统不确定/异常；入正式评测前由评审修改、核验并冻结。
- **类别刻意均衡，并非真实世界问题分布**；不能将总平均当作服务场景的总体成功概率。
- 每例具有 `case_id`、输入、向所有组共享的信息、可选后续追问、核查点、禁止项、来源与审核状态。
- 多轮场景的第二轮按预先写好的条件触发，不允许测试人员看结果后即兴追问。
- 高风险用例先进行离线测试，禁止未审查的输出自动分发给真实用户。

## 4. 对照实验设计与公平性

| 组别 | 实验定义 | 目的与边界 |
|---|---|---|
| A：Direct LLM | 同一底座模型 + 精简的共同任务说明 + 当前输入；无检索、无档案、无特制领域 Skills | 衡量直接问答的起点，不是通用聊天产品的全部实力 |
| B：RAG | 同底座 + 与当前评测语料一致的受控领域检索与基本引用提示；无 V3 复杂业务编排 | 检验知识增强本身的收益 |
| C：V3 Agent | 同底座 + 同一可用语料 + V3 Skills、Tools、场景与行动卡编排 | 衡量完整 V3 系统效果 |

**最重要的公平性**：如某案例需要孩子的感官偏好、监护人在场人数等事实，主对照应在所有组的 `shared_context` 中提供相同事实；不得让 C 组看到关键线索而 A/B 组完全不知，随后宣称 Agent 更会推理。另设“完整产品体验”副实验，允许 C 自动调档案，测试产品便利性，但应单独标注不同的信息可得性。

基准配置必须记录：模型提供商及精确模型 ID、推理设置、版本/提交 SHA、统一知识集快照、系统提示词校验和、最大轮数及输出长度、日期、运行地区/接口、超时与重试规则。依赖旧版 V2 实例且无法固定模型时，应写为“历史产品系统对比”，不可作控制变量实验。

## 5. 单个案例运行协议

1. 从已冻结案例表中装载一个 `case_id`，清空三组的会话状态和无关记忆；检查上下文仅包含约定信息。
2. 固定系统配置，同样输入分别运行 A/B/C；按预先指定的顺序轮换（避免时间与平台负载系统偏差）。
3. 记录原始用户输入、完整输出、工具轨迹、引用文本、时间、费用（可得时）、错误、系统版本。原始输出不可由测试者事后修改。
4. 按固定规则注入第二轮输入（若有），观察系统是否更新计划；第二轮不能重新选择对自己有利的输入。
5. 隐去 A/B/C 身份后，交给至少两名独立评审。技术审核侧重运行轨迹；具备相关专业能力的评审负责风险与照护建议合理性。
6. 先判硬性失败，再评 0–2 分量表；分歧保留原判、讨论记录和最终裁定。
7. 错误、拒答、超时与无输出都必须记入分母，不得只汇报成功运行的部分。

## 6. 变体和消融（仅在首轮稳定后）

优先只增加对最有争议的 4–8 个案例做配对消融：
- C 去掉档案，看约束满足率是否下降；
- C 去掉领域 Skill，仅保留模型与检索，看行动顺序和求助判断；
- C 去掉行动卡输出结构，观察可读性与覆盖，而不把格式改动误称推理能力提升。

消融只能证明相关组件在当前场景与版本中的**观察到的作用**；用例太少时不得推断普遍性。

## 7. 对外报告的证据级别

- 可信描述：“在预先锁定的 40 个合成案例上，某版本 C 的硬性失败数为 X，约束满足率为 Y/Z；评分由 N 位审查者按此规则完成”。
- 不可信描述：“通过40项测试因此临床安全”“准确率95%因此可以独立应急处置”“领先全行业”“用户疗效提升”。
- 若仅完成项目组内部审核，报告为“内部先导评测”，不写“专家背书”。

## 8. 先验失败风险与停机条件

- 若出现鼓励潜在危险行为、阻断求助、虚构专业依据、泄露敏感资料等严重问题，立即封存该次输出并触发人工复核；在核查结束前停止相关自动发布或真实用户接入。
- 同一用例两位审查者对风险分类不一致时不得简单取均值，由专业审核者判定并记录未解决分歧。
- 工具故障或上下文缺失导致模型编造事实，按真实失败记录，不进行手动修饰“补全漂亮答案”。
